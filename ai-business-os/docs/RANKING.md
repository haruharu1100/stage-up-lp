# 順位の付け方（全部の計算式）

順位をブラックボックスにしない。ここに書いていない補正は入れていない。
実装は `lib/ranking.ts`。この文書と実装がずれたら実装が誤り。

## 共通ルール

1. **取れなかった数字は0点にしない。** 材料が欠けている案件は、その順位表から**外す**（除外件数を必ず表示する）。
   0点で載せると「調べていない案件が最下位に見える」ため、調べた結果として悪い案件と区別が付かなくなる。
2. **推測で埋めない。** 日本市場の段階が `UNKNOWN` の案件は、空き度を使う表には載せない。
3. **確度を必ず掛ける。** 調査の確度（0〜1）を掛けるので、調べきれていない案件は自動的に順位が下がる。

## 1. TRENDING（海外で伸びている順）

```
点数 = 海外の言及数の成長倍率
     = 直近期間の言及数 ÷ 前期間の言及数
```

- 出どころ: `market_backtests.growth_ratio`（Hacker News / GitHub の公式APIで実測）
- 倍率が計算できない案件（言及が少なすぎる等）は載せない
- **この表だけを見て「儲かる」と判断しない。** 海外で伸びていても日本での獲得単価次第で赤字になる

## 2. JAPAN GAP（日本が空いている順）

```
点数 = 日本の空き度 × 調査の確度 × 100
```

日本の空き度（`lib/cluster.ts` の `japanGapFactor`）:

| 段階 | 意味 | 空き度 |
| --- | --- | --- |
| NOT_FOUND | 国内に類似サービスが見つからない | 1.00 |
| EARLY | ごく初期 | 0.85 |
| EMERGING | 出始めている | 0.60 |
| COMPETITIVE | 競合が多い | 0.35 |
| MATURE | 成熟している | 0.15 |
| UNKNOWN | 調べられていない | **順位表から除外**（0にしない） |

- 「検索結果の件数」ではなく「実在する国内サービスの社数」で段階を決める（`lib/research/judge.ts`）
- 同じ会社の複数ページは1社にまとめる。タイトルに「株式会社◯◯」が入っていれば会社名を鍵にし、
  無ければドメインを鍵にする。ページのタイトルは同じ会社でも1ページごとに変わるため、
  タイトルだけを鍵にすると同じ会社が「料金ページ社」「導入事例社」に割れてしまう
- ニュース記事・まとめ記事・Wikipedia・note・Qiita 等はサービスとして数えない
- 検索1種類だけでは「日本に競合がいない」と断定しない（最低2種類の情報源が要る。`MIN_SOURCES_TO_CONCLUDE = 2`）

## 3. NOTE（noteの記事として売れる順）

```
点数 = NOTE BUSINESS SCORE（100点満点）
     = 採点できた項目の獲得点の合計 ÷ 採点できた配点の合計 × 100
```

10項目 各10点（`lib/economics/exit-score.ts`）:

| 項目 | 満点の条件 | 出どころ |
| --- | --- | --- |
| 一般ユーザーの興味 | noteとYouTubeに合計30件の話題 | 日本市場調査の8指標（実測） |
| タイトルの作りやすさ | タイトルに「誰向けか」が入っている | タイトルの文字判定 |
| 数字で成果を示せるか | 価格・粗利・回収月数を試算済み | バックテスト |
| 実践可能性 | 読者が自分で再現できる（MVPの作りやすさ） | 事業性スコア |
| 初心者需要 | 人の作業を置き換えられて効果を説明しやすい | 事業性スコア |
| 情報希少性 | 日本の空き度 × 調査の確度 | 日本市場調査（実測） |
| 海外先行性 | 海外の言及数が3倍 | 市場バックテスト（実測） |
| SNS拡散性 | YouTubeに20件 | 日本市場調査の8指標（実測） |
| 有料部分を作れるか | 有料note適性100点 | 販売形態の適性 |
| SaaSへ誘導できるか | SaaS適性100点 | 販売形態の適性 |

- 実測も推定もできない項目は0点ではなく「採点対象外」にして分母から外す
- **採点できた配点が50点未満の案件は載せない**（`EXIT_MIN_WEIGHT = 50`）

## 4. MONEY（採算が良い順）

```
点数 = Money Score（100点満点）
     = 採点できた項目の獲得点の合計 ÷ 採点できた配点の合計 × 100
```

8項目の配点（`lib/economics/money-score.ts`）:

| 項目 | 配点 | 満点の条件 |
| --- | --- | --- |
| 顧客単価 | 10 | 月額10万円 |
| 粗利率 | 10 | 80% |
| 顧客獲得費（CAC） | 15 | 粗利での回収が3ヶ月以内（12ヶ月かかると0点） |
| LTV ÷ CAC | 15 | 5倍 |
| 解約されにくさ | 10 | 月次解約率2%以下（10%で0点） |
| 売りやすさ | 10 | 営業先の探しやすさと支払い動機の平均 |
| 日本市場の空き | 15 | 国内の類似サービス0社 |
| リスクの低さ | 15 | 1年目の赤字確率0%（規制業種は半分に減点） |

- **実測が無い項目は0点ではなく「採点対象外」**にして、分母（採点できた配点）から外す
- 8項目はどれも「契約1件あたりの条件の良さ」しか見ていない。
  単価も粗利も回収期間も良いのに、そもそも売れる件数が少なくて12ヶ月の利益が赤字、という案件がある。
  そこで最後に次の減点を掛ける:

  | 状態 | 扱い |
  | --- | --- |
  | バックテスト未実施 | 上限70点で頭打ち |
  | 推奨価格でも12ヶ月利益の中央値が赤字 | **点数を半分にする** |
  | 12ヶ月利益の中央値が黒字 | 減点なし |

  赤字案件を一律50点にすると全部同点になって「どれがまだマシか」が消えるため、頭打ちではなく半減にしている。
  半減なので赤字案件が黒字案件を追い越すことはない。減点した理由は必ず画面に文章で出す
- **採点できた配点が50点未満の案件は、この順位表に載せない**（`MONEY_MIN_WEIGHT = 50`）。
  分母が小さいと少数の項目だけで高得点が出てしまい、「ほとんど調べていない案件」が上位に来るため。
  これは点数を下げているのではなく、順位を付けられないものに順位を付けないという扱い

## 5. HYBRID（組み合わせて売れる順）

```
点数 = HYBRID SCORE（100点満点）
     = 採点できた項目の獲得点の合計 ÷ 採点できた配点の合計 × 100
```

10項目 各10点（`lib/economics/exit-score.ts`）:

| 項目 | 満点の条件 | 出どころ |
| --- | --- | --- |
| 無料コンテンツ需要 | X投稿と無料noteの適性が高い | 販売形態の適性 |
| note販売可能性 | NOTE BUSINESS SCORE 100点 | 上の3番 |
| SaaS販売可能性 | SaaS適性100点 | 販売形態の適性 |
| 月額化 | 毎月使う業務である | 事業性スコア |
| Upsell | AI社員・運用代行の適性が高い | 販売形態の適性 |
| Cross-sell | コンサル・テンプレ・PDF教材の適性が高い | 販売形態の適性 |
| 顧客LTV | LTV÷CAC 5倍 | バックテスト |
| 営業容易性 | 営業先が探しやすく支払い動機が強い | 事業性スコア |
| 開発容易性 | MVPが作りやすくAPIコストが軽い | 事業性スコア |
| 継続需要 | 一度入れたら使い続ける業務 | 事業性スコア |

- **採点できた配点が50点未満の案件は載せない**（`EXIT_MIN_WEIGHT = 50`）

## 4つの出口（どうやって売るか）

同じ案件でも、売り方によって採算が全く変わる。SaaSの採算だけで順位を付けると、
開発は重いが情報としては価値が高い案件を取りこぼす。出口ごとに採点表を分け、最後に売り方を決める。

| 出口 | 中身 |
| --- | --- |
| INFORMATION_PRODUCT | 情報を売る（note・PDF教材・テンプレ）。原価がほぼ無く利益率は最高だが単価が小さい |
| SAAS | 仕組みを売る（月額のAIシステム）。積み上がるが開発と保守が要る |
| SERVICE | 手を動かして売る（運用代行・コンサル・制作代行）。単価は高いが件数に上限がある |
| HYBRID | 組み合わせて売る（無料note→有料note→無料デモ→AIシステム→運用代行） |

判定の条件（`decideExit`）:

```
INFORMATION_PRODUCT の候補 = NOTE BUSINESS SCORE ≧ 60 かつ 有料note適性 ≧ 40
SAAS の候補                = Money Score ≧ 60（採点できた配点が50点以上のとき）
SERVICE の候補             = 運用代行またはコンサルの適性 ≧ 60
HYBRID                     = HYBRID SCORE ≧ 60 かつ INFORMATION_PRODUCT の候補 かつ（SAAS または SERVICE の候補）
```

- **有料note適性の足切り（40点）を別に置いている理由**: NOTE BUSINESS SCORE は10項目の平均なので、
  「有料部分を作れるか」が0点でも他の9項目が高ければ合格ラインを超えてしまう。
  だが有料部分が作れない案件は、どれだけ話題性があっても有料noteとしては売れない。平均で隠れない足切りが要る
- **HYBRID は「情報でも仕組みでも売れる」時にしか付けない。** 片方しか売れないのに HYBRID と呼ぶと、
  実際には作れない導線を前提に採算を出してしまう
- 材料が足りない案件は出口を **決めない**（`exit = null`）。「とりあえず情報を売る」と決め打ちしない

## 6. BEST BUSINESS（総合 / BEST OPPORTUNITY）

```
点数 = 機会スコア ÷ 100
     × Money Score ÷ 100
     × 日本の空き度
     × 調査の確度
     × HYBRID係数
     × 100

HYBRID係数 = 0.8 + 0.4 × (HYBRID SCORE ÷ 100)      ... 0.8〜1.2倍
           = 1.0                                    ... HYBRID SCORE を採点できていない案件
```

- 掛け算にしている理由: どれか1つでも致命的に低ければ事業として成立しないため。
  足し算にすると「海外で伸びているだけの案件」が上位に来てしまう
- 機会・Money・空き度・確度のうち1つでも欠けている案件は載せない
- 機会スコア = 10項目100点の採点（海外成長性10／日本未普及度15／市場規模10／顧客の痛み10／継続課金10／
  粗利益10／開発容易性5／営業容易性10／差別化10／自動化可能性10）
- **HYBRIDを掛け算の項としてそのまま足していない理由**: 項を1つ増やすと、
  HYBRIDを採点できていない案件が一律で不利になる。それでは「調べていない案件が落ちる」だけで
  順位の意味が変わる。中央を1.0に置いた狭い倍率（0.8〜1.2）にして、未採点は1.0倍で据え置く

## この計算式が正しいという証拠はまだ無い（採点式そのものを答え合わせする）

上の掛け算が最善だという実績はまだ無い。高得点を付けた案件が売れず、低得点の案件が売れるなら、
**案件ではなく採点式の方が間違っている**。そこで予測値と実測値の差（`score_predictions` テーブル）を
1件ずつ保存し、次を測る。

- **SCORE PREDICTION ERROR** = 実測値 − 予測値（例: 予測 契約率3% / 実測 0.7% → 誤差 −2.3pt）
- **CALIBRATION** = 「確度80%」と出した案件のうち、実際に何%が達成したか

ただし **実績が少ないうちは採点式を変更しない。** 数件の結果で式を書き換えると、
たまたまの当たり外れを法則だと思い込む。最低サンプル数に達するまでは誤差を記録するだけにする。

## 7. TOP AI BUSINESS OPPORTUNITIES（画面いちばん上の表）

```
並び順 = Money Score × 調査の確度
載せる条件 = Money Score の採点できた配点が 50点以上
```

- 実装は `lib/opportunities.ts` の `selectRankable`
- バックテスト未実施の案件は「売りやすさ」しか採点できず、分母が10点しかない。
  70点で頭打ちにしても、実際に赤字と分かって半分に減点された案件（39点前後）より上に出てしまう。
  点を下げて調整するのではなく、順位を付けられないものとして表から外す
- 外した件数は画面に「除外◯件」と必ず出す

## この順位表で言ってはいけないこと

バックテスト結果が無い状態で「売れる」「儲かる」「伸びる」と書かない。
上位に来ていることは「調べた範囲で条件が良い」であって、売れる保証ではない。
