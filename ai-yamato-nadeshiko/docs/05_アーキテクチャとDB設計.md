## 3. DB設計（主要テーブル）

### 案件まわり
```sql
-- ASPネットワーク
networks(id, name, login_url, payout_methods, min_payout_usd,
         allows_social_traffic, has_api, japan_ok, notes, verified_at)

-- 案件
offers(id, network_id, name, category, adult_flag,
       payout_type,          -- CPA / CPL / PPS / REVSHARE / PPL
       payout_amount, payout_currency, revshare_pct,

       allowed_traffic, restrictions, landing_url, tracking_url,
       approval_status,      -- NOT_APPLIED / PENDING / APPROVED / REJECTED
       epc_reported, source, verified_at)

-- 採点（判断を凍結して残す。上書きしない）
offer_scores(id, offer_id, country, score, breakdown_json,
             scored_at, model, frozen)
```

### コンテンツまわり
```sql
posts(id, status,          -- draft / approved / published / failed
      lang, text, media_ids_json, category,
      hook, cta, offer_id, campaign_id,
      image_prompt, video_prompt, outfit, scene,
      compliance_passed, compliance_notes,
      approved_by, approved_at, x_post_id, published_at,
      pattern_id)          -- ← バンディットの型ID

media(id, kind, path, engine, prompt, seed,
      face_match_score,    -- Suzuho Awano との顔一致スコア
      qa_passed, qa_notes, created_at)
```

### 計測まわり（★30日以内に必ず埋める）
```sql
post_metrics(id, post_id, snapshot_at,   -- 直後 / 翌日 / 7日後 / 30日後
             impressions, likes, replies, reposts, bookmarks,
             profile_clicks, url_link_clicks, engagements,
             fetched_ok)   -- ← 取得失敗を0にしない

clicks(id, click_id, post_id, campaign_id, country, device,
       referer, offer_id, created_at)

conversions(id, click_id, offer_id, network_id, country,
            payout_usd, status,   -- PENDING / APPROVED / REJECTED

      amount_usd, detail, occurred_at)
```

### コンプライアンスまわり（★Compliance Engine）
```sql
-- 事実主張の根拠。これが無い主張は投稿・LPに出せない
claims(id, subject_type,      -- post / lp_block / offer
       subject_id, statement,  -- 主張の本文（価格・機能・対応国など）
       source_url,             -- ★一次情報のURL。必須
       checked_at,             -- ★実際に読んだ日。必須
       expires_at,             -- 価格=checked_at+30日 / 規約・法令=+90日
       verified_by)            -- ai / human

-- 検査結果。落ちた理由を残す（上書き禁止）
compliance_checks(id, subject_type, subject_id, check_code,
                  result,       -- PASS / FAIL
                  detail, checked_at)

-- 法令台帳（Obsidian 00_SYSTEM/法令台帳.md と同期）
laws(id, name, law_version, source_url, checked_at,
     effective_date, transition_date, summary, is_primary_source)
```

**`check_code` は次の値だけを使う**（Obsidian `00_SYSTEM/COMPLIANCE.md` と1対1で対応）:

| コード | 落とす条件 |
|---|---|
| `FAKE_EXPERIENCE` | Suzuho Awano自身の現実の使用・購入・旅行の経験として書かれている（`I used` `I tried` `I bought` `I love using` `This worked for me` `When I traveled` `My experience was`） |
| `UNSUBSTANTIATED_CLAIM` | 事実主張に対応する `claims` 行が無い、または `source_url` / `checked_at` が空 |
| `AFFILIATE_DISCLOSURE_MISSING` | アフィリリンクを含むのに開示文が無い／リンクより後ろにある |
| `OUTDATED_SOURCE` | 参照している `claims.expires_at` を過ぎている |
| `ADULT` / `MINOR_LOOK` / `AI_DISCLOSURE` / `SHORT_URL` / `DUPLICATE` / `AUTOMATION` / `KEIHYO` / `REAL_PERSON` / `ASP_TERMS` / `EXP_GROUP_MISMATCH` | 既存の10項目 |

**`FAIL` が1件でもあれば承認画面に出さない。** 人が誤って承認できない状態にする。

**法令の判定は `laws` を必ず経由する。** コードに条文や日付を直接書かない
（`laws.checked_at` が90日を超えていたら**判定を止めて人間へ通知する**）。

### 申請学習まわり（★Affiliate Approval Learning）
```sql
-- 申請1件=1行。上書き禁止（修正したら版を上げて新しい行を積む）
affiliate_applications(
  id, affiliate_name, application_date,
  profile_version,        -- ★学習の軸。1回の申請で複数箇所を変えない
  x_followers, x_impressions, account_age, post_count,
  website_available, domain,
  ai_disclosure,          -- AI開示の文面そのもの
  application_text,       -- 申請フォームに書いた文面そのもの
  traffic_description, audience_description,
  result,                 -- PASS / REJECT / MORE_INFORMATION_REQUIRED / NO_RESPONSE
  rejection_reason,       -- 相手の原文をそのまま。取れなければ「取れなかった」と書く
  followup, approved_at)

-- 申請前チェック13項目の結果（上書き禁止）
application_checks(id, application_id, check_code, result, detail, checked_at)
```

**`NO_RESPONSE` を `REJECT` と混ぜない。** 原因が違う（届いていない / 保留中 / 黙殺）。
**13項目が1つでも欠けたら申請文を出力しない**（`NOT_READY`）。

### 学習まわり
```sql
-- 投稿1件の12属性。「何が伸びる原因だった可能性が高いか」を出すため
post_attributes(id, post_id,
                character, hook, topic, outfit, background,
                english_style, post_length, cta, time_slot, geo,
                affiliate_offer_id)
-- RPMは post_metrics × conversions から算出。ここには保存しない（二重管理しない）

patterns(id, name, status,  -- active / retired
         trials, wins, description, created_at, retired_at)

experiments(id, hypothesis, variable, variants_json,
            state,          -- HYPOTHESIS/TEST/OBSERVATION/RESULT/DECISION
            min_sample_size, decision, decided_at)

decisions(id, actor,        -- どのAIが決めたか
          input_json, output_json, reason, created_at)
```

**必ず守るルール**
- `fetched_ok=false` の行の数値は集計に入れない（未取得と0を混ぜない）
- `offer_scores` は上書き禁止。判断した時点の前提を凍結して積む
- `experiments.decision` は `min_sample_size` 未満なら `CONTINUE` 以外を書けない
- **`claims` に `source_url` と `checked_at` が無い事実主張は、投稿・LPに出せない**
- **`laws` の条文・日付をコードへ直接書かない。** 期限切れなら判定を止めて人間へ通知する
- `compliance_checks` は上書き禁止。**落ちた履歴を残す**

## 4. KPI の定義（フォロワー数を中心に置かない）

| KPI | 定義 | 位置づけ |
|---|---|---|
| **RPM** | 実収益 ÷ インプレッション × 1,000 | **最重要**。実績どうしの比較はこれで行う |
| **ERPM** | 1,000 × Profile/LP率 × Affiliateクリック率 × CVR × **承認率** × 平均報酬 | **実績が無い案件どうしの比較**。単価だけで選ばないための軸。実データがある段は必ず実測へ差し替える |
| EPC | 収益 ÷ アフィリクリック数 | 案件の良し悪し |
| CVR | 成約 ÷ アフィリクリック | LPと案件の噛み合い |
| X CTR | LPクリック ÷ インプレッション | 投稿の良し悪し |
| LP通過率 | アフィリクリック ÷ LPビュー | LPの良し悪し |
| 利益 | 収益 − costs合計 | 事業として成立しているか |

比較は必ず「1投稿あたり」「1万表示あたり」で行う。総インプレッションの合計で勝敗を決めない
（投稿数が多い方が勝つのは当たり前なので、意味がない）。

## 5. Obsidian 連携

場所: `/Volumes/ORICO/保存用/hp用/hp-auto-system/事業Vault/AI YAMATO NADESHIKO/`

```
00_SYSTEM/       MASTER_RULES.md（最初に読む）/ BRAND_RULES.md / COMPLIANCE.md
01_CHARACTER/    SUZUHO_AWANO_PROFILE.md / FACE_REFERENCE.md / VOICE_PROFILE.md / ENGLISH_STYLE.md
02_AFFILIATE/    NETWORKS/ OFFERS/ GEO_DATA/
03_X/            POSTS/ WINNERS/ FAILED_POSTS/
04_CONTENT/      IMAGE/ VIDEO/ PROMPTS/
05_ANALYTICS/    DAILY/ WEEKLY/ MONTHLY/
06_EXPERIMENTS/  ACTIVE/ WON/ LOST/
07_KNOWLEDGE/    LEARNINGS.md
```

**役割分担（重要）**
- **DB** = 数字と機械が読むデータ。集計・判定の唯一の正
- **Obsidian** = 人とAIが読む「なぜそう決めたか」。判断・失敗・学びの記録
- 数字をObsidianに二重管理しない（ずれると事故る）

**書き込みルール**
- AIが判断を変えたら、必ず `07_KNOWLEDGE/LEARNINGS.md` に「何を・なぜ・結果どうだったか」を追記
- 負けた投稿は消さずに `03_X/FAILED_POSTS/` に残す（同じ失敗を繰り返さないため）
- 週次で `05_ANALYTICS/WEEKLY/` に自動生成レポートを置く
- 全AIはセッション開始時に `00_SYSTEM/MASTER_RULES.md` を必ず読む
