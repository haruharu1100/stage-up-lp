# 設計11: 計測（Phase 0 項目F）

作成: 2026-08-22 / 状態: **設計確定・未実装**
**この設計はPhase 0から必須。** 実装より先に、取り逃さない仕組みを決める。

---

## 0. ★この設計が最優先である理由

**Xの `non_public_metrics`（リンククリック数・プロフィールクリック数）は、投稿から30日で永久に取得不能になる。**

| | 取り逃した場合 |
|---|---|
| 売上データ | ASP管理画面に残る。後から取れる |
| インプレッション | 後から取れる |
| **リンククリック・プロフィールクリック** | **二度と取れない。復元手段が存在しない** |

30日検証の主目的は「1万表示あたり何人がプロフィールを見るか」を測ること。
**その数字を取り逃したら、30日がまるごと無駄になる。**

## 1. 保存の3原則

### 原則1: 上書きしない（スナップショット方式）

同じ投稿の数値を、**時点ごとに別の行として積む**。

```
post_metrics(post_id=123, snapshot_at='2026-09-01T10:00', impressions=1200, ...)
post_metrics(post_id=123, snapshot_at='2026-09-02T10:00', impressions=3400, ...)
post_metrics(post_id=123, snapshot_at='2026-09-08T10:00', impressions=4100, ...)
post_metrics(post_id=123, snapshot_at='2026-09-30T10:00', impressions=4300, ...)
```

**理由**: 最新値だけ持つと「伸び方の形」が消える。
初速が速い投稿と、じわじわ伸びる投稿は別の型であり、それを区別できないと改善先が分からない。

### 原則2: 「未取得」と「0」を区別する

```sql
post_metrics(..., fetched_ok)   -- 0 = 取得失敗
```

**`fetched_ok=0` の行の数値は、集計に一切入れない。**
取得失敗を0として平均に混ぜると、**実際より悪い数字が出て、正しい施策を捨てる**。

### 原則3: 判断を凍結する

案件の採点（`offer_scores`）とAIの判断（`decisions`）は**上書き禁止**。
「その時点で何を前提にそう決めたか」が残らないと、後から間違いの原因を特定できない。

## 2. 取得タイミング（絶対）

| タイミング | 何のため | 遅れたときの影響 |
|---|---|---|
| 投稿1時間後 | 初速 | 軽微（初速の型が1本欠ける） |
| 翌日 | 実質的な到達 | 軽微 |
| 7日後 | 伸び方の形 | 軽微 |
| **投稿から30日後（期限直前）** | **最終確定値** | **致命的。取り逃したら永久に失う** |

### 取り逃さないための仕組み

| # | 仕組み |
|---|---|
| 1 | **日次バッチが、投稿後30日以内の全投稿を毎日1回まとめて読む**（4タイミングを狙い撃ちしない） |
| 2 | **投稿27日目以降の未取得を検出したら、人間へ通知**（残り3日の猶予を作る） |
| 3 | バッチが失敗したら `fetched_ok=0` で行を残す。**黙って握りつぶさない** |
| 4 | 2日連続で失敗したら通知 |

**毎日全件読む理由**: 「30日後ちょうどに読む」設計は、その日にMacが落ちていたら終わる。
**毎日読んでいれば、前日の値が残る。** 読み取り単価は $0.001/リソースなので、
90投稿×30日＝2,700リソースでも **$2.7（約400円）**。取り逃すリスクの方が高い。

### A. 投稿そのもの（`posts`）

| 項目 | 中身 |
|---|---|
| `post_id` | 内部ID（全ての紐付けの起点） |
| `x_post_id` | X側のID |
| `created_at` / `published_at` | 作成日時 / 投稿日時 |
| `text` | 本文 |
| `text_version` | 文面の版（推敲したら上がる） |
| `image_id` | `media.id` |

| `exp_group` | **`A` / `B`（EXP-001の群）** |
| `approved_by` / `approved_at` | **誰がいつ承認したか** |

### B. X側の実績（`post_metrics`・スナップショットごと）

| 項目 | 取得元 | 30日で消えるか |
|---|---|---|
| `snapshot_at` | バッチ実行時刻 | — |
| `impressions` | `public_metrics` | 消えない |
| `likes` / `replies` / `reposts` / `bookmarks` | `public_metrics` | 消えない |
| `engagements` | `organic_metrics` | — |
| **`profile_clicks`** | **`non_public_metrics.user_profile_clicks`** | **★消える** |
| **`url_link_clicks`** | **`non_public_metrics.url_link_clicks`** | **★消える** |
| `fetched_ok` | バッチ | — |

### C. LP側（`clicks`）

| 項目 | 取得元 |
|---|---|
| `click_id` | サーバー発行（UUID） |
| `post_id` / `campaign_id` | URLクエリ |
| `country` | `request.cf.country` |
| `device` | User-Agent（mobile/desktop/tablet） |
| `referer` | ヘッダ |
| `offer_id` | クリックした案件 |
| `created_at` | — |

**LPビュー**と**アフィリクリック**は別レコード。混ぜない（LP通過率が測れなくなる）。

### D. 成果（`conversions`）

| 項目 | 備考 |
|---|---|
| `click_id` | **ASPが返してくれる場合のみ**。返らないASPは post_id 単位までしか辿れない |
| `offer_id` / `network_id` / `country` | — |
| `payout_usd` | 報酬 |
| `status` | PENDING / APPROVED / **REJECTED** |
| `converted_at` / `reported_at` | 発生日 と 判明日（ずれる） |

**`status=PENDING` を売上に数えない。** 却下される。

### E. 費用（`costs`）

| `kind` | 中身 |
|---|---|
| `X_API` | 投稿（URL有無で単価が違う）・読み取り |
| `IMAGE` / `VIDEO` / `VOICE` | 生成費 |
| `LLM` | 文章生成・分析 |
| `DOMAIN` | ドメイン |

**X_APIは投稿ごとに単価が違う**（URLなし$0.015 / URLあり$0.20 / 読み取り$0.001）。
**投稿1件ごとに実費を1行記録する。** 月末にまとめて按分しない（EXP-001のA/B比較が崩れる）。

## 4. 集計の定義（この式以外を使わない）

| 指標 | 式 |
|---|---|
| エンゲージメント率 | (likes + replies + reposts + bookmarks) ÷ impressions |
| **1万表示あたりプロフィールクリック** | profile_clicks ÷ impressions × 10,000 |
| X CTR | url_link_clicks ÷ impressions |
| LP通過率 | アフィリクリック ÷ LPビュー |
| CVR | 成約（APPROVED） ÷ アフィリクリック |
| **RPM** | **(売上 − API費) ÷ impressions × 1,000** |

**全ての比較はRPMで行う。** フォロワー数・いいね数で優劣を決めない。

**分母に `fetched_ok=0` の行を入れない。**

## 5. 結論を出してよい最低サンプル（再掲・厳守）

| 判定したいこと | 最低サンプル |
|---|---|
| 投稿パターンの優劣 | 30投稿 |
| X CTR | 累計10万インプレッション |
| LP通過率 | LP訪問300 |
| **CVR** | **アフィリクリック500**（律速） |
| 案件の優劣 | 成約20件 |

**未達のうちは `CONTINUE` しか書けない。** DBの制約として実装する
（`experiments.decision` は `min_sample_size` 未満なら CONTINUE 以外を受け付けない）。

## 7. やってはいけないこと

- 最新値で上書きする
- 取得失敗を0として集計に入れる
- 30日を過ぎてから「あとで取ろう」とする
- 月末にAPI費をまとめて按分する
- `PENDING` の成果を売上に数える
- 最低サンプル未達で優劣を書く
- IPアドレスを保存する（`10_LP設計.md` §4）
