## 絶対に崩さないルール

```
正確性 > 安全性 > 利益 > 自動化率 > 商品数
```

1. **無断で外部サイトを自動操作しない。** 公式API / 法人API / データフィード / CSV / Webhook / 規約上認められた方法のみ。
   使えないなら機能を落として `CONNECTOR_NOT_AVAILABLE` / `MANUAL_APPROVAL_REQUIRED` を返す。**スクレイピングで埋めない。**
2. **Connector の capability が `api` でなければ、自動実行を実行層が拒否する。** 環境変数で true にしても動かさない。
3. **金銭を動かす処理は必ず Action Gate を通す。** 直接 Connector を呼ぶ実装を書かない。
4. **idempotency_key に UNIQUE 制約。** 購入・出品・発送・注文取込の4つは必須。
5. **在庫は個体単位。** SKU×数量方式にしない（二重販売の原因）。
6. **外部APIの「応答不明」は再送しない。** 人間へエスカレーションする。
7. **LLMに金額計算をさせない。** 利益・ROI・スコア・資金配分は決定的なコードで計算する。LLMは説明と分類のみ。
8. **LLM出力は必ずスキーマ検証。** 落ちたら SKIP（Fail Closed）。
9. **AIは自分の閾値・予算・自動化モードを変更できない。** 提案のみ。変更は人間。
10. **APIキーをコードに書かない。** `.env` / Secret Manager のみ。
11. **既定は `COMMERCE_AUTO_MODE=SAFE` / `SANDBOX=true`。** 勝手に変えない。
12. **虚偽・誇大な商品説明を生成しない。** 景表法・古物営業法を守る。
13. **商品数を増やすために判定を甘くしない。** しきい値を下げるのではなく仕入先を増やす。
14. **重複防止3層（L1 出品重複 / L2 個体重複 / L3 商品重複）を必ず通す。** L1はDBのUNIQUE制約で担保する。
15. **LLM判定は段階的コストフィルタの最終段（L4）でのみ呼ぶ。** 想定粗利がLLM費用の20倍未満なら呼ばない。
16. **値上げは必ず上限クランプを通す。** 相場上限・`MAX_PRICE`・`MAX_STEP_UPS`・売却確率下限のいずれかに触れたら値上げしない。
17. **未定義の商品状態ラベルを推測でマッピングしない。** 共通6段階（N/S/A/B/C/D）に無ければ `MANUAL_REVIEW`。
18. **商品マスタの統合は `merged_into` で行い、削除しない。** 実行は人間のみ。

## Fail Closed の3原則

- 分からないなら買わない
- データがおかしいなら止まる
- APIがおかしいなら止まる

### 実装済みで壊してはいけないもの

- 価格方式は2種類に分かれる。**新品・型番商品＝金額ベースの+5%ステップアップ／中古一点物＝市場相場に対する倍率（Market Premium Ratio）を学習。** 片方に統一しない。
- `TARGET_NET_MARGIN`（15%）は「仕入価格×1.15」ではなく**全費用を引いたあとの純利益率**。必要販売価格の式を単純化しない。
- 除外理由（`SKIP_REASONS`）は画面に日本語で出す。英語コードをそのまま人間に見せない。
- `toHalfWidth` で長音符「ー」を半角ハイフンへ変換しない（商品名が読めなくなる）。
- 取込時に確定した `DUPLICATE` は再分析で上書きしない。
- 画面（クライアント側）から状態ランクを読むときは `lib/conditions.ts` を使う。`lib/normalize.ts` は `node:crypto` を持つのでバンドルできない。

Phase 2（全市場双方向アービトラージ）で追加。**ここも崩さない。**

- **市場は「仕入先」「販売先」に固定しない。** 同じ市場が両方になる。`can_buy` / `can_sell` を勝手に落とさない。
- **「できる」と「してよい」を別の欄に分ける。** 構造＝`can_buy`/`can_sell`、許可＝`terms_status`/`automation_permission`。
  規約で使えない市場も**計算はする。実行だけ止める**（`status='BLOCKED'`）。消すと「取り逃し」が見えなくなる。
- **BUY費用とSELL費用を1つの関数に混ぜない。** `calcAcquisitionCost()` と `calcNetReceipt()` は別。
  BUY側の内訳にSELL専用費用（販売手数料・梱包・保管）を入れない。逆も同じ。
- **BUY費用をすべてゼロにすると Phase 1 の `calcProfit` と純利益が1円単位で一致する。** 式を単純化しない。
- **異常価格チェックは除外条件の一番先に置く。** 後ろに置くとデータ誤りが「最優良Route」として上位に出る。
- **手数料は市場ごと×BUY/SELL別。** 一律◯%にまとめない。`is_estimated=1` のままで自動購入しない。
- **使えない市場（BLOCKED / NOT_ALLOWED）の取り逃しは、実際の相場観測がある時だけ出す。** 参考相場で金額をでっちあげない。
- **利益が最大のRouteをベストにしない。** 利益 × 売却確率 × 資金回転 × リスクで選ぶ。

Phase 3（SHADOW学習・答え合わせ）で追加。**ここも崩さない。**

19. **SHADOWの3テーブルは `ON CONFLICT DO NOTHING`。`DO UPDATE` を書かない。**
    `route_shadow_trades` / `shadow_market_snapshots` / `shadow_evaluations`。
    後から現在値で上書きすると、常に自分が正しかったことになり学習が成立しない。
20. **「売れた」と数えるのは6条件をすべて満たす時だけ。**
    観測あり／`observed_at` あり／観測が判断より後／`price_basis='SOLD_MEDIAN'`／
    `sold_count_30d>=1`／`avg_days_to_sell` あり。
    足りなければ `ACTUAL_SALE_UNCONFIRMED`。**勝ちにも負けにもしない。**
21. **観測できなかった相場は `NO_OBSERVATION` と記録する。参考値で埋めない。**
22. **実績によるスコア補正は件数で強さを変える**（5件未満=補正なし／5〜19=0.3／20〜49=0.6／50以上=1.0）。

23. **データ信頼度の止め方は2種類あり、混同しない。**
    手数料が概算 → データ信頼度が下がり**そもそも90点に届かない**。

24. **旧料金で過去利益を再計算しない。** 変更は `fee_change_log` に記録するだけ。

    Fee Version のハッシュには**金額に影響する14項目だけ**を含める。

45. **100件の前に10件（PILOT）。** 7項目すべて満たすまで100件へ進まない。
    この10件は「データを集めるため」ではなく「**どこを自動化するか決めるため**」に入れる。
    いちばん時間がかかった工程（`observation_work_log`）が次に自動化する場所。
46. **決済・購入・注文・発送を思わせる名前のテーブルを作らない。**
    支払方法ごとの手数料表は `venue_method_fee_rules`（`venue_payment_methods` ではない）。
    受け入れテストの「実行系テーブルが存在しない」検査を緩めるのではなく、名前の方を実態に合わせる。

Phase 3.8（まず10件のPILOT・実測で次に作るものを決める）で追加。**ここも崩さない。**

47. **落ちた理由に「その他」を作らない。** 8分類（`MODEL_NUMBER_MISSING` / `NO_SELL_MARKET` /
    `PRODUCT_MATCH_FAILED` / `MARKET_DATA_MISSING` / `FEE_UNVERIFIED` / `SHIPPING_UNKNOWN` /
    `INSUFFICIENT_MARGIN` / `LOW_DATA_CONFIDENCE`）のどれかに必ず入れる。
    「その他」があると面倒なものが全部そこへ入り、何を直せばいいか分からなくなる。
    **`INSUFFICIENT_MARGIN` が多いときに閾値を下げない。仕入先を増やす**（ルール13）。
48. **同一商品の答え合わせは3択だけ。「たぶん合っている」を作らない。**
    `CORRECT_MATCH` / `INCORRECT_MATCH` / `UNCERTAIN`。
    迷ったものは `UNCERTAIN` に置き、合格へ寄せない（迷うもの＝紛らわしいもの＝いちばん危ない）。
    **`INCORRECT_MATCH`（取り違え）は1件でも重大。** 見逃しは儲け損ねだけだが、
    取り違えは実際に金を失い在庫も残る。扱いを対称にしない。
49. **人の答えで機械の判定を上書きしない。** `tracked_listings.identity_key` はそのまま残し、
    人の答えは `identity_match_reviews` に別で持つ。上書きすると
    「機械が何回間違えたか」が数えられなくなり、精度を測れなくなる。
    **「違う商品だった」を選んだときは理由の記入を必須にする**（空欄では保存させない）。
50. **時間が長い工程＝次に自動化すべき工程、ではない。**
    「商品発見」「商品情報確認」は最も時間がかかるが、無断巡回しない決まりのため自動化できない。
    秒数だけで並べると、この2つが1位になって誤った結論が出る。
    必ず **① かかっている時間の順（事実）と ② 自動化して効く順（時間×自動化しやすさ）の
    両方**を出し、②を「次に作るもの」にする。`AUTOMATION_ROI` を
    「全部自動化して0時間」にしない。測れないときは数字を作らず「計算できません」と書く。
51. **記入見本・テスト用の行に書かれた作業秒数を「実測」に混ぜない。**
    出品は実市場データ判定で弾かれても、作業ログの秒数は残る。混ぜると誰も作業していないのに
    工程の順位が出て、それを根拠に開発方針を決めてしまう（ルール33・35違反）。
    出品1件ごとの記録（`batch_id` が `LISTING:`）は **その出品が `real_market_data = 1` のときだけ数える**。
    **除外した分は黙って引き算せず、「◯分は数えていません」と画面に書く。**
52. **データの点検で見つけたものを、勝手に消したり直したりしない。** 人に見せて、人が直す。
    自動で消すと「なぜ汚れたか」が分からなくなる。
53. **100件へ進む判定は「操作性7項目」と「安全条件7項目」の両方がそろって初めて合格。**
    片方だけで進まない。**まだ1件も確認していない状態を、黙って合格にしない**
    （`unmeasurable` を持ち、○にしない）。合格できないときに条件の方をゆるめない。
54. **受け入れテストのデータに実在の型番を使わない。** `P38TESTONLY001` のようなテスト専用の
    型番にして、後片付けを型番の文字列で確実に行う。実在の型番で消すと本物の相場を巻き添えにし、
    形が違うと消し残してデータベースを汚す（実際に起きた）。

Phase 3.9（正規Connectorと「購入ページを開く」）で追加。**ここも崩さない。**

55. **AIはURLを作らない。** 商品ページのリンクは、取得元データに**実在するURLだけ**を使う。
    `buildUrl` / `makeUrl` / `generateUrl` のような**URL組み立て関数を作らない**（テストで検査している）。
    URLの出どころは `CONNECTOR_API` / `CONNECTOR_FEED` / `OFFICIAL_CSV` / `HUMAN_ENTRY` の4つだけ。
    **`AI_GENERATED` という選択肢を作らない。**
    推測で組み立てると「実在するが別の商品」のページへ人を連れて行く。
    人は「AIが出したリンクだから合っている」と思うので、**いちばん気づきにくい取り違え**になる。
56. **商品ページの状態の既定は `UNKNOWN`。`ACTIVE` を既定にしない。**
    開けるのは `ACTIVE` のときだけ（Fail Closed）。`SOLD_PROBABLY` のような「たぶん」を作らない。
    市場と違うドメイン・転送/短縮URL・ログイン情報入りURL・`http(s)` 以外は問答無用で無効。
57. **`venue_connectors.state` を `CONNECTED` にしてよいのは4条件がそろったときだけ。**
    ①正式な利用条件を読んだ ②商用利用可を確認した ③出典URLと確認日を残した ④確認者を書いた。
    **「APIがある」は `CONNECTED` の理由にならない。** 既定は `NOT_RESEARCHED`。
    **2026-08-20 時点で `CONNECTED` は0件**（12の接続先を調査した結果。`19_Connector再調査_市場別スコア.md`）。
58. **「規約に禁止と書かれていない」を、やってよい根拠にしない。**
    **robots.txt は規約ではない。別サイトの規約を根拠にしない**
    （ブックオフの禁止条項としてよく引用されるものは `fan.bookoff.co.jp` という**別サイト**のもの）。
    確認できないものは「たぶん」ではなく **`UNKNOWN`**。
59. **廃止されたAPIを前提にコードを書かない。** 検索結果には古い情報が上位に残っている。
    使う前に**公式ドキュメントで現存を確認**する。
60. **押した記録（`page_open_events`）は凍結する。** 押した瞬間の価格と判断を写して固定し、
    あとから相場が動いても書き換えない。書き換えると
    「押したときAIは何と言っていたか」が消え、当たり外れを永久に測れなくなる。
61. **実際に買った記録（`real_trade_candidates`）を SHADOW の表に混ぜない。**
    `route_shadow_trades` に `actual_purchase_price` のような列を足さない。
    混ぜるとAIの予測成績に人の行動が紛れ込む。
62. **`AUTO_PURCHASE_CAPABLE` は9条件そろっても false を返す。**
    環境変数で有効にする経路も作らない（`lib/autopurchase.ts` に `process.env` を書かない）。
    **APIがあることは、自動購入してよい理由にならない。**
63. **出せない数字を画面に並べない。** `/buy` に利益額・ROI・Route Score を出していないのは、
    出品→Route変換層がまだ無く「この1件を買ったらいくらか」の形になっていないから。
    **それらしい数字で埋めず、出していない理由を画面に書く**（ルール35の具体例）。
64. **受け入れテストが自分の安全装置を落としたら、テストの方を直す。**
    ただし直してよいのは「**テストが事実を取り違えているとき**」だけで、理由をコメントに残す。
    歯止めを消して合格させるのは本末転倒（ルール46と対になる考え方）。

Phase 3.9b（市場ごとの許可を8項目に分ける）で追加。**ここも崩さない。**

65. **市場を「使える／使えない」の2択で判定しない。** 判定は3つ。
    `CONFIRMED_ALLOWED`（できると確認）／`CONFIRMED_PROHIBITED`（できないと確認）／
    **`CONFIRMATION_REQUIRED`（公式情報はある。当社用途に使えるかは書かれていない）**。
    **確認していないものを「禁止」と書かない。**
    実際にやった失敗：Yahoo!ショッピングの公式ヘルプに「原則 非商用」とあるのを見て
    「使えない」と結論づけたが、APIは現役で、同じ記事に「すべてを禁じるものではありません」とあり、
    商用相談の導線も公式にあった。**禁止と書かれていないから許可、の逆向きの間違い**である。
66. **同じ会社の別サービスを、同じ市場として扱わない。**
    Yahoo!ショッピング（商品検索API v3 が現役）と ヤフオク!（Web APIは2018年に提供終了）は
    **結論が正反対だった**。Amazonも SP-API／Creators API／Business API で結論が3つとも違う。
    `venue_connectors.venue_code` にはサービス単位のコードを入れ、`venue_ref` で市場に紐づける。
67. **許可は8項目に分けて持つ。** `api_exists` / `commercial_use_allowed` /
    `internal_business_use_allowed` / `price_analysis_allowed` / `data_storage_allowed` /
    `automated_collection_allowed` / `automated_purchase_allowed` / `automated_listing_allowed`。
    値は `YES` / `NO` / `UNKNOWN` の3つだけで、**既定は全部 `UNKNOWN`**。
    **「APIがある」は「使ってよい」ではない。1項目でも `UNKNOWN` が残るうちは本番接続しない。**
68. **`UNKNOWN` に点を付けない（0点）。** 「たぶん大丈夫」を点数に変えない。
    採点前と0点を見分けられるよう、`priority_score` に **`DEFAULT` を付けない**（DIGESTの原則）。
69. **技術点だけ高い市場を、合計点で選ばない。**
    「使ってよいか」の4観点（商用／社内利用／価格判断／保存）のどれかが0点なら、
    合計が何点でも候補から外す（Gate）。
    これが無いと Amazon Creators API（技術点は高いが、ライセンス13条(i)が
    「統合、分析、抽出もしくは再利用する目的」を名指しで禁止）を選んでしまう。
70. **公式ドキュメント内で数字が矛盾していたら、矛盾したまま全部記録し、一番厳しい値で設計する。**
    平均を取らない。片方を採用しない（Yahoo!のRate Limitは公式内に3つの数字がある）。
71. **お金がかかる決定と、既存事業に影響する決定は、AIが単独で実行しない。**
    Amazon SP-API には大口出品 月4,900円（税抜）が要り、AUP 4.3 により
    別事業で使っている Keepa が併用できなくなるおそれがある。
    **月額費用の発生・既存サービスが使えなくなる可能性は、必ず先に人へ提示する。**
72. **「自動取得できない」を「市場として使えない」に読み替えない。**
    ヤフオク!はAPIが終了しているが、人が買うこと・売ることは普通にできる。
    `terms_status` を `BLOCKED` にすると仕入先・販売先ごと消えてしまう（実際にやりかけた）。
