# 飲食店まるごと管理OS（resto-os）

飲食店の「注文 → 厨房 → 会計 → 経営数字」までを、ひとつのシステムでまとめて回すための土台です。
月額課金SaaSとして複数店舗に売る前提で、**契約（テナント）ごとにデータを完全に分離**して動きます。

> **設計書一式は [docs/00_目次.md](docs/00_目次.md) にあります。**
> 全体構成・画面/権限・DB・API・機能仕様・業務フロー・開発計画/テスト・課金運用/営業の8本。

## 致命的な事故を防ぐ仕組み

| 事故 | 対策 |
| --- | --- |
| 注文が消える | 端末側に注文を保存して自動で入れ直す／電波復帰時にも再送／書き込みは順番待ちで取りこぼさない |
| 二重注文 | 注文ごとの固有キーで、同じ注文は何度送られても1件しか入らない |
| 他店舗の情報が見える | DBに触れる入口を1つに限定し、契約ID・店舗IDが付かない検索は実行時に停止する |
| 会計がずれる | 会計は「全部成功か全部無かったことにするか」で処理。同時押ししても2回は成立しない |
| 厨房に注文が届かない | 厨房モニターの生存確認を常時送信し、反応が無い／未着手が滞留するとPOSに赤い警告を出す |

取消・返金・値引き・価格変更・ログインなどは `audit_logs` に追記のみで記録し、書き換え・削除の経路はありません。

商品写真（絵文字 or 画像URL）／商品名／説明／税込価格／カテゴリー／人気ランキング／おすすめ／NEW／

注文履歴／現在の合計金額／店員呼び出し（店員・お冷・おしぼり・皿交換・お会計）

- **アップセル**：カートに入れた瞬間に「一緒に◯◯はいかがですか？」を表示（店舗指定 or AI）
- **AIおすすめ**：人数・時間帯・注文済みの内容から一式を提案。経由売上はダッシュボードに表示
- **注文の振り分け**：ドリンク場／焼き場／刺場／厨房／デザート別に厨房モニターを絞り込み

## お店の記憶と、これからの見込み（`/admin/history`）

使うほどその店のことが分かっていく仕組みです。**事実と推測を絶対に混ぜません。**

| 層 | 中身 | 出る場所 |
| --- | --- | --- |
| 事実（そのまま） | その日の売上・客数・客単価・天気・気温・曜日・祝日・出来事 | 白い枠。実際に起きたことしか出ない |
| 事実（確定した集計） | 毎晩まとめ直した「その日の確定値」 | 白い枠 |
| 推測（AIの見立て） | これから7日の見込み・今日の作戦・いつもと違った日 | **紫の枠**。必ず範囲・根拠・根拠の強さが付く |

推測のときに守っていること：

- **数字だけを言い切らない。** 「◯円〜◯円くらい」の範囲を先に出し、真ん中の値は補足として添えます。
- **原因だとは言いません。** 「雨が原因で下がる」ではなく「雨の日はほかの日より◯%低い傾向（過去◯日との相関）」と書きます。
- **足りないうちは出しません。** 記録が14日未満のあいだは予測そのものを出さず、「あと何日で出せるか」だけを表示します。
- **当たったふりをしません。** 予測は前日までに確定させ、あとから書き換えません。翌日に実績と突き合わせて採点し、外れた日もそのまま残します。
- **根拠の強さは的中率ではありません。** 似た日の記録の多さ・ばらつき・実際の的中実績から算出した目安で、上限85としています。

前日までに確定した予測は「確定」、まだ無い日はその場で計算して「参考」と印を付けます。

### 毎晩ひとりでに動く処理

`/api/cron`（`CRON_SECRET` が合ったときだけ動く）が、昨日を確定 → 天気を補完 →
昨日の予測を採点 → **明日から先だけ**予測を作り直します。今日と過去には触れません。
何度動いても結果が変わらない作りです（二重計上しません）。

#### 自動処理の本数はVercelの契約で決まる

Vercelの無料プラン（Hobby）は**1日1回まで・合計2本まで**しか自動処理を持てません。
また、Hobbyは規約上「個人・非商用」に限られるため、**お店へ月額で販売する前に
Proなど商用で使えるプランへ切り替える必要があります。**

Proに切り替えたら、`vercel.json` の `crons` を下記に差し替えると
**営業中1時間ごとの天候更新**（雨が降り出したらその日の見込みを取り直す）が戻ります。

```json
"crons": [
  { "path": "/api/cron?job=daily",                "schedule": "30 20 * * *" },
  { "path": "/api/cron?job=report&slot=morning",  "schedule": "10 2 * * *" },
  { "path": "/api/cron?job=report&slot=night",    "schedule": "0 18 * * *" },
  { "path": "/api/cron?job=weather&slot=am11",    "schedule": "0 2 * * *" },
  { "path": "/api/cron?job=weather&slot=pm16",    "schedule": "0 7 * * *" },
  { "path": "/api/cron?job=live",                 "schedule": "0 8-16 * * *" }
]
```

時刻はすべてUTC表記です（日本時間 −9時間）。`job=live` の `0 8-16` は
**日本時間17時〜翌1時の毎正時**にあたり、営業時間外の店は自動で見送ります。

## 朝と閉店後のレポート（`/admin/reports`）

**この画面を毎日開かなくてよくするための機能です。** 宛先をいちど登録すれば、
必要なことだけが短い文章でLINEに届きます。

| いつ | 何が届くか |
| --- | --- |
| 毎朝11時ごろ | きのうの実績（＋予測の答え合わせ）／きょうの見込み（範囲つき）／きょう気をつけること／これまでの当たり具合 |
| 閉店後（毎晩3時ごろ） | その日の実績・ピーク時間・よく出たもの／あすの見込み |

- 文章の中でも **「■ 実績（実際に起きたこと）」と「■ 見込み（AIの推測です）」を見出しで分けます。**
- 閉店後のぶんは**初期状態では送らず保存だけ**します（深夜に通知が鳴らないため）。
  送らない設定のままでも、その日の結果は翌朝のレポートに必ず入るので取りこぼしません。
- 原価・粗利は**初期状態では文章に入れません**（LINEは誰の目に触れるか分からないため）。設定で出せます。
- 予測が外れた日も、そのまま「見込みの範囲から外れました」と書きます。

### LINEに送るための設定

```bash
# resto-os/.env
LINE_CHANNEL_TOKEN=（LINE公式アカウントのチャネルアクセストークン）
```

鍵は環境変数にだけ置き、DBにも画面にも出しません。宛先IDだけを店ごとに画面から登録します。
**鍵が未設定でも止まりません。** レポートは毎日きちんと作られ、画面から読める状態になります。

## 言葉で聞ける検索（`/admin/ask`）

「先月の雨の土曜、どうだった？」のように日本語で書くと、条件に当てはまる日を数えて答えます。
レポートが「向こうから届く」仕組みなのに対して、こちらは**思いついたときに引き出す**仕組みです。

### いちばん大事な決まりごと

**数字はAIに書かせません。** AIがやるのは「質問を絞り込み条件に読み替える」ところまでで、
答えの数字は必ずこのシステムがデータベースから数えて出します。
そのため、それらしい嘘の数字が出ることが原理的に起きません。
**AIの鍵が無くても同じように動きます**（言い回しの照合だけで条件を読み取るため）。

### 読み取れる言い回し

| 種類 | 例 |
| --- | --- |
| 期間 | 先月／今月／先週／今週／きのう／去年の8月／2026年7月／直近30日／過去3ヶ月 |
| 曜日 | 土曜／平日／週末 |
| 天気 | 雨／晴れ／くもり／雪／暑い日（28度以上）／寒い日（12度未満）／大雨（10mm以上） |
| 暦 | 祝日／連休（3日以上）／給料日／月末 |
| 知りたいこと | 売上／客数／客単価／会計数／粗利 |
| 聞き方 | いちばん売れた日は？／いちばん低かった日は？／よく出た商品は？ |

読み取れなかったときは黙って決めつけず、「期間の指定が読み取れなかったので直近90日で調べました」と先に断ります。

### 答えの正直さ

- **必ず「見た日」を全部返します。** 答えの下の「根拠を見る」を開くと、もとになった日が1日ずつ表になって出ます。
- **該当が少ないときはそう言います。** 1〜2日なら「傾向とは言えません」、3〜5日なら「参考程度」と添えます。
- **比べる相手は同じ曜日のふだんの日**にそろえます（曜日の差を二重に数えないため）。
  比べる相手がいないときは、無理に高い・低いを言いません。
- **原因は言いません。**「雨だから減った」ではなく「雨の日は◯%低めでした」と書き、
  「一緒に起きていたという関係であって、原因と決まったわけではありません」と必ず添えます。
- **粗利はスタッフには出ません。** 権限が無い人が粗利を聞いた場合は、黙ってすり替えず
  「粗利は権限のある方だけがご覧になれます。ここでは売上でお答えします」と断ります。
- 誰がいつ何を聞いたかは操作ログに残ります。

## 今日の仕込み（`/admin/prep`）

廃棄と欠品は、レシートにも日報にも出てこないまま、いちばん静かにお金が消えていくところです。
「なんとなく多め」で決めていた仕込みを、明日の見込み客数という数字に結びつけます。

### 登録作業ゼロで始められます

材料もレシピも1件も登録していない状態で、今日から使えます。
すでに毎日たまっている「商品ごとの出数」と「その日の客数」だけで計算するためです。

1. 商品ごとに「お客さま1人あたり何個出たか」を出す（同じ曜日の直近10回ぶん）
2. 明日の見込み客数を掛ける
3. 出る数が多い順に並べる（そのまま厨房の作業順になります）

### 言い切りません

数量は必ず「26〜34個（目安30個）」の形で出します。
ひとつの数字だけを出すと、外れた日にシステムのせいになり、二度と使われなくなるからです。
幅で出しておけば「日もちする物は上限寄り、当日中に使い切る物は目安どおり」と人が判断に混ざれます。

- 記録が3回に満たない商品は、**提案を出しません。**「まだ出しません」と理由つきで別枠に並べます。
- 同じ曜日の記録が足りないときは、曜日をそろえずに計算し、**そのことを根拠欄に明記します。**
- 「根拠」を押すと、計算に使った日と、その日の出数・客数が全部見えます。
- ここに出る数はすべて**見込み（第2層）**です。実績とは画面上も色を分けています。

### 売り逃しの気づき

閉店後、ふだんの同じ曜日と比べて極端に出数が少なかった商品を自動で拾います（毎晩の自動処理）。
**ここの金額は推測です。**実際に売り逃した額そのものではありません
（人気が落ちただけ、その日は出していなかった、ということもあるため）。
毎日ずらずら出ると読まれなくなるので、ふだんの55%未満・2個以上・1,000円以上に絞っています。

## 材料と発注（`/admin/inventory`・PROプラン）

### システムは自分では発注しません

この画面に「自動で発注する」ボタンはありません。わざと作っていません。

```
案を作る  →  人が数量を直す  →  人が承認する  →  発注した  →  届いた（在庫に入る）
```

仕入れは現金と店の信用に直結します。一度誤発注が通ると、届いてしまい支払いも発生し、取り返しがつきません。
提案の数量（`suggest_qty`）と人が決めた数量（`approved_qty`）は別々に保存しているので、
「提案がどれだけ直されたか」をあとから見直せます。

**「発注した」を押しても在庫は増えません。**「届いた」を押して初めて増えます。
頼んだ＝ある、にしてしまうと、欠品したときに「在庫はあるはず」と表示され続け、
いちばん困る場面でいちばん嘘をつくことになるためです。

### 在庫は上書きしません

在庫の数を直接書き換えることはせず、**動きだけを積みます**（棚卸・入荷・使用・廃棄・手直し）。

```
いまの在庫 ＝ いちばん新しい棚卸の数 ＋ そのあとの増減
```

こうしておくと「誰がいつ何をしてこの数になったか」が必ず追えます。
数が合わなくなったら棚卸を入れれば、そこから数え直します。
「そのあと」は日付ではなく**記録した順**で見ます（朝に棚卸して昼に入荷、は毎日あるため）。

使用量は、毎晩「売れた数 × レシピ」で自動的に引きます。手入力は不要です。
レシピが未登録の店では何もしません（勝手な数字を作らないため）。

### 登録は少しずつで構いません

- 材料は**よく切らすもの・高いもの**から数点だけで十分効きます。
- レシピも全商品そろえる必要はありません。**よく出る上位10品**が入っていれば発注案は役に立ちます。
- 登録していない商品は計算に含めず、そのことを画面に書きます（黙って無視しません）。
- 廃棄と使用は、そのままの数（プラス）で入力します。差し引きはシステム側で行うので、符号の間違いが起きません。

## 動かし方

```bash
cd resto-os
npm install
npm run seed     # 初期データ（デモ店舗＋比較用の別契約）
npm run dev      # http://localhost:3800
```

`npm run seed` の最後にログイン情報が表示されます（デモ用の仮パスワードです。本番では必ず変更してください）。

| --- | --- | --- | --- |
| オーナー | owner@demo.test | demo1234 | 1111 |
| 管理者 | admin@demo.test | demo1234 | 2222 |
| 店長 | manager@demo.test | demo1234 | 3333 |
| スタッフ | （PINのみ） | | 4444 |

ハンディ・厨房用の端末は「店舗コード + PIN」で入ります。店舗コードも seed の出力に表示されます。

### テストプレイ（パスワード不要）

`npm run dev` で動かしている間は、ログイン画面に「テストプレイ」の入口が出ます。
オーナー／管理者／店長／スタッフ／厨房をタップするだけで、その立場のまま入れます。
トップページにはQRを読まずにお客様画面を開くリンクも並びます。

この入口は本番ビルドでは自動的に消えます（`DEMO_LOGIN=1` を明示したときだけ本番でも出せます）。
商談デモ以外では付けないでください。

デモ用に過去7日分のダミー営業データを入れる場合：

```bash
npm run demo
```

seed は「よその店 梅田店」という別契約も作ります。そちらでログインすると、
デモ店舗のデータが一切見えないことをその場で確認できます。

## AI機能について

`ANTHROPIC_API_KEY` を設定するとAI（Claude）が動きます。未設定でも止まらず、
店舗ルールベースのおすすめに自動で切り替わります（デモ・オフライン運用も可）。

```bash
# resto-os/.env
ANTHROPIC_API_KEY=（ご自身のキー）
ANTHROPIC_MODEL=claude-sonnet-4-6
```

`.env` は `.gitignore` 済みです。

## 表示ルール（重要）

- 価格はすべて **税込の通常価格のみ** を表示します。二重価格・カウントダウン等の煽りは実装していません。
- AIの提案文には「必ず」「絶対」などの断定・誇大表現を禁止する指示を入れています（景表法対応）。

## データの持ち方

SQLite（libsql）1ファイル：`data/resto.db`
`DATABASE_URL` を差し替えれば Turso 等のクラウドDBにもそのまま移せます。

主なテーブル：`tenants` / `stores` / `staff` / `menu_items` / `tables` / `orders` / `order_items` /
`checks` / `coupons` / `calls` / `audit_logs`

記憶・予測まわり：`daily_facts`（確定した事実）/ `day_weather` / `day_calendar` / `day_events` /
`forecasts`（前日までに確定した見込み）/ `forecast_results`（答え合わせ）/ `ai_insights` /
`ai_answers`（言葉で聞かれた質問と、その答え・根拠）/ `daily_reports`（送った朝・閉店後のレポート）

仕込み・発注まわり：`ingredients`（材料）/ `recipe_lines`（商品1つに使う材料）/
`stock_moves`（在庫の動き。数は上書きせず動きだけを積む）/ `order_plans`・`order_plan_lines`
（発注の案と、人が決めた数量。提案値と承認値を別に持つ）/ `stockouts`（売り逃しの見込み＝推測）

事実の表と推測の表は分けています。予測を作る処理は、事実の表に一切書き込みません。

- 業務データはすべて `tenant_id` と `store_id` を持ちます。
- 金額はすべてサーバー側で再計算します（お客様の端末から送られた金額は使いません）。
- 取消・返金は履歴に残す方式です（不正防止）。
