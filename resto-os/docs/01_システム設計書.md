## 1. システム全体構成

### 1-1. 全体像（誰が何を使うか）

```
┌──────────── お客様 ────────────┐   ┌──────────── 店舗スタッフ ────────────┐
│ 自分のスマホ（QRを読む）        │   │ ホール：スマホ／タブレット（ハンディ）│
│ 卓上タブレット（店の備品）      │   │ 厨房：タブレット／PC（KDS）           │
└───────────────┬───────────────┘   │ レジ：PC／タブレット（POS）           │
                │                    │ 事務所：PC（管理画面・分析）          │
                │                    └───────────────┬──────────────────────┘
                │                                    │
                └────────── インターネット ──────────┘
                                   │
                    ┌──────────────▼──────────────┐
                    │  アプリ本体（Next.js）       │
                    │  画面 ＋ API を1つで提供     │
                    │  ・認証／権限チェック        │
                    │  ・tenant_id 強制付与        │
                    │  ・金額サーバー再計算        │
                    │  ・操作ログ記録              │
                    └───┬───────┬───────┬─────────┘
                        │       │       │
        ┌───────────────▼─┐ ┌───▼────┐ ┌▼────────────────┐
        │ データベース     │ │ AI     │ │ 外部サービス     │
        │ SQLite→Turso等   │ │Claude  │ │ Stripe/Square    │
        │ （店舗データ）   │ │(おすす │ │ LINE / メール    │
        │                  │ │ め等)  │ │ Google予約 等    │
        └──────────────────┘ └────────┘ └──────────────────┘
```

### 1-2. 技術構成（そのまま今の試作の延長で作れる）

| 層 | 使うもの | 理由 |
| --- | --- | --- |
| 画面＋API | Next.js 14（App Router） | 画面とAPIを1つで作れる。1人で保守できる |
| データベース | libsql（SQLite互換）→ 商用は Turso | 1店舗ならファイル1つ。SaaS化時は接続先を変えるだけでクラウドDBへ移行できる |
| AI | Claude API（claude-sonnet-4-6） | おすすめ・AI店長・翻訳。**キーが無くてもルールベースで動く**（止まらない） |
| 決済 | Stripe / Square 連携（自前開発しない） | 資金決済・PCI DSSの負担を負わない。V2以降 |
| 通知 | LINE Messaging API / メール | 販促・予約・アラート。V2以降 |
| ホスティング | Vercel（アプリ）＋ Turso（DB） | 初期費用ほぼ0。契約店舗が増えても自動で伸びる |

### 1-3. 端末は「今あるもの」で動かす

専用の高い機械は不要。ブラウザだけで動く設計にします。

| 役割 | 推奨端末 | 備考 |
| --- | --- | --- |
| お客様注文 | お客様のスマホ（QR）／店の Android タブレット・iPad | 卓上タブレットは1台1万円台の中華タブでも可 |
| ハンディ | スタッフの私物スマホ or 店の予備スマホ | アプリのインストール不要（ブラウザ） |
| 厨房 | 10インチ以上のタブレット or 中古PC＋モニター | 常時表示。防水ケース推奨 |
| レジ | 店のPC or タブレット | レシートプリンタは既存のものをブラウザ印刷で流用 |

### 1-4. 「注文が消えない」ための3段構え（最重要）

飲食店のWi-Fiは切れます。切れても注文を失わない設計にします。

1. **端末に保存**：カートに入れた時点でブラウザのローカル保存に書く。画面を閉じても復元。
2. **送信**：注文ボタンで送信。失敗したら自動で3回まで再送、そのあとも「未送信1件」と赤帯で表示。
3. **サーバー確定**：サーバーが受理番号を返して初めて「注文完了」を表示する。返事が無い間は完了と言わない。

再送で二重にならないよう、注文ごとに端末が一意のキー（`client_order_id`）を作り、
サーバーは同じキーの注文を2回登録しません（詳細は 04_API設計）。

## 11. SaaS・マルチテナント設計

### 11-1. 3階層のデータ分離

```
tenant（テナント＝契約単位）
   └ company（法人・屋号）      ※1テナント複数法人も可
        └ store（店舗）          ※本店・2号店…
             └ 注文・会計・商品・スタッフ など全データ
```

| ID | 意味 | 例 |
| --- | --- | --- |
| `tenant_id` | 課金と分離の単位。**全テーブルに必ず入る** | 「田中商店（契約者）」 |
| `company_id` | 法人／屋号の単位。会計レポートのまとまり | 「株式会社タナカフーズ」 |
| `store_id` | 店舗の単位。注文・厨房・レジはここで動く | 「梅田店」「難波店」 |

**個人店（1店舗）でも同じ構造で入れます。** tenant 1・company 1・store 1 になるだけなので、
あとから2号店を増やすときにデータ移行が要りません。

### 11-2. 他店舗の情報が絶対に見えない仕組み（3重ロック）

事故が起きるとしたら「WHERE句の書き忘れ」です。人間の注意力に頼らない形にします。

1. **ロック1：入口を1本にする**
   画面やAPIから直接SQLを書かせない。`lib/tenant-db.js` という1つの関数だけがDBに触る。
   この関数はログイン情報から `tenant_id` を取り出し、**呼び出し側が書き忘れても自動でWHEREに足す**。

   ```js
   // 呼び出し側はテナントを意識しない
   const items = await ctx.select('menu_items', { active: 1 });
   // 実際に発行されるSQL： SELECT * FROM menu_items WHERE tenant_id = ? AND active = ?
   ```

2. **ロック2：IDを推測できなくする**
   URLの `?id=123` を書き換えて他店を覗く攻撃を防ぐため、
   外部に出るIDはランダム文字列（例 `st_9f3ka0dz`）。連番は外に出さない。

3. **ロック3：取得後の再検査**
   1件取得する処理では、取れたデータの `tenant_id` がログイン中と一致するか最後にもう一度確認し、
   違えば 404 を返して**操作ログに「不正アクセス試行」として記録**する。

4. **テストで担保**
   「A店のトークンでB店のデータを取りに行くと必ず404になる」自動テストを、
   全APIに対して機械的に回す（17 テスト項目 参照）。

### 11-3. データベースの持ち方

| 方式 | 内容 | 採否 |
| --- | --- | --- |
| 共有DB＋tenant_id列（採用） | 1つのDBに全店舗。全行に `tenant_id` | ○ 運用が軽く、料金も安い。100〜300テナントまで十分 |
| テナントごとにDB分割 | 契約ごとに別DB | △ 大手・大型チェーンを取る段階で、そのテナントだけ分割できる設計にしておく |
| 完全別サーバー | 契約ごとにサーバー | × 個人店向けSaaSでは費用倒れ |

将来「この大型チェーンだけDBを分けたい」となっても、`tenants` テーブルに接続先を持たせれば
アプリ側の書き換え無しで切り替えられるようにしておきます。

### 11-4. 店舗アカウントの作られ方（オンボーディング）

```
LP「30日無料で試す」
  → メール・店名・電話を入力
  → tenant / company / store を1件ずつ自動作成
  → オーナーアカウント発行（パスワード設定メール）
  → サンプル商品22点・テーブル14卓を自動投入（すぐ触れる状態にする）
  → 初期設定ウィザード（店名・営業時間・税率・提供場所・プリンタ）
  → QRコード印刷 → 営業開始
```

**最初の5分で「注文が厨房に飛ぶ」体験まで到達させる**のが目標です。
空の管理画面を見せると、ほぼ確実に離脱します。

## 12. セキュリティ要件

### 12-1. ログイン・認証

| 対象 | 方式 |
| --- | --- |
| オーナー／管理者／店長 | メール＋パスワード（bcrypt保存）＋ セッションCookie（HttpOnly / Secure / SameSite=Lax） |
| スタッフ／厨房 | **店舗ごとの4桁PINコード**（現場で毎回メール入力は不可能）。端末を店舗に紐付け、PINで個人を特定 |
| お客様 | ログイン無し。テーブルの使い捨てトークンURLのみ |

- パスワードは8文字以上。よくあるパスワードは弾く。
- 管理画面へのログイン失敗は5回で15分ロック。
- オーナーは2要素認証を任意で有効化（V2）。

### 12-2. お客様の注文URLの安全性

QRのURL（`/t/<token>`）は誰でも開けます。持ち帰られた場合の対策：

- トークンは**会計が終わると自動で作り直す**。前の客のQRは無効になる。
- 「席に着いている（着席中）」状態でないと注文できない。空席の卓には注文が入らない。
- 1卓あたりの注文レートを制限（例：10秒に1回まで）。いたずら連打を防ぐ。
- 注文できるだけで、**売上・原価・他卓の情報は一切見えない**。

### 12-3. 権限による情報の出し分け

原価・粗利・売上は、スタッフ・厨房には**APIのレスポンスにそもそも含めない**（画面で隠すだけでは不十分）。
権限チェックはAPI側で行い、画面側の制御は補助扱いにします。

### 12-4. 操作ログ（30 不正・操作ログ）

以下は**必ず**記録します。削除はできません（追記のみ）。

| 記録する操作 | 記録内容 |
| --- | --- |
| 注文取消 | 誰が・いつ・どの注文を・理由 |
| 返金 | 誰が・いつ・いくら・理由・対象会計 |
| 値引き | 誰が・いつ・いくら・理由 |
| 会計変更 | 変更前後の金額 |
| 商品削除・価格変更 | 変更前後の値 |
| ログイン／失敗 | 誰が・いつ・IP・端末 |
| 管理画面操作 | 権限変更・スタッフ追加削除・設定変更 |

保存形式は 03_DB設計 の `audit_logs`。管理画面から**日付・担当者・種類で検索**できます。
「割引が多いスタッフ」を集計できるようにし、内部不正の抑止力にします。

### 12-5. その他

- 通信はすべて HTTPS。
- 個人情報（顧客名・電話・メール）は必要最小限。クレジットカード番号は**自社で持たない**（Stripe/Square に預ける）。
- バックアップは1日1回自動、7日分保持。復元手順を文書化する。
- 退会時はデータを90日保持後に削除。エクスポート（CSV）を提供。

## 13. 将来拡張しやすいアーキテクチャ

### 13-1. 4つの層に分ける

```
[画面] app/…            見た目だけ。計算・判断はしない
   ↓
[API] app/api/…         入力チェック・権限チェック・操作ログ
   ↓
[業務ロジック] lib/domain/…   金額計算・在庫引き当て・還元率など「店のルール」
   ↓
[データ] lib/tenant-db.js     DBへの唯一の入口。tenant_id を強制付与
```

**金額計算は必ず `lib/domain/pricing.js` の1か所だけ**にします。
POSからも、お客様画面からも、レシート再発行からも同じ関数を呼ぶので、会計がずれません。

### 13-2. 機能追加が「足すだけ」で済む形にする

| 将来機能 | 差し込み口（あらかじめ用意しておく） |
| --- | --- |
| 在庫・原価 | 注文確定時に発火する `onOrderPlaced` イベント。ここに在庫引き当てを足すだけ |
| 予約 | `reservations` テーブルと `tables` の空き判定関数を先に定義しておく |
| LINE・販促 | 会計確定時の `onCheckClosed` イベントに通知処理を足す |
| 決済（Stripe/Square） | `payment_method` を「記録」から「決済プロバイダ呼び出し」に差し替えられるインターフェースにしておく |
| 多言語 | 商品名・説明は `menu_item_translations` に別テーブル化。日本語で登録→AI翻訳→店が修正可 |
| 複数店舗・本部 | すでに store_id があるので、集計のGROUP BYを変えるだけ |

### 13-3. プランによる機能ON/OFF

料金プラン（ライト／スタンダード／AI DX／PRO）は、
コードを分けずに**1つの機能フラグ表**で切り替えます。

```js
// lib/plans.js
export const PLAN_FEATURES = {
  light:    ['order', 'kds', 'pos', 'menu', 'table'],
  standard: [...light, 'coupon', 'analytics', 'history'],
  ai:       [...standard, 'ai_reco', 'ai_manager', 'multilingual'],
  pro:      [...ai, 'multistore', 'inventory', 'shift', 'reservation'],
};
```

APIも画面も同じ表を見るので、「画面には出てるのに使えない」「解約後も使える」といった
ズレが起きません。アップセル導線（上位プランの機能を押すと案内が出る）もここで一元管理します。

### 13-4. リアルタイム更新の方針

今はポーリング（一定間隔で問い合わせ）で十分です。

| 画面 | 間隔 | 将来 |
| --- | --- | --- |
| お客様 | 15秒 | 変更不要 |
| 厨房KDS | 5秒 | 店舗数が増えたら SSE（サーバー送信）に差し替え |
| POS | 8秒 | 同上 |
| ダッシュボード | 30秒 | 変更不要 |

差し替えやすいよう、更新処理は `useLiveData(url, interval)` という1つの部品に集約します。
