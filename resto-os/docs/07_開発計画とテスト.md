## 14. 開発優先順位

### 14-1. 考え方

**「機能が多いから売れる」ではなく「事故らないから解約されない」**を優先します。
順番は次の3原則で決めています。

1. 事故が起きると即解約になるもの（テナント分離・二重注文・会計ズレ・注文未達）を最初に潰す。
2. 営業で見せる価値（AIおすすめ経由売上・ダッシュボード）は既に動いているので、それを守る。
3. 課金を回収できる仕組み（契約・請求・無料体験）が無いと売っても回収できない。

### 14-2. フェーズ表

| フェーズ | 内容 | 期間目安 | 完了の意味 |
| --- | --- | --- | --- |
| **P0 土台** | tenant/company/store/staff テーブル追加、`lib/tenant-db.js` 導入、既存全APIをctx経由に書き換え | 1〜2週 | 他店のデータが構造的に見えなくなる |
| **P1 認証・権限** | ログイン、PINログイン、5権限、原価・粗利のAPI出し分け | 1週 | 誰が何をしたか特定できる |
| **P2 事故防止** | `client_order_id` による二重注文防止、オフライン耐性、KDS未達検知、会計の二重締め防止 | 1〜2週 | **致命的事故5つが全部塞がる** |
| **P3 監査・取消** | audit_logs、注文取消・会計取消・返金（理由必須）、ログ検索画面 | 1週 | 不正・オペミスを追える |
| **P4 商用化** | 申込フロー、初期設定ウィザード、サンプル自動投入、契約・請求、プラン機能フラグ | 2週 | 売れる状態になる |
| **P5 現場品質** | CSV一括取込、日次締め、レシート印刷調整、スタッフ呼び出し一覧、売り切れ即時反映 | 1〜2週 | 現場が毎日回せる |
| **P6 多言語** | menu_item_translations、AI翻訳、言語切替UI | 1週 | 外国人客の多い店に刺さる |
| **P7 実店舗検証** | 1店舗で7営業日連続稼働、不具合修正 | 2週 | **Version 1 完成・販売開始** |

合計：**おおむね2.5〜3か月**（1人開発の想定）。

## 15. MVPで不要な機能（あえて作らない）

作らない理由を明記します。「忘れている」のではなく「意図的に外している」ものです。

| 外す機能 | 理由 |
| --- | --- |
| 自前の決済処理 | 資金決済法・PCI DSSの負担が重すぎる。Stripe/Square連携で足りる |
| 予約管理 | 予約はGoogle・ぐるなび等が既にある。V1で戦う土俵ではない |
| AI電話予約 | 品質のブレが大きく、クレームに直結する。実績を作ってから |
| 在庫・発注 | 登録の手間が非常に大きく、続かない店が多い。原価管理の需要が確認できてから |
| シフト・人件費 | 既存の勤怠アプリと競合する。連携で十分 |
| 会計ソフト連携 | CSV出力で当面代替できる |
| 複数店舗の本部管理 | 個人〜5店舗が主戦場。DB構造だけ先に用意しておけばよい |
| ポイント・スタンプ | LINEと組み合わせないと効果が薄い。V2でセットにする |
| セルフレジ・券売機 | 専用ハードが必要になり「今ある端末で使える」という強みが消える |
| ネイティブアプリ（iOS/Android） | 審査・更新の手間。ブラウザで十分動く |
| 独自のレシートプリンタ制御 | 機種ごとの差が大きい。まずブラウザ印刷で対応 |
| リアルタイム通信（WebSocket） | ポーリングで足りる。障害要因を増やさない |
| 細かすぎる権限カスタマイズ | 5権限の固定で十分。設定項目を増やすと現場が混乱する |

## 17. テスト項目

### 17-1. 事故防止テスト（最重要・自動化する）

| # | テスト | 合格基準 |
| --- | --- | --- |
| T-1 | 同じ `client_order_id` で注文を10回送信 | 登録は1件のみ。2回目以降は1件目の結果を返す |
| T-2 | 注文送信中に通信を切断 → 復帰 | 注文が1件だけ登録され、カート内容も失われない |
| T-3 | A店のセッションでB店のID（卓・商品・会計・ログ）を全APIに投げる | **全件404**。かつ監査ログに記録される |
| T-4 | URLの `?id=` を1〜1000まで総当たり | 他テナントのデータが1件も返らない |
| T-5 | クライアントが改ざんした価格（1円）を送信 | サーバー再計算により正価で登録される |
| T-6 | 存在しないオプションを送信 | 加算されず、注文は正常に通る |
| T-7 | 2つの端末から同時に同じ卓を会計 | 1件のみ成立、2件目は `ALREADY_CLOSED` |
| T-8 | 会計後に同じQRから注文 | `TABLE_NOT_SEATED` で拒否 |
| T-9 | サーバーを停止 | KDSが20秒以内に全画面警告＋音 |
| T-10 | 30卓が同時に注文（負荷試験） | 全件登録、厨房表示まで5秒以内 |
| T-11 | 100会計分の 画面表示 / レシート / DB を照合 | 差異0円 |
| T-12 | 営業日切替（深夜3時の注文） | 前日の売上に集計される |

### 17-3. 監査ログテスト

| # | テスト | 合格基準 |
| --- | --- | --- |
| T-30 | 注文取消・返金・値引・会計変更・商品削除・価格変更・ログイン・管理操作を各1回 | 8件すべて記録され、誰が・いつ・何を・変更前後 が揃う |
| T-31 | 理由未入力で取消・返金 | `REASON_REQUIRED` で拒否 |

### 17-4. 業務シナリオテスト（手動・実機）

1. 4名来店 → QR注文（唐揚げ）→ セット提案でハイボール追加 → 厨房で調理中→完成 → 追加注文 →
   お会計呼び出し → クーポン適用（最低金額未満で1回弾かれる）→ 会計 → レシート → 卓が空席に戻る
2. 口頭注文をハンディで入力 → 厨房に届く
3. 途中で品切れ → 厨房から売り切れ → お客様画面から消える
4. 注文を1品取消（理由入力）→ 履歴に取消として残る → 会計金額に含まれない
5. 会計後に金額間違いが発覚 → 店長が返金処理 → ログに残る → 日次売上から除外
6. 外国人客が英語に切り替えて注文完了

## 18. 想定される重大な問題（と対策）

### 18-1. 技術的な問題

| 問題 | 起きるとどうなるか | 対策 |
| --- | --- | --- |
| **店のWi-Fiが弱い／切れる** | 注文が飛ばない・消える | 端末保存＋自動再送＋未送信の赤帯表示。導入時にWi-Fi環境を必ずチェックし、必要なら中継機を提案（有料オプション化も可） |
| **厨房タブレットが固まる** | 注文が届かない | 未達検知の全画面警告。POS側にも未着手件数を表示。予備機の常備を運用ルール化 |
| **同時注文の競合** | 二重注文・二重会計 | `client_order_id` のUNIQUE制約と `check_id IS NULL` 条件で構造的に防ぐ |
| **他テナントのデータ露出** | 事業が終わる規模の信用毀損 | DB入口を1本化して `tenant_id` 強制付与＋公開IDのランダム化＋全API横断の自動テスト |
| **AIが落ちる／遅い** | おすすめが出ない・画面が止まる | 6秒でタイムアウトしルールベースへ。AIは「無くても営業できる」位置づけを厳守 |
| **AI APIの費用が想定を超える** | 赤字 | 店舗ごとの月間上限、プロンプトキャッシュ活用、結果のキャッシュ。上限超過時はルールベースへ自動切替 |
| **DBが1つに集中して重くなる** | 全店舗が遅くなる | インデックス設計、集計の事前計算（日次サマリーテーブル）、大型テナントはDB分離できる設計を先に用意 |
| **深夜営業の日付跨ぎ** | 売上が2日に割れる | 営業日を朝5時始まりで統一（店舗ごとに設定可） |
| **消費税の扱い（軽減税率・テイクアウト）** | 会計が合わない | 税率を商品ごとに持てるようにし、税込価格を正とする |

### 18-2. 運用・ビジネス上の問題

| 問題 | 対策 |
| --- | --- |
| **導入時のメニュー登録が大変で挫折する** | CSV一括取込＋写真は後回しでOK（絵文字で始められる）。初回は自社で代行入力するオンボーディング支援を有料 or 無料特典で提供 |
| **高齢のスタッフが使えない** | スタッフの操作は「着席・代理注文・会計」の3つだけ。ボタンを大きく、文字を大きく。紙1枚の操作カードを配布 |
| **お客様がQRを読めない・注文できない** | 卓上に「読み取り方」のミニPOP。読めない客向けにスタッフのハンディで代理注文（既に実装済み） |
| **店が「前のシステムに戻す」と言う** | 30日無料体験中に必ず1回ピークタイムを一緒に立ち会う。数字（客単価・回転率）で効果を示す |
| **月額9,800円が高いと言われる** | ハンディ端末レンタル・既存POSの月額と比較して提示。人件費1時間分/月で計算して見せる。ライト¥4,980の受け皿を用意 |
| **解約が続く（チャーン）** | 利用状況（最終注文日時・ログイン頻度）を自社画面で監視し、7日使われていないテナントに連絡する |
| **サポート電話が営業中に鳴り続ける** | よくある質問を画面内ヘルプに。営業時間帯（17〜23時）の緊急窓口を明示。障害情報ページを用意 |
| **決済を自前でやれと言われる** | 断る。Stripe/Square連携で提供する方針を明記する |
| **競合（Airレジ・スマレジ・ぐるなび等）** | 「注文＋厨房＋分析＋AIまで月9,800円・初期0円・今ある端末で」に絞る。全機能勝負はしない |

### 18-3. 法務・コンプライアンス

| 問題 | 対策 |
| --- | --- |
| 景表法（優良誤認・有利誤認） | 価格は税込の通常価格のみ。二重価格・カウントダウン等の煽りは実装しない。AI生成文は断定・誇大表現を禁止 |
| アレルギー表示の誤り | 表示は店の入力責任である旨を利用規約に明記。備考・アレルギー欄は厨房画面で赤字強調 |
| 個人情報 | 収集は最小限。カード番号は自社で保持しない。プライバシーポリシーを整備 |
| 電子帳簿・領収書 | レシートは再発行可能。会計データはCSV出力。取消・返金は必ず記録として残す |
| 店舗側の不正（打ち消し・売上抜き） | 全操作をログ化し、店長・オーナーが検索可能。取消・値引きの多い担当者を集計できる |
| 障害時の責任範囲 | 利用規約でSLA（月間99.5%）と免責を明示。返金ポリシーを定める |
