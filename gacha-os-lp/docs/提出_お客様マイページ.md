## 4. お届け先

- 住所を変えても、**すでに確定した荷物の宛先は動きません**
  （注文したときの住所を、荷物ごとに写し取って保存しています）。
- 変更後の住所は、**次の依頼から**効きます。
- 変えたときは「この変更で動かない荷物が◯件あります」とお客様に伝えます。
- お届け先が未登録なら、発送依頼は受け付けません。

### 追加の本人確認（Step-up）— **つなぎました（2026-08-26）**

前回は「まだ入っていません」とお書きしました。今回、実際に効くようにしました。

**何が起きるか**

1. お客様が「お届け先を変更する」→「この内容で保存する」を押す
2. サーバーが断る（画面には「ご本人の確認をお願いいたします」と理由が出ます）
3. その場で**ログインと同じパスワード**を入れ直す
4. 通ると、そのまま保存される（入力した住所は消えません。入れ直しは不要です）

**止めているもの**

| 場面 | 求めること |
| --- | --- |
| お届け先の変更 | パスワードの入れ直し |
| 住所を変えた直後（60分以内）の、30,000円以上の発送依頼 | パスワードの入れ直し |

一度確認が通ると、**約10分間**はそのまま続けてお手続きいただけます。
毎回入れ直させると、お客様は必ず嫌がり、やがて「外してくれ」という話になるためです。

**設計として大事にしたこと**

- 通す／通さないの判断は、必ず**サーバー側**で決めています。
  画面が「確認済みです」と言ってきても、それは信用しません。
  「確認済み」と書いて送れば通る作りにすると、確認が無いのと同じになります。
- 判断の条件は**1か所だけ**に置いています（`lib/server/stepUpPolicy.ts`）。
  入口ごとに条件を書き足すと、直し忘れた入口だけが素通りになり、
  しかも素通りしていることが外から見えません。
- 断るときは 403 で返しています。401 で返すと画面が「ログインが切れた」と
  受け取ってログイン画面へ飛ばしてしまい、お客様は入力を全部失います。

**実際に公開先で確かめました**（`07-stepup.png` が、そのときの画面です）

| # | 確かめたこと | 結果 |
| --- | --- | --- |
| 1 | お客様としてログインできる | ✓ |
| 2 | お届け先の画面が「確認が必要です」と案内する | ✓ |
| 3 | 確認なしの住所変更は止まる | ✓ 403 |
| 4 | 止められたあと、住所は書き換わっていない | ✓ |
| 5 | 間違ったパスワードでは、確認が通らない | ✓ 401 |
| 6 | 正しいパスワードで、確認が通る | ✓ |
| 7 | 確認のあとは、住所を変えられる | ✓ |
| 8 | 変更が、実際に保存されている | ✓ |

### ★この作業中に、別の重大な不具合が見つかりました（直しました）

上の 7・8 が、最初は**通りませんでした**。手元では通るのに、公開先だけ落ちます。
調べた結果、**マイページの話ではなく、システム全体の土台の問題**でした。

**何が起きていたか**

Next.js（土台の部品）が、遠くのデータベースへの問い合わせを
「**同じ問い合わせなら、前の答えでいい**」と覚え込んでしまっていました。
その結果、データベースには新しい内容が入っているのに、
画面は**いつまでも古い内容を出し続けます**。

同じ一瞬に、次の2つが同時に起きることを実測しています。

- いつもと同じ文の問い合わせ → **空**（覚えていた古い答え）
- 意味は同じで、文字だけ変えた問い合わせ → **正しい値**

**これは、住所の画面だけの話ではありません**

同じ仕組みで、次のことが起こります。

| 起きること | どれくらい困るか |
| --- | --- |
| ポイントを使ったのに、残高が減らないまま見える | 事故 |
| 発送済みにしたのに、お客様の画面は「準備中」のまま | 事故 |
| **権限を外した担当者が、外す前の権限のまま通る** | **事件** |
| **締め出したはずのアカウントが、まだ入れる** | **事件** |

下の2つは、お金や信用が直接動きます。
**本番公開の前に見つかって、本当に良かった一件です。**

**なぜ手元では見つからなかったか**

手元の確認では、データベースがファイルです。ファイルはインターネットを通らないので、
この不具合は**絶対に起きません**。何度動かしても見つかりません。
公開先で実際に押して、はじめて出ました。

**どう直したか**

データベースにつなぐ場所（1か所）で、「**答えを覚えず、毎回きちんと読み直す**」と
指定しました。直したのは1か所だけで、これで全画面に効きます。

**もう一度起きないように**

- この指定が外れていないかを見張る検査を追加しました（4本）。
- その検査を「公開前に必ず通す一覧」にも登録しました。
  つまり、誰かがうっかり外すと、**公開そのものが止まります**。
- 直したあと、公開先で1分間・3秒おきに測り直し、
  **20回すべて正しい値**（5台の別々のサーバーにまたがって）を確認しました。
  直す前は、同じ測り方で**60秒間ずっと古い値**でした。

### 試験そのものの直し（今回まとめて直しました）

これまで、**中身は全部「ok」なのに、まとめだけが「失敗」と出る回**が
20回に2回くらいありました。原因は試験の中身ではなく、
データベース部品の後片付けの不具合です（異常終了・または終わらなくなる）。

★**赤いのに直す場所が無い試験は、いちばん危険です。**
何度か見ると、人は赤を無視するようになります。そうなった試験は、もう何も守りません。

そこで、2つを組にして直しました。

1. **試験のあいだは、データベースの接続を閉じない**（`lib/server/db.ts`）
   閉じなければ、落ちる原因の「閉じたあとの後片付け」が動きません。
   そのぶんプロセスは自分で終われなくなりますが、それは下で終わらせます。
   ★本番では、これまでどおり閉じます（閉じないと接続が増え続けるため）。
2. **走らせ方を作り直す**（`scripts/run-tests.mjs`）
   - 1つの試験ファイルにつき、1つのプロセスで走らせる
   - 「何本走って、何本通って、何本落ちたか」の締めくくりが出るまで、必ず待つ
   - 締めくくりが出たら、後片付けだけを待たずに終わらせる
   - まれに、締めくくりを言い終える**前**に落ちる回があります。
     そのときだけ、そのファイルを**最初から**走らせ直します（最大2回）。
     走らせ直したことは、画面に必ず出します。

★**走らせ直すのは「合否が取れなかったとき」だけ**です。
「落ちた試験があったとき」は走らせ直しません。
そこを緩めると、たまたま通るまで回す仕組みになってしまいます。

★**ごまかしていないことの確認も、実際にやりました。**

| わざと仕込んだもの | 結果 |
| --- | --- |
| 必ず落ちる試験を1本足す | ちゃんと「失敗」で止まった |
| 締めくくりの前に「成功」で勝手に終わる試験を足す | 「締めくくりが出ていない」として失敗になった |

つまり「後片付けで落ちたのを見逃す」ことはしますが、
**「走らなかった試験を、通ったことにする」ことはしません**。本数が1本でも合わなければ止まります。

★採用しなかった直し方も書いておきます。
`--test-force-exit` を足すと赤は消えましたが、
**445本のはずが417本しか走らないまま「成功」と出ました**。28本が黙って消えます。
これはいちばんやってはいけない直し方なので、使いませんでした。

★このとき、確認の道具そのものが3か所で古くなっていたことが分かり、直しました。

1. 入口が「練習用のボタン1つ」から本番と同じログイン画面に変わっていたのに、
   道具のほうが練習用のボタンを探し続けていた。
2. 左メニューが、途中でボタンから本物のリンクに変わっていた
   （別のタブで開けるようにするため）のに、道具はボタンだけを探していた。
3. 手元では一覧が一瞬で出るのに、ネット越しでは1〜2秒かかる。
   待たずに数えていたので「押せる行がありません」という**嘘の指摘**が出ていた。

★3つとも「システムが壊れていた」のではなく、**確かめる側が古かった**ものです。
ただし、古いまま放っておくと
「確かめたつもりで、一度も確かめていない」状態になります。

### 7-2-1. 今回（2026-08-26）、公開先で追加で確かめたこと

★**この節がいちばん大事です。**
