## 1. 結論（先に）

- **「オリパ・ガチャを扱ってよい」と公言している決済会社は、やはり1社もありませんでした。**
  → **全社を「要事前審査」として扱います。**「使える」と断定できる会社はありません。
- 引っかかる理由は2つあり、**当システムは両方に当たります**。
  - ① **くじ**であること（偶然性）
  - ② **ポイントを前もって売る**こと（プリペイド・前払式支払手段）
  - → 片方だけ避けても通りません。
- **いちばん大きい論点は、実は業種ではありません。**
  → マルチテナントSaaS（第4章）です。**ここを外すと、通ったあとに全部作り直しになります。**
- したがって **どこを使うかは、問い合わせて確定させるまで「不明」**です。
  **不明のまま本番実装を進めません。**

## 4. ★当システム固有の、いちばん大きな論点（ここが本丸）

**マルチテナントSaaSなので、加盟店審査は導入店舗ごとに必要になります。**

当社が1本の加盟店契約を取り、その下に他社（導入店舗）の売上を流す形は、
多くの加盟店規約で禁止されている **「加盟店資格の第三者利用」** に当たる可能性があります。

**★これは業種可否より重い問題です。**
業種で落ちたら、別の会社を当たれば済みます。
ここを外すと、**通った会社で作り込んだあと、構造ごと作り直し**になります。

### 4-1. プラットフォーム対応の状況（今回いちばんの収穫）

| 候補 | プラットフォーム型への対応 |
|---|---|
| **fincode byGMO** | **テナント機能を公式に明記している唯一の候補。** 申込時に「プラットフォームタイプ」を選択する。**本番申請の前に事前相談が必須**と明記 |
| **PAY.JP Platform** | 機能はあるが **ベータ版**。Marketplace型は**テナントごとにカードブランド審査**が入る |
| **Stripe Connect** | 仕組みはあるが、**日本におけるオリパの審査基準は非公開** |
| KOMOJU / GMO-PG / SBPS / UnivaPay / テレコムクレジット | **不明** |

→ **照会の1位は fincode byGMO に変えます**（初版は GMO-PG が1位でした）。
理由は「業種が通りやすそうだから」ではなく、
**構造（テナント）を公式に想定している唯一の候補だから**です。

## 5. 審査を通しやすくする、設計上のレバー（原文で確認しました）

PAY.JP は、ポイント販売の有効期限について、**3段階**で案内しています
（原文確認済み：help.pay.jp/ja/articles/4552559）。

| ポイントの有効期限 | PAY.JP の案内 |
|---|---|
| **6か月以内** | 「有効期限を半年以内とすることで、**法の適用対象外とすることが可能**です」 |
| **6か月1日〜1年** | **資金決済法への対応が必要** |
| **1年超** | 上に加え、途上審査で **決算書2期分**を求められる可能性 |

→ **6か月以内が、いちばん軽い。** これは他社の審査でも効く可能性が高い設計判断です。

**★ですが、コードで6か月に固定しません。**

- 当システムでは **期限は店舗設定**です（実装済み：`lib/server/pointPolicy.ts`）。
- **こちらが「180日」等の既定値を置くと、法律を避ける目的でこちらが期間を選んだことになります。**
  ですので、画面は「まだ決めていない」から始まり、
  「おすすめの期間」も書きません。
- 決めるのは、**専門家に確かめたお店の方**です。
  「専門家に確認した」の印も、お店の方が自分でチェックしたときだけ入ります。
- → `docs/point-purchase-design.md` の「店舗が有効期限を設定できる」構造は、
  **審査の面からも正しかった**ことが確認できました。

### 7-1. 「25日ルール」が当システムに与える影響

当選カードを**発送する**タイプのオリパでは、
**注文から発送までを25日以内に収める**必要が出ます。
これを超えると、オーソリが切れて**代金を取りこぼす**ことがあります。

→ 当システムは「**先にポイントを買って、ポイントで引く**」形なので、
　**決済と発送が切り離されており、この影響を受けにくい構造**です。
　（決済はポイント購入の時点で完結し、発送はポイントの使用後に起きるため）
　**★ただし、後払い（コンビニ・Paidy等）を足す日には、ここを見直すこと。**

## 8. 専門家に確認すべき事項（AIは法的助言ができません）

- **賭博罪（刑法185条）の該当性** … 「ハズレなし＝必ず商品が届く」なら当たらないとする弁護士見解が複数ありますが、設計次第で結論が変わります
- **資金決済法** … 自家型前払式支払手段の届出義務（基準日の未使用残高1,000万円超）。
  **マルチテナントで発行主体が当社か導入店舗か**は特に要確認
- **景品表示法** … 排出確率表示と還元率の表記
- **古物営業法** … 導入店舗側の許可取得を当社が確認する義務の有無
- **加盟店契約の第三者利用** … 第4章のマルチテナント構成の適法性

## 11. この調査が、実装に与える影響

- PHASE 3C（ポイント購入）は、**モック決済のまま完成させます。**
  実決済の接続は、上の照会が返ってくるまで行いません。
- **決済会社を後から差し替えられる形を守ります**（`PAYMENT_PROVIDER` で切替。実装済み）。
  1社に合わせて作り込むと、審査に落ちた日に全部やり直しになります。
- **本番で Mock 決済のまま公開することはできません。**
  `scripts/check-providers.mjs` が本番ビルドを止めます（実装済み）。
- **特定の1社向けの実装は、まだ1行も作りません。**
  ここまでで分かったのは「全社が要事前審査」であって、
  **どこが通るかは、まだ誰にも分かっていない**からです。
