# 運用データ設計（項目13）

この段階では **入れ物の形だけ** を決めています。保存先（DB）や書き込み処理はまだ作っていません。
形の定義は `lib/opsData.ts` にあります。

## なぜ先に形を決めるのか

あとから項目を足すと、**足す前の期間のデータが永久に欠けます**。
「販売速度も見たかった」と半年後に気づいても、半年分は取り戻せません。
だから、まだ貯めないうちに、貯めるべき項目を先に決めておきます。

## この設計のいちばん大事な点

**公開前バックテストの判定を、実際の結果と同じ場所に残します**（`GachaRecord.backtest`）。

こうしておくと、あとからこれが分かります。

- DANGER と判定したガチャは、本当に赤字になったのか
- SAFE と判定したガチャは、本当に無事だったのか
- しきい値（105% / 110%）は厳しすぎないか、甘すぎないか

`BacktestAccuracy` と `verdictFromOutcome()` が、その突き合わせのための形です。
実績が貯まるほど、判定の精度を **勘ではなく数字で** 直せるようになります。

判定に使ったしきい値と乱数の種（seed）、そして **判定アルゴリズムのバージョン** も一緒に残します。
あとでしきい値や判定ルールを変更しても、「当時どの基準で判定したのか」が分からなくなりません。
同じ種なら同じ結果を再現できるので、過去の判定はいつでも検証できます。

## 予測と実績の答え合わせ（項目8）

公開前に出す予測は、次の4つを必ず残します（`BacktestSnapshot`）。

| 予測 | 実績 |
| --- | --- |
| 予測 赤字確率 8% | 実際に赤字だったか（はい／いいえ） |
| 予測 利益 +¥220,000 | 実績 利益 +¥187,000 |
| 予測 実還元率 96.8% | 実績 実還元率 98.1% |
| 予測 最悪利益（P95） −¥81,000 | 実績との差 |

`compareBacktestToOutcome()` がこの突き合わせを1件分作ります。
このとき **外し方の向き** も記録します。

- **厳しすぎ** … 危ないと言ったのに無事だった → 機会損失
- **甘すぎ** … 安全と言ったのに損が出た → いちばん避けたい

同じ「外れ」でも意味がまったく違うので、必ず分けて数えます。

## 予測精度を分けて見る軸（項目9）

「全体で何％当たった」だけでは、どこを直せばいいか分かりません。
そこで、次の7つの切り口ごとにズレを集計できる形にしています（`AccuracyDimension`）。

ガチャ種類 ／ 価格帯 ／ 景品構成 ／ 口数 ／ 販売速度 ／ 商品カテゴリ ／ 市場価格変動

たとえば「高単価×少口数のときだけ判定が甘くなる」といった偏りを、
`PredictionAccuracyReport` の `tooLooseRate` で見つけられます。

### いまはまだやらないこと

**自動学習も、しきい値の自動変更もしません。** 形だけ用意しています。
件数が少ないうちに自動で基準を動かすと、たまたまの結果に引っ張られて
判定そのものが壊れるためです。十分な件数が貯まったあと、中身を人が見て決めます。

## データの持ち方

```
GachaRecord（ガチャ1本）
├── backtest        … 公開前バックテストの控え（1件）
├── outcome         … 最終結果（1件）
├── GachaDailyRecord    … 1日1件の時系列
├── PriceChangeRecord   … 価格が動くたびに1件
└── StopDecisionRecord  … 停止を判断するたびに1件
```

親（ガチャ1本）と子（日次・価格・停止）に分けています。
日次を別に持つことで、「売れ行きが止まった日」「還元率が跳ねた日」を後から特定できます。
