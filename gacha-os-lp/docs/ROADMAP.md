## BACKTEST OPTIMIZER（改善案の自動生成）

### やりたいこと

公開前バックテストが DANGER / CAUTION を出したとき、
「危ない」で終わらせず、**どう直せば安全になるか**まで出す。

出したい形の例：

```
現在の構成            800口 / 1回2,000円 / S賞 51,800円 → DANGER
  ├ 口数を1,000口に   → SAFE（赤字確率 28% → 3%）
  ├ S賞を42,000円に   → CAUTION（赤字確率 28% → 11%）
  └ 料金を2,400円に   → SAFE（赤字確率 28% → 1%）
```

### なぜ今は作らないのか

理由は2つあります。

**1. 実運用データがまだ1件もない**

改善案を出すということは、「この直し方が正しい」と言い切ることです。
いまのバックテストは、判定そのものの精度がまだ検証されていません。
検証されていない判定を土台に改善案を出すと、
**間違った方向へ自信を持って誘導する**ことになります。これがいちばん危ない状態です。

まず、実際のガチャを回して「DANGERと判定したものは本当に赤字だったか」を貯めます。
その突き合わせの形は `lib/opsData.ts` と `docs/運用データ設計.md` に用意済みです。

**2. 今は公開直前で、機能追加を止めている**

売れるかどうかが分かる前に機能を増やしても、
使われない機能の保守費用が増えるだけです。

### 着手の条件

次のすべてを満たしたときに、あらためて検討します。

- 実際のガチャの「予測と実績」が **10件以上** 貯まっている
- そのうち「甘すぎ（安全と言ったのに損が出た）」の割合が把握できている
- 判定しきい値（105% / 110%）を、実績にもとづいて1度は見直している

### 実装するときに使えるもの

- `lib/backtest.ts` … 同じ seed で何度でも同じ結果を出せる。構成を変えて再計算するだけで比較になる
- `BACKTEST_ENGINE_VERSION` … どの判定ルールで出した案かを残せる
- `PredictionAccuracyReport` … どの条件で判定が外れやすいかの集計形

## 他に「今は作らない」と決めたもの

| 案 | 今やらない理由 |
| --- | --- |
| 判定しきい値の自動調整 | 件数が少ないうちに自動で動かすと、たまたまの結果で基準が壊れる |
| 実売データからのAI自動学習 | 上と同じ。データ設計だけ済ませてある（`AccuracyDimension`） |
| バックテスト結果からの自動停止 | 停止は営業判断を伴う。当面は「候補の提示」までにとどめる |
