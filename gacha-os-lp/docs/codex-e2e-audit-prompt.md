# Codex への依頼文：販売導線のE2E監査

前回の「セキュリティ監査」とは別の依頼です。
今回は **販売導線が1本の流れとして最後まで通るか** だけを見てください。

以下をそのまま Codex に貼ってください。

---

## 依頼

あなたには、このリポジトリ（`gacha-os-lp/`）の **販売導線のE2E監査** をお願いします。
セキュリティ監査ではありません。**「営業がこのURLを配ってから、成約の管理に載るまで、データが1度も切れずに繋がっているか」** を見てください。

### なぜこの依頼をするのか

先日、`?ref=sales01`（営業担当ごとの識別子）が保存されずに消えていた不具合が見つかりました。
画面は正常に見えるのに、営業がどのURLを配っても問い合わせ側では区別できない状態でした。
**見た目では絶対に分からない種類の不具合** です。
同種の「途中で値が消える・繋がっていない」箇所を、公開前に洗い出したいです。

### 監査する1本の流れ

次の10段階を、**1本の連続した流れとして** 追跡してください。
各段階の境界で値が失われていないかが焦点です。

```
① 営業URL        … /?ref=sales01&channel=tel など
② LP             … 着地。流入元の保存
③ デモ           … /demo（別ページへの遷移をまたぐ）
④ バックテスト    … /demo の「公開前バックテスト」画面
⑤ ROI            … ROIシミュレーター利用
⑥ 料金           … 料金セクション到達・プラン選択
⑦ 問い合わせ      … フォーム送信
⑧ 流入元の保存    … ①の値が⑦の送信内容に含まれているか
⑨ 通知           … 送信先へ実際に届くか
⑩ 営業管理       … 担当者別・プラン別に集計できる形になっているか
```

### 重点的に見てほしい観点

1. **値の引き継ぎ**
   - `?ref` / `?channel` / `utm_*` が ① から ⑧ まで生き残るか
   - ページ遷移（LP → /demo → LP）をまたいでも消えないか
   - 途中で上書きされないか（最初の着地情報が保持される設計になっているか）
   - 保存先は `sessionStorage` のみ。タブを閉じたらどうなるかも明記してください

2. **切れている箇所の特定**
   - 「保存はしているが送信していない」
   - 「送信はしているが受信側で捨てている」
   - 「受信はしているが通知本文に含めていない」
   のどれかが起きていないか。**段階ごとに ○/× で表にしてください**

3. **計測イベントの実際の発火**
   - 定義されているだけで、どこからも呼ばれていないイベントがないか
   - 逆に、二重に発火するイベントがないか
   - イベントに流入元（`sales_ref` 等）が付いているか
   - 今回追加した `backtest_view` と `plan_select` が実際に発火するか
   - `plan_select` に `plan`（starter / growth / enterprise）が付いているか

4. **バックテストの数字が本物か（今回の重点）**

   このセクションは「AIが計算した結果」として売るので、
   **表示だけの見せかけになっていないか** を確認してください。

   - LPの `components/sections/Backtest.tsx` に出る数字は、
     `lib/backtest.ts` を実際に実行した結果か。ハードコードされた数字ではないか
   - LP側とデモ画面側（`components/demo/BacktestTab.tsx`）で、
     同じシナリオの数字が一致するか（別々に計算していてズレていないか）
   - 同じ seed で何度実行しても同じ結果になるか（再現性）
   - `BACKTEST_ENGINE_VERSION` と seed が結果に含まれているか
   - 「予知」「必ず赤字を防ぐ」といった保証表現になっていないか

5. **料金表示（今回追加）**
   - 金額が `config/pricing.ts` の1か所からのみ来ているか。画面に直書きがないか
   - 環境変数（`NEXT_PUBLIC_PRICE_*`）で上書きしたとき、
     LP・`/sales`・ROIシミュレーターの**すべて**が連動して変わるか
     （どこか1か所だけ古い金額が残ると、商談中に矛盾します）
   - `monitorOffer.enabled = false` のとき、モニター条件がどこにも出ていないか
   - `monitorOffer.slots` が null のとき「先着◯社」と表示されないか
     （**実際に締め切らない数を出すのは虚偽の希少性なので禁止です**）

6. **通知の到達**
   - 送信先が未設定のとき、利用者に「送れなかった」と正しく伝わるか
   - 「送信成功と表示されたのに、どこにも届いていない」状態が起こり得ないか

7. **営業管理として成立するか**
   - 届いた情報から「どの営業担当の、どの経路からの問い合わせか」を復元できるか
   - **どのプランのボタンから来たか** も復元できるか
   - できない場合、何が足りないかを具体的に書いてください

8. **使ってはいけない表現が残っていないか**
   - 「業界唯一」「日本初」など、客観的に証明できない優位性の主張
   - 「必ず儲かる」「絶対に安全」「サーバーは落ちません」などの絶対保証
   - 実データがない数値に「運営例」「モデルケース」の明記があるか
   - `scripts/check-launch.mjs` の禁止表現チェックに漏れがないか

### 報告してほしい形式

1. **10段階の通過表**（○ / △ / × と、×の理由）
2. **重大度つきの不具合一覧**（緊急 / 高 / 中 / 低）
   - 各項目に「どのファイルの何行目か」「なぜ問題か」「どう直すか」
3. **画面では気づけない不具合** を、特に分けて列挙してください
4. 修正案は **最小の変更** で提案してください

### 制約（重要）

- **大規模な仕様変更は提案しないでください。** 今は公開直前で、機能追加は止めています。
- **新機能の提案はしないでください。** 開発はここで終了しています。
  「こうしたらもっと良くなる」は `docs/ROADMAP.md` に既に整理済みです。
- 見つかった問題の指摘と、最小限の修正案までにとどめてください。
- 実際のコード修正は、こちらで内容を確認してから行います。

## 監査後にこちらで進めること

この監査が通ったら、機能開発は終了して販売開始フェーズに入ります。

1. 問い合わせの届け先を設定する（`CONTACT_WEBHOOK_URL`）
2. GA4 を接続する（`NEXT_PUBLIC_GA4_ID`）
3. Clarity を接続する（`NEXT_PUBLIC_CLARITY_ID`）
4. デモ動画を用意する（絵コンテは `docs/demo-video-storyboard.md`）
5. 本番URLを設定する（`NEXT_PUBLIC_SITE_URL`）
6. 実際の営業を開始する

料金は決定済みで `config/pricing.ts` に入っています
（STARTER 49,800円 / GROWTH 98,000円 / ENTERPRISE 個別見積 / 初期構築費 300,000〜800,000円・すべて税別）。
変更が必要になったら、このファイルの数字だけを直せばサイト全体に反映されます。

公開後は、感覚で機能を足しません。
`docs/計測ガイド.md` の「公開後に見る数字」に沿って、
どの段階で落ちているかを特定してから手を入れます。
