# PHASE 2：ポイント購入・決済の設計

作成日：2026-09-05
**この文書は設計だけです。実装はしていません。実決済も繋いでいません。**

---

## 0. 一番大事な原則

> **「決済が成功しました」という画面を見たことを理由に、ポイントを足さない。**

理由：その画面は**お客様のブラウザが出しているもの**です。
ブラウザは書き換えられます。URLも直接叩けます。
つまり「成功画面を出す」だけで、**1円も払わずにポイントを無限に増やせます**。

ポイントを足してよいのは、**決済会社のサーバーが、当社のサーバーへ直接「入金が確定した」と通知してきたとき**だけです。
（この通知を Webhook と呼びます。以下「確定通知」と書きます）

お客様が見る「ありがとうございました」の画面は、
**残高を増やす処理を一切しません。**「反映を確認しています」と表示して、確定通知の到着を待つだけです。

## 1. いまの土台（何に繋ぐのか）

現在すでにあるもの：

| もの | 役割 | 状態 |
|---|---|---|
| `customers.points` | いまの残高 | あり |
| `point_ledger` | ポイントが動いた履歴（+と−の1行ずつ） | あり。種類は `DRAW_SPEND` / `DRAW_RETURN` / `PRIZE_EXCHANGE` / `ADMIN_ADJUST` の4つ |

**残高は台帳の合計と常に一致する**ことが実測で確認済みです。
購入もこの形の中に入れます。**購入だけ別扱いにしません。**

## 2. 新しく足すもの

### 2-1. `point_products`（店舗が決めるポイント商品）

**金額をプログラムに書き込みません。店舗が管理画面で自由に決めます。**

| 項目 | 内容 |
|---|---|
| id / tenant_id | どの会社の商品か |
| name | 表示名 |
| price_yen | 支払う金額（円） |
| points | もらえるポイント |
| bonus_points | おまけのポイント（0でよい） |
| status | 販売中 / 停止中 |
| sort_order | 並び順 |
| first_time_only | 初回購入者だけに出すか |

例（**あくまで店舗が入れる初期値の例であって、固定値ではありません**）：
1,000 / 3,000 / 5,000 / 10,000 / 30,000 / 50,000

### 2-2. `point_orders`（購入の注文）

| 項目 | 内容 |
|---|---|
| id / tenant_id / user_id | 誰の注文か |
| product_id | どの商品か |
| price_yen / points / bonus_points | **注文した瞬間の内容を写して固定する** |
| status | `PENDING`（支払い待ち）→ `PAID`（入金確定・加算済み）／ `CANCELED` ／ `REFUNDED` |
| provider | 決済会社の名前 |
| provider_ref | 決済会社側の取引番号 |
| paid_yen | 決済会社から実際に届いた入金額 |
| created_at / paid_at |  |

**価格を写して固定する理由**：注文した後で店舗が値段を変えても、
お客様が見た値段と請求額が食い違わないようにするためです。

### 2-3. ポイント履歴の種類を追加

- `PURCHASE`（購入で増えた）
- `PURCHASE_BONUS`（おまけで増えた）
- `PURCHASE_REFUND`（返金で減った）

## 3. 流れ（4段階）

```
① お客様が商品を選ぶ
     ↓
   サーバーが注文を PENDING で作る
   ★この時点でポイントは1ptも増えない
     ↓
② 決済会社の支払い画面へ送る
     ↓
③ お客様が支払う
     ↓
④ 決済会社のサーバー → 当社サーバーへ「確定通知」
     ↓
   ここで初めてポイントを足す
```

お客様が戻ってくる画面（②の後）は、**「確認しています」だけ**。
確定通知が届いたら、自動で「反映されました／残高◯◯pt」に変わります。

### ④で1回のトランザクションの中でやること（全部か、全部なしか）

1. 確定通知の**署名を確かめる**（決済会社が本当に出したものか）
2. **金額を照合する** — 注文に写した `price_yen` と、通知の入金額が一致するか。
   **一致しなければポイントを足さず、管理者へ知らせる**
3. `point_orders` を `PENDING` のときだけ `PAID` に変える（**条件付き**）
4. `point_ledger` に `PURCHASE`（＋`PURCHASE_BONUS`）を書く
5. `customers.points` を足す
6. 監査ログに書く

**途中で1つでも失敗したら、全部なかったことにします。**

## 4. 二重加算を防ぐ（4重にする）

お金が増える処理なので、1つの仕組みに頼りません。

| # | 仕組み | 何を防ぐか |
|---|---|---|
| ① | `point_orders` の**条件付き更新**（`PENDING` のときだけ `PAID` にする） | 同じ通知が2回来ても、2回目は0件更新になり何も起きない |
| ② | `idempotency` に **決済会社のイベント番号**を鍵として記録 | 通知の再送（決済会社は返事が無いと何度も送ってきます）を吸収する |
| ③ | `point_ledger` の **`ref` に注文番号を入れ、一意にする** | 台帳の側でも二重を弾く。①②をすり抜けても最後の砦になる |
| ④ | **注文1つにつきポイント加算1回**という不変条件を、テストで毎回確認 | 将来の改修で壊れたことに気づける |

**なぜ4重にするか**：決済会社の確定通知は、**同じものが何度も届くのが正常です**
（当社が返事を返せなかったと判断すると、決済会社は再送します）。
1つの仕組みだけだと、そこが壊れた瞬間にお客様の残高が二重に増え、
それは**そのまま損失**になります。

## 5. 返金・取消

| 場面 | どうするか |
|---|---|
| 支払い前にやめた | 注文を `CANCELED` に。ポイントは動かない |
| 支払い後、まだポイントを使っていない | `PURCHASE_REFUND` でポイントを減らし、注文を `REFUNDED` に |
| 支払い後、**もう使ってしまった** | **★店舗の判断が要ります**（下記） |

**残高がマイナスにならないようにするのが原則**です。
使ってしまった後の返金は、以下のどちらかを店舗に選んでもらいます。

- A案：返金を受け付けない（利用規約に明記）
- B案：受け付けて、足りない分を「未回収」として記録し、管理画面に出す

**これは技術ではなく、お店の方針の話です。決めていただかないと作れません。**

なお、いわゆる**チャージバック**（お客様がカード会社に申し立てて支払いを取り消すこと）は、
店舗の意思と関係なく発生します。**B案の仕組みは、A案を選んでも結局必要になります。**

## 6. 実決済を繋がずにE2Eを通す方法（モック決済）

設定 `PAYMENT_PROVIDER` で切り替えます。

- `mock`（初期値）：支払い画面の代わりに、当システム内の確認画面を出します。
  そこで「支払ったことにする」を押すと、**本番とまったく同じ確定通知の経路**を通ります。
  → **実決済ゼロで、購入からポイント反映まで最後まで試せます。**
- `stripe` / `gmo` など：本番の決済会社。**鍵が設定されていなければ起動時に止まります**
  （「繋がっていないのに繋がっているように見える」状態を作らないため）

**モックで通したE2Eは、本番決済の代わりにはなりません。**
本番接続時には、決済会社のテスト環境で改めて全部通す必要があります。

## 7. 顧客側の画面（どこに置くか）

| 場所 | 置くもの |
|---|---|
| マイページ最上部 | 残高 ＋「ポイントを購入」 |
| ガチャ一覧の上部（残高の横） | 「＋」で購入へ |
| ガチャ詳細の残高表示の横 | 「＋」で購入へ |
| **残高不足のとき** | その場に「ポイントを購入する」を出す。**買った後、元のガチャ詳細へ戻す** |
| 購入履歴 | ポイント画面の中に、購入の行を出す |

**「戻す」のが重要です。** 買った後にトップへ飛ばすと、
お客様は自分が何を引こうとしていたか分からなくなり、そのまま離脱します。

## 8. 管理画面に足すもの

- ポイント商品の登録・編集・並び替え・停止
- 購入の一覧（誰が・いつ・いくら・状態）
- 確定通知の受信記録（届いた／届かない／金額が合わない）
- **金額が合わない通知が来たときの警告**（不正のサインです）
- 返金の操作（二人承認。既存のポイント調整の仕組みを流用）

## 9. 販売前に必ず確認が必要なこと（法律・審査）

**私は弁護士ではありません。以下は「専門家に確認すべき論点」として挙げるもので、法的な結論ではありません。**

1. **前払式支払手段（資金決済法）**
   お金を先に受け取って後で使えるポイントは、この枠に入る可能性があります。
   入る場合、**未使用残高が一定額を超えると、届出や供託などの義務**が生じるとされています。
   **有効期限の設定の有無で扱いが変わる**とされているため、
   有効期限を店舗が設定できる作りにしておきます（技術側の備え）。
   **実際にどう扱われるかは、必ず専門家に確認してください。**

2. **特定商取引法の表示**
   会社名・住所・連絡先・価格・支払方法・**ポイントは返品不可である旨**などの掲出が必要です。
   → いまの顧客側画面には**このページがありません**。作ります。

3. **決済会社の審査**
   オリパ・ガチャは審査が厳しい業種です。
   **契約できるかどうかは、システムの出来とは別の話**です。先に相談しておくべきです。

4. **未成年の購入**
   年齢確認と、保護者同意・購入上限の扱いを決める必要があります。

5. **景品表示法**
   「必ず当たる」「絶対お得」などの断定・誇大はできません。
   ボーナスポイントを出すときも、**通常価格を基準にした表示**にします。
