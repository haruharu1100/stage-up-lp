# 本番DB・検証DB・試験DBを、完全に分ける設計

最終更新: 2026-09-06 ／ 状態: **設計のみ。本番DBへの書き込みは、まだ1回もしていません。**

---

## 0. この文書がなくすべき事故

たった1つです。

> **検証のつもりで流した処理が、本番のお客様のデータを書き換える。**

この事故は、起きた瞬間には何も起きません。エラーも出ません。
気づくのは数日後、「昨日あったポイントが無い」と言われたときです。
そのときには、原因の特定も、元に戻すことも、ほぼできません。

ですので、この文書では「気をつける」を対策に数えません。
**人が忘れても壊れない形**だけを対策として書きます。

## 1. 3つのDBを、どう分けるか

| 立場 | 何に使うか | 保存先 | 誰が触ってよいか |
|---|---|---|---|
| **本番（production）** | 実際のお客様のお金・ポイント・当選 | Turso の本番DB（専用の1つ） | 運営者本人のみ |
| **検証（preview）** | 公開前の動作確認・画面の撮影・E2E | Turso の検証DB（別の1つ） | 開発・運営 |
| **試験（test / development）** | 自動テスト・手元の開発 | `file:.data/*.db`（使い捨て） | 誰でも（毎回消える） |

**★同じURLを2つの立場で使い回さないこと。**
検証で1,000回の同時抽選を流したとき、本番のポイントが本当に動きます。

### 1-1. 環境変数（これが全部の入口）

| 変数 | 本番 | 検証 | 手元 |
|---|---|---|---|
| `DATABASE_ENV` | `production` | `preview` | 未設定 or `development` / `test` |
| `DATABASE_URL` | 本番Turso の URL | 検証Turso の URL | 未設定（＝`file:.data/gacha-os.db`） |
| `DATABASE_AUTH_TOKEN` | 本番用トークン | 検証用トークン | 不要 |
| `ALLOW_PRODUCTION_DB` | `yes-i-am-sure` | 設定しない | 設定しない |

`ALLOW_PRODUCTION_DB` は「うっかり本番に向いた」を止めるための、
**もう1つの鍵**です（`lib/server/db.ts` の `databaseUrl()`）。
これが無いと、`DATABASE_ENV=production` でも接続そのものが例外で止まります。

### 1-2. 名前の付け方（**規則にします**）

Turso のDB名・URLに、立場が必ず入るようにします。

```
本番   gacha-os-prod-xxxx.turso.io
検証   gacha-os-preview-xxxx.turso.io
```

**★これは見た目の話ではありません。**
`scripts/rotate-mfa-preview.mjs` のように、**URLの文字列に `prod` が
入っているかどうかで本番を判定して止めている道具**が、すでにあります。
本番DBの名前に `prod` が入っていないと、その安全装置が効きません。

## 2. Migration（スキーマの変更）

### 2-1. いまの仕組み

- 変更は `lib/server/db.ts` の中の `M001`〜`M020` という配列で持っています（20段）。
- 適用済みかどうかは、DBの `schema_migrations` テーブルで管理します。
  **★この表の主キーの列名は `name` です（`id` ではありません）。**
  ここを読み違えたまま try で握りつぶすと、「0段」と控えられて
  **戻したあとの照合が必ず通ってしまいます**。必ず通る確認は、無いより危険です。
- `migrate()` は**アプリが最初にDBを触ったときに自動で走ります**。
  適用済みの段は飛ばします（冪等）。
- **ただし本番では、自動に任せません。** `npm run db:migrate` で人が先に済ませます
  （`scripts/db-migrate.mjs`）。理由は 2-3 に書きます。
- 途中で失敗したら、その場で例外にして止めます
  （「同じ列がすでにある」だけは、済んだものとして進めます）。

### 2-2. 守る規則

1. **前へだけ進める（forward-only）。** 済んだ段の中身を書き換えない。
   書き換えても、適用済みのDBには二度と流れません。
   直したいときは、必ず**新しい段を足す**。
2. **列を消さない・名前を変えない。** SQLite は苦手ですし、
   古い版のアプリが動いている間に消えると、その瞬間に落ちます。
3. **破壊的な変更は、2回のリリースに分ける。**
   - リリース①：新しい列を足す（古い版もそのまま動く）
   - リリース②：新しい列を読む側に切り替える
   - （必要なら）リリース③：古い列を使うのをやめる
4. **本番へ流す前に、必ず検証DBで同じ段を通す。**
   検証DBは、本番と同じ段まで進んでいる状態を保ちます。

### 2-3. 手順（本番）

```
① 検証DBで migrate が通ることを確認する
② 本番DBのバックアップを取る（第3章）
③ 本番へデプロイする
④ ★お客様が来る前に、人の手で migrate を済ませる
     npm run db:migrate  →  MIGRATION_OK = YES（20 段）
⑤ 監査ログの鎖が切れていないことを確認する（verifyAuditOfTenant）
```

**★②を飛ばさないこと。** 移行が半分だけ通った状態からの復旧は、
バックアップが無いと、実質できません。

**★④を「自動で走るから要らない」と省かないこと。**
自動に任せるということは、**最初のお客様が20段の作り替えの引き金を引く**
ということです。その人はいちばん遅い画面を見せられ、
途中で失敗すればその人の目の前で壊れます。

`npm run db:migrate` は、当てる前と後の段を並べて突き合わせ、
**「見覚えのない段」が入っていたら止めます**。
見覚えのない段があるDBは、いまのプログラムより新しい版で使われた可能性があり、
古い版のままつなぐとデータを壊します。

## 3. Backup（控えを取る）

### 3-1. Turso 側の復元について（2026-09-07 に一次情報で確認）

**確認できた事実**（出典：https://docs.turso.tech/features/point-in-time-recovery ／
https://turso.tech/pricing ／ どちらも 2026-09-07 確認）

- 指定時点への復元（PITR）は**ある**。控えは `COMMIT` のたびに自動で作られる。
- 戻すときは**新しいDBを作る形**でしか行われない。元のDBは書き換わらない。
  `turso db create <新> --from-db <元> --timestamp <RFC3339>`
  → これは第4章の「戻す先は必ず新しいDB」という決めと、そのまま一致します。
- 保持期間はプランで違う：Free 24時間／Developer 約10日／Scaler 30日／Pro 90日。

**まだ確認できていないこと（推測で埋めません）**

- **いまの契約プランが何か。** `turso plan show` は組織の解決に失敗して答えを返しません。
  → **Turso の管理画面で本人が目で見て確認すること。**
- したがって、**このアカウントで実際に何日ぶん戻せるかは未確認**です。

**★プランが分かるまで「Turso が守ってくれている」前提で運用しないこと。**
特に Free のままだと、戻せるのは24時間ぶんだけです。
金曜に壊れて月曜に気づいたら、もう戻せません。

手順は `docs/本番DB_実行手順.md` の第1章・第9章。

### 3-2. 決めておくこと（自前の控え）

Turso 側の機能が使えるかに関係なく、**自分の手元にも控えを持ちます**。
理由は単純で、契約を止めた日・支払いが通らなかった日に、
向こう側の控えごと消えるからです。

| 項目 | 決め |
|---|---|
| 何を | 全テーブルの中身（論理ダンプ） |
| いつ | 1日1回（深夜） |
| どこへ | 運営者の管理する保管先（クラウドストレージ）。**リポジトリには入れない** |
| 何日 | 直近30日ぶん＋月末ぶんを12か月 |
| 守り | 保管先は暗号化。個人情報を含むので、共有リンクを作らない |
| 誰が | 運営者（自動化するまでは手作業でよい。ただし**やった記録を残す**） |

**★控えの中身には、お客様の氏名・住所・メールが入ります。**
置き場所を決めずに取り始めないこと。取った控えの置き忘れが、
いちばん多い個人情報の漏れ方です。

### 3-3. 控えが「使える控え」かを確かめる

取っただけの控えは、控えではありません。**戻せて初めて控えです。**

**これは道具になっています（`scripts/db-restore-verify.mjs`）。**
控えを**空の新しいDBへ実際に戻して**、9項目を突き合わせます。

```bash
npm run db:restore-verify -- .data/backup-prod-YYYYMMDD
```

| # | 見るところ |
|---|---|
| R-01 | 戻す先が空である（上書きしない） |
| R-02 | 控えにある「表の作り方」がそのまま流せる |
| R-03 | 控えの全行を入れられた |
| R-04 | 表の数が同じ |
| R-05 | すべての表の行数が同じ |
| R-06 | すべての表の指紋（sha256）が一致する |
| R-07 | 適用済みの段が同じ（**かつ1段以上あること**） |
| R-08 | 全会員で、保有ポイント＝台帳の合計 |
| R-09 | すべての店舗で、監査の鎖がつながっている |

最後に `RESTORE_VERIFIED = YES` か `NO` を出し、記録を
`docs/restore-verify-<日時>.json` に残します。

**★この道具が本当に効くことは、実際に確かめてあります（2026-09-07）。**
- 正しい控え → `RESTORE_VERIFIED = YES`（44表 3089行／48人の残高一致／56店舗の鎖が無事）
- 台帳の1行だけ、わざと 1000 → 2000 に書き換えた控え
  → **R-06（指紋）と R-08（残高）が両方 NG** になり `RESTORE_VERIFIED = NO`

**壊れた控えを見つけられることまで確かめて、初めて「確認できる」と言います。**

**★R-09 は、鎖の計算を自分で書き直していません。**
本体と同じ `verifyAuditOfTenant`（`lib/server/audit.ts`）を呼びます。
書き直すと「自分の写し間違いを、自分で正しいと言う」ことになります。

**★R-07 に「1段以上あること」が入っている理由。**
最初は `schema_migrations` の列名を `id` と書き間違え、
さらに try で握りつぶしていたため、**「控え0段／戻した先0段」で必ず一致し、
この確認は永久に通っていました**（2026-09-07 に発見・修正）。
**必ず通る確認は、無いより危険です。**

- このほかに、3か月に1回、実際に手で1回戻してみること（道具任せにしない）。

## 4. Restore（戻す）

```
① まず止める（本番を停止状態にする。動いたまま戻すと、戻した後の書き込みが混ざる）
② 戻す先は、必ず「新しいDB」にする。★元のDBの上に直接書き戻さないこと
③ 新しいDBに対して、上の3-3の3点を確認する
④ 確認できてから、DATABASE_URL を新しいDBへ向け替える
⑤ 古いDBは消さずに残す（原因を調べるため）
```

**★②が最重要です。**
壊れたDBの上に控えを書き戻すと、「壊れた状態」と「戻した状態」が混ざり、
何が本当か誰にも分からなくなります。原因調査もできなくなります。

## 5. Rollback（元の版に戻す）

**コードを戻すことと、スキーマを戻すことは、別の話です。**

| 何を戻すか | やり方 | 注意 |
|---|---|---|
| コード | Vercel の以前のデプロイへ戻す | 数分で戻せる |
| スキーマ | **戻しません** | 2-2 の規則（列を消さない）を守っていれば、古いコードでも動きます |
| データ | 第4章の復元 | 最後の手段。戻した時間ぶんの取引が消えます |

**★スキーマを戻す運用を作らないこと。**
戻す道を用意すると、「あとで戻せるから」と破壊的な変更が通り始めます。
代わりに、**古いコードでも動くスキーマ変更しかしない**、という縛りにします。

## 6. Seed（初期データ）の方針

| 立場 | seed を流すか | 中身 |
|---|---|---|
| 本番 | **絶対に流さない** | 最初のお店は、運営者が管理画面から手で作る |
| 検証 | 流す | 架空の会社・架空の担当者だけ |
| 試験 | 流す（毎回作り直す） | テストコードの中で作る |

- 検証用の作成は `scripts/seed-preview.mjs`。
  `DATABASE_ENV=production` なら、何もせずに止まります。
- メールアドレスは **`.example` ドメインだけ**を使います。
  誰も持てないドメインなので、通知の設定を間違えても、他人には届きません。
- 仮の合言葉は seed 専用のもので、本番では使いません。

## 7. 本番にテストデータを混ぜない仕組み（多層）

1つの仕組みに頼りません。1つは必ず外されるからです。

| 層 | 仕組み | いまの状態 |
|---|---|---|
| ① 接続 | `DATABASE_ENV=production` かつ `ALLOW_PRODUCTION_DB` が無ければ、接続時に例外 | **実装済み**（`lib/server/db.ts`） |
| ② 道具 | seed・E2E・点検スクリプトは `DATABASE_ENV=production` なら即停止 | **実装済み**（DBにつなぐ道具 **23本すべて**） |
| ③ 名前 | 本番URLに `prod` を入れる規則 → 名前で止める道具が効く | **規則として決定。URL採番時に守る** |
| ④ 残高 | 台帳を通さない残高書き換えは `file:` のときだけ動く | **実装済み**（`scripts/lib/fixtures-danger.mjs`） |
| ⑤ ビルド | 本番ビルド時に Mock 決済・Mock メールなら失敗させる | **実装済み**（`scripts/check-providers.mjs`） |
| ⑥ 見張り | DBを触る道具に停止装置が付いているかを、ビルド前に機械で確認 | **実装済み**（`scripts/check-db-separation.mjs` を `npm run build` の並びに登録） |
| ⑦ 目視 | 本番に `.example` のメールや `demo` で始まるお店コードが無いか | **未実装**（本番DBができてから、読むだけの道具として作る） |

**★⑦は、本番DBを作った直後に必ず1回走らせること。**
「検証のつもりが本番だった」は、最初の1週間にいちばん起きます。

### 7-1. ⑥の見張りが、実際に見つけたもの（記録として残します）

見張りを作って最初に流したとき、**4本の道具に停止装置がありませんでした。**

```
scripts/peek-db.mjs        保存先の件数・直近の注文（氏名とメールを画面に出す）
scripts/peek-audit.mjs     監査ログをそのまま並べる（誰が誰に何をしたかが名前つきで出る）
scripts/peek-schema.mjs    表の設計を書き出す
scripts/audit-browser.mjs  ブラウザ点検（★残高を実際に動かす）
```

4本とも「読むだけだから」で通っていたものです。
`audit-browser.mjs` にいたっては読むだけですらなく、残高を動かします。

**★人の目視では、これは見つかりませんでした。**
だから見張りを機械にしました。この4本は
`scripts/lib/db-env-guard.mjs` の `honbanNiMukenai()` を呼ぶ形に直し、
いまは名札（`DATABASE_ENV`）と、つなぎ先の名前（`prod`）の
**どちらか片方が本番に見えた時点で、何もせず止まります。**

### 7-2. 新しく道具を作る人へ

DBにつなぐ道具を足すときは、1行目のほうにこれを書いてください。

```js
import { honbanNiMukenai } from "./lib/db-env-guard.mjs";
honbanNiMukenai("この道具が何をするものかを、日本語で1行");
```

書き忘れたまま `npm run build` を流すと、⑥の見張りが名指しで止めます。
（すでにある道具を一斉に書き換えることはしません。
　動いているものを触るほうが、事故が増えるからです）

## 9. 販売GO条件（保存先まわり）

**次の4つが全部 YES でなければ、お客様のお金を預かりません。**
1つでも欠けたら、その日は売りません。

| 判定 | 出し方 | 意味 |
|---|---|---|
| `MIGRATION_OK = YES` | `npm run db:migrate` | 表の作りが最新の段まで揃っている |
| `PRODUCTION_CLEAN = YES` | `npm run db:check-clean` | 本番に試験用のデータが1件も混ざっていない |
| `RESTORE_VERIFIED = YES` | `npm run db:dump` → `npm run db:restore-verify` | 控えが**本当に戻せる**（取れた、ではない） |
| `DB_SEPARATION_OK = YES` | `npm run check:db` | 保存先を触る道具が全部、本番で止まる |

### 守る決め

1. **「バックアップが取れた」を合格にしない。**
   `RESTORE_VERIFIED = YES` が出ていない控えは、無いものとして扱います。
2. **本番DBを作った直後に、4つとも1回ずつ出すこと。**
   このときは中身が空なので、全部 YES になるのが正しい状態です。
3. **最初のお店を登録した直後に、`PRODUCTION_CLEAN` をもう1回。**
   「検証のつもりが本番だった」は、最初の1週間にいちばん起きます。
4. **そのあとは月に1回。** 控えは毎日取り、
   `RESTORE_VERIFIED` は**3か月に1回**は必ず出し直します。
5. **判定が NO のときに、道具のほうを緩めないこと。**
   直すのはデータか設定であって、確認の条件ではありません。

### この4つに、これは入っていません（別で要ります）

- メール送信会社の契約と DKIM/SPF/DMARC → **未**
- 決済会社の審査 → **未**（可否を断定しないこと。契約形態やポイント設計で変わります）
- 店舗の法定表示（特商法・規約・プライバシー・返品特約）が埋まっていること
  → **空欄のまま公開させないこと。こちらの文例を入れて埋めないこと。**
