# 計測ガイド（GA4 / Clarity / 営業担当別）

最終更新: 2026-08-20

このサイトで「何が起きているか」を数字で見るための仕組みをまとめたものです。
**設定していなくてもサイトは normal に動きます。**（未設定なら計測タグを一切読み込まないだけ）

---

## 1. つなぎ方

環境変数（Vercel の Environment Variables）に入れるだけです。

| 変数名 | 何を入れるか | 未設定だと |
|---|---|---|
| `NEXT_PUBLIC_GA4_ID` | GA4 の測定ID（`G-` から始まる） | アクセス解析なし |
| `NEXT_PUBLIC_CLARITY_ID` | Microsoft Clarity のプロジェクトID | 録画・ヒートマップなし |

入れて再デプロイすれば、その時点から計測が始まります。

---

## 2. 取っているイベント（14種）

| イベント名 | いつ発生するか |
|---|---|
| `hero_cta_click` | トップの一番上のボタンを押した |
| `demo_start` | デモ管理画面（/demo）を開いた |
| `demo_complete` | デモを3画面以上見た、または管理者操作（販売停止・発送処理など）を試した |
| `roi_start` | ROIシミュレーターのスライダーを動かし始めた |
| `roi_complete` | 動かし終えて2秒静止した（＝数字を読んだとみなす） |
| `pricing_view` | 料金セクションまでスクロールした |
| `diagnosis_start` | 診断ウィザードの最初の選択をした |
| `diagnosis_complete` | 診断を最後まで進めた |
| `contact_start` | ご相談フォームに入力し始めた |
| `contact_submit` | ご相談フォームを送信した |
| `sales_demo_start` | 商談用ページ（/sales-demo）を開いた |
| `sales_demo_complete` | 商談用ページを最後のステップまで進めた |
| `video_play` | 製品デモ動画を再生した |
| `video_complete` | 製品デモ動画を最後まで見た |

補助として `price_shock_use`（価格急騰シミュレーター）、`diagnose_to_form`（診断→フォーム）、
`cta_click`（スマホ下部の固定ボタン）、`backtest_view`（公開前バックテストのセクション到達）、
`plan_select`（料金プランのボタン。`plan` に starter / growth / enterprise が入る）も送っています。

---

## 3. 営業担当ごとに分ける（`?ref=sales01`）

営業担当ごとに違うURLを渡します。

```
https://（本番URL）/?ref=sales01
https://（本番URL）/?ref=sales02
```

着地した瞬間に、その `ref` をブラウザ内（sessionStorage）に保存します。
**サイト内で何ページ回っても上書きされません。Cookie は使いません。**

保存した値は、上の14イベント **すべてに自動で付きます**。

| パラメータ名 | 中身 |
|---|---|
| `sales_ref` | `?ref=` の値（営業担当コード） |
| `lead_channel` | 経路（sales / google / x / direct など自動判定） |
| `utm_source` `utm_medium` `utm_campaign` | 広告用のUTM |
| `hero_variant` | トップ見出しのA/Bテスト記号 |

さらに、ご相談フォームを送信すると、通知メールにも同じ情報が入ります。
つまり「**この問い合わせは誰の営業から来たのか**」がメールを見るだけで分かります。

### GA4 側でやっておくこと（1回だけ）

GA4 の「管理 → データの表示 → カスタム定義」で、
`sales_ref` / `lead_channel` / `hero_variant` を **カスタムディメンション（イベントスコープ）** として登録してください。
登録しないと、探索レポートで担当者別に分けられません。

登録すると、探索レポートでこの形が作れます。

```
行：sales_ref
列：demo_start / roi_complete / pricing_view / contact_submit の件数
```

## 4. アポ → LP → デモ → 商談 → 成約 まで見る

| 段階 | どこで取れるか |
|---|---|
| アポ（架電・DM） | 営業スプレッドシート（手入力） |
| LP アクセス | GA4 `page_view` × `sales_ref` |
| デモ | GA4 `demo_start` / `demo_complete` |
| ROI・料金 | GA4 `roi_complete` / `pricing_view` |
| 問い合わせ | GA4 `contact_submit` ＋ 通知メール |
| 商談 | GA4 `sales_demo_start` / `sales_demo_complete` |
| 成約 | 営業スプレッドシート（手入力） |

**LP アクセス〜商談まではサイト側で自動で取れます。**
アポと成約だけは人が入れる必要があるため、そこは営業スプレッドシートと突き合わせる運用です。

### 将来の管理画面（まだ作っていません）

いまは GA4 の画面で見る前提です。自社の管理画面に一覧を出したくなった場合は、
下の形のデータを1行ずつ貯めれば足ります（**その拡張ができる形にしてあります**）。

```
営業担当 / 日付 / アクセス / デモ開始 / デモ完了 / ROI利用 / 料金到達 / 問い合わせ / 商談 / 成約
```

必要なのは「GA4 Data API から日次で読み出して1つの表に書く」処理だけで、
サイト側のコードを変える必要はありません。

## 5. 公開後に見る数字（感覚で変えない）

公開したあと、**思いつきで機能を足さない**ための数字です。
「なんとなく反応が悪い」ではなく、**どの段階で落ちているか**を特定してから直します。

### 5-1. サイト側で自動で取れる6つ

| 見る数字 | 計算 |
| --- | --- |
| **LP → デモ率** | `demo_start` ÷ `page_view` |
| **デモ → 料金率** | `pricing_view` ÷ `demo_start` |
| **料金 → 問い合わせ率** | `contact_submit` ÷ `pricing_view` |
| バックテスト到達率 | `backtest_view` ÷ `page_view` |
| ROI利用率 | `roi_start` ÷ `page_view` |
| 全体CVR | `contact_submit` ÷ `page_view` |

### 5-2. 営業担当別CVR

上のすべてを `sales_ref` で分けます（GA4のカスタムディメンションに登録済みであること）。

```
行：sales_ref
列：page_view / demo_start / pricing_view / contact_submit
→ 担当者ごとに、どの段階で落ちているかが並ぶ
```

同じ資料を配っていても、担当者によって落ちる段階が違います。
**全体の平均だけを見ていると、それが見えません。**

### 5-3. サイト側では取れない2つ（受け取り側の台帳に必ず入れる）

| 見る数字 | どう取るか |
| --- | --- |
| **プラン別の成約率** | `plan_select`（どのプランのボタンを押したか）と、台帳の `proposedPlan` を突き合わせる |
| **失注理由** | 台帳の `lostReason` に、決まった選択肢から入れる |
| **価格への反応** | 台帳の `priceFeedback` に、受注・失注どちらでも必ず入れる |

失注理由は **自由記述だけにしないでください。**
自由記述だけだと「価格で負けた件数」を数えられず、値付けの判断に使えません。
選択肢は `lib/leadStatus.ts` の `LOST_REASONS` に定義してあります。

```
価格 / 機能 / タイミング / 信頼 / 競合 / 決裁 / 不要 / その他
```

それぞれが何を指すかは同じファイルの `LOST_REASON_MEANING` に書いてあります。
人によって入れる場所がぶれると集計が使いものにならないので、
迷ったらそこを読んでから入れてください。

#### 価格への反応も必ず記録する

いまの価格（STARTER 49,800円／GROWTH 98,000円／初期構築費 300,000〜800,000円・すべて税別）は、
**「営業を始めてよい価格」であって「正解の価格」ではありません。**
最初の商談10〜20件で、次の反応を全部記録します（`PRICE_FEEDBACKS`）。

```
高い / 安い / その価格なら欲しい / 初期費用がネック / 月額がネック /
反応なし（価格の話にならなかった）
```

失注したときだけでなく、**受注したときも必ず入れてください。**
「安い」と言われて受注した件が続くなら、それは値上げの材料になります。
「いくらなら買うか」を言われた場合は `saidAcceptableMonthlyYen` に金額を入れます。

台帳に必要な項目一式は `lib/leadStatus.ts` の `LeadRecord` にまとめてあります。
商談が終わったら `REQUIRED_AFTER_MEETING`（提示プラン・価格への反応）だけは
必ず埋めてください。ここが空のまま溜まると、あとから何も分かりません。

### 5-4. 判断のしかた

- **LP → デモ率が低い** → LPの上半分の問題。機能を足すのではなく、言い方を直す
- **デモ → 料金率が低い** → デモで価値が伝わっていない
- **料金 → 問い合わせ率が低い** → 金額か、比較のさせ方の問題
- **失注理由が「価格」に偏る** → 値付けか、含まれる業務の見せ方を直す
- **失注理由が「機能」に偏る** → **ここで初めて機能追加を検討する**
- **失注理由が「信頼」に偏る** → 機能ではなく、導入事例・体制・継続性の見せ方を直す
- **失注理由が「決裁」に偏る** → 商談相手が違う。決裁者に会う導線を作る
- **失注理由が「不要」に偏る** → 営業リストの選び方がずれている。LPより手前の問題

最後の1行が、この表を作った本当の理由です。
機能追加は、感覚ではなく失注理由の集計から始めます。
