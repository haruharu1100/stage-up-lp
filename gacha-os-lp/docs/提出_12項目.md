## ① 会社コードの廃止

**結論：お客様が「会社コード」を入力する画面は、1つも残っていません。【確定】**

| 誰が | どの画面 | 会社コード欄 |
|---|---|---|
| お客様 | 会員登録（`/signup`） | **出ない**（コードで出ないようにしてある） |
| お客様 | ログイン（`/login` のお客様タブ） | **出ない** |
| お店の担当者 | ログイン（`/login` の運営タブ） | **住所からお店が決まらないときだけ出る** |

**どう作ってあるか**

- 会員登録の画面は、`needTenantCode={false}` と**固定**で書いてあります（`app/signup/page.tsx`）。
  設定でうっかり戻ることがありません。
- ログイン画面は、いま開いている住所からお店が決まるかをサーバーが先に調べ、
  **決まったなら欄そのものを作りません**（`app/login/page.tsx`）。
- 欄が出る条件は「住所からお店が決まらない」**かつ**「運営タブを選んでいる」の両方。
  片方だけでは出ません（`components/auth/LoginForm.tsx`）。
- 欄の中の例文には、**それらしい会社コードを書いていません**。
  例を書くと、本物のお客様がそれを自分のコードだと思って入れてしまうためです。

**残っている理由（消していない理由）**

お店の担当者が、**まだ独自ドメインを繋いでいない段階**で入るための入口が要ります。
ここまで消すと、契約した初日にお店の人が入れません。
**お客様には最初から見えません。**

## ② 住所（ドメイン）から、どのお店かを決める方式

**正本：`lib/server/tenantHost.ts`**

順番はこの4段です。上から順に見て、決まったらそこで止まります。【確定】

| 順 | 見るもの | 何のため |
|---|---|---|
| 1 | `tenant_domains` の表（DBに登録した独自ドメイン） | **本番の正本。**お店ごとの独自ドメイン |
| 2 | `TENANT_HOST_MAP`（環境変数） | 検証・試験用。本番では使わない |
| 3 | `DEFAULT_TENANT_CODE`（環境変数） | 1社だけで動かすときの既定 |
| 4 | どれでもない → **null（断る）** | — |

**いちばん大事な決めごと**

> **「決まらなかったので、とりあえず1社目」は、絶対にやりません。**

決まらなければ断ります。ここを曖昧にすると、**A店のお客様にB店の画面を出す**という、
このシステムでいちばん起きてはいけない事故になります。

**細かい作り**

- 大文字小文字はそろえる。末尾の点は落とす。ポート番号は残す。
- `x-forwarded-host` を `host` より優先（Vercel のような経路を通るため）。
- カンマ区切りで複数来たときは**先頭だけ**を使う。
- お店が停止中（ACTIVE でない）なら、ドメインが登録済みでも **null（断る）**。
- どの段で決まったか（`source` = `DOMAIN` / `ENV_MAP` / `DEFAULT`）を常に返します。
  **混ざりません。**ログで後から追えます。

## ⑤ 賞の呼び名の自由化

**結論：お店ごとに賞の呼び名を自由に決められます。固定の「S賞〜D賞」ではなくなりました。【確定】**

正本：`lib/server/gradeLabels.ts`／保存先：`tenant_grade_labels` の表／
画面：`components/console/GradeLabelPanel.tsx`／入口：`/api/console/grade-labels`

例：`特賞 / 1等 / 2等 / 3等 / 参加賞`、`PSA10賞 / BOX賞 / ラストワン賞`、`SSR / SR / R / N`

**壊さないために守っていること（ここが肝です）**

- **中の記号（S / A / B / C / D）は絶対に書き換えません。**
  記号は在庫の表の主キーで、当選履歴にも入っていて、還元率の計算にも使われます。
  書き換えると、在庫・履歴・還元率が丸ごと狂います。
  **持っているのは「見せる文字」だけ**で、表示の直前に足しています。
  呼び名を何回変えても、抽選・残数・当選履歴・記録は1件も壊れません。
- **お店が決めていなければ、これまでどおり「S賞」等を出します。**
  空欄のままにはしません。空欄にすると、お客様の当選画面に「（空白）が当たりました」と出ます。
- **「いま見せる呼び名」と「そのとき何と書いてあったかの記録」を、はっきり分けています。**
  - あとから変わる：売り場・ガチャ詳細・当選画面・獲得商品の一覧
  - あとから変わらない：ポイント台帳の摘要、監査ログ（記録には**記号も一緒に**残します）
  - そもそも入れない：抽選結果そのもの（連打・再送のときに保存済みの文字が返るため、
    呼び名を混ぜると、変えた日から画面と食い違います）

**専用の点検があります**：`npm run check:grade`（`scripts/check-grade-labels.mjs`）

## ⑩ Backup／Restore の設計

設計書：`docs/本番DB分離設計.md`

**戻し方の順番（ここを守ります）**

```
① まず止める（動いたまま戻すと、戻した後の書き込みが混ざる）
② 戻す先は、必ず「新しいDB」。★元のDBの上に直接書き戻さない
③ 新しいDBに対して、確認を通す
④ 確認できてから、接続先を新しいDBへ向け替える
⑤ 古いDBは消さずに残す（原因を調べるため）
```

**★②が最重要です。**壊れたDBの上に控えを書き戻すと、
「壊れた状態」と「戻した状態」が混ざり、何が本当か誰にも分からなくなります。

**販売GO条件（保存先まわり）**：次の4つが全部 YES でなければ、お客様のお金を預かりません。

| 判定 | 出し方 | 意味 |
|---|---|---|
| `MIGRATION_OK` | `npm run db:migrate` | 表の作りが最新の段まで揃っている |
| `PRODUCTION_CLEAN` | `npm run db:check-clean` | 試験用データが1件も混ざっていない |
| `RESTORE_VERIFIED` | `db:dump` → `db:restore-verify` | 控えが**本当に戻せる**（取れた、ではない） |
| `DB_SEPARATION_OK` | `npm run check:db` | 保存先を触る道具が全部、本番で止まる |

**守る決め**

1. **「バックアップが取れた」を合格にしない。**`RESTORE_VERIFIED = YES` が出ていない控えは、無いものとして扱います。
2. 本番DBを作った直後に、4つとも1回ずつ出す。

## ⑪ `RESTORE_VERIFIED` を、どうやって判定しているか

道具：`scripts/db-restore-verify.mjs`
**控えを「空の新しいDB」へ実際に戻してから**、9項目を突き合わせます。
読むだけの点検ではありません。

| # | 見るところ |
|---|---|
| R-01 | 戻す先が**空である**（空でなければ拒否して止まる。上書きしない） |
| R-02 | 控えにある「表の作り方」がそのまま流せる |
| R-03 | 控えの全行を入れられた |
| R-04 | 表の数が同じ |
| R-05 | すべての表の行数が同じ |
| R-06 | すべての表の**指紋（sha256）**が一致する |
| R-07 | 適用済みの段が同じ（**かつ1段以上あること**） |
| R-08 | 全会員で、**保有ポイント＝台帳の合計** |
| R-09 | すべての店舗で、**監査の鎖**がつながっている |

最後に `RESTORE_VERIFIED = YES` か `NO` を出し、記録を `docs/restore-verify-<日時>.json` に残します。

**★この道具が本当に効くことを、実際に確かめてあります（2026-09-07）。**

- 正しい控え → `YES`（44表 3,089行／48人の残高一致／56店舗の鎖が無事）
- **台帳の1行だけ、わざと 1000 → 2000 に書き換えた控え**
  → **R-06（指紋）と R-08（残高）が両方 NG** になり `NO`

**壊れた控えを見つけられることまで確かめて、初めて「確認できる」と言います。**

**★R-09 は、鎖の計算を書き直していません。**本体と同じ `verifyAuditOfTenant` を呼びます。
書き直すと「自分の写し間違いを、自分で正しいと言う」ことになります。

**★R-07 に「1段以上あること」が入っている理由（実際にあった失敗）。**
最初、列名を書き間違えたうえ、エラーを握りつぶしていたため、
**「控え0段／戻した先0段」で必ず一致し、この確認は永久に通っていました**（2026-09-07 に発見・修正）。
**必ず通る確認は、無いより危険です。**

**いまの本番での状態：`RESTORE_VERIFIED` は本番に対して未実施。**
本番DBがまだ無いためです（⑨の項目10）。道具と手順は完成しています。
