## この表が、なぜ先に要るのか

「固定の数字を、DBの数字に置き換える」だけでは終わりません。
置き換えたあとに、**作る・直す・消す・絞り込む・詳しく見る・記録に残す・権限で止める**
までできて、はじめて「本物になった」と言えます。

だから先に、画面ごとに

- いま、どこから数字が来ているのか
- 本当は、どの表（DB）から来るべきなのか
- まだ無い入口（API）はどれか

を、1画面ずつ確かめて書きます。**推測では書きません。**
実際にコードを読んで確かめた結果だけを書いています。

## いちばん大事な発見

13画面のうち **8画面** は、DBを一度も見ていません。

見ているのは `lib/console/state.ts` の `initialState()`（3,364行）という、
**ブラウザの中だけに置かれた見本データ**です。

これが意味することは2つあります。

1. **画面を再読み込みすると、操作した内容が消えます。**
   サーバーに保存していないからです。
2. **会社ごとの分離（テナント分離）が、この8画面では効きようがありません。**
   そもそもDBを見ていないので、「どの会社のデータか」という考えが無いためです。

サーバー側のテナント分離は既に実測で合格していますが、
それは**DBを見ている画面についてだけ**の話です。ここを取り違えないこと。

## 置き換えのときに、必ず一緒にやること

固定値をDBに差し替えるだけでは、合格にしません（ご指示 項目3）。
1画面ごとに、次の7つが揃って完成とします。

1. 一覧が出る（絞り込みができる）
2. 詳しく見られる
3. 作れる・直せる・消せる（その画面に必要な範囲で）
4. 会社をまたいで見えない（A→B・B→A の両方向で実測）
5. 権限で止まる（画面だけでなく**入口＝APIでも**止まる）
6. 大事な変更が監査ログに残る（理由つき）
7. 0件のときに、架空の数字を出さない（Empty State）

## 点検の道具が、台帳を壊せないようにした（2026-08-27）

### 何が起きていたのか

公開先（Preview）に、

> 残高はあるのに、台帳（`point_ledger`）にその理由が無い

会員が生まれていました。原因を追ったところ、**製品のコードではなく、
点検のための道具**でした。下ごしらえのつもりで、こう書かれていました。

```
UPDATE customers SET points = ...
```

`audit-preview.mjs` / `check-points-preview.mjs` / `seed-shipping-scenario.mjs` など
**12か所**。走らせるたびに、説明のつかない残高が増えます。
製品側をいくら直しても止まりません。

★これは「気をつける」で防げる種類の間違いではありません。
　便利だから書かれたのであって、便利なものは必ずまた書かれます。
　ですので、**書いた瞬間に機械で止める**形にしました。

### 何を固定したか（ご指示の5点）

| ご指示 | やったこと | 実物 |
|---|---|---|
| 残高の直接UPDATE禁止 | 直接UPDATEと、台帳の無い残高つきINSERTを検出して落とす | `scripts/check-no-direct-balance-write.mjs` |
| テストデータの変更もLedger経由 | 道具から残高を動かす唯一の入口。残高と台帳を必ず1取引で動かす | `scripts/lib/ledger-write.mjs`（12か所すべてを移行済み） |
| 直接変更するFixtureは隔離 | わざと食い違いを作る出口を1ファイルに閉じ込めた | `scripts/lib/fixtures-danger.mjs` |
| Preview/本番では実行不可 | つなぎ先が手元の使い捨てファイルでなければ、**呼んだ瞬間に停止** | 同上（試験で実際に止まることを確認） |
| CIで直接UPDATEを検出 | `npm run build` の途中に入れた。書くとビルドが通らない | `package.json`（`check:ledger` としても単体実行可） |

### 動くことを、どう確かめたか

- 検出器そのものの空振り確認：わざと違反ファイルを置くと**落ちる**／消すと**通る**を実測
- 自動テスト **613本すべて合格**（`tests/pointIntegrity.test.ts` を6本追加）
  - 食い違いを画面が見つける／一覧と詳細で差が食い違わない／直せば戻る
  - **食い違いを「危険度（不正の疑い）」に混ぜない**。ただし別の欄で必ず表に出す
  - **壊す道具が、手元の使い捨てDB以外では動かない**
- 公開先での実測 **56項目すべて合格**（`check-points-preview.mjs`）
- 管理画面の数字の実測 **17項目すべて合格**（`check-summary-preview.mjs`）

### ★残っている2名の食い違いは、消していません

公開先には、いまも台帳と残高が合わない会員が2名います
（GD-0002：+1,554,400pt ／ GD-0003：+5,000pt）。
これは**古い道具が直接書き換えた跡**で、画面の不具合ではありません。

つじつまを合わせる台帳を後から足せば、見た目は消せます。
**やっていません。** 消すと「合わない記録を、あとから作れる」ことになり、
台帳の意味そのものが無くなるからです。

そのかわり、点検の最後に必ずこう出るようにしました。

```
✓ この点検が、新しい不一致を作っていない … 合っていない人は 2人のまま（点検の前と同じ）
```

**点検の前と後で、合わない人が1人も増えていない。** これが、
今回の作業がきいていることの証拠です。
