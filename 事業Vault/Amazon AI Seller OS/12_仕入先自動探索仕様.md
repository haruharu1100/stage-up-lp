# 12. 仕入先自動探索仕様（Supplier Discovery）

親: [[00_仕様書_最上位]] ／ 前提: [[11_仕入先LIVEデータ仕様]]

> [!important] この仕様が存在する理由（ユーザー指摘・2026-08-20）
> 11番で作った Googleスプレッドシート／CSV は **「仕入先データを受け取る入口」** であって、
> **「仕入先商品の自動発見」ではない。**
> ユーザーが最終的に欲しいのは
> **「私が商品一覧を作らなくても、システムが安い商品を自分で探してくる」状態**である。
> 11番までの実装では、人が商品一覧を作らないとシステムは1件も探せない。ここを埋めるのが本仕様。

---

## 1. 用語をはっきり分ける（ここを混ぜたのが前回の誤り）

| 層 | 何をするか | 実装 | 状態 |
|---|---|---|---|
| **受け取り口**（SupplierProvider） | 人が用意した商品一覧を読む | Googleスプレッドシート／CSV | ✅ LIVE_READY |
| **自動探索**（SupplierDiscoveryProvider） | **システムが自分で商品を探す** | ★AliExpress（本命・アフィリ枠＋DS枠） | ⏳ 実装済・鍵待ち |
| **市場調査**（同じ層／役割が別） | 国内で売れている物の確認・価格比較 | Yahoo!ショッピング | ⏳ 鍵待ち・**仕入先には絶対に使わない** |

> [!warning] 「Adapterがあるだけの状態を完成扱いしない」（ユーザー承認済みの方針・継続）
> 本仕様でも同じ。コードが書けていることと、実際に商品が取れることは**別の状態として表示する**。
> 状態は `LIVE_DISCOVERY_READY` / `PARTIAL` / `UNAVAILABLE` / `MOCK_ONLY` の4区分で必ず画面に出す。

---

## 2. 大原則（11番から引き継ぎ・崩さない）

1. **非公式な認証回避・規約違反スクレイピングは禁止。** 公式APIのみ。
2. **Adapterがあるだけを完成扱いにしない。**
3. **取れない項目は UNKNOWN のまま。推測で埋めない。**
4. **失敗を「0件」で黙って隠さない。** 探索できない時は 409 で理由と必要なものを返して止まる。
5. **お金が動く処理は禁止のまま**：`AUTO_PURCHASE=false` / `AMAZON_AUTO_PUBLISH=false` / `AD_AUTO_OPTIMIZE=false` / `AUTO_REORDER=false` / `RESEARCH_AUTO_APPROVE=false`。
6. **判定基準は一切変えていない。** Research Score・A/B/C/D・MATCH SCORE・月販判定・Confidence Score は凍結どおり無変更。
   自動探索が変えたのは「**何を探しに行くか**」だけ。

---

## 3. 処理の順番（安い処理から。高いAPIは最後の一部だけ）

```
① Supplier Discovery（仕入先APIから商品候補を取得）      … 無料〜極小
   ↓
② 一次除外（無料ルールのみ。AIもKeepaも使わない）        … 0円
   ↓
③ Amazon照合の対象を絞る（見込みの高い順に上限件数だけ）  … 0円
   ↓
④ Amazon候補検索                                          … Keepa消費
   ↓
⑤ 画像・属性一致（MATCH SCORE）                           … 一部だけAI
   ↓
⑥ Keepa分析 → 月販10個以上 → 利益あり → A/B/C/D
```

> [!important] 「Supplier商品500件すべてにKeepaを使わない」の実装本体
> ②と③がそれ。②で無料ルールが危険・欠損データを落とし、
> ③で `amazonMatchLikelihood()`（JAN=45点／型番=20点／ブランド=10点／画像=10点／商品名の具体性=10点／安さ=5点）
> の高い順に並べ替え、`MAX_AMAZON_CHECKS` 件だけをKeepaへ送る。
> 上限を超えた分は**捨てるのではなく「次回に回す」**（理由コード `OVER_API_BUDGET`）。

---

## 4. 自動探索モード（6種）

`DiscoveryMode`。変えるのは探しに行く先だけで、合否の基準は変えない。

| モード | 何を探すか | 実装上の違い |
|---|---|---|
| `STANDARD` | 安定して売れる商品 | 売れている順・1ページ目から |
| `HIGH_MARGIN` | 利益率重視（とにかく安い仕入れ） | 安い順・上限800円（`DISCOVERY_HIGH_MARGIN_MAX_JPY`） |
| `LOW_COMPETITION` | 競合が少ない商品 | **3ページ目から**開始（上位の激戦区を避ける）・種語=専用/交換用/互換/パーツ/補修 |
| `SMALL_LIGHT` | 小型軽量（送料・FBA手数料が安い） | 安い順・上限1200円 |
| `REPEAT` | 消耗品・リピート商品 | 売れている順・種語=詰め替え/使い捨て/フィルター/替刃 |
| `SURPRISE` | 意外だがAmazonで売れている商品 | **5ページ目から**開始（誰も見ていない深さ） |

## 5. 双方向探索

> [!important] ★2026-08-20 既定を `BOTH` に変更し、**B（Amazon→仕入先）を先に**走らせるようにした
> ユーザー指示「特にBを重要視」「最終的にはAmazon→中国検索を主軸にする」。詳細 → 第10B節

| 向き | 意味 | 種 |
|---|---|---|
| `SUPPLIER_TO_AMAZON`（A） | 安い仕入先商品 → Amazonで売れているか | 仕入先API |
| **`AMAZON_TO_SUPPLIER`（B・主軸）** | Amazonで売れている商品 → その仕入先を探す | **Keepaで売れ行きが確認済みの商品だけ**（`reverseSeedGate()` を通ったもの。無ければ実行しない） |

- 両方向で同じ商品に届いた場合だけ `discovery_confirmed_both_ways = 1`。確度が高い候補として記録する。
- 種が1件も無い時は「種が無いので今回は逆方向を行わない」と日本語で明示する。**無理に作らない。**
- Bでは、種のAmazon画像があれば**先に公式の画像検索**（`ds.image.searchV2`）を試し、
  次に商品名・型番・JANでの検索を行う。**非公式な画像検索APIは使わない。**

## 6. 無限探索の禁止（上限）

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `MAX_DISCOVERY_ITEMS` | 100 | 1回の実行で仕入先から取る上限 |
| `MAX_DISCOVERY_DEPTH` | 1 | 横展開の深さ上限 |
| `MAX_AMAZON_CHECKS` | 20 | **Keepaへ送る上限**（ここが課金の栓） |
| `MAX_EXPAND_PER_SEED` | 10 | 有望1件から広げる上限 |

`LIVE_TEST_MODE=true` の間は、これとは別にリサーチ全体の件数上限（`LIVE_TEST_LIMIT`）も同時に効く。

## 7. 無料の一次除外ルール（②で落とすもの）

AIもKeepaも使わずに落とす。落とした理由は**必ず**保存する。

| 理由コード | 落とす条件 |
|---|---|
| `DUPLICATE` | 同じ商品を今回すでに見ている |
| `MOCK_DATA` | サンプルデータ（本番判定に絶対混ぜない） |
| `FORBIDDEN_SOURCE` | 仕入先名/URLにAmazon（ドロップシッピングポリシー違反） |
| `NO_PRODUCT_URL` | 商品URLが無い（**Aランク不可の条件でもある**） |
| `UNKNOWN_COST` | 仕入価格が取れていない |
| `PRICE_OUT_OF_RANGE` | 指定価格帯の外 |
| `NO_IMAGE` | 画像が無い（同一商品を確認できない＝誤一致の原因） |
| `HIGH_IP_RISK` | ディズニー/ポケモン/サンリオ/ジブリ/主要ブランド名等を含む（`DISCOVERY_BLOCK_IP_RISK=true`） |
| `REGULATION_RISK` | Bluetooth/無線/モバイルバッテリー/食品/化粧品/医療機器等（`DISCOVERY_BLOCK_REGULATION=true`） |

④以降で落ちたものも同じ表に残る：
`NO_AMAZON_MATCH` / `LOW_MATCH_SCORE` / `DATA_ANOMALY` / `LOW_SALES` / `NO_PROFIT` / `HIGH_COMPETITION` / `OVER_API_BUDGET`。

> [!note] なぜ全部残すのか
> 「なぜAランクが0件なのか」を後から必ず説明できるようにするため。
> **候補を増やすために判定を甘くはしない。** 詰まっている段を特定して、そこだけ直す。

## 10. Provider実態監査（2026-08-20 第2回・Alibaba ICBUを1本ずつ精査）

> [!danger] 第1回監査の重大な誤りを、ここで自分から訂正する
> 前回わたしが「Alibabaのバイヤー用API」として書いた
> **`/eco/buyer/product/search` と `/eco/buyer/product/description` は、公式ドキュメントに存在しない。**
> わたしが名前を組み立ててしまったもので、鍵を取っても永久に動かなかった。
> これはユーザーが定めた**重大な不具合の分類「APIデータ誤解釈」**に当たる。
> 該当コードは削除し、実在が確認できる `/icbu/distribution/product/*` に置き換えた。

> [!warning] 第2回監査の結論
> **Alibaba.com（ICBU）の公式APIには、買い手が全カタログをキーワードで探すAPIが存在しない。**
> したがって、ユーザーが主軸にしたい「Amazonで売れている商品 → 中国で同じ物を探す」は
> **Alibabaでは原理的に作れない。** 本命を **AliExpress** に変更する。

### 10-1. Alibaba ICBU：指定された各APIの1本ずつの判定

| API | 種別 | キーワード検索 | 第三者の商品 | 判定 | 理由 |
|---|---|---|---|---|---|
| `alibaba.icbu.product.list` | **Seller** | ❌ | ❌ 自分の出品のみ | ✕ 使えない | 「出品管理」グループ。売り手OAuth。引数は上下架状態・自分の商品グループのみ。仕入先名・全文検索・価格・国の指定が無い |
| `alibaba.icbu.product.get` | **Seller** | — | ❌ 自分の出品のみ | ✕ 使えない | 上と同じ。自分のproduct_idを渡す前提 |
| `alibaba.icbu.distribution.product.query` | Buyer寄り | ❌ | ⭕ | △ 一覧しか出せない | **引数が `page_size` と `current_page` の2つだけ。** キーワードも型番もJANも渡せない＝逆引きに使えない |
| `alibaba.icbu.distribution.product.get` | Buyer寄り | — | ⭕ | △ 上の続きだけ | 上のqueryで得たIDの詳細。入口が塞がっているので単体では役に立たない |
| `alibaba.icbu.product.inventory.get` / `.sku.inventory.get` | **Seller** | — | ❌ | ✕ 使えない | 自分の出品の在庫。仕入候補の在庫ではない |
| 物流・送料系（`alibaba.icbu.logistics.*`） | **Seller/取引後** | — | — | ✕ 使えない | 自分の受注の配送手配用。買う前の見積りではない |

**「API名が存在する」だけでは完成扱いしない**というルールに従い、上記はすべて
`ALIBABA_DISTRIBUTION_ENABLED=false` を既定にし、Providerの状態は **UNAVAILABLE** と表示する。

### 10-2. Seller API と Buyer/Discovery API の見分け方（今後のため）

| 見分ける点 | Seller API | Buyer / Discovery API |
|---|---|---|
| 誰がOAuth認可するか | 出品者アカウント | 買い手アカウント |
| 引数に何があるか | 上下架・自分の商品グループ・自分のproduct_id | **キーワード・カテゴリ・価格帯・国** |
| 返るもの | 自分の在庫・自分の注文 | **第三者の商品・価格・MOQ** |
| ドキュメントのグループ名 | 商品管理／取引管理／物流 | Distribution／Dropshipping／Affiliate |

Alibaba ICBU で「Buyer側」に該当するのは Distribution グループだけで、
そこに**検索の入口が無い**、というのが今回の結論。

## 10B. 双方向探索と「1件あたりのAPI費用」

ユーザー指示「特にBを重要視」「最終的にはAmazon→中国検索を主軸にする」に従い、
**既定を両方向（`BOTH`）に変更し、B（Amazon→仕入先）を先に走らせる**ようにした。

| 向き | 流れ |
|---|---|
| A `SUPPLIER_TO_AMAZON` | 仕入先で安い物を探す → Amazonで売れるか調べる |
| **B `AMAZON_TO_SUPPLIER`（主軸）** | Keepaで売れている商品を選ぶ → 画像・型番・JANを取り出す → 仕入先で同じ物を探す |

### Bの「種」に選ぶ条件（`reverseSeedGate()`）

- 推定月販 **10個以上**（`REVERSE_SEED_MIN_MONTHLY_SALES`）
- 出品者 **15人以下**（`REVERSE_SEED_MAX_SELLERS`）
- 30日平均と90日平均の差 **20%以内**（`REVERSE_SEED_MAX_PRICE_SWING_PCT`）
- **Amazon本体が売っている商品は種にしない**
- 商品名・型番・JANがどれも無い商品は `NO_SEED_KEY` で落とす
- 種の上限 **20件**（`MAX_REVERSE_SEEDS`）＝Discoveryの全商品にKeepaを使わないため

> [!danger] ここでもう1つ、重大な不具合を見つけて直した
> 逆方向（B）は**これまで一度も動いていなかった。**
> 種を選ぶSQLが、`research_candidates` に**存在しない列**（brand / model_number / gtin）を読んでおり、
> 毎回失敗していたのに `catch` が握りつぶして**常に0件**を返していた。
> 「失敗を0件で黙って隠さない」という原則に反していたため、
> 正しい表結合に直し、失敗したら日本語で理由を残すようにした。

### 新KPI `DISCOVERY_COST_PER_WINNER`

`discovery_direction_stats` 表に、向きごとに
「調べた件数／高一致件数／利益商品件数／推定API費用」を毎回記録する。

正直さのルール（自動検証で担保済み）：
- **利益商品が0件の向きは「1件あたり◯円」を出さない**（nullのまま。でっち上げない）
- **両方の向きで利益商品が5件以上そろうまで、「どちらが安いか」の結論を出さない**
- すべて「見積り」と明記する（実際の請求額ではない）

 7 OK 普通のまな板（画像無し）          → NO_IMAGE
 8 OK 値段不明の商品                    → UNKNOWN_COST

10 OK 転売用（仕入先=Amazon）           → FORBIDDEN_SOURCE
11 OK 重複した商品                      → DUPLICATE
→ 通過2件／除外9件。見込み点は 水切りラック70点（JANあり）＞ 製氷皿45点（型番のみ）
