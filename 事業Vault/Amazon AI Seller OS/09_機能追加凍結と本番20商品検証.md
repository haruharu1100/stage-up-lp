# 機能追加の凍結と本番20商品検証

親: [[00_仕様書_最上位]] ／ 前段: [[08_本番運用基盤仕様]]

> [!danger] このルールは発効中です（2026-08-20〜）
> **本番20商品テストが完了するまで、新機能を追加してはいけません。**
> AIはこのファイルを読んだ時点で、機能追加の提案・実装を停止すること。

---

## 1. 凍結する内容（追加禁止リスト）

本番20商品テストが完了するまで、以下は**追加しない**。

- 新しいAI社員の追加
- 新しい画面の追加
- 完全自動発注
- 自動出品
- 広告の自動変更
- その他「新しい派手な機能」

**理由：現在のシステムは本番検証に必要な機能が十分揃っている。**
今やるべきことは機能を増やすことではなく、**判断の精度を検証すること**。

### 凍結中でも許可されること
- 本番検証そのものに必要な作業（レポート作成・点検スクリプト）
- 下記「重大な不具合」の修正
- 仕様書・記録の更新

> [!note] OEM販売モード（2026-08-24 採用）との関係
> 要件定義書v1.0を採用し、**仕様としては確定した**（→ [[00_仕様書_最上位]] 第13章）。
> ただし **これは「仕様書の更新」であって、凍結の解除ではない。**
> OEMモードの新規実装（S/A/B/Cランク表示・画像6枚生成・SNS投稿・LINE通知モジュール等）は、
> 下記「凍結の解除条件」を満たすまで**着手しない**。
> 要件書に書いてあることは、実装を始めてよい理由にならない。

## 2. 本番テストの手順

### 手順0：仕入先LIVE監査（★これを通るまで先へ進まない）

```
npm run supplier:audit
```

**利益判定はしない。Amazon検索もKeepaも呼ばない。** 仕入先データが本物かだけを見る。

- [ ] 仕入先商品が実際に取れた
- [ ] **商品URLが実際に開ける（7割以上）**
- [ ] 価格が入っている
- [ ] 通貨が正しい
- [ ] 画像URLが開ける
- [ ] 最小ロット（MOQ）が入っている
- [ ] 更新日時が入っている
- [ ] **サンプル（MOCK）が1件も混ざっていない**

不合格なら理由が日本語で出る。**合格するまで手順1へ進まない。**
詳細 → [[11_仕入先LIVEデータ仕様]]

### 手順1：点検（必ず最初に）

```
npm run prelive
```

以下がすべて満たされていることを確認する。**1つでも問題があればリサーチを開始しない。**

- [ ] LIVE DATA になっている（Keepaキーが入っている）
- [ ] Mockデータ混入 0件
- [ ] `AUTO_PURCHASE=false`
- [ ] `AMAZON_AUTO_PUBLISH=false`
- [ ] `AD_AUTO_OPTIMIZE=false`
- [ ] `AUTO_REORDER=false`
- [ ] `LIVE_TEST_MODE=true`
- [ ] 最大20商品の制限が有効
- [ ] API利用上限が設定されている

※サンプルデータが残っている場合は `npm run prelive:clean` で消せる
（実績・学習データは消えない。本番実行が既にある場合は安全のため中止する）

### 手順2：20商品だけリサーチ

画面「① リサーチツール」→ リサーチ実行。
`LIVE_TEST_MODE` により自動で20件に絞られる。

> [!important] 今回の目的
> **「Aランク商品をたくさん出すこと」ではない。**
> 目的は「システムが正しい数字を取得し、正しい理由で商品を評価できているか」の確認。
> **Aランクが0件でも問題ない。むしろ条件を満たさない商品をAにしない方が重要。**

### 手順3：レポート作成

```
npm run report:test
```

`事業Vault/Amazon AI Seller OS/検証結果/` に、
ChatGPTへそのまま渡せるMarkdownと、表計算用のCSVが出力される。

※練習データで実行した場合は、ファイル名が `【練習データ】` で始まり、
本文にも警告が入る。**本番検証結果と混同しない仕組みにしてある。**

## 3. 検証で見る26項目

商品名／ASIN／仕入先／仕入価格／Amazon現在価格／30日平均価格／90日平均価格／
Sales Rank／推定月販／出品者数／Amazon本体有無／Buy Box／MATCH SCORE／
DATA FRESHNESS／CONFIDENCE SCORE／LANDED COST／想定広告費／想定純利益／
利益率／ROI／推奨仕入数量／Research Score／A/B/C/D／判定理由／
異常検知の有無／UNKNOWN項目

---

## 4. 特に確認すること

### ① Amazon商品の一致精度
仕入先商品とAmazon商品が本当に同じか。**Aランク候補は特に厳しく確認する。**
誤一致が1件でもあれば原因を分析する。
※画像が似ているだけで同一商品と断定してはいけない。

### ② 推定月販
使用したKeepaデータ・計算根拠・信頼度を必ず表示する。
**推定なのに確定値のように扱わない。**

### ③ 利益計算
Aランク商品は、販売価格から
仕入／輸送費／関税等／Amazon手数料／配送・FBA／広告／返品リスク／その他
を**1円単位で分解**する。「利益○○円」だけでは不可。

### ④ UNKNOWN率
各項目について何%取得できなかったかを集計する。
20%以上の項目は今後の改善候補にする。

### ⑤ 異常データ率
DATA_ANOMALY になった商品数と理由を集計する。

## 5. ChatGPTへ渡すレポート（12項目）

① 20商品の一覧／② A/B/C/D件数／③ Aランク商品の詳細／④ 強い推奨商品の詳細／
⑤ UNKNOWN率／⑥ 異常データ件数／⑦ API使用量・推定コスト／⑧ 誤一致があったか／
⑨ 利益計算で仮置きしている項目／⑩ システム側で怪しいと感じた部分／
⑪ Claude自身が改善したい部分／⑫ 50商品へ増やしてよいか（**GO / HOLD**）

※①〜⑨と⑫は `npm run report:test` が機械的に出力する。
※⑩⑪は結果を見たうえでClaudeが記入する。

## 6. テスト中に問題を見つけた時の扱い

> [!danger] 勝手に判定基準を変更しないこと
> 問題を見つけても、**まず記録する**。

### 即修正してよい「重大な不具合」5種のみ
1. 利益計算の間違い
2. Mockデータの混入
3. 商品の誤一致
4. APIデータの誤解釈
5. 安全スイッチの不作動

### 修正してはいけないもの
- **Research Score の基準変更**
- **A/B/C/D の判定基準変更**

→ これらは20商品の結果をChatGPTで確認してから行う。

## 6.5 記録済み：修正した不具合と、保留した改善候補

### 即修正した重大な不具合（2026-08-20・Keepa本番接続の事前検証で発見）

| # | 分類 | 内容 | 影響 | 状態 |
|---|---|---|---|---|
| 1 | 安全スイッチ不作動 | 点検スクリプトが `.env` を正規表現で読み、**空の項目で次の行の値を拾って**いた | 空の鍵を「入っています」と誤報告。安全スイッチ判定にも同じ欠陥 | 修正済（行単位で読む） |
| 2 | APIデータの誤解釈 | Keepaの画像が現在 `images:[{l,m}]` なのに廃止済み `imagesCSV` を読んでいた | **MATCH SCOREの画像40点（最大配点）が常に0**＝誤一致を防ぐ主力機能が無効 | 修正済（両対応） |
| 3 | APIデータの誤解釈 | BuyBox価格の `-2`（カート無し）を除外しておらず素通り | **「-2円」が販売価格として利益計算に流れ込む**恐れ | 修正済（0以下は全てUNKNOWN） |

### 追加で修正した重大な不具合（2026-08-20・特殊値の横断監査で発見）

| # | 分類 | 内容 | 影響 | 状態 |
|---|---|---|---|---|
| 4 | APIデータの誤解釈 | 寸法・重量を `p.packageWeight \|\| null` で受けていた。**`-1` は truthy なので素通りする** | マイナスの寸法・重量がサイズ区分計算に流れ、**FBA手数料が丸ごと狂う** | 修正済（`amazonSearch.ts` / `market/index.ts` 両方） |
| 5 | Mockデータの混入 | `npm run prelive` が仕入先を点検しておらず、仕入先がサンプルのままでも「準備OK」と言っていた | **Amazon側＝本番／仕入先＝架空の値段** という最悪の混ざり方を素通しする | 修正済（④-2を追加し、本物の仕入先が無ければ開始を止める） |

### ★実装した改善（承認済み・2026-08-20）

> [!success] Amazon手数料を仮置きから実データへ → **実装完了**
> 当初は「凍結中のため保留」としていたが、**本番20商品テスト前の唯一の精度改善として承認され実施**。
> 詳細は [[10_Amazon手数料Provider仕様]]。
> - `AmazonFeeProvider` を独立Providerとして新設
> - ACTUAL / ESTIMATED / UNKNOWN を明確に分離。UNKNOWNは0円にしない
> - 利益に効く手数料がUNKNOWN、または手数料データが古い場合は **Aランク禁止**
> - 旧仮置き計算との差を記録（実測：平均 −33円／最も減った −157円）
> - **Research Score / A・B・C・D基準 / MATCH SCORE / 月販判定 / Confidence Score は一切変更していない**

### 追加で修正した重大な不具合（2026-08-20・仕入先Providerの実態監査で発見）

| # | 分類 | 内容 | 影響 | 状態 |
|---|---|---|---|---|
| 6 | Mockデータの混入 | **Alibaba / 1688 / AliExpress の3Providerは、実体が同じ1つのクラスで、3社のどの公式仕様にも合致しない自作の呼び方だった**（`Authorization: Bearer <APP_SECRET>` ＋ `method=product.search`） | **鍵を入れても動かない。「差込口がある」だけで本物のつもりになっていた。仕入先は永久にサンプルのまま** | 修正済（AliExpressは公式仕様どおりに全面書き直し。Alibaba・1688は偽リクエストを投げない「未接続」表示へ） |
| 7 | Mockデータの混入 | 仕入先データに **LIVE / ESTIMATED / UNKNOWN / MOCK の区別が無かった** | 架空の仕入値で計算した候補が、本物と同じ顔でAランクに並ぶ | 修正済（品質区分を導入・DB保存・画面表示。MOCK／UNKNOWNはAランク禁止） |
| 8 | 商品の誤一致 | 仕入先の画像が1枚も無くても「高信頼の同一商品」と自動断定していた | 画像で確認していないのに同一商品と決めつける | 修正済（画像が無い場合は人の確認が必要な帯に留める。除外はしない） |

### ★実装した改善（承認済み・2026-08-20 その2）

> [!success] 仕入先LIVEデータ化 → **実装完了**
> 詳細は [[11_仕入先LIVEデータ仕様]]。
> - **`GoogleSheetsSupplierProvider` を新設し LIVE_READY に**（無料・審査なし・契約なし／1回設定すれば以後は自動取得）
> - AliExpressを公式仕様どおりに全面書き直し（鍵が入れば即LIVE）
> - 必須18項目・取れないものはUNKNOWNのまま（**推測で埋めない**）
> - **仕入先URLが無い商品はAランクにしない**
> - **Supplier LIVE監査**（`npm run supplier:audit`）を新設。合格するまで本番20商品テストへ進まない
> - **Research Score / A・B・C・D基準 / MATCH SCORE / 月販判定 / Confidence Score は一切変更していない**（追加したのは降格ガードのみ）

### 追加で修正した重大な不具合（2026-08-20・仕入先自動探索の実態監査で発見）

| # | 分類 | 内容 | 影響 | 状態 |
|---|---|---|---|---|
| 9 | APIデータの誤解釈 | AliExpressのフォールバック処理で、読んでいた**フィールド名の約半分が別APIのもの**（`productMainImageUrl` / `storeName` / `item_title` / `sale_price` / `productId`） | 鍵を入れても**画像・店名・商品名・価格が永久に空**になる。空を「取れなかった」と誤解したまま運用してしまう | 修正済（公式仕様どおりに8点修正） |
| 10 | APIデータの誤解釈 | AliExpressの**MOQ・在庫は公式仕様上そもそも返らない**のに、取れる前提のコードだった | 取れない値を「0」等として扱い、仕入判断を誤らせる | 修正済（UNKNOWN固定に変更。**推測で埋めない**） |
| 11 | 安全スイッチの不作動 | Yahoo!ショッピングAPIの**既定の利用条件は非商用**だが、鍵さえあれば使えてしまう設計だった | 規約が白でない状態で商用の商品収集を始めてしまう | 修正済（`YAHOO_SHOPPING_COMMERCIAL_ACK=true` を**人が明示的に立てるまで絶対に使わない**ゲートを追加） |

### ★実装した改善（承認済み・2026-08-20 その3）

> [!success] 仕入先の自動探索（Supplier Discovery）→ **配線は完成。ただし「完成」ではない**
> 詳細は [[12_仕入先自動探索仕様]]。
> - **受け取り口（[[11_仕入先LIVEデータ仕様|11番]]）と自動探索を別の層に分離**した。スプレッドシートは自動探索ではない
> - **費用の安い順のファネル**（無料ルール →並べ替え →上位だけKeepa）。500件すべてに高額AIを使わない
> - **上限を必ず持たせ無限探索を禁止**。超過分は捨てずに次回へ回す
> - **落とした理由を全件保存**（`discovery_rejections`）し、画面に内訳を表示
> - **Research Score / A・B・C・D基準 / MATCH SCORE / 月販判定 は一切変更していない**
>
> [!danger] 凍結ルールとの関係
> 自動探索は**新しい派手な機能ではなく、本番20商品テストを始めるための材料（＝検証対象の商品）を用意する作業**であり、
> 「本番検証そのものに必要な作業」として実施した。**新しいAI社員・新しい画面・自動発注・自動出品・広告自動変更は1つも追加していない**
> （`/research` 画面内に表示ブロックを足しただけで、画面は増えていない）。
> そして**`LIVE_DISCOVERY_READY` は0件のため、これは完成扱いにしない。**

その他の記録（実装しない）：
- **楽天市場API**は、楽天ウェブサービス規約**第10条**が閉じた環境・内部利用を認めていないため使わない（実装もしない）
- **Yahoo!ショッピングAPI**は商用利用がすべて禁止というわけではなく、問い合わせ窓口で相談できると明記されている。**ユーザーが確認を取るまでは使わない**
- キーワード検索で拾った候補は、Keepa側にオファー情報が無いとBuy Boxが取れないことがある（取れない時はUNKNOWNと出るので誤りではない）
- JAN/EANは商品によって取れない（中国仕入の無名商品ほど取れない）。型番とブランドは取得率が高い
- **1688の非公式API代理サービス**は使わない（規約違反リスク）。代行業者からの提供データをスプレッドシートで受け取る方が確実

## 7. 凍結の解除条件

以下がすべて満たされた時点で、このルールは解除される。

1. 本番20商品テストが完了している
2. レポートをChatGPTへ渡し、確認が終わっている
3. 50商品への拡大が GO と判断されている
