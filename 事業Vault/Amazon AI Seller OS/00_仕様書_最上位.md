## 1. このシステムの目的（誤解しやすいので最初に）

このシステムの目的は **「Amazonへの自動出品」ではない。**

目的は、以下を一本につないだ **「AIによるAmazon事業経営システム」** を作ること。

```
商品発掘 → 利益判定 → 仕入れ判断 → 商品ページ制作 → 出品
   → 広告運用 → 価格調整 → 在庫管理 → 売上分析 → 再学習 → 商品発掘へ戻る
```

「何を売るか」だけでなく **「何個仕入れるか」** までAIが判断する。

### 成功の定義／失敗の定義（最重要）

> [!warning] 両方とも「失敗」と判断する
> - ❌ **大量に売れているが赤字**
> - ❌ **黒字だが、ほとんど売れていない**
>
> ✅ 正解は **BALANCED GROWTH MODE**＝「十分な販売数があり、なおかつ利益もしっかり残る」状態。
> 最重要指標は ACOS ではなく **NET PROFIT AFTER ADS（広告後純利益）**。

## 2. 絶対に崩してはいけない安全ルール（法務・規約）

以下は機能追加より優先される。**どんな改善指示よりも上位。**

1. **Amazonサイトの無許可スクレイピングをしない。**
   市場データはKeepa等の正規API／CSV入力／手動ASIN入力から取る。API化できないデータは「外部データプロバイダー」「CSV」「手動入力」に切り替えられる構造にする。
2. **商品画像は MASTER PRODUCT IMAGE がある時だけ生成する。**
   許される画像ソースは5区分のみ ①自社撮影 ②メーカー提供 ③問屋提供 ④使用許可取得済み ⑤自社が権利所有。
   Amazonや他社の商品画像を無断コピーしない。**MASTER画像が未登録なら画像を1枚も作らない**（mockでも偽画像を作らせない＝ImageProviderのmockは例外を投げる）。
3. **商品そのものの形・色・容量・内容量・パッケージ表記をAIが勝手に変更しない。**
4. **誇大表示・虚偽表示・存在しない性能や効果の生成は禁止。**
   食品について健康効果・疾病改善等を勝手に生成しない（景表法・薬機法・食品表示法）。
5. **`AMAZON_AUTO_PUBLISH=false` が既定。** trueにしない限りAmazonへ1件も送信しない。
6. **問題が1つでもあれば AUTO PUBLISH を停止する。** コンプラAIが「停止」を1つでも出したら自動出品は動かない。
7. **`AD_AUTO_OPTIMIZE=false` が既定。** 広告はAIが改善案を出し、人間が承認してから変更する（→[[02_権限ルール（AI自動／人間承認）]]）。
8. **APIキーをコードに直接書かない。** 環境変数か `.env` のみ。
9. **LLM自体を勝手に再学習しない。** 履歴DB・評価ロジック・RAG・統計データで判断精度を上げる。
10. **外部Web情報の取得（Firecrawl等）は「公開Web上の市場トレンド調査用」に限る。**
    Amazon商品ページを無制限にスクレイピングする目的では使わない。
11. **Amazon内の別出品者から仕入れて顧客へ直送しない（ドロップシッピングポリシー違反）。**
    仕入れ先は必ずAmazonの外（卸・メーカー・eBay・Alibaba等）。商品は一度自分の手元を経由させ、自分の名前の納品書で発送する。
12. **既にAmazonに存在する商品で新規ASINを作らない（重複出品違反）。**
    既存商品は相乗り。新規ページを作れるのは「Amazonにまだ無い商品」と「自社OEM商品」だけ。
13. **輸入規制を通っていない商品を仕入れ判断に出さない。**
    食品衛生法／薬機法／PSE／技適／商標（並行輸入要件）をコンプラAIが仕入れ**前**に判定する。

## 3. AIとAPIの役割分担（AIを大量契約せず、役割で分ける）

| 担当 | 役割 |
|---|---|
| **Claude API / Claude Code** | **司令塔・開発担当**。仕事の振り分け、エラー修復、コード改善、文章生成（タイトル・説明文・コピー） |
| **OpenAI API** | **画像＋商品理解＋最終チェック**。商品写真から「2枚目はこれ／3枚目はこの訴求／Amazonで一番クリックされそうな構成」を判断して画像生成。さらに **Claudeが書いた商品説明をOpenAIにも確認させる＝AI二重チェック** |
| **Amazon SP-API** | 価格・出品・商品属性・既存ASIN・Listingの**正式な情報源**。カテゴリ別の必須属性は **Product Type Definitions API** から取得する |
| **Keepa API** | **商品発掘担当**。90日価格推移／ランキング推移／出品者数の変化／Amazon本体の在庫有無で評価 |
| **仕入先データAI** | Amazonの販売データ × 自社の問屋価格を**常時比較** |
| **Amazon Ads API** | 広告の実績取得と入札・予算の変更（利用可能なら連携）→[[01_広告最適化AI仕様]] |
| **動画生成API** | 紹介動画の生成（fal / Runway 等） |
| **Firecrawl等** | Amazon **以外**（Google Trends・楽天・Yahoo!ショッピング・SNS・ニュース）の市場トレンド調査 |

### 仕入先比較の計算イメージ
```
Amazon販売価格   5,980円
自社問屋価格     2,800円
Amazon手数料       900円
FBA配送料          500円
広告費             300円
────────────────────────
想定利益         1,480円   ROI 52.8%
```

### コスト制御ルール
- 単純な分類・計算・データ整理 → **安価なモデル**
- 商品の**最終判断だけ** → 高性能モデル
- 画像 → OpenAI Image のみ

## 5. 商品発掘AI（毎日約10,000商品を自動分類）

**「売れてから探す」のではなく「これから売れそうな商品を探す」。**
ランキングはまだ低いが**急上昇している**商品を先回りする。

### A / B / C / D ランク分類

| ランク | 意味 | 扱い |
|---|---|---|
| **A** | 今すぐ仕入れ | 人間の承認待ちリストの最上位に出す |
| **B** | 値下がりしたら仕入れ | 価格ウォッチに登録し、条件到達で通知 |
| **C** | 競合が減ったら仕入れ | 出品者数ウォッチに登録 |
| **D** | 販売しない | 除外理由を記録（同じ商品を毎日再評価しない） |

### 判定に使うシグナル
- 90日の価格推移／ランキング推移（Keepa）
- 出品者数の変化（競合の増減）
- Amazon本体の在庫有無
- レビュー数の増加ペースと平均評価
- 在庫切れの発生頻度
- 仕入先（問屋）価格との差＝想定利益とROI
- Amazon外のトレンド（Google Trends・楽天・Yahoo!・SNS・ニュース）

## 6. 商品ハンター（24時間監視）

以下の変化を24時間監視し、条件を満たしたら通知する。

**監視シグナル**：価格の急上昇 ／ ランキングの急上昇 ／ 競合の減少 ／ 在庫切れの増加 ／ レビューの急増

**流れ**
```
シグナル検知 → 問屋価格を検索 → 利益計算 → 条件クリア → 通知
```

**通知の例（この粒度で出す）**
> ○○食品が直近7日でランキング+63%、競合8社→3社、現在価格4,980円、自社仕入2,100円、推定利益1,230円

## 8. 学習（すべての判断と実績を蓄積して次に活かす）

AIの判断と実績を **Obsidian と DB の両方** に蓄積し、次回の判断に反映する。

蓄積する項目：
- 何が売れたか／何が売れなかったか
- どの商品を何個仕入れたか（仕入数の当たり外れ）
- どの価格なら売れたか
- どの広告設定が最も利益を残したか
- どのキーワードが利益につながったか
- どの季節・曜日・時期に売れたか

学習方式は **LLMの再学習ではなく、実績DB＋採点の重み再計算**。
安全装置：実績5件未満では重みを動かさない／1回の変更幅は **±20%** まで。

## 11. リサーチツール（2026-08-19 追加・実装済み）

> [!important] 位置づけ
> **ユーザーが商品を入力して調べる道具ではない。**
> システムが自分で「安い仕入先の商品 → Amazonで売れている同一商品 → 利益が出る商品」を
> 探してきて並べる。ユーザーは毎朝 `/research` を開いて眺めるだけでよい状態を目標とする。
> 詳細仕様は **[[06_リサーチツール仕様]]**。

### 画面構成は3つに固定
`① リサーチツール /research` ／ `② 商品を発掘する /discover` ／ `③ 商品ページを作る /`

### 処理の順番（この順番自体が仕様）
```
仕入先から大量取得 → Amazonから同一商品を検索 → MATCH SCORE で同一判定
→ 推定月販でふるい → 全費目で利益計算 → Research Score 採点 → A/B/C/D
→ 有望なものだけ類似商品へ芋づる探索（深さ・件数の上限あり）
```

### 追加の絶対ルール（第2章に準ずる）
14. **商品名だけで同一商品と判定しない。** 画像・型番・JAN/GTIN・ブランド・サイズ・容量・
    カラー・素材・セット個数・仕様を総合して MATCH SCORE 100点満点で判定する。
    配点は 画像40／型番・JAN20／商品名10／サイズ・容量10／色・仕様10／その他10。
    **90以上＝高確率一致／80〜89＝人が確認／79以下＝原則除外。**
15. **画像が似ているだけで同一商品と断定することを禁止。**
    型番・JANの一致もサイズ・仕様の裏付けも無い場合は、コード側で強制的に
    「人が確認」以下へ落とす（設定で外せないハード制約とする）。
16. **すべての商品を高額AIでチェックしない。** 判定は必ず安い順に進め、決着したら打ち切る。
    `通常計算 → ルール判定 → 画像pHash → テキスト類似 → Embedding → AI Vision`
    **一次判定のAI料金ゼロは、どんな改善でも絶対に崩さない。**
    有料AIの呼び出し回数には上限を持たせる（0にすれば完全無料運用）。
17. **販売数を断定しない。** 正確な販売数が取れない場合は「月販10個確定」ではなく
    **「推定月販 約N個」** と表示し、根拠（Keepa実測／ランキング推定／不明）を必ず併記する。
18. **`AUTO_PURCHASE=false` が既定。** 仕入れの発注はシステムから一切行わない。
    `true` になっているとリサーチスクリプトは実行そのものを拒否する。
    `RESEARCH_AUTO_APPROVE=false`＝AIが候補を承認することもない。
19. **鍵が無い部分は嘘の数字を作らず「分かりません」と返す。**
    画像確認AIは鍵が無ければ `unknown` を返し、推測で「同一」とは言わない。
    サンプルデータで動いている時は画面に必ず「実在の商品ではありません」と出す。

### Research Score（100点満点・リサーチ専用）
需要20 ／ 利益25 ／ Amazonとの商品一致精度15 ／ 競合の弱さ10 ／ 仕入価格差10 ／
価格安定性5 ／ 仕入安定性5 ／ 商品ページ改善余地5 ／ リスクの低さ5

※ 第10章の「採点100点満点」は `③ 商品ページを作る` 側の採点。**別物なので統合しない。**

### 毎朝の画面（第7章の具体化）
```
本日調査した商品 → Amazon一致候補 → 月N個以上売れている
→ 利益条件クリア → Aランク → 今日の強い推奨
```
「今日の強い推奨」＝Aランクのうち、需要も利益も**基準の1.5倍**を超え、リスクゼロのもの。
この欄（最大3件）だけ読めば当日の判断が終わる状態を維持する。

### 実装の落とし穴（実測で判明。再発させないこと）
> [!warning] 2026-08-19 実測
> AI Vision に **画像を渡せていないのに呼び出す** と、商品名の日本語・中国語の違いだけで
> 「別商品」と自信満々に答え、pHash 91〜95%＋型番一致の正しい候補を14件も壊した。
> しかも架空データに対して実際に課金が発生した。
> → **両側に本物の画像URLが無ければ Vision を呼ばない**（`sample://` 等の擬似URLも弾く）。
> → **JAN/GTINが完全一致している場合、Visionの「別商品」判定だけで除外しない**
>   （「人が確認」の帯に留める。1つのAI意見で確かな証拠を捨てない）。
> → 確信度0.6未満の「別商品」は判定保留として扱う。
>
> また、画面の数字は必ず**絞り込みの順に減る**ように数えること。
> 「Amazon一致0件なのに月10個以上が3件」のような表示は人を誤解させる。

## 12. 実績学習ループ（2026-08-20 追加・実装済み）

> [!important] この段階の目的
> **新しい派手な機能より「本当に儲かる商品を見抜く精度」を優先する。**
> ①本番データで精度を測る ②見つけた商品が本当に売れたかまで追跡する
> ③結果を次の商品選定に反映する。詳細仕様は **[[07_実績学習ループ仕様]]**。

### 画面は6つに再編
`① /research` ／ `② /discover` ／ `③ /` ／
**`④ 仕入れ・販売の記録 /lifecycle`** ／ **`⑤ 予測の答え合わせ /learning`** ／ **`⑥ 自動運転とAPI代 /ops`**

### 追加の絶対ルール（第2章・第11章に準ずる）
20. **Mockデータと本番データを混ぜない。**
    `KEEPA_API_KEY` があれば自動で本番へ切替え、画面に緑の **`LIVE DATA`** を出す。
    鍵が無い時は **「これは練習用の仮データです。この数字で仕入れを判断しないでください。」** を出す。
    本番実行にサンプル由来の候補が混入した場合は**機械的に捨て**、捨てた件数を赤帯で表示する。
21. **取得できなかった項目を推測値で埋めない。** `UNKNOWN（取れていません）` と表示し、
    UNKNOWNの一覧も出す。UNKNOWNが多いほど CONFIDENCE を下げる。
22. **承認ボタンは外部へ1円も発注しない。**
    「この条件で買うと決めた」記録と、その瞬間の予測値の凍結スナップショットを保存するだけ。
    実際の注文はユーザーが仕入先サイトで行う。2段階確認＋`AUTO_PURCHASE` 二重ロック。
23. **仕入数量はAIだけで決めない。数式・統計を優先する。**
    `推定月販 ÷ 30 ×（リードタイム＋安全在庫）` を、初回予算・上限個数・MOQで頭打ちにする。
    **初回は大量仕入れを避ける。** 画面には必ず 推奨数／理由／**最悪ケース**／想定売切日数 を出す。
24. **予測の精度は 需要・利益・価格を別々に測る。** まとめて1つにしない（どこが外れたか分からなくなるため）。
25. **カテゴリー別の補正は統計（中央値）で行い、LLMに丸投げしない。**
26. **AIが採点の配点を勝手に変えない。** 学習は「AI推奨重み」の**提案どまり**。
    人間が承認して初めて反映。変更幅は±20%まで。**実績5件未満では学習そのものを動かさない。**
27. **古すぎるデータの商品をAランクにしない**（DATA_FRESHNESS・`maxDataAgeHours`）。
28. **ランクと一緒に必ず CONFIDENCE を出す。**「Aランク Confidence 96%」と「72%」を区別する。
    `minConfidenceForA` 未満はAに上げない。
29. **同じ内容の仕入先データを毎回再計算しない。** 内容ハッシュで差分だけ再評価する（API代の節約）。
30. **API代に月額上限を持たせ、超えそうならB・Cの見張りから自動で止める。Aの見張りは止めない。**
31. **`RESEARCH_AUTO_RUN=true` は許可、`RESEARCH_AUTO_APPROVE` / `AUTO_PURCHASE` /
    `AMAZON_AUTO_PUBLISH` / `AD_AUTO_OPTIMIZE` はすべて `false` 既定。**
    → **調査と分析は自動でよい。お金が動く行為だけは必ず人が承認する。**
32. **仕入先データも LIVE / ESTIMATED / UNKNOWN / MOCK を区別する。**
    画面に `SUPPLIER DATA: LIVE` と出せるのは、実際の仕入先から取得できている時だけ。
    Amazon側の `live_data` とは**別の判定**として持ち歩き、DBにも保存する。→ [[11_仕入先LIVEデータ仕様]]
33. **「この商品をどこから買えるか」のURLが無い商品は、Aランクにしない。**
    仕入先がサンプル（MOCK）や必須項目欠け（UNKNOWN）の商品も同じくAにしない。
34. **仕入先の商品画像が1枚も無い場合、「高信頼の同一商品」と自動断定しない。**
    画像で確認できないものは人の確認が必要な帯に留める（除外はしない）。
35. **「Adapterがある」「差込口がある」だけを完成扱いにしない。**
    公式仕様に合わない自作の呼び方は本物ではない。接続できないProviderは、
    偽のリクエストを投げず「未接続」と正直に表示する。
36. **仕入先には「受け取り口」と「自動探索」の2層があり、混同しない。**
    Googleスプレッドシート／CSVは**人が作った商品一覧を受け取る入口**であって、
    安い商品を自分で見つけてくる機能ではない。自分で探すのは
    SupplierDiscoveryProvider（Yahoo!ショッピング／AliExpress／Alibaba／1688）。
    → [[12_仕入先自動探索仕様]]
37. **探索は必ず「安い判定から先」に並べる。最初から全商品に高額AIを使わない。**
    自動取得 → 無料ルールで除外 → Amazon一致しやすさで並べ替え → 上位だけKeepa →
    月販 → 利益、の順。上限（`MAX_DISCOVERY_ITEMS` / `MAX_DISCOVERY_DEPTH` /
    `MAX_AMAZON_CHECKS`）を必ず持たせ、無限探索は禁止。
38. **落とした商品は理由コード付きで必ず保存する。**（`discovery_rejections`）
    `NO_AMAZON_MATCH` / `LOW_MATCH_SCORE` / `LOW_SALES` / `NO_PROFIT` /
    `HIGH_IP_RISK` / `REGULATION_RISK` / `UNKNOWN_COST` / `NO_IMAGE` /
    `NO_PRODUCT_URL` など。捨てずに次の改善材料にする。

### 商品の一生（10ステータス）
```
DISCOVERED → WATCHING → APPROVED → ORDERED → RECEIVED → LISTED → SELLING → SOLD_OUT
                                                    ↘ STOPPED  ↘ FAILED
```
APPROVED以降はすべて**人間が押して進める**。失敗は10分類で記録し、次回のリサーチで
「過去の失敗からの注意」として同条件の商品に警告を出す。成功したら周辺を8方向に掘る（横展開）。

### 13-1. OEMモードの商品条件（基本プリセット・管理画面から変更可）

| 条件 | 基準 |
|---|---|
| Amazon販売価格 | 1,000円〜15,000円 |
| 1商品あたり利益 | 500円以上 |
| 利益率 | **30%以上**（27%は原案の誤記。不採用） |
| ROI | 20%以上 |
| 推定月間販売数 | 100個以上 |
| レビュー数 | 50〜1,000件 |

レビュー・月販は**条件のみで完全除外せず**、例外表示できること。

### 13-2. 商品評価100点（OEMリサーチ用プリセット）

既存のResearch Score配点は変更しない。以下は**OEMモード専用のプリセットとして追加**する。

| 評価項目 | 配点 |
|---|---|
| 利益性 | 30 |
| 販売需要 | 25 |
| 競合状況 | 15 |
| 仕入安定性 | 10 |
| レビュー参入難易度 | 10 |
| 広告適性 | 5 |
| 商品リスク | 5 |

### 13-3. ランク：S / A / B / C

- **OEMモードの表示は S/A/B/C**。既存モードの A/B/C/D は互換のため残す。
- S＝基準を大きく上回る／A＝全基準を満たす／B＝一部未達または情報不足で人間確認／C＝基準未達・高リスク
- **既存のAランク禁止条件はそのまま効く**：商品URL未確認、送料・MOQ・重量・重要コストがUNKNOWN → **A以上にしない**。

### 13-4. 探索の方向（既存の主軸を維持）

```
Amazon需要確認
  → VERIFIED済み仕入先で検索（AliExpress等）
  → MATCH SCORE（同一商品可能性 0〜100%・初期基準80%以上）
  → LANDED COST（総原価）
  → 利益判定
  → S / A / B / C
  → 人間承認
```

**仕入先は要件書の「1688＋Alibaba固定」を採用しない。** SupplierDiscoveryProvider構造を維持し、
AliExpress／1688／Alibaba／中国輸入代行／Google Sheets／CSV／将来の別仕入先を並列に持つ。
**DOCUMENTED → AUTHORIZED → CONNECTED → VERIFIED を実際に通ったProviderだけLIVE利用する。**
要件書に名前が書いてあることは、実装完了の根拠にならない。

### 13-5. FBA前提の利益計算

OEMモードはFBAを基本とする。利益計算に入れる費用：
商品仕入原価／中国国内送料／国際送料／関税／輸入消費税／検品費／OEM加工費／パッケージ費／ラベル費／
日本国内送料／**FBA納品送料**／**Amazon販売手数料**／**FBA配送代行手数料**／**FBA保管料**／広告費／想定返品・不良コスト。

**既存のAmazon手数料Providerと利益ロジックは変更しない**（ACTUAL／ESTIMATED／UNKNOWNの区分もそのまま）。

### 13-6. Amazon商品画像6枚（メイン1＋サブ5）

正式仕様として採用。作成タイミングは**仕入承認後・出品情報確定後**。

1. メイン：白背景・販売商品のみ・文字/ロゴ/透かし/装飾なし
2. 別角度：誤認を招く加工をしない
3. サイズ・仕様：商品内容と一致する情報のみ
4. 使用シーン：同梱されない小物で誤解させない
5. 特徴訴求：薬機法・景表法・知財・Amazonポリシーに抵触しない
6. 比較・補足：競合を誹謗せず、根拠のないNo.1表記・保証表現を使わない

**必須ゲート**：Amazon画像要件チェック → 知財・法令・誇大表現チェック → **人間承認**。
**画像が未承認の商品は、出品登録・販売開始へ進めない**（工程ブロック）。
サプライヤー画像の無断転載を前提にしない。AI生成画像だけで実物と異なる印象を与えない。

### 13-7. 広告（BALANCED GROWTH MODE が上位）

- ACOS20%以下は **初期の目安** として使う。
- ただし**最重要指標は NET PROFIT AFTER ADS（広告後純利益）**。ACOSだけを下げない。
  「販売数も十分」かつ「広告後の純利益も残る」の両立が目的（→ 第1章の成功の定義）。
- 取得する実績：広告費／広告売上／注文数／ACOS／ROAS／CPC／CTR／CVR／インプレッション／クリック／検索語句／キーワード／ターゲットASIN。
- **`AD_AUTO_OPTIMIZE=false` は変更しない。** AIは改善提案まで。入札変更・停止は人間承認。

### 13-8. SNS（X＋Instagram・週2投稿）

- 1商品につき週2投稿を初期プリセット（管理画面で変更可）。
- 例：月曜=商品紹介／木曜=使用メリット・使用シーン／翌週月曜=特徴・差別化／翌週木曜=FAQ・使い方。
- **媒体ごとに文章を変える**（同一文の単純転載をしない）。
- **投稿前に人間承認。自動投稿しない。**（`AMAZON_AUTO_PUBLISH=false` と同じ思想）
- 景表法：「必ず儲かる」等の断定・誇大、根拠のない二重価格・煽りは不可。

### 13-9. LINE通知（正式モジュール）

Sランク発見／Aランク発見／発注承認待ち／Amazon販売開始／在庫不足／売上急増／売上急減／
広告ACOS悪化／広告費上限到達／SNS投稿失敗／APIエラー／仕入価格急騰／Amazon販売価格急落／
競合急増／利益率30%未満への低下。条件は管理画面からON/OFF。

### 13-10. 発注（人間承認必須・変更不可）

- **`AUTO_PURCHASE=false` / `AUTO_REORDER=false` は変更しない。**
- 発注承認画面に1画面で表示：Amazon画像・URL・価格・推定月販・レビュー・BSR／仕入画像・URL・サプライヤー・仕入単価・MOQ／発注数量・商品代金・想定送料・想定総原価／1個利益・利益率・ROI・月間利益予測／商品リスク／AI分析。ボタン＝承認／保留／却下。
- 仕入先の**発注API**も4段階ゲートの対象。VERIFIEDを通るまで発注連携は作らない（それまでは実発注は人間）。

ユーザー指示：
> 価格RAW値の監査表示は「実装する」で確定です。
> AliExpress初回LIVE商品取得時に、APIが返した価格・通貨の生値と、
> システム解釈後の値を必ず並べて表示してください。**RAW値は加工・丸め・換算禁止です。**

  画面表示と、監査ログ `live_first_product_audit` の両方。
- **RAWに手を加えない**：丸めない／換算しない／大文字化しない／カンマを消さない。
  JSON表記のまま残すので、引用符の有無で「文字列で来たのか数値で来たのか」まで判る。
- **選ばなかった項目も残す**：応答に含まれた価格・通貨らしき項目を全部そのまま保存する。
  「そもそも拾う項目名を間違えていた」は、採用した1つだけを残すと絶対に見つからないため。
