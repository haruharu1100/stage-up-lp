## 2. 鍵を入れた直後にやること（固定手順）

```
npm run aliexpress:plan             … 手順の確認だけ（外部APIを1回も呼ばない）
npm run aliexpress:live             … STEP1→STEP2 まで。商品1件が取れた時点で★必ず止まる
npm run aliexpress:live:continue    … ChatGPT監査が済んでから STEP3以降へ進める
```

`npm run aliexpress:live` は**上から順にしか進まない**。1つ落ちたらそこで止まる。

> [!important] ★2026-08-22 追加：STEP2 で必ず一度止まる（ChatGPT監査ゲート）
> ユーザー指示：「STEP2で、『AliExpressから本物の商品1件を取得できた』時点で一度止めてください。」
>
> **なぜ止めるか**
> Keepa では実際に、
> **画像形式の読み違い／`-2` の意味の読み違い／寸法 `-1` のすり抜け** が起きた。
> どれも「最初の1件の生データを人が見ていなかった」ために後から気づいた。
> AliExpress でも同じ種類の**仕様の読み違い**が最初の実レスポンスに潜んでいる可能性が高い。
>
> **正しい順番**
> 鍵取得 → **1件だけ本物取得** → **ChatGPT監査** → 詳細/送料/画像 → 5件 → 20件
>
> 止まるのが**既定**。人が `npm run aliexpress:live:continue` を打つまで、
> STEP3以降の API は**1回も呼ばれない**。

### STEP 1 — 認証確認だけ（商品は取らない）

- 見るもの：APP_KEY / APP_SECRET / 署名が作れるか / アクセストークンの素性 / API契約台帳
- 合格：`AUTHENTICATED = true`
- **★このSTEPでは商品を1件も取得しない。**

> [!warning] 正直な但し書き
> AliExpress に「認証だけを確かめる公式API」は**確認できませんでした（UNKNOWN）**。
> 存在しないAPIを勝手に作って呼ぶことはしないので、
> **相手サーバーが本当に受け入れたかは STEP2 の1回目で判定します。**
> STEP2 で認証に失敗した場合は、**商品の中身を一切見ずに止めます**（意図は守っています）。

### STEP 2 — 商品を1件だけ取得（`aliexpress.ds.text.search`）

確認する8項目：**商品ID／商品名／価格／通貨／商品画像／商品URL／店舗／カテゴリー**

- APIの生データと、システムが表示する値を**1件ぶん照合**する
- 取れない項目は **UNKNOWN**。推測で埋めない
- **商品URLが取れない商品はAランク禁止**

#### ★1商品目で必ず保存する13項目（監査ログ）

保存先テーブル：`live_first_product_audit`
**秘密情報は絶対に入れない**（`request_params` に app_key / sign / access_token を含めない）

| # | 項目 | 列名 |
|---|---|---|
| 1 | 呼び出したAPI名 | `api_name` |
| 2 | request項目（秘密情報を除く） | `request_params` |
| 3 | HTTP status | `http_status` |
| 4 | AliExpress側 code | `aliexpress_code` |
| 5 | success / error | `success` / `error_text` |
| 6 | 取得した product ID | `product_id` |
| 7 | 商品名 | `product_title` |
| 8 | 価格 | `price` |
| 9 | 通貨 | `currency` |
| 10 | 画像 | `image_url` |
| 11 | 商品URL | `product_url` |
| 12 | 取得日時 | `fetched_at` |
| 13 | UNKNOWN項目 | `unknown_fields` |

**取れなかったものは `null`（＝UNKNOWN）のまま。`0` や `"00"` で埋めない。**
とくに `aliexpress_code` は、返ってこなければ勝手に `"00"`（成功）を入れない。

#### ★価格・通貨の RAW 値も別欄に保存する（＋5項目・2026-08-24 確定）

ユーザー指示（2026-08-24）：
> 価格RAW値の監査表示は「実装する」で確定です。
> AliExpress初回LIVE商品取得時に、APIが返した価格・通貨の生値と、
> システム解釈後の値を必ず並べて表示してください。**RAW値は加工・丸め・換算禁止です。**

上の表の `price` / `currency` は **ValueGuard を通したあと**の「解釈後」の値。
それとは別に、**APIが返したそのままの値**を次の5列に保存する。

| # | 項目 | 列名 |
|---|---|---|
| 14 | 価格RAW（無加工） | `price_raw` |
| 15 | 価格RAWの項目名（どの項目から取ったか） | `price_raw_field` |
| 16 | 通貨RAW（無加工） | `currency_raw` |
| 17 | 通貨RAWの項目名 | `currency_raw_field` |
| 18 | 応答にあった価格・通貨らしき項目すべて（選ばなかったものも含む） | `price_fields_raw` |

**なぜ2つに分けるのか**
Keepa では **解釈後の値しか残していなかった**ため、`-2` を販売価格として
利益計算に流していたことを後から検証できなかった。同じ形を繰り返さないための保険。
価格の読み違いは、そのまま「赤字商品を黒字と判定する」に直結する唯一の項目。

**RAWには一切手を加えない**
丸めない／換算しない／大文字化しない／カンマを消さない。
JSON表記のまま残すので、**引用符の有無で「文字列で来たのか数値で来たのか」まで判る**
（`"12.34"` なら文字列、`12.34` なら数値）。
唯一の例外は、万一 鍵が混ざっていた場合。そのときは**加工せず丸ごと捨てて**事実だけ残す。

**選ばなかった項目まで残す理由**
Keepa の事故は「値の読み違い」だけでなく「拾う項目名そのものを間違えていた」ことも原因だった。
採用した1つだけを残すと、その間違いは監査で絶対に見つからない。

**画面には必ず並べて出す**

```
★価格・通貨の RAW 監査（生値 ⇔ システム解釈後）
  価格  RAW  targetSalePrice = "12.34"
        解釈後  12.34
  通貨  RAW  targetSalePriceCurrency = "USD"
        解釈後  USD
  応答に含まれていた価格・通貨らしき項目（選ばなかったものも含め全部そのまま）：
    originalPrice            = "20.00"
    targetSalePrice          = "12.34"  ← これを採用
```

**次の3つは「要目視」として自動で強調する**（合否判定ではなく、人が見る場所の指示）

| 見つけた状態 | なぜ危ないか |
|---|---|
| 生値は返っているのに、システムが弾いて UNKNOWN にした | Keepa の `-2` 事故と同じ形。仕様の読み違いが最も疑われる |
| 生値と解釈後で**数字や文字が動いた**（`"1,234.50"`→`1234.5`、`"usd"`→`"USD"`） | カンマ・大文字化の解釈が本当に正しいか要確認 |
| 想定した価格項目が無いのに、別名の価格らしき項目はある | 拾う項目名そのものが違う可能性 |

`"12.34"` → `12.34` のような**型が変わっただけ**の違いは強調しない。
正常な商品でも毎回警告が出ると、本当に見るべき上の3つが埋もれるため
（型の変化は引用符ごと表示されるので隠れてはいない）。

#### ★STEP2 の直後に画面へ出る10項目（ChatGPTへそのまま貼る）

1. 使用したAPI
2. 認証結果
3. 実レスポンスから取得できた項目
4. UNKNOWN項目
5. APIレスポンスで想定外だった点
6. 商品URL
7. 価格 ← **★RAW（無加工）とシステム解釈後を並べて表示**（2026-08-24 確定）
8. 画像取得結果
9. VERIFIEDにしてよいか
10. 次のSTEP3へ進めてよいか

**9と10の最終判断は人が行う。** システムは「自分の5項目チェックは通った」としか言わない。
監査で読み違いが見つかったら差し戻す。`verdict` 列は人が後から入れる欄で、**AIは埋めない**。

### 4-1. 5件・20件の価格検査（2026-08-24 追加）

1商品目の「RAW値の並べ表示」は**1件だけ**を深く見るためのもの。
これに対して5件・20件は、**件数の偏り**を見つけるための検査。
「たまたま1件目が正常だっただけ」を見逃さないようにする。

**やること**

| 段階 | 検査 | 保存先 |
|---|---|---|
| 5件 | 1件ずつ 価格・通貨 を検査 | `api_response_samples`（`sample_kind = 'live_step5'`） |
| 20件 | 1件ずつ 商品URL・画像・価格・通貨 を検査 | `api_response_samples`（`sample_kind = 'live_step20'`） |

**出力の形（実際の出力）**

```
★価格：20件中 3件を弾きました（受け取れたのは 17件）
    「不明」を表す特殊な値だった（-1 / -2 / 9999999 など）：2件
    0だった（0円・在庫0個は「不明」と区別して扱う）：1件
    弾いた値そのもの（無加工）：-1 , -2 , "0.00"
```

- **件数を必ず出す**（「20件中3件」の形）。全体の取得率に混ぜて薄めない。
- **弾いた値そのものを無加工で出す**。丸めない・換算しない。
  値を消してしまうと「なぜ弾いたか」を後から人が判断できない。
- 全件を弾いた場合は、値ではなく**こちらの読み方を疑う**ように出す。

```
★全件を弾いています。値がおかしいのではなく、こちらの読み方が違う可能性が高い
```

> [!warning] ここで直した2つの不具合（2026-08-24）
> 1. **5件の検査結果が捨てられていた** — 検査自体はしていたが、
>    表示も保存もしていなかったので、誰も見られなかった。
> 2. **20件は1件も検査していなかった** — さらに、保存されていた検査結果は
>    **1商品目（STEP2）のもの**だった。記録は埋まって見えるのに、
>    中身は20件について何も語っていない状態だった。
>
> どちらも「動いていないのに動いて見える」種類の不具合なので、
> 実データを取る前に潰しておく必要があった。

> [!danger] 読めなかった値を「0」にしていた不具合も修正した
> 価格・在庫の読み取りで、**数値でも文字列でもない値**（例：`{amount:"12.34"}`）や
> **数字でない文字列**（例：`"abc"`）が来たとき、内部で空文字に変換され、
> 結果として **`0` として通っていた**。
> つまり「在庫が読めなかった」が「**在庫0個**」になっていた。
>
> これは大原則の【取得できなかったデータを、0として扱わない】に正面から反する。
> 修正後は「数値として読めなかった」として弾き、理由も正しく出る。
> （`0` という値そのものが返ってきた場合は、これまで通り 0 として扱う。区別している。）

## 7. アクセストークンの扱い

保存するのは **取得日時／期限／refreshの有無と期限／権限／末尾4桁** だけ。
**トークン本体はDBに入れない**（`.env` のみ）。

`.env` に入れる任意項目（入れると期限管理ができる）：

```
ALIEXPRESS_TOKEN_OBTAINED_AT=2026-08-25T10:00:00Z
ALIEXPRESS_TOKEN_EXPIRES_AT=2026-11-23T10:00:00Z
ALIEXPRESS_REFRESH_EXPIRES_AT=2027-02-21T10:00:00Z
ALIEXPRESS_TOKEN_SCOPES=ds
```

> [!important] 期限切れを「商品0件」にしない
> 期限が切れていることが分かっていれば、**呼びに行かずに AUTH_ERROR で止める**。
> ただし **期限が分からないときは「有効」と断定しない**。
> 公式説明では90日とされているが、**実際に発行された日を機械は知らない**ので、
> `.env` に取得日が無ければ期限は **UNKNOWN** と表示する。

## 8. 秘密情報の扱い（マスキング）

- App Secret / Access Token / Refresh Token / 署名 を
  **ログ・画面・Obsidian・DB に平文で置かない**
- 出すときは必ず `****1234` の形（8文字未満の値は `****` のみ）
- 保存の直前に「.env の生の値がそのまま混ざっていないか」を最終確認し、
  混ざっていたら**本文ごと保存しない**
- 実装：`lib/providers/secretMask.ts`（出口を1か所にまとめて、書き忘れによる漏れを防ぐ）

## 9. コストの見張り（API が無料でも数える）

無料＝無制限ではない。次を必ず数えて残す。

- AliExpress の呼び出し回数（STEPごとに `live_test_steps` へ1行）
- Keepa の**消費トークン**（呼び出し回数で代用しない）
- OpenAI の使用回数
- Rate Limit に当たった回数

**「商品候補1件を見つけるまでに、何をいくつ使ったか」**を後から必ず言えるようにする。

## 10. 鍵が届いたあとの進め方

```
認証 → 1件 → ★ChatGPT監査（ここで必ず止まる） → 詳細/送料/画像 → 5件 → 20件
```

**★2026-08-22 変更点**
以前は「認証 → 1件 → 5件 → 20件」を一気に走らせる設計だった。
いまは **1件取れた瞬間に必ず停止**し、人がChatGPTで監査してから先へ進む。
理由は Keepa で仕様の読み違いが3回起きたため（画像形式／`-2`／寸法 `-1`）。

20件まで通ったら、次は **Amazon → AliExpress の向き**で本番テストを行う。

```
Keepaから需要のあるAmazon商品を少数抽出
  ↓ AliExpressへ逆検索
  ↓ 候補取得
  ↓ 画像・商品仕様の照合
  ↓ 利益計算
```

最後の20件の結果が出たら、**ChatGPTへ渡すレポートを作成する**。
