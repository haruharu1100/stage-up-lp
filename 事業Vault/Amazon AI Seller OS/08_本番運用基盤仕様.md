# 本番運用基盤仕様（第4段階）

親: [[00_仕様書_最上位]] ／ 前段: [[07_実績学習ループ仕様]]

> [!important] この段階の目的
> **機能を増やす段階は終わった。** ここからの目的は3つだけ。
> ① 本番運用できる状態にする
> ② 実際のお金の流れまで正確に追えるようにする
> ③ 止まっても復旧できるようにする
>
> そして次の最大テーマは **「本物のデータで本当に利益商品を当てられるか」**。
> 機能量ではなく、的中率で評価する段階に入る。

---

## 1. いきなり大量に叩かない（LIVE_TEST_MODE）

`LIVE_TEST_MODE=true`（既定）＋ `LIVE_TEST_LIMIT=20`（既定）。

- Keepaの本番キーが入っている時だけ作動する安全弁。
- 何件指定しても、1回のリサーチで扱う商品数を上限まで強制的に切り詰める。
  画面には「指定は100件でしたが、安全のため20件だけ調べます」と理由を出す。
- 上限を上げるのは**人が .env を手で書き換えた時だけ**。AIは自分で上げない。
- MockとLiveは絶対に混ぜない。混在を検知した件数は `mixed_data_blocked` として
  実行記録に残り、混ざったデータは判断に使わない。

## 2. 本番データの異常検知（DATA_ANOMALY）

実データは必ず壊れた値が混ざる。次を検知して**隔離**する。

- 価格が0／異常に高い／異常に安い、ランキングが桁違い、レビュー数が急に消えた、
  在庫数が明らかにおかしい、同一商品なのに前回と極端に違う

**隔離された商品は仕入判断に使わない。人間が確認を終えるまでAランクにしない。**
画面 `/research` の異常一覧から、人が「確認済み」または「除外」を選んで初めて解除される。

## 3. 本当の利益（REAL_NET_PROFIT）

Amazonの売上だけを見て黒字判定しない。**12費目すべてを引く。**

仕入原価／国際送料／関税／国内送料／FBA手数料／販売手数料／保管料／返品損失／
広告費／廃棄費用／値下げ損失／為替差損

→ `REAL_NET_PROFIT` として保存し、これを唯一の「儲かったか」の基準にする。

## 4. キャッシュフローと現金化日数

- 入金予定・仕入支払・広告費支払・現在の資金拘束額を管理する。
- `CASH_CONVERSION_DAYS`（仕入 → 入金までの日数）を商品ごとに出す。
- **利益が高くても現金化まで120日かかる商品は評価を下げる。**
  黒字倒産を避けるため、利益率だけで並べない。

## 5. 商品ごとの投資効率

GMROI／在庫回転率／1商品あたり30日利益／資金拘束日数 を出し、
**「どの商品に資金を集中すべきか」**を金額で示す。

## 6. 初回仕入の安全係数（NEW_PRODUCT_SAFETY_FACTOR）

**初めて扱う商品は、推奨仕入数をそのまま買わせない。**

- 既定 `0.5`。推奨30個 → 初回は15個。
- 実績が良ければ **15 → 30 → 50** と段階的に増やす。
- 増やすのは実績が出てから。予測だけでは増やさない。

## 7. 再発注AI（REORDER_RECOMMENDER）

売れ行き・在庫・リードタイムから「いつ・何個」を推奨する。
**ただし `AUTO_REORDER=false` を維持。推奨するだけで、発注は絶対にしない。**

## 8. 広告AIとの完全連携

7日ごとに12指標を集計し、5段階で判定する。

`SCALE`（伸ばす）／`OPTIMAL`（維持）／`OVERSPEND`（使いすぎ）／
`UNDEREXPOSED`（露出不足）／`POOR`（撤退検討）

> **「売れるが赤字」も「黒字だがほぼ売れない」も、どちらも失敗。**
> BALANCED GROWTH MODE を維持する。損益分岐点ACOSを超えた週から先に手を打つ。

**`AD_AUTO_OPTIMIZE=false` のまま。** AIは変更案を出すだけで実行しない。

## 9. アカウント健全性画面（9項目）

出荷遅延率／注文不良率／キャンセル率／返品率／知的財産の申立／
在庫パフォーマンス／出荷期限超過／低評価レビュー／アカウント警告

> **広告や新規仕入れより、アカウント保護を最優先する。**
> アカウントが止まれば、他のすべての数字に意味がなくなるため。

## 10. 出荷期限アラート

今日出荷すべき注文／明日／期限超過 を一覧化し、通知Providerにも接続する。

## 11. システム停止対策（★パソコンをつけっぱなしにしない）

`scheduler:loop` を「PCをつけっぱなし」だけに依存しない構造にした。

`npm run scheduler:install` を**一度だけ**実行すると、macOSのlaunchdに2つ登録される。

| 登録するもの | 起動方法 | 落ちた時 |
|---|---|---|
| Webサーバー（ポート3900） | パソコン起動時に自動 | **自動で立ち上げ直す**（KeepAlive） |
| 定期実行（5分ごと） | パソコン起動時に自動 | 5分後に自動で再実行（1回きり起動の繰り返し） |

定期実行を「回り続けるループ」ではなく「5分ごとに1回だけ動かす」形にしたのが要点。
**固まったまま気づかれない状態**が原理的に起きない。

確認: `npm run scheduler:status` ／ 解除: `npm run scheduler:uninstall`

## 12. ジョブ管理（5状態）

`QUEUED` / `RUNNING` / `SUCCESS` / `FAILED` / `RETRYING`

失敗したジョブは **何時／何をしようとして／どこで失敗したか** を必ず残す。
電源断などで `RUNNING` のまま残った記録は、次回起動時に自動で片づける。

## 13. 自動再試行（★無限リトライ禁止）

**1分後 → 5分後 → 30分後** の3回まで。

4回目で `FAILED` に確定し、「4回試しても直らなかったので、これ以上は繰り返しません」
と記録して停止する。無限に繰り返してAPI代を垂れ流すことは構造的に起こらない。

## 14. API障害対策

Providerごとに `HEALTHY` / `DEGRADED` / `DOWN` を記録する。

**DOWN の間はそのProviderを呼ばない。** そして――
**止まっている時に、推測の数字で埋めない。** その仕事は「見送りました」と記録して飛ばす。

## 15. バックアップ

毎日1回（`BACKUP_INTERVAL_HOURS=24`）、次を丸ごと保存する。

承認スナップショット／仕入記録／販売実績／広告実績／予測結果／学習データ／
Research Score変更履歴 ほか計18種類

- 保存先 `backups/YYYY-MM-DD_HHMM/`（gitには含めない）
- 各表を1ファイルずつ＋データベース本体の写し＋「この中身について.json」
- 1つの表で失敗しても、他の表の保存は続ける
- 古い世代は `BACKUP_KEEP=30` 世代で自動削除。**消すのは写しだけ。本体には絶対にさわらない。**
- **戻す作業は必ず人の手で行う。自動では戻さない。**
- バックアップだけは、自動リサーチが止まっていても必ず動く（API代が1円もかからないため）

## 16. 学習データを守る

> **今後このシステムで一番価値が高くなるのは「自社販売実績DB」。**
> Keepaのデータは買い直せるが、自社の実績は二度と買えない。

このため実績系テーブルは「買い直せない（irreplaceable）」と印を付けて管理し、
バックアップの対象から外れないようにしてある。

## 17. Aランクの的中率（管理画面の最上部）

過去30日について、実績だけで数える。予測は一切混ぜない。

Aランク商品数／実際に仕入れた数／黒字商品数／赤字商品数／**的中率**／平均予測誤差

**実績が3件に満たない間は「まだ判定していません」と正直に出す。**
1勝0敗を「的中率100%」とは絶対に表示しない。

## 18. AI社員の成績表

| AI社員 | 何で採点するか |
|---|---|
| リサーチAI | Aランクの的中率 |
| 需要予測AI | 推定月販と実績月販のズレ |
| 利益予測AI | 予測利益と実利益のズレ |
| 仕入数AI | 仕入れた数に対して売り切れた割合 |
| 広告AI | 損益分岐点ACOSを下回った週の割合 |

**点数はすべてわり算。AIが自分を採点することはない。**
実績3件未満は「まだ判定できません」と出す。

## 19. 今は完全自動化しない（4つのfalseを維持）

```
AUTO_PURCHASE=false
AMAZON_AUTO_PUBLISH=false
AD_AUTO_OPTIMIZE=false
AUTO_REORDER=false
```

**調査と分析は自動。お金が動く行為は必ず人間承認。** この方針は崩さない。

## 20. 本番検証手順（★この順番を守る）

> **いきなり大量にAPIを実行しない。** 各段階で必ず結果を確認してから次へ進む。

```
まず最大20商品  →  結果確認  →  50商品  →  100商品  →  問題なければ本格運用
```

### 段階0：鍵を入れる（人がやる）

`.env` に `KEEPA_API_KEY` を設定する。この時点では他は既定のまま触らない。

### 段階1：20商品（`LIVE_TEST_LIMIT=20`）

1. `/research` で「リサーチ実行」を押す
2. 見るところ
   - **LIVE DATA と出ているか**（Mockが混ざっていないか）
   - UNKNOWN が多すぎないか（多い＝Keepaから項目が取れていない）
   - DATA_ANOMALY に隔離された件数と、その中身が妥当か
   - Aランクの件数と、その根拠（Confidence・データ鮮度）
   - `/ops` の「API代」が想定どおりか

**この20商品の結果を丸ごとChatGPTへ渡す。** ← ユーザー決定済みの引き渡しポイント

### 段階2：50商品

`.env` の `LIVE_TEST_LIMIT` を **50** に手で書き換えて再実行。
20商品の時と傾向が変わっていないかを見る（急にAランクが増えたら基準を疑う）。

### 段階3：100商品

同様に **100** へ。ここでAPI代の月額見込みが現実的かを判断する。

### 段階4：本格運用

- `LIVE_TEST_MODE=false` にするか、上限を実運用値に上げる
- `RESEARCH_AUTO_RUN=true` で毎日の自動リサーチを開始
- `npm run scheduler:install` で常駐させる
- **4つのfalseは引き続き維持**
