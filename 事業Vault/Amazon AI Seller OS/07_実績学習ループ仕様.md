# 実績学習ループ仕様（第3段階）

親: [[00_仕様書_最上位]] ／ 前段: [[06_リサーチツール仕様]]

> [!important] この段階の目的
> 新しい派手な機能を増やすことではない。**「本当に儲かる商品を見抜く精度」を上げること**だけが目的。
> そのために ①本番データで精度を測る ②見つけた商品が本当に売れたかまで追跡する
> ③結果を次の商品選定に反映する の3点を完成させる。

## 0. 追加された画面（メニューは6つに再編）

| メニュー | パス | 役割 |
|---|---|---|
| ① リサーチツール | `/research` | 仕入先→Amazon→利益→A/B/C/D（第2.2段階） |
| ② 商品を発掘する | `/discover` | 発掘エンジン（第2段階） |
| ③ 商品ページを作る | `/` | AI社員7名（第1段階） |
| **④ 仕入れ・販売の記録** | **`/lifecycle`** | **承認→発注→入荷→出品→販売→実績入力（新規）** |
| **⑤ 予測の答え合わせ** | **`/learning`** | **予測vs実績・カテゴリー補正・配点提案・失敗分類・横展開（新規）** |
| **⑥ 自動運転とAPI代** | **`/ops`** | **予定表・API代・仕入先取込・ランク変動理由（新規）** |

## 1. 最優先1：Keepa本番接続（Mockと本番を絶対に混ぜない）

### 1-1. LIVE DATA 表示
- `KEEPA_API_KEY` を `.env` に入れるだけで、次回のリサーチから自動で本番データに切り替わる。コード修正は不要。
- 本番データで動いたリサーチには画面上部に緑の **`LIVE DATA`** バッジと「本番データです」を表示。
- 鍵が無い時は琥珀色の **`サンプルデータ`** バッジと
  **「これは練習用の仮データです。この数字で仕入れを判断しないでください。」** を必ず表示する。
- 候補カード1件ごとにも `live / sample` を持たせる（`research_candidates.data_source` / `live_data`）。

### 1-2. 混在の禁止（機械的にブロック）
> [!danger] 絶対ルール
> **Mockデータと本番データが1回のリサーチ結果に混ざることを禁止する。**
> 実装では、本番実行中に混入したサンプル由来の候補を**自動で捨て**、
> 捨てた件数を `research_runs.mixed_data_blocked` に記録し、赤い帯で
> 「★本番データとサンプルデータが混ざりかけたため、N件を自動で捨てました。」と表示する。

### 1-3. 取得する最低13項目
ASIN ／ 商品名 ／ 画像 ／ 現在価格 ／ 30日平均価格 ／ 90日平均価格 ／ Sales Rank ／
Sales Rank履歴 ／ 出品者数 ／ Amazon本体の販売有無 ／ Buy Box価格 ／ 月販推定 ／ データ取得日時

### 1-4. UNKNOWN の扱い（推測禁止）
> [!warning] 取れなかった項目を推測値で埋めない
> Keepaが `-1` を返した項目は `null` にし、画面には **「UNKNOWN（取れていません）」** と出す。
> さらに候補ごとに「取れなかった項目（UNKNOWN）」の一覧を表示し、
> **「分からない項目は推測で埋めていません」** と明記する。
> UNKNOWNが多い商品は後述の CONFIDENCE が下がり、Aランクに上がりにくくなる。

## 2. 最優先2：実績学習ループ

### 2-1. 10ステータス（商品の一生）
```
DISCOVERED → WATCHING → APPROVED → ORDERED → RECEIVED
   → LISTED → SELLING → SOLD_OUT
                    ↘ STOPPED（途中でやめた）
                    ↘ FAILED（失敗した）
```

| ステータス | 日本語 | 誰が動かすか |
|---|---|---|
| DISCOVERED | 見つけた | システム |
| WATCHING | 見張り中（B・C） | システム |
| **APPROVED** | **仕入れると決めた** | **人間だけ** |
| ORDERED | 仕入先で注文した | 人間（自分で注文後に押す） |
| RECEIVED | 商品が届いた | 人間 |
| LISTED | Amazonに出品した | 人間 |
| SELLING | 売れ始めた | 人間 |
| SOLD_OUT | 売り切れた | 人間 |
| STOPPED | 途中でやめた | 人間 |
| FAILED | 失敗した（理由を10分類で記録） | 人間 |

### 2-2. 承認ボタンの絶対ルール
> [!danger] 承認しても1円も発注しない
> - 承認ボタンは **「この条件で買うと決めた」という記録** と
>   **その瞬間の予測値（凍結スナップショット）** を保存するだけ。
> - 押しても仕入先へは何も送信しない。確認文に
>   **「実際の注文は仕入先サイトでご自身で行ってください。ここでは記録だけを残します。」** を出す。
> - 2段階確認（1回押す→確認文→もう1回押す）。
> - `AUTO_PURCHASE=true` や `RESEARCH_AUTO_APPROVE=true` の場合、APIは承認そのものを**拒否**する（二重ロック）。

**凍結スナップショット**＝承認した瞬間の 仕入価格／販売価格／推定月販／予想利益／利益率／ROI／
競合数／Research Score／CONFIDENCE／推奨仕入数 を固定保存する。
後から相場が動いても「あのとき何を根拠に決めたか」が消えないようにするため。

### 2-3. PURCHASE_QUANTITY_RECOMMENDER（何個仕入れるか）
> [!important] AIだけで決めない。数式・統計を優先する。
> 計算式（統計が主・LLMは使わない）：
> ```
> 推奨数 = 推定月販 ÷ 30 × (仕入リードタイム日数 + 安全在庫日数)
> ```
> そのうえで次の上限で必ず頭打ちにする：
> - 初回予算 `FIRST_BUY_BUDGET_JPY`（既定30,000円）を超えない
> - 上限個数 `maxFirstOrderQty`（管理画面から変更可）を超えない
> - MOQ（最低ロット）を下回らない
> - **初回は大量仕入れを避ける**（自己発送フェーズは原則MOQ寄り）

**必ず画面に4点セットで出す**：
1. 推奨仕入数（例：20個）
2. その理由（推定月販・リードタイム・安全在庫・予算のどれで決まったか）
3. **最悪ケース**（全部売れ残ったらいくら損か・何日で資金が戻らないか）
4. 想定売切日数

### 2-4. FORECAST_ACCURACY（予測の答え合わせ）
売れた実績（売れた数／平均売値／広告費／実利益／返品数）を入力すると、
**需要・利益・価格を別々に**採点する。

| 指標 | 意味 |
|---|---|
| 需要の的中率 | 推定月販 vs 実際の月販 |
| 利益の的中率 | 予想利益 vs 実際の利益 |
| 価格の的中率 | 想定売値 vs 実際の平均売値 |

まとめて1つの精度にしない。**どれが外れているか分からないと直せないため。**

> [!warning] 実績5件未満では学習を動かさない
> `minSamplesForBias`（既定5）件たまるまで、精度の数字も補正も出さない。
> 「実績がまだ1件です。5件たまるまで、精度の数字は出しません」と正直に表示する。
> 少ないデータで数字をいじると、間違った学習が固定化するため。

### 2-5. カテゴリー別補正（統計優先・LLMに丸投げしない）
カテゴリーごとに「予測に対して実績が何倍だったか」の**中央値**を取り、次回の見積もりに掛ける。
例：キッチン用品の需要倍率 ×0.7 → 次からは推定月販を0.7倍して見る。
平均でなく中央値を使うのは、1件のバズで全体が歪むのを防ぐため。
サンプル数が足りないカテゴリーは `applied=0`（使わない）にする。

### 2-6. Research Score の自動改善（提案どまり）
> [!danger] AIが勝手に配点を変えない
> 学習は **「AI推奨重み」＝提案** を作るところまで。
> 人間が `/learning` で **「この配点にする（承認）」** を押して初めて採点が変わる。
> 却下もできる。承認していない提案は1点も効いていない。
> 1回の変更幅は **±20%** まで。実績5件未満では提案自体を作らない。

### 2-7. 失敗の10分類（同じ失敗を2回しない）
仕入れが失敗した時、理由を10種類から選んで記録する。件数と損失額を集計し、
次回のリサーチで同条件の商品に **「過去の失敗からの注意」** として警告を出す
（`research_candidates.failure_warnings`）。

### 2-8. 横展開（成功商品の周辺を8方向に掘る）
1個当たったら、その周辺を掘る。同じ仕入先の別商品／同じカテゴリー／色違い／サイズ違い／
上位モデル／セット売り／消耗品 など8方向に自動で「種」をまき、次のリサーチで順番に探す。
種は `queued → explored` で管理し、何件見つかったかを記録する。

## 3. 最優先3：自動運転（調べる・数える・学ぶ だけ）

### 3-1. 仕入先データ取込（Adapter方式）
CSV ／ Googleスプレッドシート ／ メール添付CSV・XLSX ／ API ／ SFTP ／ 共有URL を
差し替え可能なアダプタとして実装。使える／未設定を `/ops` に一覧表示する。

> [!important] 差分取込（API代を使わない核心）
> 行ごとに内容ハッシュ（sha1）を取り、**前回と中身が同じ商品は再計算しない。**
> 取込結果は 読込／新規／変更／変化なし／消えた の5数字で表示する。
> 実測：同じCSVを2回取り込むと2回目は「新規0／変更0／変化なし8」となり、8件とも再計算されない。

### 3-2. 仕入価格の変動監視 → 自動ランク昇格（記録だけ）
仕入価格が下がってAランク条件を満たしたら、自動でAへ上げ、**理由を必ず残す**。
> 例：昨日1,595円 → 今日1,420円（Aランク条件は1,481円以下）→ 自動的にAへ昇格
> 理由欄：「仕入価格175円下落によりA昇格」

逆にAの条件を割ったらBへ下げ、こちらも理由を残す。
`/ops` の「値下がり・条件割れでランクが動いた商品」で 日時／商品／変化（B→A）／理由 を一覧できる。
**ランクが上がっても、買うかどうかは必ず人が決める。**

### 3-3. 定期リサーチと24時間監視
- 毎日 **9:00**（管理画面 `/ops` から変更可）に自動リサーチ。
- 見張り頻度はランク別：**A=高頻度／B=中頻度／C=低頻度／D=原則停止**（分単位で設定可）。
- 予定表に 仕事／動かすか／いつ／前回／次回／説明 を表示。
- 実際に時間どおり動かすには `npm run scheduler:loop` を常駐させるか cron / launchd に登録する。

### 3-4. APIコスト管理
`/ops` に 今日の呼び出し回数 ／ 今月の合計金額 ／ **商品1件あたりの金額** ／ 上限に対する使用率 を表示。
`monthlyBudgetJpy` を超えそうな時（既定 `budgetStopRatio`＝80%）、
**B・Cの見張りのような「急がない仕事」から自動で止める。Aの見張りは止めない。**
Keepa消費・OpenAI呼び出しは実呼び出し回数で数える（推定値ではない）。

### 3-5. DATA_FRESHNESS（データの新しさ）
価格・Sales Rank・仕入価格それぞれの取得からの経過時間を持ち、
**`maxDataAgeHours` より古いデータの商品はAランクにしない**（`stale` フラグを立てて赤字表示）。
古い数字で「今すぐ仕入れ」と言わせないため。

### 3-6. CONFIDENCE SCORE（この判断の信頼度）
ランクと一緒に必ず信頼度を出す。
> 「Aランク **Confidence 96%**」＝ 自信を持って推奨
> 「Aランク **Confidence 72%**」＝ 条件は満たすが不確実（要確認）

内訳7項目（データの新しさ／UNKNOWNの少なさ／MATCH SCORE／サンプル数／価格安定性／
仕入先の確からしさ／実績との整合）を全部画面に出し、下がった理由も日本語で書く。
`minConfidenceForA` 未満はAランクに上げない。

### 3-7. 今日の強い推奨
Aランクのうち需要も利益も基準の1.5倍を超えたものを最大3件。
**なぜ良いか／何個買うか／予想利益／予想売り切り期間／最悪ケース／過去の失敗からの注意** を
1画面にまとめ、その場に承認ボタンを置く。

## 4. 安全設定（既定値・崩さない）

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `RESEARCH_AUTO_RUN` | **true** | 毎日の自動リサーチ（探して並べるだけ） |
| `RESEARCH_AUTO_APPROVE` | **false** | AIが仕入候補を承認することは無い |
| `AUTO_PURCHASE` | **false** | true にするとスクリプトもスケジューラも起動を拒否 |
| `AMAZON_AUTO_PUBLISH` | **false** | Amazonへ1件も送信しない |
| `AD_AUTO_OPTIMIZE` | **false** | 広告の入札変更は人間承認 |

> [!danger] 方針（一文で）
> **調査と分析は自動でよい。お金が動く行為だけは必ず人が承認する。**
> 自動で動くのは「調べる・数える・学ぶ」だけ。
> 発注・出品公開・価格変更・広告の入札は、どのボタンからも自動では起きない。
> `/lifecycle` には「この画面でできないこと」として明示する。

## 6. 実測ログ（2026-08-20）

- `npm run research`：21商品調査 → Amazon一致19 → A=4 / B=2 / C=5 / D=8 → 強い推奨2件、**AI課金0回**
- 仕入先CSVの差分取込：1回目「新規3／変更5／変化なし0」→ 2回目「新規0／変更0／変化なし8」（8件とも再計算せず）
- ライフサイクル一周：承認(20個・凍結スナップショット CONFIDENCE 75) → ORDERED → RECEIVED →
  LISTED → SELLING → 実績入力(14個・平均11,800円) →
  **需要の的中26% ／ 利益の的中55% ／ 価格の的中93%** を別々に自動算出
- 実績5件ゲート：`propose_weights` は「実績が1件しかありません。5件たまるまで重みの見直しはしません」で停止、
  カテゴリー補正も `applied=0` で不採用。**少ない実績で数字をいじらない設計が実動作で確認できた。**
- 横展開：成功商品から8方向の種を自動生成
