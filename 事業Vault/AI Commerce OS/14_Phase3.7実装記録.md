## 0. なぜこの修正をしたか（きっかけ）

ユーザーからの指摘。

> メルカリの「振込手数料200円」は、1商品ごとの販売コストではなく、
> 売上金を銀行へ振り込む "申請1回ごと" の費用です。
> もし現在の利益計算で商品1件ごとに200円を引いているなら、それは修正が必要です。

**指摘は正しく、実装は間違っていた。**

Phase 3.6 の時点で、メルカリの販売手数料の行はこうなっていた。

```
fee_rate  = 0.10   （販売価格の10%）
fixed_fee = 200    （1取引ごとの固定費として200円）← ここが誤り
```

コード内のコメントには「1件ずつ振り込む最悪の場合で見ておけば安全」と書いてあった。
これは Fail Closed のつもりだったが、Fail Closed の意味を取り違えている。

- Fail Closed ＝ **分からないものを買わない**
- 今回やっていたこと ＝ **分かっているものを100倍高く見積もって捨てる**

1回の振込申請で100件分をまとめれば、1商品あたりは2円。
200円で計算すると、本当は利益が出る商品を「利益不足」として除外していた。
特に安い商品ほど影響が大きい（1,000円の商品なら、手取りが900円ではなく700円になっていた）。

あわせて、もう1つの指摘。

> メルカリで仕入れる側の支払い手数料も固定ではありません。
> クレジットカード払い、メルペイ残高払い、Apple Pay、FamiPay などは現在無料ですが、
> コンビニ・ATM・キャリア決済では金額に応じた手数料があります。

これも実装に無かった。仕入側の決済手数料は「0円」として計算に入っていた。

## 2. 費用の考え方（ここが今回の中心）

### 2-1. 3種類に分ける

```
GROSS_PROFIT          粗利       ＝ 販売価格 − 仕入価格
  ↓ 販売手数料10% / 送料 / 梱包費 / 商品ごとの費用を引く
TRANSACTION_NET_PROFIT 取引後利益 ← ★ 買う／買わないの判定はこの数字で行う
  ↓ 振込手数料200円 ÷ 1回でまとめる件数 を引く（参考）
PAYOUT_ALLOCATED_NET_PROFIT 振込費按分後利益
  ↓ 実績が無いぶんの控えめ補正
CONSERVATIVE_NET_PROFIT 保守利益  ← ★★ 実際にお金を出すときはこの数字で考える
```

### 2-2. 按分は「参考」であって判定材料ではない

按分の分母（1回の申請で何件まとめるか）は運用でいくらでも変わる。
これを判定に入れると、**設定を変えるだけで買う／買わないが変わってしまう**。
それは商品の良し悪しではない。

だから `decision`（判定）と `route_score`（点数）は按分前の数字で決める。
受け入れテストで、分母を1と100に変えても判定と点数が1点も動かないことを毎回確認している。

### 2-3. 数字で確認した例（受け入れテストの実測）

| 販売価格 | 修正前の手取り | 修正後の手取り |
|---|---|---|
| 10,000円 | 8,800円 | **9,000円** |
| 1,000円 | 700円 | **900円** |

振込費用は 200円 ÷ 100件 ＝ **1商品あたり2円** として、別枠で表示する。

## 3. 仕入時の支払方法

8種類を用意し、**実際に自分が使う方法**を設定で選ぶ。

| 支払方法 | 手数料 | 状態 |
|---|---|---|
| クレジットカード払い | 0円 | 確認済み |
| メルペイ残高払い | 0円 | 確認済み |
| Apple Pay | 0円 | 確認済み |
| FamiPay | 0円 | 確認済み |
| コンビニ払い | **不明** | 未確認（金額で変わる） |
| ATM払い | **不明** | 未確認（金額で変わる） |
| キャリア決済 | **不明** | 未確認（金額で変わる） |
| その他 | **不明** | 未確認 |

**8件中4件が「不明」。** これを0円で埋めていない。
不明な支払方法を選んだまま、その商品を STRONG BUY にはしない。

### やらなかったこと

**「いちばん安い支払方法を自動で選ぶ」機能は作らなかった。**
安い方を勝手に選ぶと、実際には使っていない支払方法を前提にした利益が画面に出る。
それは実態と違う数字なので、判断材料として害になる。
受け入れテストで、`cheapest` / `lowest` / `best` という名前の関数が
コード内に増えていないことを毎回検査している。

## 4. 費用の確からしさ（COST_CONFIDENCE）

5費目それぞれに状態を持たせた。

| 費目 | いまの状態 |
|---|---|
| 販売手数料（SELL_PLATFORM_FEE） | 確認済み（公式ヘルプ） |
| 仕入時の決済手数料（BUY_PAYMENT_FEE） | 支払方法による（4/8が不明） |
| 送料（SHIPPING_COST） | 推定のまま（商品と発送方法で変わる） |
| 梱包費（PACKING_COST） | 推定のまま |
| 振込手数料（PAYOUT_COST） | 確認済み（200円／申請1回） |

**全部そろっても100点にしない（上限95点）。**
公式ページに書いていない実費（送料・梱包費）が必ず残るので、
「完全に確認済み」と名乗れる状態は原則として来ないため。

### あわせて厳しくしたところ

仕入（BUY）側の決済手数料は、**0円でも未確認なら確認済みと認めない**ようにした。
理由は「決済手数料0円」が、本当に0円なのか、まだ調べていないだけなのか区別できないため。
支払方法で変わる費用なので、0のまま通すとコンビニ払いの手数料が永久に計算へ入らない。

その結果、メルカリの仕入側手数料は `ESTIMATED`（概算）のまま。
確認済みの手数料は **18件中1件（5.6%）** に下がった。数字としては悪化だが、実態に合っている。

## 5. 検証ファネル（「100件」だけを追わない）

ユーザー指摘：

> 「100件」という数字だけを追わない方がいいです。
> 100件登録 → 80件商品一致 → 60件Route成立 → 30件STRONG BUY候補
> → 7/30/90日後に答え合わせ のように、ファネルで見るシステムにした方が強いです。

5段の表を作った。

| 段階 | 意味 | 落ちる理由 |
|---|---|---|
| 観測した出品 | 人が公開画面を見て書き写した件数（入口） | — |
| 他市場と同じ商品だと確かめられた | 別の市場に同じ商品の相場がある | 型番・JANが無い／比べる相手の相場が無い |
| Routeを作れた | 利益計算まで進んだ | 商品マスタと結びついていない／費用が確定しない |
| 答え合わせの対象になった | SHADOW記録された | 利益の見込みが立たなかった |
| STRONG BUY候補 | 最上位の判定に届いた | 費用や同一商品の確からしさが足りない |

**最重要KPIを「100件集めた」から次の3つに変えた。**

- `MATCHABLE_RATE`（他市場と同じ商品だと確かめられた割合）
- `ROUTE_GENERATION_RATE`（Routeを作れた割合）
- `SHADOW_ELIGIBLE_RATE`（答え合わせ対象になった割合）

カテゴリの偏りも測る。最多カテゴリが60%を超えたら警告を出す。
1種類だけで100件集めても、他のカテゴリで同じ結果になる保証はないため。

**STRONG BUY候補を増やすために判定を甘くすることはしない。**
増やす手段は「手数料の実額を確認する」「仕入先を増やす」の2つだけ。

## 6. まず10件（PILOT）

ユーザー指示：

> 修正後、いきなり100件入力しないでください。まず10件で操作性テスト。
> そこで人間が面倒だと感じた工程が、次に自動化すべき機能になります。

100件入れてから「この項目は要らなかった」と気づくと、90件分の手間が無駄になる。
10件で止めれば直すのは10件分で済む。

**この10件の目的は「データを集めること」ではなく「どこを自動化するか決めること」。**

### 合格条件（7項目・全部満たすまで100件へ進まない）

1. まず10件を実際に入力した
2. 入力にかかった時間を測れている（8件以上で計測）
3. 他市場と同じ商品だと確かめられた割合が50%以上
4. Routeを作れた割合が30%以上
5. カテゴリが1種類に偏っていない（最多60%以下）
6. 大事な項目（商品名・価格・状態・ブランド・型番）の空欄が半分以下
7. 入力を止めるほどの問題が出ていない

**2026-08-20 時点：0 / 7 項目**（実市場の出品がまだ0件のため）。

### 次に自動化する場所の決め方

「面倒だった気がする」ではなく、工程ごとに実測した秒数で決める。
いちばん時間がかかっている工程を機械が名指しする。
まだ1件も計測していないので、現時点では
**「どこを自動化すべきかは決められない」** と表示している。推測で書かない。

## 7. 送料の精度

観測CSVに5項目を追加した。

- 荷物サイズ（ネコポス／宅急便コンパクト／60〜120サイズ以上／不明）
- 発送方法（らくらくメルカリ便／ゆうゆうメルカリ便／ヤマト／日本郵便／佐川／その他／不明）
- 送料の負担者（出品者／購入者／不明）
- 見込み送料
- 実際の送料

見込みと実額の両方が入った出品が増えれば、送料の見積もりのズレを測れる。
**0件のうちは「精度100%」ではなく「まだ測れません」と出す。**
