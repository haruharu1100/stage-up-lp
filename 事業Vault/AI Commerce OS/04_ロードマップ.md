# 開発ロードマップ（MVP → 完全自動化）

> 上位文書: [[00_設計書v1_最上位]]

**原則：各Phaseには「これができたら次へ進んでよい」という卒業条件を必ず置く。**
条件を満たさないまま次へ行かない。特に Phase 5 → 6（実弾の自動購入）は厳格に。

> 残っているのは **答え合わせ**：30日後に「本当にその値段で売れたか」を突き合わせる仕組み。

### やること
- [ ] `shadow_trades` の記録
- [ ] 30日後の自動評価バッチ
- [ ] `ai_predictions` の誤差計測（ブランド別・カテゴリ別・販路別）
- [ ] 精度ダッシュボード
- [ ] バックテスト基盤（旧ルール vs 新ルール）
- [ ] 日次レポート

#### v1.1 でここに入るもの
- [ ] 発見数KPI（`discovery_kpi`：発見数・重複除外数・利益候補数・LLM到達数・費用）
- [ ] 発見の異常検知（[[06_商品大量生成とパイプライン]] §7）
  ```
  前日比 50%未満 → 取込故障の疑い（通知）
  前日比 300%超  → 重複の疑い（評価を停止）
  利益候補率が3倍超 → 相場データ破損の疑い（FULL AUTO 停止）
  ```
- [ ] `price_experiments` の記録開始（[[07_価格戦略設計]] §6）
  - **この段階は SHADOW の仮想価格を記録するだけ。実際の値上げはしない**
  - 打ち切り（`censored`）を「売れなかった」と混同しない実装にする
- [ ] `price_elasticity` の素データ蓄積（SKU層／モデル層／セグメント層）
- [ ] 一点物向けの `PREMIUM_RATIO`（出品価格 ÷ 相場中央値）の記録

### 卒業条件
[[03_安全設計と事故防止]] §8 の卒業条件を満たす。
```
SHADOW取引 100件以上を評価済み
売却日数の予測誤差（中央値） <= ±30%
純利益の予測誤差（中央値）   <= ±20%
STRONG BUY の推定黒字率      >= 85%
undecidable 率               <= 20%
```

> [!important] ここが最大の関門
> **Phase 3 を飛ばして Phase 5 以降に行くことを禁止する。**
> 実績データが無いままの自動購入は、ただのギャンブル。

- [ ] 価格AB実験の自動実行（`EXPLORE_RATIO` 20%。8割は既知の最適価格で確実に売る）
- [ ] 仕入先ごとのレート制限を守った自動巡回（Run種別 `discover` / `requeue` / `expand`）

### 開始条件（すべて必須）
```

SHADOW の予測精度が基準を維持

```

**段階解禁**：最初は「1ブランド・上限日次5万円・1商品3万円まで」から始め、事故が無ければ広げる。
いきなり全カテゴリ・全予算で解禁しない。

#### v1.1 でここに入るもの

  - **適用前にバックテストを通す。通らなければ適用しない**

- 月次レポートが「来月こうすべき」まで書けている
- 弾力性を使った価格が、固定ルールの価格より**総利益で上回っている**（バックテストで確認）

## Phaseに属さない作業：仕入先を1社増やす

仕入先の追加は Phase の途中でも随時発生する。**そのたびに11ステップの手順を最初から通す。**
手順は [[08_仕入先ネットワークと勝ち筋拡張]] §7。特に **手順9（少量の実地検証）を飛ばさない。**

新規仕入先は必ず `capability: manual` から始める。
規約とAPIを文書で確認できるまで `api` に昇格させない。

## この計画で一番やってはいけないこと

> [!danger] 「商品数が増えない」を理由に判定を甘くする
> 発見数KPIを追い始めると、**しきい値を下げれば数字が伸びる**という誘惑が必ず来る。
> だが誤マッチだらけの1万件は、正しい100件より価値が低い。実際に損をするのは前者。
>
> 優先順位は変わらない：
> ```
> 正確性 > 安全性 > 利益 > 自動化率 > 商品数
> ```
> 商品数を増やしたいときは、**しきい値ではなく仕入先を増やす。**
