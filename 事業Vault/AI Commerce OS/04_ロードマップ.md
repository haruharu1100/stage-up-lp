## Phase 3.5：実市場データ接続・SHADOW精度検証 ✅ 仕組み実装完了（2026-08-20）

**目的：Phase 3 の卒業条件を「測れる形」にし、実市場データで精度を証明するまで先へ進ませない。**

Phase 3 完了時点で分かったのは「仕組みは動くが、数字がすべてテストデータ由来」ということ。
テストデータ上の平均ROI 42.6%・予想純利益196万円は**成果ではない**。
そこで Phase 4（在庫・出品）へ行く前に、Phase 3.5 を挟んだ。

> ユーザー指示（原文）
> 「次の大きな目標は「100件集めること」そのものではなく、
> **STRONG BUYだけに絞ったとき、どれくらいの確率で本当に利益が出るのかを測ること**です。」
> 「最終的に「STRONG BUYの実市場Precision 90%」のような数字が出てくれば、
> そこから初めて少額の実取引へ移す価値が出てきます。」

### やったこと（27節すべて実装）

- **手数料の確からしさを4段階に**（`VERIFIED` / `ESTIMATED` / `OUTDATED` / `UNKNOWN`）。出典URL・確認日・有効期間を持つ。
  `VERIFIED` 以外はデータ信頼度が満点にならず、**どれだけ利益が大きくても STRONG BUY に届かない**。
- **料金改定は履歴に残すだけで、過去のSHADOWを新料金で再計算しない**（後出しで自分を正当化しない）。
- **相場を追記型の時系列で保存**（`market_snapshots`）。現在価格でDBを上書きしない。
- **実市場データ判定**（`REAL_MARKET_DATA`）。仕入側・販売側の**両方**が実観測のときだけ実データと数える。片方でも不明なら実データにしない（Fail Closed）。
- **利益機会の半減期**を市場の組ごとに測り、「人が承認する時間に間に合うか」を判定
  （`HUMAN_APPROVAL_OK` / `TIGHT` / `AUTO_ONLY` / `UNKNOWN`）。
- **予測を3本立てに**（RAW＝理論値 / CALIBRATED＝実績で補正 / CONSERVATIVE＝保守）。80%予測レンジと下振れ利益・最大想定損失も持つ。
  **将来の実購入判断は CONSERVATIVE を使う**と決めた。
- **判断の間違いを2種類に分けて記録**（FALSE POSITIVE＝買って損した／FALSE NEGATIVE＝見送ったが儲かっていた）。
  **FPをFNの3倍の重さで数える。** 買って損する方が現金が減るため、痛みが同じではない。
- **STRONG BUY 的中率**とその95%下限（Wilson下限）を算出。偶然の当たりを精度と呼ばない。
- **Phase 4 卒業条件を14項目の機械判定に**。測れていない項目は**不合格**として扱う。
- **少額実取引の安全設計だけ**を作った（1件1万円・1日3万円・同一商品1個・STRONG BUYのみ・手数料実額確認済みのみ）。**実行する処理は書いていない。**
- **経営者向けの結論1行**を毎日出す（`npm run report` ／画面 `/readiness`）。文言は卒業条件の判定から機械的に作られ、**AIが書き換えられない**。

**結論：まだ実購入に進めません。**

> [!danger] 0件を隠さない
> テストデータの成績は成績表に**一切入れていない**。実市場データが0件なら「的中率100%」ではなく
> **「測定不能」＝不合格**と表示する。データが無いほど通りやすい仕組みにしてはいけない。

### 卒業条件（Phase 4 へ進む条件・14項目）

```
実市場データのSHADOW件数            >= 100件（テストデータは数えない）
答え合わせが済んだ件数              >= 100件
STRONG BUY の判断件数               >= 30件
STRONG BUY の的中率                 >= 90%
同・95%下限                         >= 75%
BUY以上の的中率                     >= 85%
買うと判断して損した割合（FP率）    <= 10%
売れたか確認できなかった割合        <= 30%
手数料が実額確認済みの市場の割合    >= 90%
実際に使った市場の手数料の確認割合  >= 90%
相場データの信頼度（平均）          >= 80点
相場データの信頼度（最低）          >= 70点
実データが集まった市場の組み合わせ  >= 3通り
実データが集まった商品カテゴリ      >= 3種類
```

> [!important] 二重の鍵
> 上の14項目が全部通っても、**人間が `PHASE4_UNLOCKED` を true にしない限り何も起きない。**
> さらに現時点で実購入のコードは**1行も存在しない**。鍵が両方開いても勝手には買わない。

> [!danger] 条件は緩めない
> ユーザー指示「勝手に条件を緩和しないでください」。
> 判定コードは条件を**測るだけ**で、条件を書き換える経路をコードに持たない。
> 判定の履歴は `phase_gate_log` に残り、後から「いつ緩めたか」を人が追える。
> 画面を開いただけでは履歴を増やさない（履歴が埋もれると監査にならないため）。

### 今いちばんの詰まり（2026-08-20）

**正規の取得手段が1件も契約できていない。** 無断の自動巡回はしないと決めているため、
実市場データ0件は「サボり」ではなく**方針どおりの結果**。
最短の打開策は、**人が実際の画面を見て記録したCSV**（`MANUAL_OBSERVATION`）を1市場ぶん入れること。
これは規約上いちばん安全な実データの入り口で、契約を待たずに今日から始められる。

- 仕入先ランキングが1ヶ月分そろっている

## Phaseに属さない作業：仕入先を1社増やす

仕入先の追加は Phase の途中でも随時発生する。**そのたびに11ステップの手順を最初から通す。**
手順は [[08_仕入先ネットワークと勝ち筋拡張]] §7。特に **手順9（少量の実地検証）を飛ばさない。**

新規仕入先は必ず `capability: manual` から始める。
規約とAPIを文書で確認できるまで `api` に昇格させない。

## この計画で一番やってはいけないこと

> [!danger] 「商品数が増えない」を理由に判定を甘くする
> 発見数KPIを追い始めると、**しきい値を下げれば数字が伸びる**という誘惑が必ず来る。
> だが誤マッチだらけの1万件は、正しい100件より価値が低い。実際に損をするのは前者。
>
> 優先順位は変わらない：
> ```
> 正確性 > 安全性 > 利益 > 自動化率 > 商品数
> ```
> 商品数を増やしたいときは、**しきい値ではなく仕入先を増やす。**
