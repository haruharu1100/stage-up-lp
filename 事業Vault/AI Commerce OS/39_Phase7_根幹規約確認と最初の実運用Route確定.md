## §2 KEEPA と AMAZON のドメイン分離（設計・未実装）

指示§2・§3・§4 に対応。**Amazonの回答がどちらであっても、この分離は先に決めておく。**

### 2.1 2つのドメインを完全に分ける

| | **KEEPA ANALYTICS DOMAIN** | **AMAZON OPERATIONS DOMAIN** |
|---|---|---|
| 目的 | 需要分析・価格分析・仕入候補分析 | 所有在庫の出品・在庫更新・注文・発送 |
| データ源 | Keepa 公式API のみ | Amazon SP-API のみ |
| DBテーブル接頭辞 | `ka_` | `al_` |
| 学習に使ってよいか | **条件付きで可**（§2.3） | **不可**（`ML_TRAINING_ALLOWED = false`） |
| 相手側APIへの接続 | SP-API へ接続しない | Keepa へ接続しない |

### 2.2 物理的な禁止事項（実装時のルール）

- `ka_` テーブルと `al_` テーブルを **ASIN で JOIN してはならない。**
- 両者を同一テーブルに書き込んではならない。
- 同一の画面に両者の数値を並べる場合も、**内部的にはデータが混ざっていない**ことを保証する。
- 将来、Amazon から「分離が必須」と回答された場合は、**別サービス・別権限**へ物理分離する（§1.3 の設問6）。

### 2.3 Keepa 側は「学習データ」と呼ばない

指示§4 に対応。Keepa の U1/U2 等の利用条件が完全に確認できるまで、
Keepa 由来のデータを **「学習データ」と呼ばない**。

呼称：**`ANALYTICS_EVIDENCE`（分析の根拠）**

- 用途：人が判断するための材料、および画面表示。
- 用途外：モデルのパラメータ更新、閾値の自動学習、Research Priority の自動学習。
- Keepa の条件が確認できた時点で、初めて `LEARNING_DATA` へ昇格させるか判断する。

```

ML_TRAINING_ALLOWED (amazon_spapi) = false
```

### 3.4 Yahoo! を使う場合の設計上の呼称

指示§6 に対応。Yahoo!ショッピングは **`EPHEMERAL_OPERATIONS_CONNECTOR`（一時処理専用の接続口）** として設計する。

```
Yahoo! API から受け取る
  → 必要な処理をその場で行う（出品／在庫更新／注文取得）
  → 保持が禁止されているデータは処理後に破棄
  → 保持してよいもの（自社SKU、内部ID対応表、監査ログ）だけを残す
```

- 蓄積型パイプライン（`ka_` のような分析用の積み上げ）には**繋がない。**
- `DATA_RETENTION_POLICY(yahoo) = RETENTION_UNKNOWN` → **保持期間 0 日として設計する。**
- 回答が来て初めて、保持できる範囲を確定する。

### 4.4 API・自動化の可否（本丸）

### 4.5 データ保持（Yahoo!との決定的な違い）

**Yahoo!のような「一切保持してはならない」条項は、Shopify には存在しない。**（探した範囲：利用規約全16章、API規約全14章、AUP全文、保護顧客データDocs）

代わりにあるのは、**目的限定＋用済み削除**型の弱い制限。

| 条項 | 内容 |
|---|---|
| API規約 6.2.1 | マーチャントデータは「そのマーチャントへアプリのサービスを提供するために必要な範囲でのみ」使用・保存できる |
| API規約 6.2.3 | アンインストール時／サービス提供に不要になった時／削除要請を受けた時は、**30日以内に全ての複製を削除** |
| API規約 6.2.5 | マーチャント・顧客の情報を **競合ベンチマークに使ってはならない** |
| API規約 6.2.8 | Shopifyから受け取ったデータを（匿名・集計・派生形を含め）第三者や**自分が所有する別のアプリ**へ移してはならない |

→ **自社ストアの注文履歴を自社システムに蓄積し続けること自体は、正面から禁止されていない。**
ただし「サービス提供に必要」と言える範囲かどうかの判断主体が明記されておらず、**§4.8 の問い合わせ事項に含める。**

### 4.6 AI/機械学習の扱い（最重要の発見）

**API規約 2.3.24（2026-02-27 発効）:**

> not use any information derived from the Shopify API, Merchant Data, any Merchant Store, the Services, or any aspect or portion thereof (including any anonymous, aggregate, or derived forms of data), to create, develop, **train, fine tune, or improve any machine learning or artificial intelligence systems, models, or technologies, including large language models** except with: (a) Shopify's prior written consent, or (b) **solely with respect to Merchant Data or a specific Merchant Store, the relevant Merchant's consent.**

**日本語の意味：**
- 原則、Shopify API から得た情報で AI や機械学習モデルを学習させてはいけない。
- ただし例外が2つある。(a) Shopify の事前書面同意がある場合。**(b) 自分の店のデータに限っては、その店のマーチャント（＝オーナー）の同意がある場合。**
- 当システムは**自分が店のオーナー本人**なので、(b) の道が使える可能性が高い。**これは Amazon には無い逃げ道。**

**ただし未確定：**
- (a)号には "prior **written** consent"（事前の書面同意）と明記されているのに、(b)号には "written" も "prior" も付いていない。**同意の形式・記録方法が規約にもDocsにも定義されていない。**
- 条文の対象は「Merchant Data」だけでなく「the Services」も含むが、(b)の免除は「Merchant Data または特定のストアに関してのみ」に限定されている。**「Shopifyというプラットフォームの挙動そのものから得た知見」は (b) では免除されないと読める。**

**当面の設計方針（Fail Closed）：**
```
SHOPIFY_ML_TRAINING_ALLOWED = UNKNOWN  ← 「可」にはしない
→ 自己同意の書面（日付入り・内部保管）を先に作る
→ その上で §4.8 の問い合わせで白黒を付ける
→ 確定するまで、Shopifyデータも ANALYTICS_EVIDENCE 扱い（§2.3 と同じ）
```

### 7.6 結論：最初の本命 Route

**`Route C`（NETSEA → Shopify）を最初の実運用Routeとする。**

理由（`LEGAL_ELIGIBLE` を最優先した結果であり、儲かるからではない）：

1. **階層1で唯一「進める余地あり」なのが Route C だけ。** A・B は問い合わせ回答待ちで、待っている間に何も進まない。
2. Shopify には **Keepa 併用を制限する条項が存在しない。**（Amazon最大の争点がそもそも発生しない）
3. Shopify には **Yahoo!のような全面データ保持禁止が存在しない。** 蓄積型の設計と衝突しない。
4. AI学習禁止条項は存在するが、**自分がマーチャント本人なので (b) の同意例外で解除できる可能性が高い。** Amazonにはこの逃げ道がない。
5. **審査不要・初期費用0円・月3,650円で始められる。** 失敗したときの損失が最も小さい。

**ただし条件付き：**

```
Route C を進めてよいのは、以下が全部そろってから
  ① NETSEA の回答が来て Entry Gate が PASS すること
  ② Shopify の Partner Program Agreement 要否が確定すること
  ③ AI学習の自己同意の書面を作って内部保管すること
```

**Route A・B は捨てない。** 問い合わせの回答が来た時点で階層1を再判定し、
`LEGAL_ELIGIBLE` が ○ になった Route を順次追加する。

## §9 最初の出品テストの進め方（指示§15・§16・§17）

### 9.1 段階（絶対に守る）

```
1商品を出品 → 【停止】 → 人が13項目を確認 → OKなら
5商品を出品 → 【停止】 → 人が確認 → その先は改めて判断
```

**最初から多商品の自動出品はしない。**

### 9.2 出品の前提条件（既存ルール維持）

```
OWNED_CONFIRMED = true でなければ自動出品しない
```
＝**実際に手元に商品が届いて、自分が所有していることを確認するまで出品しない。**

### 9.3 最初の1商品で必ず確認する13項目

| # | 項目 | 確認方法 |
|---|---|---|
| 1 | 仕入価格 | 仕入先の請求書・注文明細の実額 |
| 2 | 実送料（仕入時） | 実際に請求された額。見積もりではない |
| 3 | 在庫所有 | 現物が手元にあること。写真で記録 |
| 4 | 商品一致 | 仕入れた商品と、出品しようとしている商品が同一であること（型番・JAN） |
| 5 | 販売先の商品データ | 販売先に登録した商品名・説明・画像が正しいこと |
| 6 | 出品価格 | 実際に設定した価格 |
| 7 | 販売手数料 | **売れた後の実際の明細**で確認。事前の想定値ではない |
| 8 | 配送費（販売時） | 実際に発送した際の実額 |
| 9 | 保守純利益 | 1〜8をすべて実額で埋めた上での差額 |
| 10 | ROI | 保守純利益 ÷ 投下資金 |
| 11 | 販売先の規約 | 出品したカテゴリ・商品が規約に反していないこと |
| 12 | 商品画像の権利 | 仕入先から提供された画像を使う場合、**Shopify へサブライセンス可能な権利があるか**（§4.7） |
| 13 | 売却までの日数 | 出品日〜売却日の実日数 |

**この13項目が1つでも埋まらないうちは、次の5商品へ進まない。**
