# Phase 6.5（修正版）— Source分類の分離と、TOP5の二本立て

> [!danger] この文書がやっている修正は、たった1つの区別です
> **「商品データを取れる」と「実際にその商品を仕入れられる」は、まったく別のことです。**
> [[33_Phase6.5_候補の採点とTOP5]] は、この2つを1本のランキングに混ぜていました。
> ここで分離し直します。**バリューコマースを仕入先だと即断していたのが、最大の誤りでした。**

---

## 0. 先に結論

### 「今すぐ1商品だけ正式APIで検索できる Supplier はあるか？」 → **NO**

Legal Gate を**全部**通った仕入先は、依然として **0件**です。
最も近いのは **NETSEA**（総合77点・`FIRST_SUPPLIER_CANDIDATE`）ですが、詳細監査の結果、
規約が明確にYESと言っているのは **商用利用と自動取得の2点だけ**で、
**保存・加工・価格比較の3点はすべて UNKNOWN**（条文そのものが存在しない）と確定しました。
この3つは当システムの中核機能そのものです。**「繋いでから聞く」ではなく、聞いてから繋ぎます。**

そして今回の分離で、もう1つはっきりしました。

> [!warning] バリューコマースは「2位の仕入先」ではありませんでした
> 商品APIは **アフィリエイトサイト向けの商品API** として公式に提供されているものです。
> **「APIに商品URLがある＝当社が仕入れられる」ではありません。**
> したがって：
> - `SOURCE_TYPE` = **AFFILIATE_DATA / MARKET_INTELLIGENCE**
> - `PURCHASABLE_SUPPLIER` = **UNKNOWN**
>
> ただし価値が下がったわけではありません。**役割が変わっただけ**です。
> 社内利用が正式に許可されれば、**PRICE DISCOVERY CONNECTOR（同じ商品を一番安く売っている店を見つける装置）**として、当システムの中核になり得ます。

## 1. SOURCE_TYPE — 5分類（新設）

これまで「仕入データ源」と一括りにしていたものを、5つに分けます。

| SOURCE_TYPE | 意味 | 当社にとっての役割 | 例 |
|---|---|---|---|
| `WHOLESALE_SUPPLIER` | 卸価格で、継続的に、ロットで仕入れられる | **本命。ここが増えないと事業が伸びない** | NETSEA / BigBuy / vidaXL / orosy |
| `PURCHASABLE_SUPPLIER` | 事業として実際に購入できる（卸とは限らない） | 仕入先。ただし利幅は薄い | 一般小売EC（法人利用が許される場合） |
| `ONE_OFF_MARKETPLACE` | 買えるが**一点物**。同じ商品を再度買えない | 単発利益のみ。自動化の対象外 | ヤフオク! / 中古リユース各社 / eBay |
| `MARKET_INTELLIGENCE` | 価格・在庫・需要を**知る**ためのデータ源。仕入先ではない | 「どこが安いか」「売れるか」を判断する目 | Keepa / Amazon SP-API / Yahoo!商品検索 |
| `AFFILIATE_DATA` | アフィリエイト目的で提供される商品データ | MARKET_INTELLIGENCE の一種。**提供目的が広告なので用途制限が強い** | **バリューコマース** / Datafeedr / A8 |

> [!note] なぜこの分離が「非常に重要」なのか
> 分けないと、こういう事故が起きます。
> 「バリューコマースのAPIに商品URLがある」→「じゃあそこから仕入れよう」→
> **実際にはその店は法人相手に卸してくれない／転売目的の購入を規約で禁じている。**
> データが取れることと、取引口座を持てることは、まったく別の話です。

## 2. データ源の3段階（DISCOVERY → PURCHASABLE → VERIFIED ROUTE）

さらに、1つの商品が「BUY候補」になるまでを3段階に分けます。**この3つを混ぜないことが要です。**

| 段階 | 名前 | 何を保証するか | 通らないとどうなるか |
|---|---|---|---|
| ① | **DISCOVERY SOURCE** | その商品と価格が**存在する**ことを見つけられる | 候補が見つからない |
| ② | **PURCHASABLE SOURCE** | 当社が**実際にそこから仕入れられる** | 「安い店は見つかったが買えない」で終わる |
| ③ | **VERIFIED ROUTE** | **売り先の規約まで確認済み**（Amazonに出していいか） | 仕入れたのに売れない／アカウント停止 |

**③まで通ったものだけが BUY 候補になります。** ①だけで BUY は出しません。

### 第1本命 Route（これを最初に完成させる）

```
Keepa
  ↓  Amazon需要の強いASIN
JAN
  ↓  Amazon SP-API Catalog Items（identifiers）で正式に橋渡し
NETSEA API
  ↓  同一JANの商品
卸価格（price）
  ↓
在庫（sold_out_flag）
  ↓
Amazon販売可否（サプライヤー単位／商品単位）
  ↓
利益計算
  ↓
月間利益予測（EXPECTED_MONTHLY_UNITS × 単品利益）
  ↓
BUY候補 →［購入ページを開く］
```

> [!danger] 最後の1行は変わりません
> **注文・購入・決済は人間が行います。** システムは「購入ページを開く」までです。

### 第2 Route（バリューコマースの社内利用が許可された場合のみ）

```
Amazon需要商品
  ↓
JAN
  ↓
バリューコマース 商品API
  ↓
複数の広告主（店舗）の同一商品価格
  ↓
一番安い店舗を発見
  ↓
【店舗ごとの別Gate】その店から事業として仕入れてよいか？
  ↓  YESのときだけ
PURCHASABLE SOURCE へ昇格
```

> [!warning] 安い店が見つかっても、それは②ではありません
> 「安い店を見つけた」は①DISCOVERYまでです。**店舗ごとに別のGateを通します。**
> Gateが未確認の店舗は `PURCHASABLE_SUPPLIER = UNKNOWN` のままで、BUYにはしません。

#### 販路フラグ：フィールド名を特定できた。**ただしAmazon個別の可否は取れない**

`GET/POST /items` のレスポンスに、**商品単位で**次のフラグがあります。

| フィールド名 | 意味 |
|---|---|
| `deal_net_shop_flag` | ネット販売可（Y／N） |
| `deal_net_auction_flag` | ネットオークション可（Y／N） |
| `direct_send_flag` | 商品配送可（Y／N） |
| `image_copy_flag` | 画像転載可（Y／N） |
| `net_bulk_order_flag` | CSVダイレクト注文可（Y／N） |

前3つ＋画像は**検索の絞り込み条件としても指定できます**（`direct_send_flag` は絞り込み不可）。
CSV側も AE＝画像転載可／AF＝ネット販売可／AG＝ネットオークション可／AH＝消費者直送可／AI＝品切れ で対応が取れました。

> [!danger] ここが今回いちばん重要な訂正です
> **Amazon / 楽天 / Yahoo / メルカリ / 自社EC を個別に区別するフィールドは、存在しません。**
> 取れるのは「ネット販売可」という**粗い1フラグだけ**です。
> したがって **`deal_net_shop_flag = Y` は「Amazonに出品してよい」証明にはなりません。**
>
> [[33_Phase6.5_候補の採点とTOP5]] に書いた「使ってよい商品をシステムが自動で判別できる唯一の候補」という評価は、
> **「ネット販売可か否か」までは正しく、「Amazonに出してよいか」までは誤り**でした（ルール76に従い、元の記述は消さずここに訂正を残します）。
>
> → 結果として、**当面ほぼすべての商品が `AMAZON_RESALE_ALLOWED = UNKNOWN` → `POLICY_REVIEW_REQUIRED` に入ります。**
> これは設計の欠陥ではなく、**正しい挙動**です。人がサプライヤーに確認してYESにするまで、BUYにはしません。

なお `/suppliers` は `id` / `corp_name` / `trade_name` の3項目のみで、**販路情報を一切持ちません**。
販路フラグは商品オブジェクト直下にあるため、**同一サプライヤー内でも商品ごとに条件が変わり得る構造**です。
→ 「商品Policy ＞ サプライヤーPolicy」という設計方針は、この構造と一致しています。

> [!note] 呼称の食い違いを1件、そのまま記録します
> API は `direct_send_flag`＝「**商品配送可**」、CSVは AH＝「**消費者直送可**」、ヘルプは「**消費者直送可能**かつ取引申請が承認されているサプライヤーの商品に限る」。
> **同じものか別物かは一次資料からは確定できません。** 問い合わせ項目に追加します。

#### 継続仕入（Repeatability）の実態

| 項目 | 取得可否 | 実態 |
|---|---|---|
| `AVAILABLE_QUANTITY` | **NO** | `sold_out_flag`（Y品切れ／N在庫あり）の**有無フラグのみ**。実数フィールドは存在しない |
| `QUANTITY_DISCOUNT` | **NO（段階表は無い）** | あるのは `set_num`（セット毎数量）・`price`（卸単価）・`set_price` 系と、期間割引率（`discount_rate` / `item_discount_rate` / `shop_discount_rate` 等）。**「100個ならいくら」の段階表は取れない** |
| `REORDER_AVAILABLE` | **APIでは不可** | **APIに発注機能が無い**。提供エンドポイントは `/suppliers` `/categories` `/items` `/items/stock` `/tariffs` の**5本のみ**。発注は人の手動操作かCSV発注 |
| 送料 | **YES** | `/tariffs` で**都道府県別**に取得可（`prices[].price1/price2`、`gradual_border_price` が送料無料ラインに相当する段階切替） |

> [!note] 「発注APIが無い」は、当システムにとっては都合が良い
> もともと **購入は人間が行う** 方針です。自動発注の手段が存在しないこと自体は、方針と矛盾しません。
> 一方で送料が都道府県別に取れるのは大きな利点で、**利益計算の精度が上がります**（送料を推測で埋めなくて済む）。

#### 手続き・費用

- **バイヤー会員登録：無料**（「入会金・月会費などはかかりません」）。有料オプション「NETSEAプライム」月額980円（税抜）は任意。
  ただし会員規約第21条は「入会金、月会費その他の料金を…支払う」と規定しており、**現時点の運用が無料**という位置づけです。
- **API利用申請**：マイページ【登録情報管理】→API登録情報欄→規約同意→申請→トークン発行。**審査の有無・費用の記載は無く UNKNOWN。**
- トークン有効期限180日、規約有効期間は認証日から半年（再認証で延長）。
- 会員資格：第17条3項二により「**日本国内に営業所又は居所を有しない**」場合は登録不可。

#### 到達できなかったページ（正直な申告）

- **API設定画面 `netsea.jp/account/`** — ログイン必須。個別のレート制限や追加規定がここに載る可能性があるが**未確認**。
- **サプライヤー個別の販売条件（商品詳細の「販売条件」欄）** — 「商品の卸価格は会員様にのみ公開」のためログイン後にしか見えない。登録もスクレイピングもしていないため未確認。
- **第3条にいう「当社が作成する諸規定」の本体** — 規約から参照されているが公開URLを特定できず（**存在しないとは断定しない**）。
- **APIの実レスポンス** — APIコールを一切していないため、スキーマ記載と実挙動の一致は未検証。

## 5. サプライヤー単位・商品単位の販路可否（DB設計）

> [!danger] 今回の調査で最も設計を変える発見
> **「Amazonに出していいか」は、卸モールの規約では決まりません。**
> ほぼすべてが「**サプライヤー（出展企業）ごとの個別条件**」に落ちています。
> したがって、モール単位のフラグ1個で管理してはいけません。

### 5-1. `supplier_marketplace_policy`（サプライヤー単位）

| 項目 | 型 | 説明 |
|---|---|---|
| `supplier_id` | ID | どのサプライヤーか |
| `amazon_allowed` | YES / NO / UNKNOWN | Amazonでの販売可否 |
| `rakuten_allowed` | YES / NO / UNKNOWN | 楽天市場での販売可否 |
| `yahoo_allowed` | YES / NO / UNKNOWN | Yahoo!ショッピングでの販売可否 |
| `mercari_allowed` | YES / NO / UNKNOWN | メルカリでの販売可否 |
| `own_ec_allowed` | YES / NO / UNKNOWN | 自社ECでの販売可否 |
| `consumer_direct_shipping_allowed` | YES / NO / UNKNOWN | 消費者直送の可否 |
| `policy_source` | text | **どの一次資料に書いてあったか**（URL／CSVのフィールド名／回答メール） |
| `verified_at` | date | いつ確認したか |
| `confidence` | 0〜100 | 確からしさ |

### 5-2. `product_marketplace_policy`（商品単位）

同じサプライヤーでも、**商品AはAmazon可・商品BはAmazon不可**があり得ます。
したがって商品単位のテーブルも持ちます。フィールドは `product_id` を主キーとする以外は同じ構成です。

> [!warning] 優先順位は「商品Policy ＞ サプライヤーPolicy」
> 商品単位の指定があれば、**必ずそちらを優先**します。
> サプライヤーが「Amazon可」でも、その商品が「Amazon不可」なら **不可** です。

### 5-3. UNKNOWN商品は絶対にAmazon Routeへ流さない

例えばこういう商品があったとします。

```
NETSEA商品
JAN一致
利益 3,000円
Amazon需要 強い
```

これでも `AMAZON_RESALE_ALLOWED = UNKNOWN` なら：

| 判定 | 扱い |
|---|---|
| ~~BUY~~ | **出しません** |
| **POLICY_REVIEW_REQUIRED** | ← ここへ入れます |

**「儲かるから」は、可否が不明であることの言い訳になりません。**
人が販路条件を確認して YES にするまで、BUY候補にはなりません。

## 6. 継続仕入（Repeatability）の評価項目

NETSEA のような卸の最大の価値は、**一点物ではなく、同じ商品を繰り返し仕入れられること**です。
以下を商品ごとに評価します。

| 項目 | 意味 | 取れないときの扱い |
|---|---|---|
| `REPLENISHABLE` | 再仕入れができるか | UNKNOWN（NOにもYESにもしない） |
| `AVAILABLE_QUANTITY` | 在庫数量（実数） | 有無フラグしか無ければ **数量はUNKNOWN** |
| `REORDER_AVAILABLE` | 同じ条件で再発注できるか | UNKNOWN |
| `WHOLESALE_PRICE` | 卸価格 | 必須。取れなければ利益計算をしない |
| `QUANTITY_DISCOUNT` | ロット別の価格 | 無ければ単価のみで保守的に計算 |
| `STOCK_STABILITY` | 在庫が安定しているか（時系列で観測） | 観測が貯まるまで UNKNOWN |

> [!note] 在庫「有無」と在庫「数量」を混同しない
> NETSEAの `sold_out_flag` は**有無**です。**数量ではありません。**
> 「100個仕入れられる」と判断する根拠にはなりません。数量が要る判断は、人が確認するまで止めます。

## 7. 単発利益ではなく月間利益で見る（新指標）

卸取引では、**利益1,000円 × 月100個 = 月10万円**のような商品が本命です。
「1回だけ5,000円儲かる商品」より、はるかに価値があります。

| 指標 | 意味 | 作り方 |
|---|---|---|
| `EXPECTED_MONTHLY_UNITS` | 月に何個売れそうか | **Keepaの需要Evidence**と組み合わせる |
| `EXPECTED_MONTHLY_NET_PROFIT` | 月にいくら残るか | 単品純利益 × `EXPECTED_MONTHLY_UNITS` |

> [!warning] 推定値であることを画面上で必ず明示する
> `EXPECTED_MONTHLY_UNITS` は**推定**です。実測ではありません。
> Keepaの数値を「実測の販売数」と呼ばない、という既存ルールをそのまま引き継ぎます。
> 成約データが貯まるまでは、勝敗を確定させません。
