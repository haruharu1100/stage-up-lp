# Schema Drift の教訓 — 「不明」を2種類に分ける

作成日：2026-08-25 ／ 対象：AI Commerce OS Phase 3.10（KEEPA_READ_ONLY）
関連：`21_Phase3.10実装記録_KEEPA_READ_ONLY.md` ／ CLAUDE.md ルール95・96・**97**

---

## 一行でいうと

**「不明（UNKNOWN）と表示されているから安全」ではなかった。**
不明には「本当にデータが無い」と「データはあるのに当社が読めていない」の2つがあり、
後者はシステムの不具合である。混ぜていたので、自分のバグが市場のせいに見えていた。

---

## 何が起きたか

2026-08-25、Keepa から初めて実データを1件だけ取得した（ASIN B0978NB1VQ・実消費1トークン）。
その生の応答を開いて、当社の読み取り結果と1項目ずつ突き合わせたところ、
**在庫切れ割合（`outOfStockPercentage30 / 90`）が毎回「不明」になっていた**。

原因は、値が無かったからではない。**形が違った**からである。

| | 当社が想定していた形 | Keepa が実際に返す形 |
|---|---|---|
| `stats.outOfStockPercentage90` | `4`（1つの数） | `[100, 100, 100, -1, …]`（36個の配列） |

配列をそのまま数値に変換しようとして `NaN` になり、`null`＝不明に落ちていた。
配列の中身は `stats.current` と同じ添字（0＝Amazon本体／1＝新品／2＝中古）である。

### なぜテストで見つからなかったか

受け入れテストの偽データが `outOfStockPercentage90: 4` という**実物と違う形**だった。
そのため **267項目のテストは全部合格していた**。
値の正しさだけを検査しても、形が違えば意味がない。

### なぜ「不明で安全」ではなかったか

品切れが多い商品＝他の出品者が売り切らしていて自分が入り込める商品である。
つまりこの取りこぼしは、**勝てる商品を黙って見送る方向**に効いていた。

> **Fail Closed は「止まる」ことであって「静かに機会を捨てる」ことではない。**

止まれば人が気づく。静かに不明にすると誰も気づかない。後者の方が危ない。

---

## 対策（実装済み）

### 1. 不明を2種類に分けた（ルール97）

| 分類 | 意味 | 誰の問題か |
|---|---|---|
| `DATA_NOT_AVAILABLE` | Keepa に値が無い | 市場データの問題。当社にできることは無い |
| `PARSER_OR_SCHEMA_ERROR` | 値はあるのに当社が読めていない | **当社のコードの不具合。直す対象** |

判定の順番（`lib/keepa/schema.ts`）：

- 項目そのものが無い／`null`／`-1`／`-2`／空文字／空配列 → **データが無い**
- **それ以外で値が入っているのに読めていないものは、全部こちらの不具合とみなす**

`-1` は「値なし」、`-2` は「そもそも今回頼んでいない」。どちらも不明だが、
**`0`（本当に0人・0%）とは絶対に混ぜない**（ルール96）。

### 2. 人への表示と、内部の監査を分けた

- **人へ見せるのは従来どおり「不明」の一語**（`unknownFields`）。安全側に倒す方針は変えない。
- **内部の監査には理由を必ず残す**（`unknownDetails` / `parserErrors` / `schema`）。
- **安全側に倒すことと、原因を隠すことは別である。**

### 3. 応答の「形」を毎回監査する（SCHEMA_MISMATCH）

主要36項目について、想定する型（number / string / array / object / null / missing）と
配列の最小長を表にして持ち、実際の応答と突き合わせる。
食い違えば `SCHEMA_MISMATCH` として **異常一覧（`findAnomalies`）に必ず出す**。
**「読めなかったので不明」で静かに通さない。**

### 4. 偽物のテストデータを実物と同じ形に直した（ルール95）

実物にあって偽物に無かった項目を追加した：
`csv`（36枠）／`availabilityAmazon`／`stats.totalOfferCount`／
`stats.retrievedOfferCount`／`stats.buyBoxPrice`。

さらに「**わざと形を壊したら必ず SCHEMA_MISMATCH が出るか**」を検査する項目を追加した。
壊したのに黙って通るなら、この仕組みは役に立っていない。

### 5. 枠を使わずに検算できるコマンドを作った

```
npm run keepa:audit                  … 保存済みのASIN一覧
npm run keepa:audit -- --asin=B0…    … その1件を検算
```

**Keepa へ一切通信せず、枠を1つも使わず、APIキーも読まない。**
使うのは `keepa_raw_responses` に保存済みの生の応答だけである。

これが要る理由：読み取り方を直したときに取り直して確かめると、
①枠を使う ②その間に相場が動く の2つが起きる。
すると「直ったから値が変わったのか」「相場が動いたから変わったのか」が区別できない。
**生データを残してあるのは、まさにこのためである。**

### 6. 鮮度の線は動かさない

`KEEPA_FRESHNESS_MAX_DAYS = 30`。
**目の前のデータが古いからといって、この数字を動かさない。**
「今回だけ35日にすれば判定できる」は、判定できたことにしているだけである。

保存済みの B0978NB1VQ の応答に対して実施：

- 検査した項目：**36**
- 形の食い違い（SCHEMA_MISMATCH）：**0件**

受け入れテストは 11個 すべて合格（Phase 3.10 は 267 → **309項目**、合計 **1,353項目**）。
`npm run build` も通過。

## 一般化できる教訓（他のプロジェクトにも効く）

1. **「不明」「該当なし」「取得できず」を一語にまとめない。**
   外部データが無いのか、自分が読めていないのかを必ず分けて記録する。
   分けないと、自分のバグが永久に外部のせいに見える。

2. **偽物のテストデータは、実物と同じ「形」で作る。**
   新しい項目を足すときは、必ず一度**実物の生データを開いて形を確かめる**。
   値の正しさだけを検査しても、形が違えば意味がない。

3. **外部APIの生の応答は必ず保存する。**
   保存してあれば、修正の検算を**追加費用ゼロ・相場の変動なし**で何度でもやり直せる。
   取り直して確かめると、直った効果と相場の変動が混ざって切り分けできなくなる。

4. **安全側に倒した箇所ほど、静かに壊れる。**
   エラーで止まる不具合は誰かが気づく。「不明」に化ける不具合は誰も気づかない。
   だから安全側に倒すときこそ、**なぜ不明になったのかの記録を残す**。

5. **閾値は、目の前のデータが通らないという理由で動かさない。**
   通したくて動かした閾値は、もはや判定ではない。

## 次にやること

- 生きている実在ASIN（Amazon.co.jpで販売中・複数出品者あり）を**人が1件指定**する。
  **ASINを推測して作らない。**
- そのASINで**1回だけ**取得し、`PARSER_OR_SCHEMA_ERROR` が0件であることを実データで確認する。
- そこまで確認できたら 1 → 5 → 20 → 100 と段階を上げる。**AIが自分で段階を進めない。**
- `BUY_DECISION` は `UNAVAILABLE` のまま。利益判定にはまだ進まない。
- Keepa の U1（正規化保存の線引き）／U2（契約終了後の扱い）は未確認のまま。
  用途は `INTERNAL_VERIFICATION_ONLY` に固定。
