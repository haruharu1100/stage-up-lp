## 1. 画像 — 市場データの問題ではなく、当社のバグだった

### 何が起きていたか

当社は `imagesCSV` という項目名を見ていた。
**Keepa の公式仕様書の本文に、この名前は1回も出てこない。**
現在は `images` で、中身は文字列ではなく**オブジェクトの配列**
（`{ l, lH, lW, m, mH, mW, variant }`）。画像URLは
`https://m.media-amazon.com/images/I/` ＋ ファイル名 で組み立てる、と公式に書かれている。

結果、5件すべてで「項目なし＝画像なし」と表示されていた。
**Keepa には画像があったのに、当社が読めていなかった。**

### 直したこと

- 読み取りを **`lib/keepa/images.ts` の1ファイル**に集約（何も import しない＝画面へ載せられる／ルール37）
- **現在仕様（`images`）を先に見る。旧名（`imagesCSV`）は後ろ**（ご本人の指示：
  「旧フィールド名を黙ってFallbackとして残さず、現在仕様 ↓ 必要ならLegacy互換 の順にしてください。」）
- 旧名から読めた場合は `imageLegacyFieldUsed = true` を立てて**画面に出す**（黙って拾わない）
- **「画像が無い」を2種類に分けた。絶対に混ぜない。**

| 状態 | 意味 | 誰の問題か |
|---|---|---|
| `IMAGE_OK` | 読めた | — |
| `IMAGE_DATA_NOT_AVAILABLE` | Keepa にも本当に画像が無い | 市場データの問題。当社にできることは無い |
| `IMAGE_PARSER_ERROR` | **Keepa にはあるのに当社が読めていない** | **当社のコードの不具合** |

混ぜると、自分のバグが市場のせいに見える（ルール97の具体例）。

### 直したあとの結果

**保存済み7件すべてで画像が読めた。`IMAGE_PARSER_ERROR` は 0件。**
つまり「画像が無い商品ばかりだった」のではなく、**最初から全部あった**。

## 2. 「販売数」の呼び方 — 実測でも、推定でもなかった

ご本人の指示：
> このKeepa値を、`ACTUAL_MONTHLY_SALES` / 実測販売数 とは呼ばないでください。
> 正式名称を公式フィールド・公式説明に合わせて確認してください。

公式仕様書（`keepa.com/api-docs/product-object.html`）の本文を実際に読んだ結果、
**「実測」でないだけでなく、「推定」でもなかった。**

| 公式の記述 | 意味 |
|---|---|
| **"It is not an estimate."** | 推定値ではない |
| 値は **"10+" "100+"** のような区切り／**"at least"** | **「◯個以上」という区分の下限** |
| **"Most ASINs do not have this value set."** | **大半の商品では空** |

→ 当社での正式な呼び方を決めた。

- 内部名：**`keepaMonthlySoldAtLeast`**
- 画面表示：**「Keepaの月間購入回数（「◯個以上」の区分値）」**
- **`ACTUAL_MONTHLY_SALES` と「実測販売数」の2語は禁止語として登録**し、
  受け入れテストが `lib/` `app/` `scripts/` を機械的に走査して0件であることを確認する
  （走査前にコメントを除去する＝ルール64）

> ご本人が挙げた案 `KEEPA_MONTHLY_SALES_ESTIMATE` も採用していない。
> 公式が「推定ではない」と書いているため、「推定」という語を入れると別の誤解になる。
> ご本人の「**または公式名称に対応した名前**」という許可の範囲で判断した。

## 3. 需要の材料を1つの数字にまとめない（DEMAND_EVIDENCE）

ご本人の指示：「この3つを一つの数字に統合しないでください。」

`lib/keepa/demand.ts`（依存ゼロ）に、**7つの材料を別々のまま**持つようにした。
どれにも**出どころ（SOURCE）が必ず付く**。

| 材料 | 出どころ |
|---|---|
| 30日間の順位下落回数（`RANK_DROPS_30D`） | KEEPA |
| Keepaの月間購入回数（◯個以上） | KEEPA |
| 当社の推定需要シグナル | 当社の計算 |
| 出品者で等分した場合の取り分（暫定モデル） | 当社の計算 |
| 新品の出品者数 | KEEPA |
| Amazon本体が売っているか | KEEPA |
| データの新しさ | KEEPA |

**表示と記録だけ。仕入判定には使っていない。**

- 取り分は **「自分が月◯個売れる」と書かない**（あくまで等分した場合の目安・暫定モデル）
- **Keepa値が無い商品を自動的に低評価にしない。** `UNKNOWN` のまま他の材料で見る

## 4. 食い違いは、どちらかに寄せず「食い違い」のまま残す

ご本人の指示：「勝手にどちらかを採用しないこと。」

当社の推定と Keepa の区分値が **3倍以上**ずれたら `DEMAND_SIGNAL_CONFLICT`。
画面には **「需要指標が食い違っています。追加検証が必要です」** と出る。

- 片方が無いときは `CANNOT_COMPARE`。
  **これは「食い違いが無い」という意味ではない。材料が足りないだけ**（ルール97と同じ考え方）
- 倍率（Keepa値 ÷ 当社推定）は **分析専用**。
  **`lib/sellability.ts` は `demand.ts` を1行も import しない**（受け入れテストが検査）。
  こうしておかないと、食い違いや倍率が仕入判定へ染み出す
- **既存の判定式は1文字も変えていない。** 判定は4種のまま：
  **`SELLS` / `CROWDED` / `DOES_NOT_SELL` / `UNKNOWN`**
  （ご本人の指示文の `TOO_COMPETITIVE` / `NOT_SELLING` は `CROWDED` / `DOES_NOT_SELL` と同じものを指す。
  「まだ変更しない」という指示に従い、**コード側を改名しなかった**）
- `CALIBRATED_SELLABILITY_SCORE` は**予定として文章で持つだけ。まだ実装していない**

## 7. 途中で自分がやった間違いと、直し方

- **受け入れテストの禁止語スキャンで、コメントを除去せずにソース全文を検査してしまった。**
  結果、「この語は使いません」と**説明しているコメント自体**にテストが反応して3件落ちた。
  **これはルール64に4件記録済みの、同じ形の間違いの5件目。**
  → 走査を `codeOnly()`（コメント除去済み）へ切り替えた。
  あわせて、本当に文字列として残っていた2か所も言い換えた。
- **判定名を、ご本人の指示文の表記（`TOO_COMPETITIVE` / `NOT_SELLING`）で書いたテストを作ってしまった。**
  実際のコードは `CROWDED` / `DOES_NOT_SELL`。
  **コードではなくテストの方を直した**（「既存4判定はまだ変更しない」という指示があるため）。
- **`test:phase3-10` の「依存ゼロ」検査が、正しい変更に対して落ちた。**
  `normalize.ts` が `./images` を読むようになったため。
  判断の基準は「読んでいるファイル数」ではなく「**読んでいる相手が依存ゼロか**」なので、
  テストの許可リストへ `./images` を足した（310項目に増えた）。
