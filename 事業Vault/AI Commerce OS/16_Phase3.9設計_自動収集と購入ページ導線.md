# 16. Phase 3.9 設計（人が入力する仕組みから、自動で集める仕組みへ）

作成日：2026-08-20
前：`15_Phase3.8実装記録.md`
市場別の調査結果：`03_市場別_正規データ取得調査.md`（別ファイル）

## 0. なぜ方針を変えたか

ユーザーからの指示。

> 正規に取得できる市場は自動収集し、取得できない市場だけ半自動にする方向にします。

> 現在の10件PILOTは一度保留してください。

理由もはっきりしている。**人が大量に入力するシステムを完成形にしたくない。**

Phase 3.6〜3.8 で作ったのは「人が1件ずつ手で入れる」ための道具だった。
それ自体は正しく動く。だが、その形のまま100件・1000件へ伸ばすと、
**このシステムの正体は「入力作業を人にやらせる装置」になる。** それは目指す形ではない。

目指す形はユーザーの言葉のとおり。

> AI Commerce OSが自動で市場を調査し、利益商品を発見し、
> 私は買いたい商品の「購入ページを開く」を押すだけ

ただし、ここには**絶対に外さない一線**がある。

> 「画面を勝手に巡回するスクレイピング」ではなく、公式API・法人連携・正式フィードがある市場から自動化し、
> ない市場はURL連携方式にします。

つまり「自動化する」の中身は**取得手段を正規のものに限る**ということであって、
「面倒だから勝手に巡回する」ではない。ここを取り違えると全部が違法・規約違反になる。

## 1. 現在のPILOT設計との影響確認（指示①）

10件PILOTを保留すると、これまで作ったものはどうなるのか。**捨てるもの・残るもの・形が変わるもの**を分ける。

### 1.1 そのまま残る（むしろ自動収集で必須になる）

| 作ったもの | なぜ残るか |
| --- | --- |
| 脱落理由の8分類（`lib/dropout.ts`） | 自動で1000件取っても、Routeにならない理由の内訳は必要。むしろ件数が増えるほど効く |
| 同一商品判定の答え合わせ（`lib/matchreview.ts`） | **自動取得になると、より危なくなる。** 人が1件ずつ見ていない分、取り違えが黙って通る |
| データ点検（`lib/integrity.ts`） | API由来のデータも汚れる。二重登録・価格0・日時逆転は同じように起きる |
| Route計算・SHADOW・精度KPI | 取得手段が変わっても、計算と答え合わせの仕組みは同じ |
| 100件へ進むGate | 「材料が自動で増えたから安全」ではない。判定は残す |
| 実市場データ判定（`lib/realdata.ts`） | 記入見本を実測に混ぜない仕掛けは、そのまま必要 |

**つまり、Phase 3.6〜3.8 で作ったものの大半は無駄にならない。**
保留になるのは「人が手で入力する作業」であって、「入力されたものを数える道具」ではない。

### 1.2 止まる

| 止まるもの | 内容 |
| --- | --- |
| 10件の手入力そのもの | ユーザーがメルカリを見て10件書き写す作業。これを行わない |
| 工程別の秒数計測 | 人が作業しないので測れない。**「0秒」にはしない。未計測のまま** |
| 次に自動化する工程TOP3 | 上と同じ理由で出ない。「まだ記録がありません」と正しく表示され続ける |

### 1.3 形が変わる（ここが要注意）

**（a）実市場データの入り口が増える**

いまは「実市場データ = 人が公開画面を見て記録したもの」だけを想定している。
ここに「Connectorが正規APIから取得したもの」が加わる。
両者は同じ `real_market_data = 1` だが、**出どころは別々に残さなければならない**。
混ぜると「APIで取れた分」と「人が見た分」の精度差が分からなくなる。

→ `data_source` に `CONNECTOR_API` / `CONNECTOR_FEED` を追加し、既存の `MANUAL_OBSERVATION` と区別する。

**（b）安全条件7項目の5番目が、永久に測れなくなる**

安全条件の5番は「入力時間が現実的（1件平均180秒以下）」。
人が入力しなくなると、この項目は永久に `unmeasurable` になり、**Gateは永久に7/7にならない。**

これは「勝手に条件を緩めない」ルールと正面からぶつかる。
だから**この場で勝手に直さない。** 選択肢だけ出して、判断はユーザーに預ける。

| 案 | 内容 | 副作用 |
| --- | --- | --- |
| A | 5番を「人手経路のみに適用」に変える。自動取得分は対象外 | 人手経路が1件も無いと、やはり測れない |
| B | 5番を「1件あたりの取得コスト（自動なら実行時間、人手なら入力秒数）」に置き換える | 意味が変わる。過去の判定と比較できなくなる |
| C | 5番を残したまま、7項目を「6項目＋保留1項目」と表示する | 正直だが、いつまでも合格にならない |

**現時点の推奨はC。** 理由は、条件を書き換えると「進めないから条件を変えた」という
一番やってはいけない形になるため。まず自動収集が動き、そのあとで人手経路の位置づけが
決まってから直すのが順番として正しい。

**（c）人手入力の経路は消さない**

指示24にあるとおり、APIが無い市場は `MANUAL / SEMI AUTO` として残る。
`/validation` の観測CSV取込は、**そのまま「半自動市場の入り口」として使う。**
作り直しではなく、位置づけが「主役」から「APIが無い市場の受け皿」に変わるだけ。

### 1.4 結論

**保留にしても、失われるものはほとんど無い。**
止まるのは「人が10件書き写す作業」と「工程別秒数」の2つだけ。
ただし**安全条件5番が測れなくなる**ことは、黙って通してはいけない副作用なので上に書いた。

## 2. Connector設計の確認（指示②）

### 2.1 いまあるもの

すでに Connector の受け皿は2種類ある。

| ファイル | 役割 | 現状 |
| --- | --- | --- |
| `lib/connectors/types.ts` | 仕入先Connector（商品カタログ） | CSVのみ。purchase は全社 `manual` 固定 |
| `lib/connectors/market.ts` | 市場Connector（相場・手数料・在庫） | `CsvMarketConnector` 以外は全部 `unavailable` を返す実体 |

そして**すでに正しい歯止めが入っている**。

```
canAutoFetch(c, op) = c.termsChecked && c.capabilities[op] === 'api'
```

`'api'` でなければ実行層は動かない。環境変数で true にしても動かない。
`UnavailableMarketConnector` は「後で実装する」というコメントではなく、
**実際に拒否を返す実体**として置いてある。空クラスを誰かが足すのを防ぐため。

### 2.2 指示との差（3つ）

**差1：取得手段の段階が5つしかない**

| いま（`Capability`） | 指示（7段階） |
| --- | --- |
| `api` | `OFFICIAL_API` / `BUSINESS_API` / `PARTNER_API` の3つに分かれる |
| `csv` | `OFFICIAL_CSV`（事業者提供）と `MANUAL_OBSERVATION`（自分で見て記録）は**別物** |
| `webhook` | （7段階には無い。`AUTHORIZED_INTEGRATION` に含める） |
| `manual` | `MANUAL_OBSERVATION` |
| `unavailable` | （状態側で `PROHIBITED` / `NOT_RESEARCHED` として持つ） |

とくに **`csv` を1つにまとめているのが危ない**。
「事業者から正式に提供されたCSV」と「自分で画面を見て書き写したCSV」は、
ファイルの形が同じでも立場がまったく違う。これは `lib/venues.ts` の
`csv_available` のコメントで一度訂正済みの論点で、同じ間違いを Connector 側でも直す。

→ `AccessMethod` として7段階を新設する。

```
OFFICIAL_API > BUSINESS_API > PARTNER_API > OFFICIAL_DATA_FEED
             > OFFICIAL_CSV > AUTHORIZED_INTEGRATION > MANUAL_OBSERVATION
```

**差2：取得関数が5つで、指示は6つ**

| 指示の関数 | いまの対応 |
| --- | --- |
| `fetchProducts()` | **無い**（商品そのものを取る関数が市場Connectorに無い） |
| `fetchListings()` | `fetchCurrentListings()` |
| `fetchSoldHistory()` | `fetchSoldHistory()` |
| `fetchCurrentPrice()` | **無い**（`fetchMarketStats()` は統計であって1件の現在価格ではない） |
| `fetchInventory()` | `fetchInventory()` |
| `fetchFees()` | `fetchFees()` |

→ 6つに揃える。`fetchMarketStats()` は7つ目として残す（統計は統計で必要）。

**差3：「調査の進み具合」を持つ場所が無い**

これが一番大きい。

指示8の9状態（`NOT_RESEARCHED` 〜 `PROHIBITED`）は、
**Connectorの実装能力ではなく、その市場との契約・申請の進み具合**である。
いまの `Capability` に混ぜると「まだ調べていないのにAPIあり」という状態が作れてしまう。

だから**2つの軸を分けて持つ。**

| 軸 | 何を表すか | 例 |
| --- | --- | --- |
| `AccessMethod`（7段階） | どの手段で取るか | `OFFICIAL_API` |
| `ConnectorState`（9状態） | いまどこまで進んでいるか | `APPLICATION_REQUIRED` |

**両方そろって初めて自動実行してよい。**

```
自動実行してよい = ConnectorState === 'CONNECTED'
                && AccessMethod ∈ { OFFICIAL_API, BUSINESS_API, PARTNER_API, OFFICIAL_DATA_FEED }
                && termsChecked === true
                && 認証情報が Secrets に存在する
```

`OFFICIAL_CSV` と `AUTHORIZED_INTEGRATION` は「正規だが人の操作が要る」ので**半自動**。
`MANUAL_OBSERVATION` は Scheduler が**絶対に呼ばない**。

### 2.3 9状態の意味（指示8）

| 状態 | 意味（人間向け） | 自動取得 |
| --- | --- | --- |
| `NOT_RESEARCHED` | まだ調べていない | しない |
| `RESEARCHING` | 調査中 | しない |
| `AVAILABLE` | 正規手段があると確認できた。まだ申し込んでいない | しない |
| `APPLICATION_REQUIRED` | 申請・審査が必要と確認できた | しない |
| `WAITING_APPROVAL` | 申請済み・返事待ち | しない |
| `CONNECTED` | 実際に接続でき、取得できることを確認した | **する** |
| `MANUAL_ONLY` | 正規の自動取得手段が無い。人がURLを登録する | しない |
| `PROHIBITED` | 規約で禁止と確認できた | **絶対にしない** |
| `UNKNOWN` | 調べたが一次情報を確認できなかった | しない |

**`CONNECTED` にしてよい条件を機械で縛る。**
ユーザー指示：「適当に『APIあり』と判断しないでください。正式利用可能性を確認したものだけ `CONNECTED` に。」

→ `CONNECTED` にするには次の4つが全部必要。1つでも欠けたら保存を拒否する。

1. 出典URL（`terms_source_url`）が入っている
2. 確認日（`terms_verified_at`）が入っている
3. 確認した人（`verified_by`）が入っている
4. 実際に1回以上の取得成功記録（`market_fetch_log`）がある

4番が肝で、**「書類上はできるはず」では `CONNECTED` にできない。**

### 2.4 既存テーブルとの関係

`venues` にはすでに `api_available` / `csv_available` / `manual_only` / `terms_status` /
`automation_permission` がある。ここに9状態を足すと**二重管理**になり、必ずズレる。

→ 新テーブル `venue_connectors` を「正」とし、`venues` の5項目は**そこから導出して表示するだけ**にする。
片方だけ直して食い違う事故を、構造で防ぐ。

```
venue_connectors
  venue_code, operation（6+1種）, access_method（7段階）, state（9状態）,
  terms_source_url, terms_verified_at, verified_by, rate_limit_note,
  credential_key（Secretsの名前だけ。値は保存しない）, note, updated_at
  UNIQUE(venue_code, operation)
```

**操作ごとに1行**なのが重要。
「価格は取れるが成約履歴は取れない」市場が普通にあるので、市場単位で1つの状態にできない。

## 4. 購入ページURL導線の設計（指示④）

### 4.1 いちばん大事な一行

ユーザー指示2：

> リンク先をAIが生成してはいけません。取得元データに実際に存在するURLだけ使用してください。

これは「気をつける」で守れるものではない。**構造で守る。**

理由：AIが商品名から `https://jp.mercari.com/item/m12345678901` のような
それらしいURLを組み立てるのは簡単で、しかも**見た目では本物と区別が付かない。**
押した先が別人の商品だったら、そのまま誤購入になる。

### 4.2 4つの歯止め

**歯止め1：URLは必ず取得元レコードから丸ごとコピーする**

URLを部品から組み立てる関数を**作らない**。
`venue + item_id → URL` のような関数が1つでもあると、いつか誰かが使う。
Connectorが受け取った生データの文字列を、加工せずそのまま保存する。

**歯止め2：出どころを必ず記録する（`URL_SOURCE`）**

| 値 | 意味 |
| --- | --- |
| `CONNECTOR_API` | 正規APIのレスポンスに含まれていたURL |
| `CONNECTOR_FEED` | 正式なデータフィードに含まれていたURL |
| `OFFICIAL_CSV` | 事業者から正式提供されたCSVにあったURL |
| `HUMAN_ENTRY` | 人が商品ページを開いて貼り付けたURL |

**`AI_GENERATED` という値は作らない。** 値を用意すると、それを使う実装が生まれる。
この4つのどれでもないURLは、そもそも保存できない。

**歯止め3：市場コードとホスト名が一致しないと登録しない**

`MERCARI` の出品なのにホストが `jp.mercari.com` でなければ拒否。
市場ごとの許可ホスト一覧を持ち、一覧に無いホストは登録拒否。
AIが作った偽URLは、たいていここで落ちる。加えて**短縮URL・リダイレクタも拒否**する
（押すまで行き先が分からないものを人に押させない）。

**歯止め4：URLは人が押したときだけ開く**

`target="_blank" rel="noopener noreferrer"` の普通のリンクにする。
AI側から `fetch` も `open` もしない。**AIはURLを表示するだけで、一度も触らない。**

### 4.3 URLの信頼性を持つ4項目（指示3）

| 項目 | 内容 |
| --- | --- |
| `SOURCE_PRODUCT_URL` | 商品ページのURLそのもの（すでに `tracked_listings.product_url` として存在） |
| `URL_SOURCE` | 上の4値 |
| `URL_VERIFIED_AT` | そのURLの状態を最後に確認できた日時 |
| `URL_STATUS` | `ACTIVE` / `SOLD` / `REMOVED` / `UNKNOWN` |

### 4.4 ボタンを無効にする条件

ユーザー指示：「無効なURLの場合は『購入ページを開く』を無効化してください。」

| `URL_STATUS` | ボタン | 画面の書き方 |
| --- | --- | --- |
| `ACTIVE` | **押せる** | 「購入ページを開く」 |
| `SOLD` | 押せない | 「売り切れを確認済み」 |
| `REMOVED` | 押せない | 「ページが消えています」 |
| `UNKNOWN` | 押せない | 「いまの状態が確認できません」 |

**`REMOVED` を `SOLD` にしない。** これは Phase 3.6 で決めたルール
（「消えた＝売れた」にしない）と同じ。ページが消えた理由は、売れた・出品取り下げ・
アカウント停止・一時的な障害と何通りもある。勝手に「売れた」と決めない。

**古いだけでは無効にしない。** `URL_VERIFIED_AT` が古いときはボタンは押せるが、
「最終確認から◯時間経過しています」と必ず添える。
確認が古いことと、無効であることは別。ここを混ぜると、押せる候補がすぐ0件になる。

### 4.5 開いたときの記録（指示15）

「購入ページを開く」を押した瞬間に `OPENED_FOR_PURCHASE` を1行残す。

```
purchase_intents
  listing_key, route_id, opened_at,
  opened_price（開いた時点の出品価格）,
  opened_decision（STRONG_BUY等）, opened_expected_profit, opened_route_score,
  outcome（下の5択・最初はNULL）, outcome_at, outcome_note
```

**開いた時点の判断を丸ごと凍結する。**
これは SHADOW と同じ考え方で、あとから相場が動いても、
「押したときAIは何と言っていたか」が書き換わらないようにするため。
書き換わると、AIの判断が当たっていたのか外れていたのかが永久に測れなくなる。

**結果は5択（指示15）**

| 選択肢 | 記録 | 扱い |
| --- | --- | --- |
| 購入した | `PURCHASED` | 実取引の候補として記録 |
| 見送った | `PASSED` | 理由の記入を任意で受ける |
| 売り切れていた | `SOLD_OUT` | 機会の寿命（`opportunity_half_life`）の実測値になる |
| 価格が変わっていた | `PRICE_CHANGED` | 変わった後の価格を記入。データ鮮度の実測値になる |
| **違う商品だった** | `DIFFERENT_ITEM` | **重大。FALSE MATCH と同じ扱い。理由の記入を必須にする** |

`DIFFERENT_ITEM` は Phase 3.8 の `INCORRECT_MATCH` と同じ重さで数える。
1件でも出たら100件へ進まない。**画面上で一番儲かって見えるものが、一番危ないから。**

### 4.6 「購入した」を選んだとき（指示16）

ユーザー指示：

> 現段階では購入機能自体をAI Commerce OSから実行しません。

だから記録するのは**買った後の報告**だけ。入力するのは3つに絞る。

- 実際の購入価格
- 実際の送料
- 購入日時

これは **SHADOW ではなく `REAL TRADE候補記録`** として別テーブルに置く。

**なぜ分けるか。** SHADOWは「買っていないが、買ったつもりで答え合わせする」記録。
実購入は「本当に買った」記録。混ぜると、AIの予測精度の分母に
「人間が最終判断して買ったもの」が混ざり、**AIの成績が実際より良く見える。**

| 17 | データConfidence | ― | ― |
| 18 | **購入ページを開く** | 右端に固定 | 無効時はグレー＋理由 |

**空欄を0で埋めない。** 未計測は「未計測」、不明は「不明」と書く。
0と書くと「計算した結果0だった」に見え、判断を間違える。

### 5.2 並べ替え（指示13）

Route Score／保守的利益／保守的ROI／30日売却確率／Liquidity Score／
Opportunity Speed／必要仕入額 の7種類。**既定は Route Score。**

「保守的利益」の並びを用意するのが効く。額面利益で並べると、
**売れない高額品が上位に来て、資金だけ止まる。**

### 5.3 🔥 今すぐ確認（指示14）

> クリックすると購入元ページを開くだけ。AIは購入しません。

出す条件（全部満たすもの）：

1. 判定が `STRONG_BUY`
2. `URL_STATUS` が `ACTIVE`
3. 機会の残り時間が半減期の半分を切っている（＝早く消える）
4. 手数料が `VERIFIED`（実額確認済み）
5. 同一商品判定に `INCORRECT_MATCH` が付いていない

3番の「早い」だけで選ぶと、**急いで買わせる装置**になる。
だから1・4・5の安全条件を必ず一緒に課す。

### 5.4 いま足りていないもの（正直に）

| 足りないもの | 何が困るか |
| --- | --- |
| 商品画像のURL | `tracked_listings` に画像URLの列が無い |
| 実出品からRouteを作る経路 | `arbitrage_routes` は仕入先商品（`supplier_product_id`）が起点。実市場の出品が起点になっていない |
| BUY側の実出品価格 | いまRouteのBUY価格は相場から来ている。「この1件の出品を、この価格で買う」という形になっていない |

**2番目が本丸。** ここを繋がないと「自動で見つけて、その商品ページを開く」が成立しない。
実装は、実市場の出品1件を仕入候補として扱う変換層を1枚入れる形になる。

## 6. 自動収集Schedulerの設計（指示⑥）

### 6.1 7つの取得関数

| 関数 | 取るもの | 頻度の考え方 |
| --- | --- | --- |
| `fetchProducts()` | 商品そのもの（型番・JAN） | 少なめでよい。商品情報は頻繁に変わらない |
| `fetchListings()` | 現在の出品一覧 | **一番速く古くなる。**短い間隔 |
| `fetchCurrentPrice()` | 1件の現在価格 | 押す直前の確認に使う |
| `fetchSoldHistory()` | 成約履歴 | 1日1回で足りる |
| `fetchInventory()` | 自社在庫 | 変わったときだけ |
| `fetchFees()` | 手数料 | **自動で書き換えない。**変化の検知だけ |
| `fetchMarketStats()` | 市場統計 | 1日1回 |

`fetchFees()` だけ扱いが違う。手数料が自動で書き換わると、
**昨日と今日で利益計算が変わった理由が誰にも分からなくなる。**
だから取得するのは「変わったかもしれない」の検知までで、
実額の更新は人が出典を確認して行う（Phase 3.5 で決めたルールのまま）。

### 6.2 実行してよいかの判定（毎回、実行の直前に行う）

```
実行可 = state === 'CONNECTED'
      && access_method ∈ { OFFICIAL_API, BUSINESS_API, PARTNER_API, OFFICIAL_DATA_FEED }
      && terms_verified_at が入っている
      && Secrets に認証情報がある
      && Rate Limit の残りがある
```

1つでも欠けたら**実行せず、理由を記録して止まる**（Fail Closed）。
「たぶん大丈夫だから動かす」を作らない。

### 6.3 守ること

- **Rate Limit**：市場ごとに1分あたり・1日あたりの上限を持ち、**こちら側で先に止める。**
  相手に止められる前に止めるのが礼儀であり、アカウント停止を避ける唯一の方法。
- **利用条件**：取得したデータを規約が許す範囲でしか保存・利用しない。
  「保存禁止」「24時間以内に破棄」等の条件がある市場は、その条件をテーブルに書いて機械で守る。
- **法人契約**：契約が要る市場は、契約前に1回も叩かない。
- **同時実行しない**：同じ市場へ複数の取得を同時に投げない。

### 6.4 二重に取り込まない

同じ出品を2回取っても増えないようにする（すでにその形になっている）。

- `tracked_listings` は `listing_key` が UNIQUE
- `listing_observations` は `(listing_key, observed_at)` が UNIQUE

取得のたびに新しい行を積み、上書きはしない。
上書きすると「7日前はいくらだったか」が消え、値下げが起きたことすら分からなくなる。

### 6.5 失敗したとき

**古いデータで判断を続けない。**
取得に失敗した市場のデータは「鮮度切れ」として扱い、
その市場が絡むRouteは `MARKET_DATA_MISSING` で落とす。

「前回の値がまだあるから、それで計算する」は一番危ない。
相場が動いたから儲かるように見えているのか、データが古いから儲かるように見えているのか、
区別が付かなくなる。

### 6.6 起動方法

**最初は手動コマンド（`npm run collect`）だけ。**
常駐（cron）は、1回目の取得が正しく動くことを人が確認したあとで、承認を得てから。

理由：常駐は「気付かないうちに大量に叩き続ける」事故が起きる。
最初の1回は必ず人が見ている前で動かす。

## 7. 安全・規約設計（指示⑦）

### 7.1 いまも実装しないもの（コードごと存在させない）

- 商品の自動購入
- 自動出品
- 決済
- 発送
- 自動ログイン
- 無許可のスクレイピング／画面の自動巡回
- CAPTCHA の自動突破

これは「機能をオフにしている」のではなく、**処理そのものを書かない。**
オフにしただけのものは、いつか誰かがオンにする。

受け入れテストで、これらの処理が**存在しないこと**を毎回検査する（Phase 3.8 から継続）。

### 7.2 `AUTO_PURCHASE_CAPABLE` は構造だけ作る（指示17・18）

将来のために「フラグの置き場所」だけ用意する。**今は必ず `false`。**
そして `true` にできる条件を、いまのうちに厳しく決めておく。

ユーザー指示18：

> APIがあるだけで自動購入可能にしないでください。

`true` にするには**9つ全部**が必要。1つでも欠けたら不可。

1. その市場が**公式に**自動購入を認めている（規約・API仕様で確認できる）
2. 手数料が `VERIFIED`（実額確認済み・推定値ではない）
3. 同一商品判定の確信度が高い
4. 判定が `STRONG_BUY`
5. 保守的ROIが基準を超えている
6. 実市場での的中率（Precision）が基準を超えている
7. 在庫・出品が実在することを確認済み
8. 予算の範囲内
9. すべての安全Gateを通過している

**6番が一番効く。** 「理屈上は儲かる」と「実際に当たっている」は別物で、
実績が無いまま自動購入を許すと、AIの間違いがそのまま現金の損になる。

### 7.3 秘密情報

APIキー・ログイン情報・決済情報は**コードに書かない。**
`.env` / Secrets管理に置き、`venue_connectors` に持つのは
「どの名前のSecretsを使うか」だけ。値は1文字も保存しない。

### 7.4 判断の順番（変えない）

```
正確性 > 安全性 > 利益 > 自動化率 > 商品数
```

自動収集を始めても、この順番は変わらない。
**取得件数を増やすために判定を甘くしない。**
件数が伸びないなら、緩めるのではなく、正規に取得できる市場を増やす。
