## 1. Phase 3 の範囲（ユーザー指示そのまま）

> 「AIが買うと判断した商品が、本当にその後利益になったのか」を自動で答え合わせする

## 2. 最重要の設計判断

### 2.1 判断は「凍結」する。後から書き換えない

`route_shadow_trades` / `shadow_market_snapshots` / `shadow_evaluations` の
INSERT はすべて **`ON CONFLICT DO NOTHING`**。`DO UPDATE` は1箇所も無い。

理由：答え合わせの目的は「当時の自分がどう間違えたか」を測ること。
後から現在値で上書きすると、**常に自分が正しかったことになり、学習が成立しない。**

受け入れテストで、`lib/shadow.ts` のソースを実際に読んで
`DO UPDATE` が無いこと・`DO NOTHING` が3つ以上あることを検査している。
「そういう方針です」ではなく、コードがそうなっていることを毎回確かめる。

### 2.2 相場は「その時の全部」を保存する（現在値だけでは意味がない）

保存項目：`price` / `price_basis` / `low_price` / `median_price` / `avg_price` /
`listing_count` / `sold_count_30d` / `avg_days_to_sell` / `price_stddev_ratio` /
`source_type` / `observed_at` / `data_age_hours`

**BUY側とSELL側を別レコードで持つ**（`role` 列）。仕入相場と販売相場は別物なので混ぜない。

### 2.3 「売れたことにする」条件を厳しくした ← ここが Phase 3 の核心

`judgeOutcome()` は、次を**すべて**満たさない限り `SOLD` と言わない。

1. 観測データが存在する
2. `observed_at` が入っている
3. 観測時刻が **判断時刻より後**（判断前のデータで答え合わせしない）
4. `price_basis === 'SOLD_MEDIAN'`（成約価格である。出品価格ではない）
5. `sold_count_30d >= 1`（実際に売れた件数がある）
6. `avg_days_to_sell` が入っている

出品価格しか取れない市場は `ACTUAL_SALE_UNCONFIRMED`。
**勝ちにも負けにもしない。** 無理に勝敗を決めると、勝率がただの願望になる。

> 実測：今回のシード（11件）では判定保留 0件だったが、これは
> サンプルCSVが成約データを持っていたから。本番の外部データでは保留が出る前提。

### 2.4 少ない実績でスコアを動かさない

Route勝率による補正は件数で強さを変える。

| 実績件数 | 段階 | 重み | 意味 |
|---|---|---|---|
| 5件未満 | NONE | 0.0 | 補正しない |
| 5〜19件 | WEAK | 0.3 | 弱く補正 |
| 20〜49件 | MID | 0.6 | 中程度 |
| 50件以上 | FULL | 1.0 | 通常補正 |

補正幅は上下 **±10点まで**（`MAX_SCORE_ADJUSTMENT`）。

理由：3件連続で外しただけで「この市場は駄目」と決めつけると、
たまたま悪かっただけの組み合わせを永久に捨ててしまう。

> 実測：今回の Route勝率はすべて1〜4件だったため **補正はすべて +0点**。
> これは仕様どおりの正しい挙動。「学習していない」のではなく「まだ学習してはいけない」。

### 2.5 利益が大きくても、データが悪ければ最優先で買わない

`combineConfidence(market, fee, match)` で
`overall = 一番弱いもの×0.5 + 平均×0.5`。**一番弱い項目が判定の上限も決める。**

実際に検証して分かったこと（当初の想定は間違っていた）：

- 手数料が**概算**だと、そもそもRoute点数が90に届かない
  （データ信頼度15点分が下がるため）。だから `STRONG_BUY` にならない。
- 手数料を公式確認すると同じ利益でも点数が上がり `STRONG_BUY` になる。
- **同一商品と確認できていない**（`identityKey = null`）場合は、
  点数が89まで出ていても `confidenceCapped` が発動して `WATCH` まで落ちる。

つまり止め方が2種類ある。**「点数が上がらない」と「点数が高くても蓋をする」は別物**。
テストでは3ケースを並べて両方が効いていることを確認している。

### 2.6 手数料は「いつ・どこで確認したか」まで持つ

`venue_fee_profiles` に追加：
`source_url` / `source_type` / `verified_at` / `effective_from` / `effective_to` /
`is_estimated` / `manually_verified_by` / `fee_version`

`fee_version` は `f{E|V}-{ハッシュ8桁}` 形式。`E`=概算、`V`=確認済み。
**金額に影響する14項目だけ**をハッシュに含める（備考を直しただけで版が変わらないように）。

手数料が変わったら `fee_change_log` に記録するだけ。
**過去の判断は当時の版のまま残す。** 新料金で過去利益を再計算すると
「当時いくらの利益を見込んで買うと決めたのか」が消え、答え合わせが嘘になる。

### 2.7 画面で「概算」を目立たせた

`/venues` に赤い警告帯を追加：

> 手数料 18 件のうち 18 件が「概算」のままです。

手数料表の**一番左**に「確からしさ」列（概算／確認済み）を置き、
出どころ・確認日・確認した人・版・備考まで並べた。
奥に隠すと「確認したつもり」で使い続けてしまうため、並び順も概算を上にした。

### 3.1 記録できた量

| 項目 | 件数 |
|---|---|
| SHADOW（判断の凍結） | 11件 |
| 相場スナップショット | 22件（BUY 11 / SELL 11） |

これは正しい挙動。ここに参考値を入れた瞬間、答え合わせが自己満足になる。

### 3.2 AIはどれくらい外したか

| 期間 | 的中率 | 売れた | 売れなかった |
|---|---|---|---|
| 7日後 | 90.9% | 1件 | 10件 |
| 30日後 | 54.5% | 1件 | 10件 |
| 90日後 | 18.2% | 2件 | 9件 |

- 販売価格の平均ズレ：**−4,678円**（高く売れると読みすぎ）
- 純利益の平均ズレ：**−4,210円**
- **予想ROI 57.4% → 実績ROI 47.3%（−10.1ポイント）**

ユーザーが想定していた「予想ROI 25% → 実績ROI 17%」というズレの構造が、
そのまま数字として出るようになった。**これが Phase 3 の成果物そのもの。**

的中率が90.9% → 18.2% と落ちるのは、
「7日で売れる確率」の予測は当たるが「90日で売れる確率」の予測は外す、という意味。
※ 的中率は「売却確率の予測が当たったか」であって「売れた割合」ではない。
（実装で一度これを取り違えてテストが落ちた。§4参照）

## 4. 間違えたこと（同じ失敗を繰り返さないため）

| 間違い | 何が起きたか | 正しくは |
|---|---|---|
| 的中率を「売れた÷判定できた」だと思い込んだ | テストが落ちた | `hit_rate = AVG(probability_correct)`。**売却確率の予測精度**であって成約率ではない |
| 「手数料が概算なら信頼度の蓋が発動する」と思い込んだ | テストが落ちた | 概算だと**そもそも90点に届かない**。蓋が発動するのは「90点以上なのに信頼度が低い」時だけ（例：同一商品と確認できていない） |
| `calcFreshness` を位置引数で呼んだ | 型エラー7箇所 | 第2引数はオプションの入れ物 `{freshHours, normalHours, now}` |
| テーブル名を `route_accuracy` と書いた | SQLエラー | 正しくは **`prediction_accuracy`** |
| `ownership_state` を `products` から読んだ | SQLエラー | この列は **`supplier_products`** にある |
| `new URL(...).pathname` でファイルを読んだ | ENOENT | リポジトリのパスに日本語が含まれるためパーセントエンコードされる。**URLオブジェクトをそのまま渡す** |
| 誤差集計で `actual_sell_price` を無修飾で書いた | ambiguous column | JOINする2表の両方に同名列がある。必ず `e.` / `s.` で修飾する |

## 7. 次にやること（Phase 4 へ行く前に）

優先度順。上から潰すほど数字の信頼性が上がる。

1. **手数料18件を公式の料金ページで実額確認する**（今すぐ効く・最重要）
   今は全件概算なので、どのRouteも実力より低く評価されている。
   確認すれば同じ商品でも判定が `BUY` → `STRONG_BUY` に上がる。
2. **仕入側の相場観測を入れる**（今はBUY側11件すべて `NO_OBSERVATION`）
   仕入相場が見えないと「安く買えたか」の答え合わせができない。
3. **SHADOW件数を50件以上ためる**
   Route勝率の補正が効き始めるのは同一Routeで5件から、本格的に効くのは50件から。
   今は11件なので、まだAIは学習していない（学習してはいけない段階）。
4. **実データのConnectorを1つだけ繋ぐ**（公式APIのみ。スクレイピングは不可）
   受け皿（`fetchCurrentListings` / `fetchSoldHistory` / `fetchMarketStats` /
   `fetchFees` / `fetchInventory`）は作ってあるので、中身を入れるだけ。

その後で SEMI AUTO → 少額の実購入 → FULL AUTO の順に解禁する。
**予想と実績のズレが安定して10ポイント以内に収まるまで、実購入へは行かない。**
