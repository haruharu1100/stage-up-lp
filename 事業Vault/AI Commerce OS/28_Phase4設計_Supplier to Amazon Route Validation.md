## 1. 完成した1本の流れ（§1）

```
仕入価格
  → JAN / 型番 / 商品名
  → Amazon ASIN Matching
  → Keepa（保存済みデータ）
  → Amazon需要確認
  → Amazon想定販売価格
  → Amazon手数料
  → 送料・梱包・保管など
  → 保守純利益
  → 保守ROI
  → BUY / WATCH / REVIEW / SKIP
  → [仕入先の商品ページを開く]
```

**この流れの途中で Keepa へ通信しない。** 使うのは Phase 3.15 で取り終えた保存済み100件だけ。
利益計算のたびに枠（Token）が減る作りにすると、計算をやり直すだけで費用が出ていく。

## 2. Keepa の位置づけを固定した（§2）

Keepa は「**Amazon販売側のデータ源**」であって、判定装置ではない。

> 「**Keepa単体で、『買うべき』とは判定しません。**」

コードでもこれを守っている。BUY 判定は4段階で、①同じ商品か → ②売れているか →
③利益が出るか → ④危ないところ、の順に見る。**②で止めて BUY を出す経路が存在しない。**
`SELLABILITY_ALONE_CAN_BUY = false` はその印である。

## 3. 仕入先の取り方（§3・§25・§26）

`SUPPLIER_CONNECTOR_KINDS` は5種類。いま**実際に動くのは2つだけ**。

| 種類 | 意味 | いま動くか |
|---|---|---|
| MANUAL_SUPPLIER_INPUT | 人が手で入力した | ○ |
| CSV_SUPPLIER_IMPORT | CSVファイルから取り込んだ | ○ |
| OFFICIAL_API | 仕入先の公式APIから取得した | × |
| PARTNER_FEED | 提携先から受け取ったデータ | × |
| AUTHORIZED_CONNECTOR | 許可を得た自動取得 | × |

- **スクレイピングは「種類」の名前にすら入れていない。** 名前だけ置くと、いつか誰かが実装する。
- 将来つなぐ候補（KOMEHYO / BOOKOFF / HARD_OFF / SECOND_STREET / MERCARI / SNKRDUNK / YAHOO）は
  **名前を置いてあるだけ**。`SUPPLIER_FIRST_PARTNER_FIXED = false`。
  ご本人の指示「**最初からKOMEHYOだけに固定しないでください。**」をそのまま定数にした。

## 4. 仕入先データ16項目（§4）

> 「**分からないものはNULL。推測禁止。**」

空欄では受け取らないのは**5項目だけ**。

- 仕入先の名前 / 仕入先での商品番号 / 商品名 / **仕入価格** / その値を見た日時

残り11項目（ブランド・JAN・EAN・UPC・型番・色・サイズ・状態・送料・在庫・商品ページURL）は
**空欄でよい**。埋まっていなくても分析は進む。

**仕入価格だけが例外**で、これが無い行は「仕入ルートが成り立つか」の検証にならないので受け取らない。

### 0円と「不明」を分ける（ルール115）

送料が空欄の行を 0円 として計算すると、利益が実際より多く出る。
多く出た利益は、そのまま現金の損になる。だから：

- 送料無料 → `0`
- 分からない → **空欄のまま**（`null`）＋「空欄のまま進みます」と本人に表示

8桁未満の数字は JAN として受け取らない（短い数字を通すと、まったく別の商品に当たる）。
`N/A` `不明` `なし` `—` のような Excel 由来の空欄表現も、そのまま文字列にしない。

## 5. 仕入先URLは必須ではない（§5）

> 「分析自体は、URLが無くても可能にしてください。」
> 「**URLをAIが推測生成するのは禁止を維持。**」

- `SUPPLIER_URL_REQUIRED_FOR_ANALYSIS = false`
- `SUPPLIER_URL_AI_GENERATION_ALLOWED = false`

画面の「仕入先の商品ページを開く」は、**保存してあるURLをそのまま `href` に置くだけ**。
組み立て関数（`buildUrl` の類）は Phase 4 のどのファイルにも無い。

開かない条件：見本データ／空欄／URLの形でない／`https` でない／ログイン情報が埋め込まれている。
開けないときは、**理由を日本語で出す**（黙って消さない）。

## 6. Match Gate（§6・§7）

3段階に統一した。

| 門 | 意味 | BUYへ進めるか |
|---|---|---|
| HIGH_CONFIDENCE | 同じ商品と言い切れる | ○ |
| REVIEW_REQUIRED | 人が確かめる | × |
| REJECTED | 違う商品 | × |

- 旧い言い方（MATCHED / NEEDS_HUMAN_CHECK / MISMATCH）と**1対1**で対応させた。
- **知らない値は必ず REVIEW_REQUIRED へ寄せる。** 安全に見える側へ寄せない。
- > 「**候補ASINが複数ある場合、勝手に1件へ決定しないこと。**」
  → 候補が複数のときは1件に決めず、「候補が何件あるか」を画面に出す。
- > 「**FALSE MATCHは今までどおり重大事故扱い。**」
  → `FALSE_MATCH_IS_CRITICAL = true` / 理由の記入必須。
- **人が出した答えで、機械の判定を書き換えない**（ルール49）。
  人が「同じ商品」と確かめれば門は開くが、機械の判定は文面に残したまま持つ。

## 7. Amazon想定販売価格は2本立て（§8・§9）

| 名前 | 使い道 |
|---|---|
| RAW_EXPECTED_SELL_PRICE | 表示用。**判断には使わない** |
| CONSERVATIVE_SELL_PRICE | **BUY判定はこれだけ** |
| CALIBRATED_SELL_PRICE | 実成約データが貯まるまで**必ず空欄** |

> 「**ただしBuy Boxが無ければ、無理に埋めず別Confidenceにしてください。**」

| 出どころ | 確からしさ |
|---|---|
| BUYBOX | HIGH |
| NEW_PRICE | MEDIUM |
| AVG_NEW_90 / AVG_NEW_30 | LOW |
| 手がかり無し | UNKNOWN（値段は空欄。0円にしない） |

保守価格の作り方：**手に入る値段のうちいちばん安いもの**を土台にして、
確からしさに応じた下げ幅（HIGH 5% / MEDIUM 10% / LOW 15%）と、
出品者の多さによる下げ幅（最大5%）を引く。

BUY へ進めるのは確からしさ **MEDIUM 以上**のときだけ。

## 8. Amazon費用と当社費用を完全に分離（§10）

**箱①：Amazonが決めている額（Keepa由来）**
- 販売手数料（率×想定販売価格）／FBA料
- **片方でも欠けたら合計は `null`。0で埋めない。**
- 両方そろったときだけ `VERIFIED`。`VERIFIED` 以外は BUY へ進めない。

**箱②：当社が決めている額（設定から変更可）**

| 費目 | 既定値 | 設定キー |
|---|---|---|
| 納品送料 | 500円 | SUPPLIER_ROUTE_INBOUND_SHIPPING |
| 仕入送料 | 0円（仕入先データが優先） | SUPPLIER_ROUTE_SUPPLIER_SHIPPING |
| 梱包 | 150円 | SUPPLIER_ROUTE_PACKAGING |
| 保管 | 100円 | SUPPLIER_ROUTE_STORAGE |
| 返品の見込み損 | 販売価格×2% | SUPPLIER_ROUTE_RETURN_LOSS_RATE |
| その他 | 0円 | SUPPLIER_ROUTE_OTHER_COST |

**2つの箱は最後まで混ぜない。** 混ぜると、実績と食い違ったとき
「Amazonの手数料が想定と違ったのか、自分の梱包費が甘かったのか」が分からなくなる。
返品の見込み損は**必ず「仮置き」の印**を付け、画面でそう断る。

## 9. 利益8項目と「いくらまでなら買えるか」（§11・§12）

1. 仕入総額（仕入価格＋仕入送料）
2. 売れたときの手取り（素）
3. 素の純利益
4. **保守の純利益** ← 判定はこれ
5. 素のROI
6. **保守のROI** ← 判定はこれ
7. 損益分岐の売値
8. **買ってよい仕入価格の上限（MAX_BUY_PRICE）**

上限額は**2つの条件の厳しいほうを採る**。

- 利益額が `SUPPLIER_ROUTE_MIN_NET_PROFIT`（既定3,000円）以上
- ROIが `SUPPLIER_ROUTE_MIN_ROI`（既定15%）以上

画面には §12 の形でそのまま出せる：

> 現在の仕入価格 52,000円 ／ 買ってよい上限 45,300円 ／ あと 6,700円 下がれば条件を満たします

**マイナスの上限額を0円に丸めない。** マイナスは「いくら下がっても条件を満たさない」という意味で、
0円に丸めると「0円なら買える」と読めてしまう。

手数料が1つでも欠けていれば、利益も上限額も**出さない**。
「たぶん10%くらい」で埋めた瞬間に、この数字は根拠を失う。

## 10. BUY判定 v0（§13・§14）

> 「まだAIモデルは作らず、**透明なRule Base**で構いません。」
> 「**『売れるから買う』は禁止。**」

判定は4段階を上から順に通る。どこで止まったかを必ず残す。

```
① 同じ商品か（MATCH）
② 売れているか（SELLABILITY）※データの新しさも先に見る
③ 利益が出るか（PROFITABILITY）
④ 危ないところ（RISK）
```

出口は4つ：**BUY / WATCH / REVIEW / SKIP**。

- 判定にAIモデルも乱数も使っていない。人が理由を全部たどれる。
- しきい値は**すべて設定から変更できる**（`SUPPLIER_ROUTE_*`）。
- 赤字・利益不足は、上限額との差が `SUPPLIER_ROUTE_WATCH_MAX_GAP`（既定20,000円）以内なら
  **消さずに WATCH**（値下がり待ち）、それより遠ければ SKIP。

### 即SKIPにしないもの（§15・§16）

> 「**即SKIPにはしないでください。**」（需要の食い違い）
> 「**即SKIPにはまだしない。**」（Amazon本体）

- 需要の手がかりが食い違っている → 「弱い」として扱い、**WATCH**（見送らない）
- Amazon本体がカートを取っている → **WATCH**（見送らない）
- Amazon本体が出品しているだけ → BUY を止めない
- 本体の有無が分からない → `UNKNOWN`（「いない」にしない）

## 11. ファネルと脱落理由（§22・§23・§24）

### 6工程

仕入候補 → ASIN候補あり → 一致が高い → Amazonデータあり → 利益が計算できた → BUY/WATCH

**人数は途中で増えない。** 増える作りにすると KPI が100%を超えて、数字そのものが信用できなくなる。

### 落ちた理由10分類

NO_ASIN / MULTIPLE_ASIN / LOW_MATCH / AMAZON_DATA_MISSING / DEMAND_UNKNOWN /
FEE_UNKNOWN / LOSS_MAKING / ROI_TOO_LOW / STALE_DATA / SUPPLIER_URL_MISSING

**書き分けが目的**である。同じ「人が確かめてください」でも：

- 候補0件 → Amazon側に見つからない（仕入先データにバーコードを足す話）
- 候補1件 → 確からしさが足りない（型番・色・入数を足す話）
- 候補2件以上 → どれか1つに決められない（見分ける材料を足す話）

で、次にやることが全部違う。全部「候補が複数」と書くと §23 の分類が意味を失う。

### 最重要4KPI

1. 仕入先 → 同じ商品にたどり着けた割合
2. 一致 → Amazonデータがそろった割合
3. データ → 利益が計算できた割合
4. 利益が出る → BUY/WATCH になった割合

**分母が0のときは 0% と書かず、空欄にして「まだ1件も通っていません」と出す**（ルール115）。

## 14. 事故と対策：見本データが本物の候補に混ざった

**実装後、画面で初めて見つかった。** 受け入れテストでは見つからなかった。

### 何が起きたか

仕組みを確かめるために入れた見本データが、`is_sample` の印を付けずに保存されていた。
結果、**仮の仕入価格から出た利益額が、本物の仕入候補と同じ表に並んだ**。
根拠のない金額を見て人が現金を出す、というこのシステムでいちばん避けたい形である。

### 3つの直し方

1. **中身から見本を見分ける**（`looksLikeSampleRow`）
   仕入先名・商品番号・商品名・ブランド・URL に見本の印（SAMPLE / テスト / サンプル 等）が
   含まれていたら、指定が無くても見本として取り込む。
   **向きは片方だけ。** 印があれば見本へ上げるが、印が無いことを理由に「本物だ」と下げない。
   間違える方向を、必ず**候補から外れる側**に固定した。
   直したことは黙らず「見本として入れました」と画面に出す（黙って直すと、次も同じ付け忘れをする）。

2. **判断の記録も見本を外す**（`saveOfferRoute`）
   候補（`saveOfferMatchCandidates`）は最初から見本を外していたのに、
   **判断だけ残していた**。片側だけ守っても意味がない。両側そろえた。

3. **データの手当て**
   見本だった4行に `is_sample = 1` を立て、そこから作られた
   **ルート判断4件とASIN候補3件を削除**した。
   **Keepaで取得済みの100件には一切手を触れていない**（§31）。

### 学び

- 「テストが全部通る」は「画面が正しい」を意味しない。**必ず画面を見る。**
- 印を付け忘れる事故は必ず起きる。**付け忘れても安全な側に倒れる作り**にする。
