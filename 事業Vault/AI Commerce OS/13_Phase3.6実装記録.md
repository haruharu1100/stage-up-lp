## 0. 一番大事なこと（ここだけ読むなら）

**Phase 3.6 は「メルカリの本物の出品を100件、初回→24時間→3日→7日→14日→30日と見届けるための入れ物」を作った工程。**
まだ1件も集めていない。作ったのは器であって、成果ではない。

この工程で守った約束は3つ。すべてユーザー指示そのまま。

1. **「ページが消えた＝売れた」にしない。**
2. **いくらで売れたかを推測しない。** 確認できなければ「不明」と出す。0円とも出品価格とも書かない。
3. **同じURLを見るたび、上書きせず新しい行を積む。**

そして最重要（§23）：
**購入・出品・決済・発送・自動ログイン・無許可スクレイピングは1行も書いていない。**
フラグでOFFにしているのではなく、処理そのものが存在しない。

## 1. ユーザーによる考え方の訂正（これが今回の起点）

Phase 3.5 の報告で、私（AI）は手動観測CSVのことを
**「CSV連携だから規約上いちばん安全な方法」** と書いた。

ユーザーからの訂正：

> 自分で公開画面を見て必要な情報を手動記録することと、事業者から正式に提供されたCSVデータフィードは別物なので、
> システム上も `MANUAL_OBSERVATION` と `OFFICIAL_CSV_FEED` は分離しておいた方がいいです。

**これは正しい。CSVという「ファイルの形」は、法的な立場の説明にならない。**
ファイル形式はこちらの都合であって、相手がデータを提供している事実ではない。

### コードへの反映

- `lib/realdata.ts` の `SourceClass` を、ファイル形式ではなく**立場**で3分類。
  - `PROVIDED_BY_VENUE`（事業者から正式に提供された）
  - `SELF_OBSERVED`（自分で公開画面を見て書き写した）
  - `NOT_REAL`（テスト・サンプル）
- `SELF_OBSERVED` のときは必ず注意文（`SELF_OBSERVED_CAUTION`）を画面に出す。黙って通さない。
- **`lib/venues.ts` の `csv_available` を全12市場 `1` → `0` に訂正した。**
  以前は「CSVファイルとして取り込めるから1」にしていたが、これが上の誤りそのもの。
  **正式なCSV提供が確認できている市場は、現時点で1つも無い。**
  確認できた市場だけ、出典を書いたうえで1にする。推測で1にしない。
- 既存DBの行も `UPDATE venues SET csv_available = 0` で揃えた（seedは既存行を上書きしないため）。

## 2. メルカリを第1実市場に固定した理由（§1 §2）

**理由は1つだけ：販売手数料が公式ページに明記されているから。**
「売れそうだから」でも「商品が多いから」でもない。**数字の根拠を確認できるかで選んだ。**

### 確認した事実（2026-08-20）

| 項目 | 値 | 出典 |
|---|---|---|
| 販売手数料 | 販売価格の **10%** | [メルカリの手数料 - メルカリ](https://help.jp.mercari.com/guide/articles/65/) |
| 端数 | 切り捨て（999円 → 99円） | 同上 |
| 売上振込手数料 | 一律 **200円** | 同上 |

`venue_fee_profiles` の MERCARI / SELL を
`SELL_FEE_RATE=10%` `STATUS=VERIFIED` `SOURCE_TYPE=OFFICIAL` `VERIFIED_AT=2026-08-20` 出典URL付きで登録した。

### 送料を勝手に確定しなかった（§2 後段）

ユーザー指示：「送料等は商品・発送方法で異なるため、一律固定値として勝手に確定しないでください。」

そこで **手数料の項目を1つずつ検証する仕組み**にした（Phase 3.6 で追加）。

- `VENUE_RATE_FIELDS`（市場が決めている率。公式ページで確認できる）→ `VERIFIED` にできる
- `ITEM_COST_FIELDS`（送料・梱包費など商品ごとに変わる）→ **推定のまま据え置く**
- 率だけ確認済みで原価が推定の状態は `FEE_CONFIDENCE_CAP_COST_ESTIMATED = 85`。
  **つまり STRONG BUY(90点) には構造上届かない。** 送料が推定のままなら自動で強気にならない。

**手数料の実額確認は 18件中 1件（5.6%）。** メルカリのSELLだけ。残り17件は推定のまま。

## 3. 作ったもの（§3〜§9）

### 3-1. テーブル3つ（`lib/db/schema.ts` の `SCHEMA_OBSERVATION`）

| テーブル | 役割 | 上書き |
|---|---|---|
| `tracked_listings` | 追いかけている出品1件につき1行（最新の状態） | する |
| `listing_observations` | **観測するたびに積む記録** | **絶対にしない** |
| `observation_work_log` | 人間の作業時間 | しない |

**なぜ相場テーブル（`venue_market_prices`）と別なのか。**
相場テーブルの主語は「この商品の相場は10万円」。
今回知りたいのは「2026-08-20 に 105,000円 で出ていた**この1件**が、7日後どうなったか」。
主語が違うので、同じ表に入れてはいけない。

### 3-2. 同じ出品を同じものと数える鍵

`listing_key` = URLの `ホスト名 + パス`（末尾スラッシュは落とす、クエリは捨てる）。
広告用パラメータ（`?afid=...`）が付いただけで別物になると、追跡が途切れるため。

### 3-3. 二重取り込みの防止

`listing_observations` に `UNIQUE(listing_key, observed_at)` ＋ `ON CONFLICT DO NOTHING`。
**同じCSVを2回取り込んでも観測回数は増えない。**
ただし確認日時が違えば必ず新しい行が積まれる（上書きではない）。

### 3-4. 状態は5つだけ（§8）

| 状態 | 画面の日本語 |
|---|---|
| `ACTIVE` | まだ出品中 |
| `CONFIRMED_SOLD` | 売り切れを実際に確認した |
| `REMOVED_UNKNOWN` | ページが見当たらない（売れたかどうかは不明） |
| `PRICE_CHANGED` | 出品中だが価格が変わった |
| `UNKNOWN` | 確認できていない |

**`SOLD_PROBABLY` のような「たぶん」を作らなかった。** 観測できないものを状態にしない。

言葉の対応表（`STATE_WORDS`）で、
**「削除」「消えた」「見つからない」「404」「非公開」「取り下げ」は全部 `REMOVED_UNKNOWN` に落ちる。**
売り切れ側に入るのは「売り切れ」「完売」「sold」など、**画面でその表示を実際に見たときの言葉だけ**。

読み取れない言葉が書いてあったら `parseListingState()` は `null` を返す。**近い方に寄せない。**

### 3-5. 売れた値段（§9）

- `sold_price` が書いてあっても、**状態が `CONFIRMED_SOLD` でなければ採用しない。**
  採用しなかったことは警告として画面に出す（黙って捨てない）。
- 売り切れは確認できたが値段が分からない場合は `sold_price_known = 0`。
  画面には **「不明」** と出る。**出品価格で代用しない。**
- 追跡で上書きするときも `COALESCE(actual_sold_price, ?)` と `MAX(sold_price_known, ?)`。
  **一度判明した値段を、あとの観測で消せないようにしてある。**

### 3-6. 価格が変わったときだけ導出する

前回の観測価格と今回の観測価格が違えば `PRICE_CHANGED` にする。
これは推測ではない。**両方とも人が実際に見た数字**なので、差を取っているだけ。
導出したことは `state_source = 'DERIVED_PRICE_DIFF'` として必ず残す。

### 3-7. 追跡の予定（§6）

初回 → 24時間後 → 3日後 → 7日後 → 14日後 → 30日後（0/24/72/168/336/720時間）。
ちょうどの時刻に見られるわけがないので許容幅を持たせた（7日目なら±36時間）。
どの予定にも当てはまらない観測は `EXTRA` として**捨てずに残す**。

`npm run validation` と `/validation` 画面に「そろそろ確認する時期のもの」が出る。
すでに `CONFIRMED_SOLD` のものは追跡対象から外れる（もう見る必要がない）。

## 4. CSV仕様（§3 §4）

### 列（1行目の見出し）

```
確認日時,市場,商品名,ブランド,カテゴリ,型番,JAN,SKU,サイズ,色,状態,
出品価格,送料込み,出品者,商品URL,販売状況,成約価格,成約日,備考,入力秒数
```

英語の見出し（`observed_at`, `product_url` …）でも受け付ける。表記ゆれも吸収する。

### 必須項目は「初回」と「2回目以降」で変える（§4）

| | 必須 |
|---|---|
| 初回（そのURLが未登録） | 商品URL / 確認日時 / 商品名 / 出品価格 / 状態 |
| 2回目以降 | 商品URL / 確認日時 / 販売状況 |

**追跡のたびに商品名を書き写させるのは、ただの苦行で、間違いも増える。**

### 分からない項目は空欄（§3）

ユーザー指示：「分からない項目は空欄で構いません。推測禁止です。」
だから**記入見本もわざと空欄だらけにしてある**。全部埋まった見本を出すと「埋めなければ」と思わせてしまう。

### 市場コードが空欄ならメルカリ、知らないコードなら止める

§1でメルカリに固定しているので空欄は `MERCARI` 扱い。
ただし**登録されていない市場コードが書いてあったら、黙って直さずその行を弾く。**

## 5. 実データとテストデータを混ぜない仕組み（§5）

**ダッシュボードの実績値には `real_market_data = 1` の行しか使わない。**

`judgeRealMarketData()` が Fail Closed で判定する。
URLや備考に `TEST` / `SAMPLE` / `ダミー` / `記入例` などの印があれば **実市場データにしない**。

### ここで自分の設計ミスを見つけて直した

画面の入力欄には記入見本が最初から入っている。
最初、見本のURLを `m00000000001` にして備考を空にしていた。
**この状態でうっかり「取込」を押すと、架空の3件が実市場データ100件に混ざる。**

直した内容：
- 見本のURLを `mSAMPLE0000001` / `mSAMPLE0000002` に変更
- 備考をすべて「記入例（サンプル）」で始める
- **「画面の記入例をそのまま取り込んでも実市場データにはしない」という受け入れテストを追加**（再発防止）

受け入れテスト自身も、テスト用の行を `mACCEPT…` というURLで入れ、**最後に必ず消して、実績件数が元に戻ることを検査**している。
（`TEST` や `SAMPLE` を含むURLにすると実データ判定を素通りしてしまい、肝心の経路を試したことにならないため、あえて別の印にしてある。）

## 6. 人間の作業時間（§19 §20）

工程を5つに絞った。細かくしすぎると計測自体が面倒になって続かない。

`FIND`（商品を探す）／ `IDENTIFY`（同じ商品かを確かめる）／ `RECORD`（数字を書き写す）／
`IMPORT`（取り込む）／ `VERIFY`（結果を見て確かめる）

- CSVに「入力秒数」列があれば、取込時に自動で `RECORD` として記録する
- 画面のフォームから工程ごとに手入力もできる
- 集計すると「1件あたり何秒」「100件までおよそ何時間」「一番時間を食っている工程」が出る

**まだ1件も計測していないので、画面には**
**「まだ作業時間を1件も計測していません。どの工程を自動化すべきかは、まだ数字で言えません。」**
**と出る。** 感覚で「ここが大変そう」とは書かない（§20）。

## 7. 画面とコマンド（§14 §16）

### `/validation`（REAL MARKET VALIDATION）

大きく出しているもの：
集めた出品 `0 / 100` ／ メルカリの販売手数料「確認済み（実額）」 ／
7日後まで見届けた `0件` ／ 30日後まで見届けた `0件` ／ STRONG BUY の的中率「**測定不能**」

さらに、状態の内訳・そろそろ確認する時期のもの・取込フォーム・追跡中の一覧・
作業時間・手数料の確認状況、そして
**「これは自分で公開画面を見て記録したデータであって、事業者から提供されたものではない」** という注記。

### `npm run validation`

同じ数字を端末でも出す。**数字を良く見せる加工は一切しない。0件なら0件と出す。**

§16 の比較（理論値 RAW / 補正後 CALIBRATED / 保守 CONSERVATIVE のどれが実績に近かったか）も出すが、
実市場データで答え合わせが済んだものが0件なので
**「まだ比べられません」** と表示する。**近そうな方を選んで書かない。**

### §15 の歯止め

画面にもコマンドにも常時この2行を出している。

- 100件そろっても、それだけでは購入しない。必ず14項目の卒業条件で判定する。
- 購入・出品・決済・発送・自動ログインの処理は、このシステムに存在しない。

## 9. 失敗と対処（次のAIが同じ穴に落ちないように）

### 失敗1：記入見本が実データを汚すところだった
→ 5章のとおり。**画面に最初から入っている文字列は、必ず「取り込まれる可能性がある」と考える。**
受け入れテストで再発防止済み。

### 失敗2：`csv_available` を全市場1にしていた
→ 「CSVで取り込める」を「CSVを提供されている」と書いてしまっていた。全市場0に訂正。
**こちらの都合を、相手の事実として書かない。**

### 失敗3：画面がビルドできなくなった
症状：`node:path` が読めない、というビルドエラー。
原因：ブラウザ側の部品（`WorkTimeForm.tsx`）が `lib/observation.ts` を読み、
そこからデータベース層まで引きずられた。

対処：**言葉の定義だけを `lib/listing.ts` に切り出した**（外部依存ゼロ）。
状態名・日本語訳・追跡予定・工程名・記入見本はここに置く。
`lib/observation.ts` はそこから再輸出しているので、呼び出し側の書き方は変えていない。

**これは `lib/conditions.ts` と `lib/normalize.ts` の関係とまったく同じ話。**
すでに1度やった失敗を、別の場所で繰り返した。
→ **画面から読むファイルには `node:` で始まる読み込みを絶対に混ぜない。**

### 失敗4（過去分の再掲・忘れない）
`GateResult` に `total` は無い（`passedCount` / `totalCount` / `verdictJa`）。
`assertNoExecutionPath()` の戻りは `message`（`detail` ではない）。

## 10. 受け入れテスト

```
npm run test:phase1     66件
npm run test:phase2     50件
npm run test:phase3    113件
npm run test:phase3-5  112件
npm run test:phase3-6  107件   ← Phase 3.6 で 55件 → 107件に増やした
                       合計 448件・不合格 0件
```

**仕様を変えたら5つとも通す。1つだけ通して満足しない。**
`npm run build` も通す（3で書いたビルドエラーは、テストだけでは見つからなかった）。

Phase 3.6 で足した主な検査：
- 「消えた」系の言葉が絶対に `CONFIRMED_SOLD` にならない
- 状態が `CONFIRMED_SOLD` でなければ成約価格を採用しない
- 同じCSVを2回取り込んでも観測が二重にならない
- 一度判明した成約価格が、あとの観測で消えない
- 画面の記入例をそのまま取り込んでも実市場データにならない
- 受け入れテストのデータを実績に残していない

## 11. まだできていないこと（正直な残り）

- **本物の100件がまだ0件。** 器はできたが中身が無い。ここからは人が画面を見て記録する作業。
- §16の比較（RAW/CALIBRATED/CONSERVATIVE vs 実績）は端末（`npm run validation`）には出るが、**画面には出していない。**
- §18（100→500→1,000→10,000件）は設計上は増やせるが、**大量件数での動作は確認していない。**
- 手数料の実額確認が **1/18件**。メルカリ以外は推定のまま。

## 12. 次に入るAIへの申し送り

1. **§21：メルカリ100件が安定するまで、次の市場を同時に追加しない。** 市場を増やす方が楽しいが、増やすと何も検証できない。
2. **「消えた＝売れた」に触らない。** ここを緩めると、このシステムが集めるデータは全部無意味になる。
3. **成約価格を出品価格で埋めない。** 「不明」は不良品ではなく正しい記録。
4. **記入見本・テストデータが実績に混ざっていないか、必ず確認する。**
5. **画面から読むファイルに `node:` の読み込みを混ぜない**（`lib/listing.ts` を使う）。
6. **5つのテストと `npm run build` を全部通す。**
7. 購入・出品・決済・発送・自動ログイン・無許可スクレイピングは**コードごと書かない**。人の明示指示があるまで着手しない。
8. **報告のタイミングは3つだけ**（§22）：A 100件登録完了／B 重大な問題発生／C 正規のデータ取得方法が見つかった。
