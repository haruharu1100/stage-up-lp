## 0. 30秒サマリー（先に結論）

**作るもの**：仕入先を見張り、同じ商品を別の市場から探し、本当に売れるかを確かめ、手数料まで引いた「本当の利益」で仕入れを判断し、売って、学習する会社の頭脳。

**最初の想定（KOMEHYO仕入 → スニダン販売）は、調査の結果そのままでは成立しない。**

| 論点 | 調査でわかった事実 | 影響 |
|---|---|---|
| スニダンで売る | **スニダンBizの「法人販売（出品）プラン」は新規申込を停止中** | 「スニダンに自動出品」は現時点で入口が閉じている |
| スニダンで買う | 「法人購入（仕入）プラン」は受付中。ただし**年商1億円以上が目安・月200万円以上購入・古物商必須** | 現状の事業規模では審査が通らない可能性が高い |
| KOMEHYOで買う | **KOMEHYOオークション（BtoB）は古物商があれば法人／個人事業主で参加可能・月3,000円・月4回開催** | 仕入口としては現実的。ただし「オークション」なので固定価格ではない |
| 古物商 | 既に保有（Lila Flow・62208R087012号） | 仕入の法的前提はクリア。ただし名義の整合は要確認 |

→ 詳細と一次情報リンクは [[02_Phase0_外部連携調査]]。

**したがって v1 の設計方針は「特定2サイト前提を捨てる」こと。**
仕入先・販売先を **Connector（差し替え可能な接続部品）** として完全に外出しし、
**中核（同一商品判定・利益計算・売却確率・スコア・資金配分・学習）だけを先に完成させる。**
接続先は契約が取れた順に差し込む。これなら「スニダンが開かない」でシステム全体が止まらない。

**v1.3 でさらに一歩進めた。**
仕入先／販売先という区別そのものを捨て、すべてを **VENUE（市場）** に統合した。
同じ市場が、安ければ買う場所に、高く売れるなら売る場所になる。
スニダンは「売れないから対象外」ではなく、**「計算はするが実行できない市場」**として扱い、
いくら取り逃しているかを画面に出す（→ §4.13）。

## 1. このシステムの目的（誤解しやすいので最初に）

目的は「価格比較ツール」でも「スクレイピングツール」でもない。

目的は、次を一本につないだ **「AIによる物販経営システム」**。

```
                    ┌──── 勝ち筋拡張ループ（売れた商品から次を探す）────┐
                    ↓                                                  │
商品発見 → 市場調査 → 同一商品特定 → 利益計算 → 仕入判断 → 購入          │
  → 出品 → 在庫管理 → 値付け → 販売 → 発送 → 利益分析 → 再仕入れ → 学習 ─┤
      ↑                              │                                 │
      └──────────────────────────────┴── 価格弾力性ループ（+5%テスト）──┘
```

「何を買うか」だけでなく **「いくら買うか」「どこで売るか」「いくらで売るか」「いつ諦めるか」「次に何を探すか」** までAIが判断する。

### これは「数個見つけて終わり」のツールではない（v1.1で明確化）

**条件を満たす商品を、24時間ひたすら発見・登録・販売候補化し続ける**構造にする。
人間が1商品ずつ登録するのではなく、**AIが毎日数百〜数千件の候補を自動生成する**。

```
仕入先を監視 → 新商品発見 → 同一商品調査 → 利益判定 → 販売候補作成 → 次の商品 → 次の商品 → …
```

同時に、次の3つの自己成長ループを回す。

| ループ | 内容 | 詳細 |
|---|---|---|
| **① 大量生成ループ** | 仕入先を増やし、候補商品を大量に作り続ける | [[06_商品大量生成とパイプライン]] |
| **② 価格弾力性ループ** | 売れたら+5%して、最も儲かる価格を見つける | [[07_価格戦略設計]] |
| **③ 勝ち筋拡張ループ** | 売れた商品から同シリーズ・類似商品を追加探索する | [[08_仕入先ネットワークと勝ち筋拡張]] |

> [!danger] 大量生成しても品質は落とさない
> 商品数を増やすために同一商品判定を甘くすることは **禁止**。
> 自信が無い商品は大量生成せず `MANUAL_REVIEW` へ送る。**数より正確性が常に上。**

人間の役割を **「商品を探す人」から「AI会社を監督する人」** へ変える。

### 成功の定義／失敗の定義

> [!warning] 次はすべて「失敗」と判断する
> - ❌ **利益率は高いが1年売れ残る**（資金が死ぬ）
> - ❌ **すぐ売れるが手数料込みで赤字**（回せば回すほど減る）
> - ❌ **AI予測は当たったが、そもそも買えていない**（機会損失）
> - ❌ **一番高い価格で売れたが、月に1個しか売れない**（v1.1追加）
> - ❌ **候補を大量生成したが、誤マッチだらけで使えない**（v1.1追加）
>
> ✅ 正解は **CAPITAL EFFICIENCY MODE** ＝「資金拘束日数あたりの純利益が最大」の状態。
> 最重要指標は 利益率でも売上でも**販売価格の高さ**でもなく、
> **月次 ROIC（投下資金あたり純利益）** と **在庫回転日数**。

> [!important] 目指すのは「最大価格」ではなく「最大利益」
> ```
> 120,000円 × 月1個 × 利益30,000円 = 月利益 30,000円
> 105,000円 × 月4個 × 利益18,000円 = 月利益 72,000円  ← AIはこちらを選ぶ
> ```
> 最大化する対象は **利益 × 販売数 × 在庫回転率**。詳細は [[07_価格戦略設計]]。

### 最重要開発原則（これより上位のルールは無い）

```
正確性 > 安全性 > 利益 > 自動化率 > 商品数
```

**商品数を増やすために正確性を落とさない。** 判定に自信が無ければ、作らずに `MANUAL_REVIEW` へ送る。

金銭を伴う処理は必ず次の3原則（**Fail Closed**）に従う。

1. **分からないなら買わない**
2. **データがおかしいなら止まる**
3. **APIがおかしいなら止まる**

最初から自動化率100%を目指さない。誤判断で大量購入するシステムには絶対にしない。

## 2. 絶対に崩してはいけない安全ルール（法務・規約）

機能追加よりも上位。どんな改善指示よりも優先する。

1. **各サイトを無断で自動操作しない。** 優先順位は
   ① 公式API ② 法人向けAPI ③ 正式データフィード ④ CSV連携 ⑤ Webhook ⑥ 正式な法人販売機能 ⑦ 規約上認められた方法。
   これらが無い接続先では、機能を落として `CONNECTOR_NOT_AVAILABLE` を返す。**代わりに勝手にスクレイピングで埋めない。**
2. **自動購入・自動出品が規約上認められていない販路では、その自動フラグを強制的にfalseへ固定する。**
   環境変数でtrueにしても、Connectorのcapabilityが `api` でなければ実行層が拒否する（設定ミスで事故らせない）。
3. **古物営業法を守る。** ブランド中古の仕入・販売は古物商許可の範囲内で行う。仕入先ごとに取引記録（相手方・日時・品目・特徴）を保存できる構造にする（→ `purchase_orders` / `audit_logs`）。
4. **虚偽・誇大な商品説明を生成しない。** 状態説明はAIが盛らない。「新品同様」「未使用に近い」等の判定は元データの状態表記を超えない。
5. **景表法を守る。** 二重価格・根拠のない「最安」「必ず儲かる」等の表現を商品ページに出さない（→ DIGESTの表現規制ルールに従う）。
6. **偽物を売らない。** 真贋リスク（`AUTHENTICITY_RISK`）が閾値を超える商品は FULL AUTO 購入を禁止する。
7. **APIキー・ログイン情報・決済情報をコードに書かない。** Secrets管理のみ。
8. **LLMを勝手に再学習しない。** 精度は履歴DB・評価ロジック・統計・RAGで上げる。
9. **`COMMERCE_AUTO_MODE=SAFE` が既定。** 明示的に変更しない限り、金銭を伴う処理は1件も実行しない。

## 3. 構想の整理（自分の言葉で）

このシステムは、次の3つの層でできている。

### 層1：世界を見る（Perception）
仕入先と販売先から、商品と価格と売れ行きを取り込み、**バラバラのデータを1つの共通形式に揃える**。
ここの品質が全部を決める。同じ商品を同じ商品だと分からなければ、以降の計算はすべて無意味。

### 層2：判断する（Judgement）
揃ったデータから **「本当に儲かるか」を、手数料・送料・返品・保管・資金拘束まで含めて計算**し、
**「本当に売れるか」を確率で出し**、その2つを合わせて **仕入スコア** を出す。
さらに、限られた資金をどう配分するかを決める。

### 層3：手を動かす（Action）
判断結果に従って、買う・出す・値を変える・送る・諦める。
**この層だけが金銭を動かす**ので、ここに全ての安全装置（承認・上限・冪等性・緊急停止）を集中させる。

そして、実績を層2へ返して学習させる。これが循環。

> [!important] 設計上いちばん大事な分離
> **層1・層2は外部サービスが無くても動く。層3だけが外部サービスに依存する。**
> だから接続先が1つも契約できていない状態でも、SHADOW MODE で層1・層2を鍛え続けられる。
> これが「スニダンが開かなくても開発が止まらない」ための構造。

## 4. 必要機能一覧

- [ ] ブランド名・型番・カラー・サイズの表記ゆれ正規化辞書
- [ ] 取得データの鮮度管理（何時点のデータかを必ず保持。古いデータで買わない）

### 4.2 同一商品判定
- [ ] 決定的キー照合（JAN / GTIN / SKU / 型番）
- [ ] テキスト類似（ブランド・商品名・カラー・サイズ・年式・素材）

### 4.3 市場調査
- [ ] 販路別の価格分布（現在・最安・平均・中央値）
- [ ] 過去成約価格と成約件数（売れた実績＝需要の証拠）
- [ ] 出品数・競合数
- [ ] 売却速度（成約までの日数分布）

### 4.6 判断

### 4.13 全市場双方向アービトラージ（v1.3追加・**Phase 2で実装済**）

> [!danger] この節は v1.1 までの「仕入先 → 販売先」という前提を **置き換える**
> 市場を「仕入先」と「販売先」に固定しない。**同じ市場が、安ければ仕入先／高く売れるなら販売先の両方になる。**
> 「スニダンで買ってメルカリで売る」も「メルカリで買ってスニダンで売る」も、どちらも計算対象。
> **方向という概念を持たない。**

- [x] **VENUE（市場）** を1つの概念に統合。`can_buy` / `can_sell` を市場ごとに持つ
- [x] すべての市場 × すべての市場を総当たりで比較（同一市場内の自己売買は除外）
- [x] **BUY COST と SELL COST を完全に分離**（→ §11.7）
- [x] 手数料は市場ごと × BUY/SELL別。**一律◯%は禁止**（→ §11.8）
- [x] **ARBITRAGE_ROUTE** を第一級のデータとして保存（→ §11.9）
- [x] **ROUTE SCORE**（利益 × 売却確率 × 資金回転 × リスク）で最適Routeを選ぶ
- [x] 商品詳細に **BEST ROUTE** を表示（→ §10）
- [x] **Reverse Arbitrage**（逆方向）を必須計算
- [x] **Market Matrix**（仕入↓ × 販売→ の期待ROI一覧）
- [x] **Route Performance Analytics**（Routeランキング・Routeごとの得意商品）
- [x] **LIQUIDITY SCORE** / **CAPITAL VELOCITY** / **EXPECTED_30D_RETURN**
- [x] **Route Shadow Trading**（実購入なしで全Routeを記録し、後で答え合わせ）
- [x] 「今日この予算を使うなら」の市場をまたいだ資金配分（→ §11.10）
- [ ] **Triangle Arbitrage**（A買→B売→B買→C売）は Phase 3 以降。データ構造だけ拡張可能にしてある
- [ ] クロスリスティング（同じ在庫を複数市場へ同時出品）は **別概念**。Phase 4 で実装

**正式機能名**：Multi-Venue Engine / Bidirectional Arbitrage / Reverse Arbitrage / Arbitrage Route /
Route Scoring / Route Shadow Trading / Market Matrix / Route Performance Analytics /
Liquidity Score / Capital Velocity / Buy-Sell Fee Separation / Venue Capability Management

#### 「できる」と「してよい」は別の欄で持つ（v1.3で確立した原則）

| 欄 | 意味 | 例 |
|---|---|---|
| `can_buy` / `can_sell` | **市場の構造**として売買機能があるか | スニダンは出品機能を持つ → `can_sell = 1` |
| `terms_status` / `automation_permission` | **いま我々に使う許可があるか** | 法人出品プランが新規停止中 → `BLOCKED` / `NOT_ALLOWED` |

`can_sell = 0` にして消すと「本当は一番儲かるはずの販売先」が画面から消え、
**取り逃していること自体が見えなくなる。** だから計算はする。実行だけを止める。

#### 取り逃しをでっちあげない（v1.3で確立した原則）

使えない市場について、**実データが無いのに参考相場を当てはめて「◯◯円の取り逃し」と表示してはいけない。**
実際の相場観測がある市場だけ、取り逃し額を出す。無いものは「データなし」と書く。
（景表法の観点でも、根拠のない機会損失額を自分の判断材料にしない）

### 4.14 在庫の所有状態（v1.3追加）

`ownership_state` を商品ごとに持つ。

| 値 | 意味 |
|---|---|
| `NOT_OWNED` | まだ持っていない（Phase 2 は全件これ） |
| `PURCHASED_NOT_RECEIVED` | 買ったが手元に無い |
| `IN_STOCK` | 手元にある |
| `DROPSHIP_CANDIDATE` | 所有せず販売する候補 |

> [!danger] 所有していない商品を先に売る処理
> **販売先・仕入先の双方の規約で明確に許可されている場合のみ可能。**
> 不明なら `MANUAL_ONLY`。Phase 2 では実装していない。

### 4.15 SHADOW学習と答え合わせ（v1.4追加・**Phase 3で実装済**）

目的はひとつ。**「AIが買うと判断した商品が、本当にその後利益になったのか」を自分に都合よくごまかさずに測ること。**
実装の詳細・実測値・つまずきは [[11_Phase3実装記録]]。ここには**崩してはいけない原則だけ**を書く。

#### 判断は凍結する

`route_shadow_trades` / `shadow_market_snapshots` / `shadow_evaluations` への INSERT は
**すべて `ON CONFLICT DO NOTHING`。`DO UPDATE` を書いてはいけない。**
後から現在値で上書きすると、常に自分が正しかったことになり学習が成立しない。

判断時に凍結する項目：仕入価格・総取得原価・想定販売価格・想定手取り・想定純利益・想定ROI・
Route Score・流動性スコア・想定販売日数・7/30/90日の売却確率・
相場データ信頼度・手数料データ信頼度・同一商品判定の信頼度・BUY/SELLの手数料版。

#### 相場は「その時の全部」を保存する

現在値だけ見ても答え合わせにならない。BUY側とSELL側を**別レコード**（`role` 列）で持ち、
最安値・中央値・平均値・出品件数・30日成約件数・平均販売日数・価格ばらつき・
取得元・観測時刻・データ経過時間まで保存する。

観測できなかったら `NO_OBSERVATION` と記録する。**参考値で埋めない。**

#### 「売れた」と数える条件（Phase 3 の核心）

次を**すべて**満たさない限り `SOLD` と言わない。

1. 観測データが存在する ／ 2. `observed_at` がある ／ 3. 観測時刻が判断時刻より後
4. `price_basis === 'SOLD_MEDIAN'`（成約価格。出品価格は不可）
5. `sold_count_30d >= 1` ／ 6. `avg_days_to_sell` がある

出品価格しか取れない市場は `ACTUAL_SALE_UNCONFIRMED`。
**勝ちにも負けにもしない。** 無理に勝敗を決めると勝率がただの願望になる。

データの優先順位：**実際の成約/SOLDデータ > 販売履歴 > APIの成約データ > 信頼できる市場統計**。

#### 実績によるスコア補正は件数で強さを変える

| 実績件数 | 段階 | 重み |
|---|---|---|
| 5件未満 | NONE | 0.0（補正しない） |
| 5〜19件 | WEAK | 0.3 |
| 20〜49件 | MID | 0.6 |
| 50件以上 | FULL | 1.0 |

補正幅は上下 **±10点まで**（`MAX_SCORE_ADJUSTMENT`）。
3件外しただけで市場を切り捨てない。**少ない実績で点数を動かさない。**

#### 利益が大きくてもデータが悪ければ最優先で買わない

`combineConfidence(相場, 手数料, 同一商品)` → `overall = 一番弱いもの×0.5 + 平均×0.5`。
**一番弱い項目が判定の上限も決める。** 止め方は2種類あり、混同しないこと。

- 手数料が**概算**：データ信頼度が下がるので**そもそも90点に届かない** → `STRONG_BUY` にならない
- 同一商品と確認できていない：**90点近くまで出ていても蓋をして** `WATCH` へ落とす（`confidenceCapped`）

#### 手数料は「いつ・どこで確認したか」まで持つ

`source_url` / `source_type` / `verified_at` / `effective_from` / `effective_to` /
`is_estimated` / `manually_verified_by` / `fee_version` を持つ。
`fee_version` は `f{E|V}-{ハッシュ8桁}`（`E`=概算 / `V`=確認済み）。
**金額に影響する14項目だけ**をハッシュに含める。

手数料が変わったら `fee_change_log` に記録するだけ。
**旧料金で過去利益を再計算してはいけない。取引時点の Fee Version を保持する。**
再計算すると「当時いくらの利益を見込んで買うと決めたのか」が消え、答え合わせが嘘になる。

概算のままの手数料は `/venues` 画面で赤帯＋一覧の最上部に出す。奥に隠すと「確認したつもり」で使い続ける。

#### 利益機会の寿命

`first_seen_at` / `best_seen_at` / `last_profitable_at` / `expired_at` を記録し、
**Opportunity Speed Score（0〜100）** を出す。90以上なら「非常に短時間で消える価格差」。
価格差の発生原因（`cause_class`）も記録する。

## 6. AI構成（どのAIに何をさせるか）

**AI Provider は交換可能にする。特定AIに強く依存しない。**

| 役割 | 担当 | 内容 | LLM必須か |
|---|---|---|---|
| 開発・システム管理 | Claude Code | 設計・実装・改修・仕様統合 | — |
| コードレビュー・テスト | Codex | 実装差分のレビュー、テスト生成 | — |
| **Matcher（同一商品判定）** | OpenAI（画像＋テキスト） | 画像照合・属性照合の最終判定 | 部分的（決定キー一致時はLLM不要） |
| **Analyst（市場解釈）** | Claude | 相場の異常・トレンドの言語化 | はい |
| **Judge（仕入判断の説明）** | Claude | BUY_SCOREの根拠を自然文で説明 | はい |
| **Copywriter（商品ページ）** | Claude | タイトル・説明・属性の生成（誇大禁止） | はい |
| **Advisor（自然言語質問）** | Claude | 自社DBを読んで経営質問に回答 | はい |
| **Scorer（点数計算）** | ロジック（LLM無し） | 利益・確率・スコアの計算 | **いいえ（必ず決定的計算）** |
| **Allocator（資金配分）** | ロジック＋LLM補助 | 最適化計算はコード、説明はLLM | 主にコード |

> [!warning] LLMに金額計算をさせない
> 利益・ROI・スコア・資金配分は **必ず決定的なコードで計算** する。LLMは説明と分類にだけ使う。
> LLMの出力は必ずスキーマ検証（Zod等）を通し、検証に落ちたら `SKIP` にする（Fail Closed）。

### コスト管理
LLM呼び出しは高い。**決定的キー（JAN/型番）で一致した商品にはLLMを呼ばない。**
画像判定は「候補が絞れて、かつ金額が大きい商品」だけに限定する。
呼び出し回数・トークン・費用を `ai_usage` テーブルに記録し、日次上限を設ける。

## 7. 外部サービス Connector 構成

### 7.1 capability 宣言（設計の心臓部）

すべてのConnectorは、自分に何ができるかを宣言する。

```ts
type Capability = 'api' | 'csv' | 'webhook' | 'manual' | 'unavailable'

interface ConnectorCapabilities {
  readCatalog:      Capability  // 商品一覧が取れるか
  readPrice:        Capability  // 現在価格が取れるか
  readSalesHistory: Capability  // 過去成約が取れるか
  purchase:         Capability  // 購入できるか
  list:             Capability  // 出品できるか
  reprice:          Capability  // 価格変更できるか
  readOrders:       Capability  // 注文が取れるか
  ship:             Capability  // 発送連携できるか
}
```

**実行層のルール（絶対）**

| capability | 挙動 |
|---|---|
| `api` / `webhook` | 自動実行を許可（他の安全条件を満たせば） |
| `csv` | ファイル出力までを自動化。取り込み・アップロードは人間 → `MANUAL_APPROVAL_REQUIRED` |
| `manual` | 作業指示書を出すだけ。実行しない → `MANUAL_APPROVAL_REQUIRED` |
| `unavailable` | 機能を出さない → `CONNECTOR_NOT_AVAILABLE` |

環境変数で `AUTO_BUY=true` にしても、その販路の `purchase` が `api` でなければ **実行層が拒否する。**

### 7.2 Connectorの種類

## 8. 3つの自動化モード ＋ SHADOW

## 9. 自動化できる部分 / 人間承認が必要な部分

| 工程 | 判定 | 理由 |
|---|---|---|
| 商品データ取得 | ✅ 自動 | 正規手段が確保できれば安全 |
| 正規化・同一商品判定 | ✅ 自動 | 金銭を動かさない |
| 相場調査・利益計算・スコア | ✅ 自動 | 金銭を動かさない |
| 資金配分案の作成 | ✅ 自動 | 提案までは安全 |
| **購入** | ⚠️ **モード依存** | 金銭が出る。SAFEでは必ず人間 |
| **出品** | ⚠️ **モード依存** | 誤出品＝クレーム・アカウント停止リスク |
| 商品説明の生成 | ✅ 自動（内容は要ガード） | 誇大・虚偽が出ないようルール検証を通す |
| **値下げ** | ⚠️ モード依存 | 赤字ラインを割る変更は常に禁止 |
| 注文取込・在庫引当 | ✅ 自動（api時） | 早いほど良い。ただし二重販売防止が前提 |
| **発送** | ⚠️ 半自動 | ラベル生成まで自動、現物梱包は人間 |
| **損切り実行** | ❌ 常に人間承認 | 確定損なので必ず人間が押す（FULL AUTOでも既定は承認） |
| **再仕入れ** | ⚠️ FULL AUTOのみ | 実績のある商品に限る |
| **予算・閾値の変更** | ❌ 常に人間 | AIに自分の上限を上げさせない（最重要） |
| **モード変更** | ❌ 常に人間＋二段階確認 | SAFE→FULL AUTO は特に厳重に |

> [!danger] AIに自分の制限を緩めさせない
> 予算上限・スコア閾値・自動化モードは **AIが書き換えられない領域** に置く。
> AIは「上限を上げるべき」と提案はできるが、変更は人間の操作のみ。

## 11. 主要ロジックの定義

### 11.1 純利益
```
EXPECTED_NET_PROFIT =
  予想販売価格
  − 商品仕入価格
  − 販売手数料 − 決済手数料 − 送料 − 梱包費
  − 鑑定関連費 − 倉庫費 − 広告費
  − 為替コスト − 輸入関連費
  − 返品期待損失（返品率 × 往復送料＋再販ロス）
  − その他販路別費用

EXPECTED_ROI = EXPECTED_NET_PROFIT / 商品仕入価格
PROFIT_PER_CAPITAL_DAY = EXPECTED_NET_PROFIT / 予想販売日数
```

### 11.2 BUY_SCORE（0〜100）
重み付き合成。**重みは設定ファイルに置き、バックテストで調整する。**

| 要素 | 既定重み |
|---|---|
| 純利益額 | 15 |
| ROI | 15 |
| 30日売却確率 | 20 |
| 資金拘束日数あたり利益 | 15 |
| 競合数・相場安定性 | 10 |
| 値崩れリスク（逆） | 8 |
| 真贋リスク（逆） | 7 |
| 返品リスク（逆） | 5 |
| 自社過去実績 | 5 |

判定：90+ STRONG BUY / 80-89 BUY / 70-79 WATCH / 60-69 LOW PRIORITY / 59- SKIP

### 11.3 売却確率
初期は **統計ベース**（同ブランド・同カテゴリ・同価格帯の過去成約データから、価格分位ごとの成約日数分布）。
自社実績が貯まったら **自社データを優先**（→ §12）。LLMは使わない。

### 11.4 最適販路 → **v1.3で ROUTE SCORE に置き換え**（§11.9）
販路だけを選ぶ考え方は捨てた。**買う場所と売る場所の組み合わせ**を選ぶ。
最高価格ではなく、**利益 × 売却速度 × 成約確率 × リスク** で決める点は変わらない。

### 11.5 異常価格
相場中央値からの乖離が閾値超（例：−30%以上）→ `PRICE_ANOMALY_DETECTED`。
**異常なほど同一性確認を厳格化**（MATCH_SCORE要求を95→98へ、画像照合を必須化、人間承認を強制）。
価格誤表記・別商品・状態違い・付属品欠品を疑う。

### 11.6 資金配分
制約付き最適化。単純な「利益率順に全額」は禁止。

```
最大化：Σ PROFIT_PER_CAPITAL_DAY × 投入額
制約：
  現金維持率 >= MIN_CASH_RATIO（既定20%）
  1商品 <= MAX_PER_ITEM
  1ブランド <= MAX_PER_BRAND_RATIO（既定30%）
  1カテゴリ <= MAX_PER_CATEGORY_RATIO（既定40%）
  1SKU保有数 <= MAX_UNITS_PER_SKU
  日次／週次仕入上限
```

---

### 11.7 BUY COST と SELL COST の完全分離（v1.3追加・**非常に重要**）

> [!danger] 混ぜてはいけない理由
> Phase 1 の `calcProfit` は「仕入価格＋販売費用」を1つの固定費に畳んでいた。
> 市場が仕入先にも販売先にもなる以上、それでは **どこで買うかを比較できない。**

```
【BUY側】仕入市場で発生する費用だけ
  ITEM_PRICE（商品代金）
+ BUYER_FEE（購入手数料）
+ PAYMENT_FEE（決済手数料）
+ DOMESTIC_SHIPPING（自分に届くまでの送料）
+ AUTHENTICATION_FEE（鑑定料）
+ TAX（税）
+ IMPORT_DUTY（関税）
+ CURRENCY_FEE（為替手数料）
+ OTHER_BUY_COST
= TOTAL_ACQUISITION_COST（仕入総額）

【SELL側】販売市場で発生する費用だけ
  EXPECTED_SELL_PRICE（予想販売価格）
− SELLER_FEE（販売手数料）
− PAYMENT_FEE（決済手数料）
− OUTBOUND_SHIPPING（買った人へ送る送料）
− AUTHENTICATION_FEE（鑑定料）
− PACKING_COST（梱包資材）
− WAREHOUSE_COST（保管費）
− ADVERTISING_COST（広告費）
− RETURN_EXPECTED_LOSS（返品・キャンセルの見込み）
− CURRENCY_FEE / OTHER_SELL_COST
= EXPECTED_NET_RECEIPT（販売後の入金予想）

EXPECTED_NET_PROFIT = EXPECTED_NET_RECEIPT − TOTAL_ACQUISITION_COST
EXPECTED_ROI        = EXPECTED_NET_PROFIT ÷ TOTAL_ACQUISITION_COST
```

丸めは常に自分に不利な側へ。**費用は切り上げ、手取りは切り捨て。**

> [!check] Phase 1 との整合は受け入れテストで担保
> BUY側の費用をすべてゼロにすると、Route の純利益は Phase 1 の `calcProfit` と**1円単位で一致する**。
> これを `npm run test:phase2` で毎回検算している（式を単純化した瞬間に落ちる）。

### 11.8 手数料は市場ごと × BUY/SELL別（v1.3追加）

`MERCARI_BUY` / `MERCARI_SELL` / `SNKRDUNK_BUY` / `SNKRDUNK_SELL` … と**別々に持つ**。
**一律10%などは禁止。** 同じ市場でも買う側と売る側で費用構造が違う。

各 Fee Profile は必ず持つ：`effective_from` / `effective_to` / `source_url` / `verified_at` / `is_estimated`

> [!danger] 公式料金を確認できていない手数料は `is_estimated = 1`
> 概算のままの手数料で **自動購入は禁止**。画面にも「手数料が概算」と出す。

### 11.9 ARBITRAGE_ROUTE と ROUTE SCORE（v1.3追加）

1つのRouteが持つもの：
`buy_venue` / `sell_venue` / `acquisition_price` / `acquisition_total_cost` /
`expected_sell_price` / `expected_net_receipt` / `expected_net_profit` / `expected_roi` /
`expected_days_to_sell` / `sell_probability_7d,30d,90d` / `route_score` / `risk_score` / `data_confidence`

```
ROUTE_SCORE（0〜100）
 = 利益 25点 + ROI 25点 + 30日売却確率 20点 + 資金回転 15点 + データ信頼度 15点
 − リスク（最大20点減点）
```

判定は BUY_SCORE と同じ閾値：STRONG_BUY 90 / BUY 80 / WATCH 70 / LOW_PRIORITY 60。

**除外条件は Fail Closed の順で見る（順番も仕様）**：
異常価格（安すぎ／高すぎ）→ 赤字 → 利益不足 → ROI不足 → 売却確率不足。
**異常価格チェックを一番先に置く。** 後ろに置くと、データ誤りが「利益が大きいRoute」として上位に出る。

#### LIQUIDITY SCORE（0〜100）
30日成約件数・出品件数・平均売却日数・価格ばらつきから算出。
実データが無ければ `DEFAULT` として低く出し、**その旨を画面に書く**。

#### 資金回転（参考指標）
```
CAPITAL_VELOCITY        = 365 ÷ max(想定売却日数, 下限日数)
EXPECTED_30D_RETURN     = ROI × (30 ÷ 想定売却日数) × 30日売却確率
EXPECTED_ANNUALIZED_RETURN = ROI × (365 ÷ 想定売却日数) × 30日売却確率
```
**年率は保持するが画面には出さない。** 実態より大きく見えるため。

#### 相場データの信頼度
成約価格（SOLD）を最優先。出品価格（ASK）しか取れない場合は信頼度を下げる。
**その市場の相場が未登録なら `REFERENCE_FALLBACK`**（参考相場を当てはめた仮定値）として
信頼度を大きく下げ、画面にもそう書く。**数字を作らない。**

### 11.10 市場をまたいだ資金配分（v1.3で拡張）

「今日この予算を使うなら」は、**Route単位**で `EXPECTED_30D_RETURN` の高い順に選ぶ。
1ブランド・1販売先への偏りを上限で止め、**外した理由と件数を画面に出す。**

## 12. 自社データを最重要資産にする

市場データは誰でも取れる。**「自社では実際に何が、いくらで、何日で売れたか」だけが競争優位。**

- すべての予測に対し実績を必ず保存し、誤差を測る（→ `ai_predictions`）
- ブランド別・カテゴリ別・販路別・価格帯別に **補正係数** を持つ
  例：「ルイヴィトン × スニダン は予想販売日数を1.3倍に補正すべき」
- 補正係数は自動更新するが、**適用前に必ずバックテストを通す**（→ [[03_安全設計と事故防止]]）
- 十分なサンプル（既定30件）が貯まるまでは補正を適用しない

**将来の姿**：一般的なAIではなく、**この会社の販売実績を学習した独自仕入AI**。

## 15.5 実市場データ接続とSHADOW精度検証（Phase 3.5・v1.5で追加）

Phase 3 完了時点の数字は**すべてテストデータ由来**だった。
テストデータ上の「平均ROI 42.6%」「予想純利益196万円」を成果として扱わない、と正式に決めた。
Phase 4（在庫・出品）へ進む前に、**実市場データで精度を証明する関門**を置く。

### 15.5.1 手数料の確からしさ（4段階）

`venue_fee_profiles` に `fee_status` / `source_url` / `source_name` / `verified_at` / `effective_from` / `effective_to` を持つ。

| status | 意味 | 扱い |
|---|---|---|
| `VERIFIED` | 公式ページ等で実額を確認済み | 満点。STRONG BUY に到達しうる |
| `ESTIMATED` | 概算 | データ信頼度が上がらず、**利益がいくら大きくても STRONG BUY にならない** |
| `OUTDATED` | 有効期限切れ | 同上 |
| `UNKNOWN` | 不明 | 同上 |

**料金改定があっても、過去のSHADOWを新しい料金で再計算しない。** 変更は履歴に残すだけ。
取引時点の `fee_version` を保持する（§11.8・ルール24と同じ思想）。

### 15.5.2 実市場データの判定（Fail Closed）

`REAL_MARKET_DATA` は、**仕入側と販売側の両方**が実観測のときだけ真になる。
片方でも不明・参考値なら実データとして数えない。
テストデータ（seed）は成績集計から完全に除外する。

### 15.5.3 相場は時系列で持つ

`market_snapshots` は**追記型**。現在価格でレコードを上書きしない。
上書きすると「価格がいつ動いたか」が消え、利益機会の寿命が測れなくなる。

### 15.5.4 利益機会の寿命と「人の承認に間に合うか」

市場の組ごとに**半減期**（利益機会の半分が消えるまでの時間）を測り、
人が承認するのに必要な時間（`OPPORTUNITY_HALF_LIFE` / `humanReachHours`）と比べて4段階で判定する。

| 判定 | 意味 |
|---|---|
| `HUMAN_APPROVAL_OK` | 承認時間の2倍以上残る。人の確認を挟んでも取れる |
| `TIGHT` | 承認時間ぶんしか残らない。ぎりぎり |
| `AUTO_ONLY` | 承認前に消える |
| `UNKNOWN` | 消滅実績5件未満。判定しない |

> [!danger] `AUTO_ONLY` は「自動化してよい」という意味ではない
> **「人の承認前提では取れない機会である」という事実の記録**である。
> × 間に合わないから自動購入を解禁する
> ○ 間に合わないから、その市場の組は**今の体制では取りに行かないと決める**
> 速さのために安全確認を飛ばさない。

### 15.5.5 予測は3本立てにする

| 名前 | 意味 | 用途 |
|---|---|---|
| `RAW` | 理論値（補正なし） | 素の計算を残すため |
| `CALIBRATED` | 実績のズレで補正した値 | 学習の効き具合を見るため |
| `CONSERVATIVE` | 保守的に割り引いた値 | **将来の実購入判断はこれを使う** |

あわせて 80%予測レンジ（`sell_price_low_80` / `high_80`）、
`DOWNSIDE_PROFIT`（下振れ時の利益）、`MAX_EXPECTED_LOSS`（最大想定損失）を持つ。

補正は**実市場データからのみ**作る。テストデータ由来の −10.1pt を本番補正に使わない。

### 15.5.6 間違いの重さは同じではない

| 種類 | 意味 | 痛み |
|---|---|---|
| FALSE POSITIVE | 買うと判断したが損した | **現金が減る** |
| FALSE NEGATIVE | 見送ったが儲かっていた | 儲け損ねただけ |

**FPをFNの3倍の重さで数える。** 「赤字商品を大量購入する方が危険」だから。
重み付き誤りスコア ＝ (FP×3 + FN) ÷ 全体。

`WATCH` は「買う」と判断していないので、FP側には数えない。

### 15.5.7 精度KPI

`BUY_PRECISION` / `STRONG_BUY_PRECISION` / `FALSE_POSITIVE_RATE` / `FALSE_NEGATIVE_RATE`。
的中率には必ず**95%下限（Wilson下限）**を併記する。少ない件数の「偶然の当たり」を精度と呼ばない。
実市場データが0件なら、的中率は「100%」ではなく**「測定不能」＝不合格**。

### 15.5.8 Phase 4 卒業条件（14項目・機械判定）

条件と実測は [[04_ロードマップ]] Phase 3.5 を参照。ここでは原則だけ書く。

> [!danger] 条件を緩めない
> ユーザー指示「**勝手に条件を緩和しないでください**」。
> 判定コードは条件を**測るだけ**で、条件を書き換える経路をコードに持たない。
> しきい値は設定（`GATE_*`）にあるが、AIがそれを変更する手段は実装されていない。
> 判定結果は `phase_gate_log` に残り、「いつ緩めたか」を人が後から追える。
> 画面を開いただけでは履歴を増やさない（履歴が埋もれると監査にならない）。

> [!important] 二重の鍵
> 鍵1：14項目すべて合格 ／ 鍵2：人間が `PHASE4_UNLOCKED` を true にする
> **鍵1が全部通っても、鍵2が無ければ何も起きない。**
> さらに現時点で実購入のコードは1行も存在しない。両方開いても勝手には買わない。

### 15.5.9 少額実取引の安全設計（**設計のみ・実装しない**）

| 上限 | 値 |
|---|---|
| 1件あたり | 10,000円 |
| 1日あたり | 30,000円 |
| 同一商品 | 1個まで |
| 対象判定 | `STRONG_BUY` のみ |
| 手数料 | 買う側・売る側とも `VERIFIED` のみ |

これに加えて 人の解錠済み／卒業条件合格／実市場データ／半減期が `AUTO_ONLY` でない／
冪等キーあり、の全条件を満たしたときだけ「実行してよい」と**判定するだけ**。
`EXECUTION_PATHS`（purchase / listing / payment / autoLogin）は**全て false**で、
実行する処理そのものが存在しないことをテストで毎回確認する。

### 15.5.10 毎日の経営者向けレポート

`npm run report`（画面は `/readiness`）。**一番上に結論を1行だけ**置く。数字の羅列を先に見せない。

> [!important] AIが勝手に「進める」に変えられない
> 結論の文言は卒業条件の判定結果から**機械的に**生成される。
> 条件を1つでも満たしていなければ、必ず「**まだ実購入に進めません**」になる。
> 「次にやること」も1つだけ出す（3つ並べると一番簡単なものだけやって終わるため）。

### 15.5.11 定期観測は Read Only

`npm run observe` は**市場を1つずつ**確認する。まとめて全市場を回す機能は作っていない。
規約とレート制限を守り、取得できなかった理由を
「0件だった」「規約上できなかった」「実行していない」で区別して記録する。**推測で埋めない。**

## 15.6 メルカリ実市場検証（Phase 3.6・v1.6で追加）

実装記録は [[13_Phase3.6実装記録]]。ここには**決まりごとだけ**を書く。

### 15.6.1 第1実市場はメルカリ。理由は手数料の根拠が公式にあること

「売れそうだから」でも「商品が多いから」でもない。**数字の根拠を確認できるかで選ぶ。**

| 項目 | 値 | 出典 |
|---|---|---|
| 販売手数料 | 販売価格の **10%**（端数切り捨て） | [メルカリの手数料 - メルカリ](https://help.jp.mercari.com/guide/articles/65/)（確認日 2026-08-20） |
| 売上振込手数料 | 一律 **200円**（**振込申請1回ごと。商品1件ごとではない** → §15.7） | 同上 |

**送料・梱包費は商品と発送方法で変わるため、一律固定値として確定しない。**
手数料は項目ごとに検証する。市場が決めている率（`VENUE_RATE_FIELDS`）だけ `VERIFIED` にでき、
商品ごとに変わる原価（`ITEM_COST_FIELDS`）は推定のまま据え置く。
率だけ確認済みの状態は上限85点＝**STRONG BUY(90点)には構造上届かない。**

### 15.6.2 「自分で見て記録した」と「提供された」を混同しない

**CSVというファイル形式は、規約上の安全性の説明にならない。**
ファイル形式はこちらの都合であり、相手がデータを提供している事実ではない。

- `SELF_OBSERVED`（自分で公開画面を見て書き写した）… 注意文を必ず画面に出す
- `PROVIDED_BY_VENUE`（事業者から正式に提供された）
- `NOT_REAL`（テスト・サンプル）

**`venues.csv_available` は「正式なCSV提供があるか」であり、取り込める形式かではない。
2026-08-20 時点で該当する市場は0件。推測で1にしない。**

### 15.6.3 出品1件の追跡（相場テーブルとは別物）

主語が違う。相場テーブル＝「この商品の相場は10万円」／こちら＝「105,000円で出ていた**この1件**の行方」。

- `tracked_listings`（1URL＝1行・最新状態）と `listing_observations`（**観測のたびに積む・絶対に上書きしない**）
- 同一判定の鍵 `listing_key` ＝ URLのホスト＋パス（クエリは捨てる）
- `UNIQUE(listing_key, observed_at)` ＋ `ON CONFLICT DO NOTHING` で二重取り込みを防ぐ
- 追跡予定：**初回 → 24時間後 → 3日後 → 7日後 → 14日後 → 30日後**（許容幅あり。予定外の観測も捨てない）

### 15.6.4 状態は観測できる5つだけ

`ACTIVE` / `CONFIRMED_SOLD` / `REMOVED_UNKNOWN` / `PRICE_CHANGED` / `UNKNOWN`。

- **「消えた」「削除」「404」「非公開」「取り下げ」は全部 `REMOVED_UNKNOWN`。売れた扱いにしない。**
- `CONFIRMED_SOLD` は**売り切れ表示を画面で実際に見たときだけ**
- 読み取れない言葉は `null` を返す。**近い方に寄せない**
- `SOLD_PROBABLY` のような「たぶん」の状態を作らない
- `PRICE_CHANGED` だけは前回と今回の観測価格の差から導出してよい（**どちらも人が見た実数**）。導出したことは記録に残す

### 15.6.5 売れた値段を推測しない

- 状態が `CONFIRMED_SOLD` でなければ、書かれていても成約価格として採用しない（採用しなかったことは警告表示）
- 確認できなければ `sold_price_known = 0` ＝ 画面に **「不明」**。**出品価格でも0円でも代用しない**
- 一度判明した成約価格を、あとの観測で消せないようにする（`COALESCE` / `MAX`）

### 15.6.6 実データとテストデータを完全に分ける

**ダッシュボードの実績値には `real_market_data = 1` の行だけを使う。**
画面に最初から入っている記入見本は、うっかり取り込まれてもサンプル判定で弾かれるようにする
（**画面に置く文字列は「取り込まれる可能性がある」前提で作る**）。
受け入れテストのデータは必ず削除し、実績件数が元に戻ることを検査する。

### 15.6.7 人間の作業時間を実測してから自動化を決める

工程は5つ（探す／同じ商品か確かめる／書き写す／取り込む／確かめる）。
**計測が0件のうちは「どの工程を自動化すべきか」を書かない。感覚で決めない。**

### 15.6.8 進捗画面（`/validation`・`npm run validation`）

集めた出品 `X / 100` ／ 手数料の状態 ／ 7日・30日の完了件数 ／ STRONG BUY 的中率を大きく出す。
**数字を良く見せる加工をしない。0件なら0件、測れないなら「測定不能」と出す。**
理論値・補正後・保守と実績の比較も、実績0件なら**「まだ比べられません」**と書く（近そうな方を選ばない）。

### 15.6.9 歯止め（変えてはいけない）

- **100件そろっても、それだけでは購入しない。必ず14項目の卒業条件で判定する。**
- **メルカリ100件が安定するまで、次の市場を同時に追加しない。**
- **購入・出品・決済・発送・自動ログイン・無許可スクレイピングはコードごと存在しない。**
- 報告のタイミングは3つだけ：**A 100件登録完了／B 重大な問題発生／C 正規のデータ取得方法が見つかった。**

## 15.7 費用の分離・支払方法・検証ファネル（Phase 3.7・v1.7で追加）

**§15.6 の記述のうち「振込手数料200円を販売費用として `VERIFIED` 登録」は誤りだったので、
ここで訂正して上書きする。** 以下が現行仕様。

### 15.7.1 振込手数料は「商品1件ごと」の費用ではない

ユーザー指摘：

> メルカリの「振込手数料200円」は、1商品ごとの販売コストではなく、
> 売上金を銀行へ振り込む "申請1回ごと" の費用です。

Phase 3.6 では `fixed_fee = 200`（1取引ごとの固定費）として登録していた。
「1件ずつ振り込む最悪の場合で見ておけば安全」という理屈だったが、これは Fail Closed ではない。

- Fail Closed ＝ 分からないものを買わない
- 実際にやっていたこと ＝ 分かっているものを最大100倍高く見積もって捨てる

**`fixed_fee = 0` / `payout_fee_fixed = 200` に訂正した。**
1万円の商品の手取りは 8,800円 → **9,000円**、1,000円の商品は 700円 → **900円**。

### 15.7.2 費用を3種類に分ける

```
TRANSACTION_COST  商品1件ごとにかかる費用
                  ＝ 販売手数料10% ＋ 送料 ＋ 梱包費 ＋ その他商品固有費用
PAYOUT_COST       振込申請1回ごとの費用（200円）。商品単位ではない
BUY_PAYMENT_FEE   仕入時の支払方法ごとの手数料。支払方法で変わる
```

### 15.7.3 利益は4段階で表示する

| 名前 | 意味 | 用途 |
|---|---|---|
| `GROSS_PROFIT` | 粗利（販売価格 − 仕入価格） | 参考 |
| `TRANSACTION_NET_PROFIT` | 取引後利益 | **買う／買わないの判定はこの数字** |
| `PAYOUT_ALLOCATED_NET_PROFIT` | 振込費按分後利益（200円 ÷ まとめる件数） | **参考表示のみ** |
| `CONSERVATIVE_NET_PROFIT` | 保守利益 | **実際にお金を出すときはこの数字** |

**按分後の数字を `decision` と `route_score` に入れない。**
按分の分母（`PAYOUT_ITEMS_PER_REQUEST`）は運用で変わる数字であって、商品の良し悪しではない。
設定を変えるだけで判定が変わる構造にしてはいけない。

### 15.7.4 仕入時の支払方法（`BUY_PAYMENT_METHOD`）

8種類（クレジットカード／メルペイ残高／Apple Pay／FamiPay／コンビニ／ATM／キャリア決済／その他）。
前の4つは無料（確認済み）、後ろの4つは**金額で変わるため「不明」**。

- **不明を0円として計算に足さない。** 不明のまま STRONG BUY にしない。
- **いちばん安い支払方法をシステムが勝手に選ばない。**
  基準は設定 `DEFAULT_MERCARI_BUY_PAYMENT_METHOD` ＝ **実際に自分が使う支払方法**。

### 15.7.5 手数料の確認は費目ごと。全体を100%にしない

5費目（販売手数料／仕入決済手数料／送料／梱包費／振込手数料）に分けて状態を持つ。
**`COST_CONFIDENCE` の上限は95点。** 公式ページに書いていない実費が必ず残るため、
「完全に確認済み」を名乗れる状態は原則として来ない。

あわせて、**仕入側の決済手数料は0円でも未確認なら確認済みと認めない**。
「決済手数料0円」は、本当に0円なのか調べていないだけなのか区別できず、
0のまま通すとコンビニ払いの手数料が永久に計算へ入らなくなるため。
結果としてメルカリの仕入側手数料は `ESTIMATED` のまま（確認済みは18件中1件・5.6%）。

### 15.7.6 検証ファネル（最重要KPIの変更）

ユーザー指摘：

> 「100件」という数字だけを追わない方がいいです。

**「100件登録した」は成果ではなく入口。** 次の5段で見る。

```
観測した出品 → 他市場と同じ商品だと確かめられた → Routeを作れた
→ 答え合わせ（SHADOW）の対象になった → STRONG BUY候補
```

最重要KPIを `MATCHABLE_RATE` / `ROUTE_GENERATION_RATE` / `SHADOW_ELIGIBLE_RATE` に変更。
カテゴリの偏りも測り、最多カテゴリが60%を超えたら警告する。

**候補を増やすために判定を甘くしない。**
増やす手段は「手数料の実額を確認する」「仕入先を増やす」の2つだけ。

### 15.7.7 100件の前に10件（PILOT）

ユーザー指示：

> 修正後、いきなり100件入力しないでください。まず10件で操作性テスト。
> そこで人間が面倒だと感じた工程が、次に自動化すべき機能になります。

**この10件の目的はデータ収集ではなく「どこを自動化するか決めること」。**
合格条件は7項目（10件入力済み／時間を計測できている／商品一致50%以上／
Route成立30%以上／カテゴリ偏り60%以下／大事な項目の空欄が半分以下／重大な問題ゼロ）。
**全部満たすまで100件へ進まない。**

次に自動化する場所は、工程ごとに実測した秒数で決める。
未計測のうちは「どこを自動化すべきかは決められない」と表示する（推測で書かない）。

### 15.7.8 送料の精度

観測項目に 荷物サイズ／発送方法／送料の負担者／見込み送料／実際の送料 を追加。
見込みと実額の両方が入った出品が0件のうちは「まだ測れません」と出す。

### 15.7.9 歯止め（変えてはいけない）

- **`fixed_fee` に振込手数料を戻さない。**
- **按分した振込費用を判定に使わない。**
- **不明な支払手数料を0円として足さない。**
- **安い支払方法を自動選択する関数を作らない。**
- **`COST_CONFIDENCE` を100点にしない（上限95）。**
- **「100件入力した」だけで前へ進まない。**
- **購入・出品・決済・発送・自動ログインは、いまもコードごと存在しない。**

## 15.8 まず10件のPILOT（Phase 3.8・v1.8で追加）

### 15.8.1 この段階の目的

**新機能を増やさない。** 人が10件入力して、どこが面倒か・どこまで自動判定できるかを測る。
測った数字で「次に作るもの」を決める。10件が終わるまで100件へ進まない。

### 15.8.2 落ちた理由は8分類（「その他」を作らない）

`MODEL_NUMBER_MISSING` / `NO_SELL_MARKET` / `PRODUCT_MATCH_FAILED` / `MARKET_DATA_MISSING` /
`FEE_UNVERIFIED` / `SHIPPING_UNKNOWN` / `INSUFFICIENT_MARGIN` / `LOW_DATA_CONFIDENCE`。

どれが多いかで打つ手が変わる（入力方法を直す／市場を増やす／仕入先を増やす）。
**`INSUFFICIENT_MARGIN` が多くても閾値は下げない。**

### 15.8.3 同一商品の答え合わせは3択（「たぶん」を作らない）

`CORRECT_MATCH` / `INCORRECT_MATCH` / `UNCERTAIN`。

**見逃しより取り違えの方が危険**（見逃し＝儲け損ね／取り違え＝実際に金を失い在庫も残る）。
`INCORRECT_MATCH` は1件でも重大とし、100件へ進む条件に入れる。
機械の判定（`identity_key`）は人の答えで上書きせず、`identity_match_reviews` に別で持つ
（そうしないと「機械が何回間違えたか」が測れなくなる）。
「違う商品だった」を選んだときは、何が違ったかの記入を必須にする。

### 15.8.4 次に自動化する工程は、実測の秒数 × 自動化しやすさで決める

**時間が長い工程＝自動化すべき工程ではない。**
「商品発見」「商品情報確認」は最も時間がかかるが、無断巡回しない決まりのため自動化できない。
①かかっている時間の順（事実）と②自動化して効く順の両方を出し、②を採用する。
`AUTOMATION_ROI` は「全部自動化して0時間」にしない。測れないときは数字を作らない。

**記入見本・テスト行に書かれた秒数は「実測」に混ぜない**（実際にこの不具合があり修正した）。
除外した分は黙って引き算せず、画面に「◯分は数えていません」と書く。

### 15.8.5 100件へ進む条件は7項目（操作性7項目とは別）

重大な不具合0／**取り違え0**／二重登録0／テスト行の混入0／入力時間が現実的／
Route計算が正常／SHADOW記録が保存できている。

**操作性7項目と安全条件7項目の両方**がそろって初めて100件へ進む。
まだ1件も確認していない状態は、黙って合格にしない。

### 15.8.6 終了時の報告は①〜⑧

実測結果／いちばん時間がかかった工程／いちばんデータが取れなかった項目／
同一商品判定で起きた問題／Routeにならなかった主な理由／見つかった不具合／
次に自動化すべき工程TOP3／100件へ進んでよいか。
コマンドは `npm run pilot`、画面は `/validation`。

### 15.8.7 歯止め（変えてはいけない）

- **落ちた理由に「その他」を作らない。**
- **同一商品の答えに「たぶん合っている」を作らない。**
- **人の答えで機械の判定を上書きしない。**
- **記入見本の秒数を実測に混ぜない。**
- **点検で見つけたものを勝手に消さない・直さない。**
- **合格できないときに条件の方をゆるめない。**
- **購入・出品・決済・発送・自動ログインは、いまもコードごと存在しない。**

## 15.9 正規Connectorと「購入ページを開く」（Phase 3.9・v1.9で追加）

### 15.9.1 方針の変更

**人が全部入力する形をやめ、正規に取得できる市場は自動収集する。取得できない市場だけ半自動で残す。**
そのうえで、**最終購入だけは必ず人が商品ページで確認して行う**。

**10件PILOT（§15.8）は保留**。仕組みは消さない（自動収集でも落ちた理由・工程実測は必要になるため）。

### 15.9.2 Venue Connector に一本化（指示6・7・8）

外部からのデータ取得は必ず Connector を通す。取得手段の優先順位は

```
OFFICIAL_API > BUSINESS_API > PARTNER_API > OFFICIAL_DATA_FEED
  > OFFICIAL_CSV > AUTHORIZED_INTEGRATION > MANUAL_OBSERVATION
```

状態は9種：`NOT_RESEARCHED` / `RESEARCHING` / `AVAILABLE` / `APPLICATION_REQUIRED` /
`WAITING_APPROVAL` / `CONNECTED` / `MANUAL_ONLY` / `PROHIBITED` / `UNKNOWN`。

**既定は `NOT_RESEARCHED`。適当に「APIあり」と判断して `CONNECTED` にしない。**
`CONNECTED` にしてよいのは、①正式な利用条件を読み ②商用利用可を確認し
③出典URLと確認日を残し ④確認者を書いた、**4つがそろったときだけ**。

**2026-08-20 時点で `CONNECTED` は 0件**（9市場を調査した結果。[[17_市場別_正規データ取得調査]]）。
最初に繋ぐ候補（`FIRST_LIVE_CONNECTOR`）は **Yahoo!ショッピング商品検索API(v3)** だが、
公式ヘルプが Web API を「原則 非商用」と書いているため、**書面確認が取れるまで `APPLICATION_REQUIRED`**。

### 15.9.3 「購入ページを開く」導線（指示1〜4・12〜16）

すべての仕入候補に `SOURCE_PRODUCT_URL` を持たせ、一覧の右端にボタンを置く。
ボタンは**新しいタブで商品ページを開くだけ**。

**AIは、購入ボタンを押さない・注文を確定しない・決済しない・ログインしない。**
これはフラグOFFではなく、**その処理がコードに1行も無い**。

- **AIはURLを作らない。** 取得元データに実在するURLだけを使う。
  出どころは `CONNECTOR_API` / `CONNECTOR_FEED` / `OFFICIAL_CSV` / `HUMAN_ENTRY` の4つのみ。
  **`AI_GENERATED` という選択肢を作らない。** URL組み立て関数が増えていないことをテストで検査する。
- 商品ページの状態は `ACTIVE` / `SOLD` / `REMOVED` / `UNKNOWN` の4つ。
  **既定は `UNKNOWN`。開けるのは `ACTIVE` のときだけ**（Fail Closed）。「たぶん出品中」を作らない。
- 市場と違うドメイン・転送/短縮URL・ログイン情報入りURL・`http(s)` 以外は問答無用で無効。
- 押した記録（`page_open_events`）は**押した瞬間の価格と判断を凍結**する。あとで書き換えない。
- 開いた結果は5択：`購入した` / `見送った` / `売り切れていた` / `価格が変わっていた` / **`違う商品だった`**。
  **`違う商品だった` は重大扱いで理由の記入を必須**とし、その出品は以後開けなくする。
- `購入した` の記録は `real_trade_candidates` に入れ、**SHADOWの表には1列も足さない**。
  混ぜるとAIの予測成績に人の行動が紛れ込む。
- 送料が分からないときは**空欄。0円と書かない**。

### 15.9.4 自動購入は構造だけ（指示17・18）

`AUTO_PURCHASE_CAPABLE` を true にしてよい条件を9つ定義した
（`VENUE_OFFICIALLY_ALLOWS` / `FEE_VERIFIED` / `MATCH_CONFIDENCE_HIGH` / `DECISION_STRONG_BUY` /
`CONSERVATIVE_ROI_OK` / `REAL_PRECISION_OK` / `STOCK_CONFIRMED` / `WITHIN_BUDGET` / `ALL_GATES_PASSED`）。

**9つ全部そろっても、いまは必ず false を返す。** 環境変数で有効にする経路も作らない。
**APIがあることは、自動購入してよい理由にならない。**

### 15.9.5 いま画面に出していないもの（正直に）

`/buy` に**利益額・ROI・Route Score・売却確率を出していない**。
いまの利益計算は「仕入先の商品」起点で、「この1件の出品を買ったらいくらか」の形になっていないため。
**無い数字をそれらしく埋めない**（ルール35）。画面にもその理由をそのまま書く。

### 15.9.6 歯止め（変えてはいけない）

- **AIはURLを作らない。**
- **既定は `UNKNOWN`。確認していないページを開かせない。**
- **`CONNECTED` は4条件がそろうまで付けない。**
- **「規約に禁止と書かれていない」を、やってよい根拠にしない。**
- **robots.txt を規約と混同しない。別サイトの規約を根拠にしない。**
- **廃止されたAPIを前提にコードを書かない。**
- **手作業が面倒だからという理由で無許可の自動巡回を作らない。**
- **購入・注文・決済・発送・自動ログインは、いまもコードごと存在しない。**

## 15.10 市場ごとの「許可」を8項目に分ける（Phase 3.9b・v2.0で追加）

詳細は **[[19_Connector再調査_市場別スコア]]**。ここには結論と歯止めだけ書く。

### 15.10.1 なぜやり直したか（AIの間違いの記録）

Phase 3.9 で **Yahoo!ショッピングを「使えない」と結論づけたのは誤り**だった。
根拠にしたのは公式ヘルプの「原則 非商用」という記述だが、

- 商品検索API(v3) は**現役**である
- **同じ記事の中に**「すべてを禁じるものではありません」と書かれている
- 商用利用の相談窓口が公式に存在する

つまり正しい結論は **「禁止」ではなく「当社の使い方で使えるかがまだ確認できていない」**。
「禁止と書かれていないから許可」の**逆向きの間違い**をした。

### 15.10.2 判定を2択から3択にした

| 判定 | 意味 |
|---|---|
| `CONFIRMED_ALLOWED` | 公式情報で使ってよいと確認できた |
| `CONFIRMED_PROHIBITED` | 公式情報で禁止と確認できた |
| **`CONFIRMATION_REQUIRED`** | **公式情報はあるが、当社の用途に使えるかは書かれていない（禁止という意味ではない）** |

**確認していないものを「禁止」と書かない。**

### 15.10.3 許可を8項目に分けて持つ

`api_exists` ／ `commercial_use_allowed` ／ `internal_business_use_allowed` ／
`price_analysis_allowed` ／ `data_storage_allowed` ／ `automated_collection_allowed` ／
`automated_purchase_allowed` ／ `automated_listing_allowed`。

値は `YES` / `NO` / `UNKNOWN` の3つだけ。**既定は全部 `UNKNOWN`。**
**「APIがある」は「使ってよい」ではない。1項目でも `UNKNOWN` が残るうちは本番接続しない。**

### 15.10.4 同じ会社の別サービスを1つの市場にまとめない

| まとめてはいけない組 | 結論が違う理由 |
|---|---|
| Yahoo!ショッピング / ヤフオク! | 商品検索API v3 は現役 ／ ヤフオク!のWeb APIは2018年に提供終了 |
| Amazon SP-API / Creators API / Business API | 用途・ライセンス・費用がすべて別。結論も3つとも違う |

`venue_connectors.venue_code` には**サービス単位のコード**を入れ、`venue_ref` で市場に紐づける。

### 15.10.5 CONNECTOR PRIORITY SCORE（10軸100点）と Gate

10軸のうち4軸（**商用／社内利用／価格判断／保存**）は **Gate**。
**どれか1つでも0点なら、合計が何点でも候補から外す。**
これが無いと Amazon Creators API（技術点は高いが、ライセンス13条(i)が
「統合、分析、抽出もしくは再利用する目的」を名指しで禁止）を合計点で選んでしまう。

| 順位 | 接続先 | 合計 | Gate |
|---|---|---|---|
| 1 | **Amazon SP-API（出品パートナーAPI）** | **77** | **通過** |
| 2 | Yahoo!ショッピング 商品検索API v3 | 55 | 不通過（商用可否が未確認） |
| 3 | Amazon Creators API | 45 | 不通過（ライセンスが当社用途を禁止） |
| 4 | eBay Browse API | 31 | 不通過（ライセンスが seller arbitrage を禁止） |
| 5 | Amazon Business API | 13 | 不通過 |
| 6 | KOMEHYO / メルカリ / ヤフオク! / スニダン / BOOKOFF / HARD OFF / セカンドストリート | 0 | 不通過 |

**`UNKNOWN` に点を付けない（0点）。** 採点前と0点を見分けるため `priority_score` に `DEFAULT` を付けない。

### 15.10.6 第1自動市場（FIRST_LIVE_CONNECTOR）は未確定

`FIRST_LIVE_CONNECTOR = null`。**AIが単独で確定しない。**
Gate を通ったのは Amazon SP-API の1件だけだが、着手するには人の決定が要る。

**2026-08-22 更新（重要）。** 大口出品が契約済みと判明したため、規約の本文を実際に開いて確認した。
**費用の論点は消えたが、代わりにもっと重い論点が2つ確定した。詳細は §15.11。**

| 論点 | 2026-08-20 時点 | 2026-08-22 実確認後 |
|---|---|---|
| 月額費用 | 月4,900円（税抜）が新たに必要 | **契約済み。追加費用なし**（論点が消えた） |
| Keepa の併用 | 「できなくなるおそれ」 | **AUP 4.3 の原文により、併用できないと読むのが素直（確定）** |
| 商品ページURL | 「返るか未確認」 | **返らない（確定）。`/buy` の導線が作れない** |

**お金がかかる決定と、既存事業に影響する決定は、必ず先に人へ提示する。**
そして **費用の壁が消えたことを、着手してよい理由にしない。**

### 15.10.7 歯止め（変えてはいけない）

- **市場を「使える／使えない」の2択で判定しない。**
- **確認していないものを「禁止」と書かない。**
- **同じ会社の別サービスを同じ市場として扱わない。**
- **`UNKNOWN` に点を付けない。**
- **技術点だけ高い市場を合計点で選ばない（Gate）。**
- **公式内で数字が矛盾したら、矛盾したまま全部記録し、一番厳しい値で設計する。**
- **「自動取得できない」を「市場として使えない」に読み替えない**
  （ヤフオク!は自動取得できないが、人が買うこと・売ることは普通にできる）。
- **CONNECTED は引き続き0件。** 12接続先を調べても1件も付けなかった。

## 15.11 規約の本文を実際に開いて読む（Phase 3.9c・v2.1で追加）

**きっかけ：** ユーザーから「すでに大口出品プランになっている」との情報。
これで「月4,900円（税抜）が新たにかかる」という論点は消えた。
**だが「安くなったから進める」にはしない。** 費用の壁が無くなったので、その先の規約の壁を先に確認した。

**結果：未確認5件のうち2件が確定し、2件とも当社に不利な内容だった。**

### 15.11.1 【確定】Keepa は併用できない

**AUP 4.3（日本語原文・逐語）**

> 「Amazonのウェブサイトから入手した情報またはデータを提供する外部の（Amazon以外の）データサービスの使用、提供、宣伝をしてはいけません。」

Keepa は「Amazonのウェブサイトから入手したデータを提供する外部（Amazon以外の）データサービス」
そのもので、この条項は「提供」「宣伝」だけでなく **「使用」** まで禁じている。
**読み方を工夫して逃げ道を探さない（Fail Closed）。**

ただし正確に書くと、**この条項は SP-API を使い始めなければ掛からない。**
規約違反かどうかの話ではなく、次のどちらを取るかの経営判断である。

| 選ぶもの | 得るもの | 失うもの |
|---|---|---|
| SP-API を使う | Amazonの他社出品価格・売れ筋順位を正規に自動取得できる | **Keepa が使えなくなる** |
| Keepa を使い続ける | 既存事業が今のまま回る | AI Commerce OS の第1自動市場候補が消える |

### 15.11.2 【確定】カタログAPIは商品ページURLを返さない

Catalog Items API v2022-04-01 の応答項目を1つずつ確認した。`Item` にも
`ItemSummaryByMarketplace` にも**商品ページURLの欄が無い**（画像URLと売れ筋カテゴリURLはある）。
返るのは ASIN / JAN / EAN / UPC / 型番 / ブランド / 画像 / 売れ筋順位まで。

ASIN からURLを組み立てれば作れてしまうが、**それはルール55「AIはURLを作らない」に
真正面から反するのでやらない。**
したがって **SP-API 単体では `/buy`（購入ページを開く）の導線は作れない。**
採点表の「商品ページURL＝0点」は推測ではなく**確定**になった。

### 15.11.3 【確認】保存期間 18か月は正しかった（ただし義務は「削除」）

**DPP（日本語原文・逐語）**

> 「ソリューションプロバイダーは、法令や規制により、より長期の保存が必要とされる場合を除き、個人識別情報以外のデータ（PII以外のデータ）を18か月以内に削除する必要があります。」

「18か月保存してよい」ではなく **「18か月以内に削除する必要がある」**。
SP-API を実装するなら、**削除処理は任意機能ではなく必須項目**になる。

### 15.11.4 出典URLの訂正

`developer-docs.amazon.com/sp-api/docs/acceptable-use-policy` と `.../data-protection-policy` は、
**別ホストへ転送されたうえで「Page Not Found」になる**（実際に開いて確認）。
規約本文が読めるのは以下。**ルール59はAPIだけでなく出典リンクにも当てはまる。**

| 文書 | URL |
|---|---|
| 利用規定（AUP・日本語） | `https://sellercentral.amazon.com/mws/static/policy?documentType=AUP&locale=ja_JP` |
| データ保護ポリシー（DPP・日本語） | `https://sellercentral.amazon.com/mws/static/policy?documentType=DPP&locale=ja_JP` |

### 15.11.5 まだ分からない3件（憶測で埋めない）

| # | 分からないこと | 状況 |
|---|---|---|
| A2 | AUP 4.5「Amazonのビジネスに関するインサイト」の定義 | **本文に定義が無い。** 一番厳しく読むと当社の仕入判断が該当しうる |
| A3 | Amazon以外の市場で売る商品の仕入判断に使ってよいか | 規約に記述が無い |
| A5 | プライベート開発者登録の審査基準・所要日数 | 公式ページに到達できず。**それらしいURLを書かない** |

### 15.11.6 点数は動かない。だが「1位のままだから進めてよい」ではない

商品ページURLはもともと0点だったので**合計77点・Gate通過は変わらない**。
**点数は「どれが有望か」を示すもので、「着手してよいか」を示すものではない。**
着手の可否は §15.11.1 と §15.11.2 を人が判断してから決まる。

## 15.12 売れるかテスト（Phase 3.9d・v2.2で追加）

### 15.12.1 ご本人の判断（2026-08-22）

> 「一旦これが売れるものなのかどうかテストするので keepa を使用して」

これを受けて次の2つが決まった。

| 項目 | 決まったこと |
|---|---|
| Amazon SP-API | **見送り**（当面進まない） |
| Keepa | **使い続ける** |

**規約上の整理**：AUP 4.3（外部データサービスの使用禁止）は **SP-API を使い始めてはじめて掛かる**条項。
SP-API に手を出さない以上、Keepa を使い続けること自体に規約上の問題は生じない。

**ただし決まったのは「見送り」だけで、第1自動市場はまだ決まっていない。**
SP-API を外した結果、**Gate を通った候補は0件**になった。
ここで2位を繰り上げることはしない（繰り上げたらGateを置いた意味が消える）。

### 15.12.2 なぜ「売れるかテスト」を作ったか

これまでの `/validation` は、1件の出品を7日・30日・90日と見張って
「本当に売れたか」を確かめる仕組みだった。正確だが **答えが出るまで3ヶ月かかる**。

先に知りたいのは1つだけ。**「この商品は、そもそも売れているのか」。**
過去の販売履歴を見れば待たずに分かる。それを人が Keepa の画面で見て、数字を書き写す。

- 画面：**`/sellability`**
- 判定：`lib/sellability.ts`（外部依存ゼロ）／記録：`lib/sellcheck.ts`／表：`sellability_checks`
- 受け入れテスト：`npm run test:phase3-9d`（**76項目**）

### 15.12.3 判定は4種類（2択にしない）

| 判定 | 意味 |
|---|---|
| `SELLS` | 売れている（自分にも回ってきそう） |
| `CROWDED` | **売れてはいるが、ライバルが多く自分に回りにくい** |
| `DOES_NOT_SELL` | 売れていない |
| `UNKNOWN` | 判断できない（材料が足りない） |

**`CROWDED` を消して2択に戻さない。**
月30個売れていても出品者が60人いれば自分の番は来ない。
これを「売れる」に入れると回転しない在庫を掴み、「売れない」に入れると勝てる商品を捨てる。

取り分の計算は **ライバル数 +1**（自分を数に入れる）。+1 を外すと取り分を多く見積もる。

### 15.12.4 いちばん大事な但し書き

**Keepa の「売れ筋順位の下落回数」は、販売数そのものではない。**

- 1回の注文で2個売れても、下落は1回のことがある
- 下落が起きない販売もある
- 販売以外の理由で順位が動くこともある

だからそこから出した値は **必ず「推定」と呼ぶ**（変数名も `estimated*`、画面表示も「推定」）。
確定した販売数として書いた瞬間に「正確性 > 安全性 > 利益」の順番が崩れる。

### 15.12.5 閾値（勝手に緩めない）

| 条件 | 判定 |
|---|---|
| 期間中に1回も下がっていない | 売れていない |
| 下落が **3回未満** | 判定しない（たまたまと区別がつかない） |
| 自分が加わると **月1個**に届かない | `CROWDED` |
| 観測が **30日**より古い | 判定しない |
| 必要な欄が空いている | 判定しない（推測で埋めない） |

**下げれば候補は必ず増える。だから下げない。**
変えるときは理由・変えた人・日付をファイルに残す（ルール81）。

### 15.12.6 Keepa の扱い（許可8項目）

| 項目 | 値 |
|---|---|
| 8項目すべて | **`UNKNOWN`** |
| Gate | **不通過**（自動接続の候補にしない） |
| いまの使い方 | 人がブラウザで見て書き写す（`HUMAN_ENTRY`） |
| システムからのアクセス | **一切なし** |

**なぜ全部 UNKNOWN なのか**：keepa.com は自動アクセスを **403 で拒否**するため
（`keepa.com/#!api` と `keepa.com/api-docs/` の両方で確認）、**規約本文を読めていない**。
検索で出てくる料金・仕様の記述は第三者記事であって一次情報ではないので根拠にしない。

### 15.12.7 Keepa 由来を実市場データに数えない

`sellability_checks.counts_as_real_market` は **0で固定**（引数で切り替えられない）。

理由は2つ。①Keepa は Amazon ではなく第三者サービスで、市場から正式に提供されたデータではない
②その使い方が規約上認められているか未確認。

**数え始めてよいのは、ご本人が Keepa の規約を読んで商用利用と保存の可否を確認したあとだけ。**

### 15.12.8 「売れる」を「買ってよい」にすり替えない

`/sellability` が出すのは「売れているか」だけ。
利益が出るか・手数料がいくらか・状態が合っているかは、まったく別の判定である。
`SELLABILITY_SCOPE_NOTE` を画面から消さない。

### 15.12.9 いまの正直な数字（2026-08-22）

|---|---|
| 調べた商品 | **0点** |
