## 0. なぜこの修正をしたか（きっかけ）

ユーザーからの指示。

> ここでは新機能を増やさず、まず「人が10件入力したときに、どこが面倒か・
> どこまで自動判定できるか」を測るのが一番価値があります。

> ここからは機能を思いつきで追加するのではなく、実測で"次に作るもの"を決める段階です。
> これが一番重要です。

これまでは「機能を作る → 動くか確かめる」の順で進めてきた。
Phase 3.8 はその順番を変える。**先に人が10件やってみて、かかった時間を測り、
その数字で次に作るものを決める。**

だから今回作ったものは、新しい儲けの仕組みではなく、
**「10件やってみた結果を、ごまかさずに数える道具」**である。

## 1. 作ったもの（6つ）

### ① 落ちた理由を8分類で数える（`lib/dropout.ts`）

10件入力しても、全部が「買える候補」になるわけではない。
どこで落ちたのかを、次の8つのどれかに必ず入れる。

| 分類 | 意味（人間向け） |
| --- | --- |
| `MODEL_NUMBER_MISSING` | 型番が分からず、商品を特定できなかった |
| `NO_SELL_MARKET` | 売れる市場が1つも無い |
| `PRODUCT_MATCH_FAILED` | 他市場の商品と同じ商品だと確認できなかった |
| `MARKET_DATA_MISSING` | 比べる相手の相場が無い |
| `FEE_UNVERIFIED` | 手数料の実額が確認できていない |
| `SHIPPING_UNKNOWN` | 送料が分からない |
| `INSUFFICIENT_MARGIN` | 計算はできたが、利益が足りない |
| `LOW_DATA_CONFIDENCE` | データの確からしさが足りない |

**「その他」を作っていない。** 「その他」があると、面倒なものが全部そこへ入り、
結局なにが原因か分からなくなるため。受け入れテストで「その他」の存在を禁止している。

大事なのは、この8つのうち **どれが多いかで、打つ手がまったく違う** こと。

- 型番が取れない → 入力方法を直す（自分でできる）
- 相場が無い → 市場を増やす（自分でできる）
- 利益が足りない → **判定を甘くするのではなく、仕入先を増やす**（CLAUDE.md ルール13）

### ② 同じ商品かどうかを人が答え合わせする（`lib/matchreview.ts` ＋ 画面）

機械は型番の文字列で「同じ商品」と判定している。これは**必ず間違える場面がある**。
色違い・サイズ違い・年式違い・国内版と海外版・セット品と単品。

ユーザー指示：

> 利益商品を見逃すより、違う商品を同じ商品として扱う方が危険です。

この非対称さを、そのまま実装に落とした。

- **見逃し**（買えたはずの商品を逃した）→ 損失は儲け損ねだけ。財布からお金は出ない。
- **取り違え**（違う商品を同じだと計算した）→ 8万円の相場だと思って5万円で仕入れたら
  実物は相場2万円の別モデル。**実際に3万円を失い、在庫も手元に残る。**

だから答えは3択だけにした。

| 答え | 扱い |
| --- | --- |
| 同じ商品で合っている（`CORRECT_MATCH`） | 合格 |
| **違う商品だった（`INCORRECT_MATCH`）** | **重大。1件でもあれば100件へ進まない** |
| 判断が付かない（`UNCERTAIN`） | 合格にも不合格にもしない |

**「たぶん合っている」という選択肢を作らなかった。**
迷ったものが全部そこへ入り、それが結局は合格として扱われるため。
そして迷うもの＝紛らわしいもの＝いちばん危ないもの。

**機械の判定を人の答えで上書きしない。**
`tracked_listings.identity_key`（機械の判定）はそのまま残し、人の答えは別の表
`identity_match_reviews` に置く。上書きすると「機械が何回間違えたか」が数えられなくなる。

「違う商品だった」を選んだときは、**何が違ったかの記入を必須**にした
（空欄では保存できない）。理由が残らないと、次に同じ取り違えを防げないため。

### ③ 次に自動化する工程を、実測した秒数で決める（`lib/automation.ts`）

工程は6つ（商品発見／商品情報確認／型番確認／状態確認／CSV入力／その他）。
観測CSVに工程ごとの秒数を書くと、自動で集計される。

ここには**間違えやすい落とし穴**がある。

> 時間が長い工程 ＝ 次に自動化すべき工程、ではない。

「商品発見」と「商品情報確認」はたいてい一番時間がかかるが、
**このシステムでは自動化できない**。外部サイトを無断で自動巡回しない決まりだからで、
公式APIか正式なデータ提供が無い限り、人が見るしかない。
秒数だけで並べると、この2つが上位に来て「そこを自動化しよう」という誤った結論になる。

そこで**2つの並びを両方出す**。

1. **かかっている時間の順**（事実）
2. **自動化して効く順**（時間 × 自動化しやすさ）← こちらが「次に作るものの順番」

`AUTOMATION_ROI` は「1000件やるなら何時間か／自動化後に何時間残るか」を出すが、
**「全部自動化して0時間」にはならない**式にしてある。人が残る工程があるため。
測れないときは数字を作らず「計算できません」と書く。

### ④ データが汚れていないかの点検（`lib/integrity.ts`）

8つの点検。重大5つ・気になる点3つ。

重大：同じ商品ページの二重登録／記入見本やテスト行の混入／売り切れを確認していないのに
成約価格が入っている／価格が0以下／観測日時が初回より前。

**見つけても黙って直さない。人に見せて、人が直す。**
自動で消すと「なぜ汚れたか」が分からなくなるため。

### ⑤ 100件へ進むための安全条件7項目（`lib/pilot.ts`）

ユーザー指示の7条件をそのまま機械判定にした。

1. 重大な不具合が0件
2. **取り違え（FALSE MATCH）が0件**
3. 同じ商品ページの二重登録が0件
4. 記入見本・テスト行の混入が0件
5. 入力時間が現実的（1件平均180秒以下）
6. Routeの計算が正常
7. 答え合わせ（SHADOW）の記録が保存できている

Phase 3.7 で作った**操作性7項目とは別に持ち**、**両方そろって初めて100件へ進む**。
片方だけでは進まない。

「まだ1件も確認していない」状態を、黙って合格にしない仕掛けも入れた
（`unmeasurable` という状態を持ち、○にしない）。

### ⑥ ①〜⑧の報告（`npm run pilot` ／ 画面 `/validation`）

ユーザー指示14の8項目を、そのまま出す。
①実測結果 ②いちばん時間がかかった工程 ③いちばんデータが取れなかった項目
④同一商品判定で起きた問題 ⑤Routeにならなかった主な理由 ⑥見つかった不具合
⑦次に自動化すべき工程TOP3 ⑧100件へ進んでよいか。

## 2. 今回みつけた不具合（実際に直した）

**記入見本の作業時間を「実測」として数えていた。**

画面に最初から入っている記入見本（`SAMPLE`）を取り込むと、
出品そのものは「実市場データではない」と正しく弾かれる。
ところが**そこに書いてある作業秒数だけは作業ログに残っていた**。

その結果、誰も実際には作業していないのに

```
型番確認  2分（26%） 自動化しやすい
商品発見  2分（25%） 正規の取得手段が無いと難しい
```

という表が出ていた。**この数字を見て「次は型番確認を自動化しよう」と決めていたら、
一度も測っていないものを根拠に開発方針を決めることになる。**

CLAUDE.md ルール33（実績値には実市場データだけを使う）と
ルール35（測っていない数字を良く見せない）に反していた。

**直した内容**：出品1件ごとの作業記録は、その出品が実市場データのときだけ数える。
除外した分は黙って引き算せず、「記入見本・テスト用の行に書かれていた ◯分 は
実際の作業ではないので数えていません」と画面と `npm run pilot` に必ず書く。

直したあとの表示：

```
工程ごとの作業時間（実測）と、自動化の効き目
   まだ記録がありません。
   工程ごとの作業時間がまだ1件も記録されていません。まず観測CSVに工程ごとの秒
   数を書いてください。（記入見本・テスト用の行に書かれていた 8分 は、実際の
   作業ではないので数えていません）
```

**これが正しい状態。** まだ誰も入力していないのだから、順位が出る方がおかしい。

### テスト自体で起きた失敗と対策

受け入れテストが**後片付けに実在しない形の商品キーを書いていた**ため、
1回目の失敗時にテスト用の相場行が開発用データベースへ残り、2回目が
「同じ行が既にある」で落ちた。

- 原因：商品キーの実際の形は `bm:NIKE|DZ5485612||` で、テストは
  `model:nike|dz5485-612` を消そうとしていた。
- 対策：テスト用データは**実在の型番を使わない**（`P38TESTONLY001` のような
  テスト専用の型番にする）。そうすれば型番の文字列で確実に消せて、
  本物の相場データを巻き添えにしない。残っていた1行は手作業で除去済み。

## 5. 次にやること（人がやる作業）

**メルカリの実出品を10件、手で入力する。** ここは自動化しない（無断巡回しない決まり）。

- 型番・JANが取りやすいものを優先（スニーカー／ゲーム機／カメラ／型番付き家電／トレカ）
- **1カテゴリに偏らせない**（最多でも6件程度）
- **分からない項目は推測せず空欄**
- **工程ごとの秒数を必ず書く**（最低でも入力秒数）

入力後に `npm run pilot` を実行すると、①〜⑧が自動で出る。
そこで初めて「次に自動化する工程」が数字で決まる。

**10件が終わるまで100件へ進まない。**
