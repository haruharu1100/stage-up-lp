# Phase 6.5 — 仕入データ源の探索：採点基準

> [!info] この文書の役割
> 「どのデータ源を使うか」を**気分で決めないため**の物差しです。
> 候補を調べる**前に**基準を固定し、あとから基準を動かして特定の候補を勝たせることを防ぎます。
> 実際の候補30件の採点結果は [[33_Phase6.5_候補30件の採点とTOP5]] に記録します。

---

## 0. Phase 6.5 のゴール（これが達成できなければ次へ進まない）

**世界中から、AI Commerce OS の社内自動仕入調査に「正式に」使える商品データ源を見つける。**

有名ECサイトを1つずつ調べることがゴールでは**ありません**。
最終目的は**利益の出る商品を見つけること**であって、Connectorの数を増やすことではありません。

### 合格ライン（1件でも満たせば次へ進める）

次の4つが**すべて YES** のデータ源が、最低1つ確認できること。

| 項目 | 必要な値 |
|---|---|
| `COMMERCIAL_USE_ALLOWED` | YES |
| `INTERNAL_BUSINESS_USE_ALLOWED` | YES |
| `AUTOMATED_RETRIEVAL_ALLOWED` | YES |
| `PURCHASABLE_PRODUCTS` | YES |

> [!danger] 1件も見つからなければ、Live Connector の実装へは進まない
> 「見つからなかった」も正しい結論です。無理に接続する方が事業を壊します。

## 1. 探す対象（小売ECだけに絞らない）

前回までは「有名EC」に寄りすぎていました。今回は次の全部を対象にします。

| 種別 | 例 |
|---|---|
| EC公式API | 小売ECが公開する商品検索API |
| 卸会社API | B2B卸事業者のAPI |
| メーカー商品Feed | メーカーが直接配る商品データ |
| 卸商品Feed | 卸が配る商品データ |
| Affiliate Product Feed | ASPが配る商品データフィード |
| Partner API | 提携事業者だけが使えるAPI |
| 法人向け商品データ | 有料の法人契約データ |
| 価格比較データ | 価格情報を売っている事業者 |
| 在庫Feed | 在庫数の配信 |
| CSV / XML / JSON Feed | ファイル形式での配布 |
| B2B Marketplace API | 法人向けマーケットプレイス |
| 海外卸API | 海外の卸プラットフォーム |
| 正規Distributor Feed | 正規代理店の商品データ |

---

## 2. 「APIがある」だけでは不合格

APIの存在は入口にすぎません。次の8つが揃って初めて、仕入の道具になります。

1. 商品を**実際に購入できる**か
2. **価格**が取れるか
3. **在庫**が確認できるか
4. **商品を識別**できるか（JAN / GTIN / 型番）
5. **商品URL**が取れるか
6. **商用利用**できるか
7. **社内分析**に使えるか
8. **自動取得**してよいか

---

## 3. 記録スキーマ（全候補を同じ形で記録する）

26項目。値は原則 **YES / NO / UNKNOWN** の3値。

| # | 項目 | 意味 |
|---|---|---|
| 1 | `SOURCE_NAME` | データ源の名前 |
| 2 | `COUNTRY` | 国 |
| 3 | `SOURCE_TYPE` | 上の「種別」のどれか |
| 4 | `API_EXISTS` | 公式APIがあるか |
| 5 | `DATA_FEED_EXISTS` | データフィード配布があるか |
| 6 | `CSV_EXISTS` | CSVで受け取れるか |
| 7 | `COMMERCIAL_USE_ALLOWED` | 商用利用が認められているか |
| 8 | `INTERNAL_BUSINESS_USE_ALLOWED` | 社内限定の業務利用が認められているか |
| 9 | `AUTOMATED_RETRIEVAL_ALLOWED` | 自動取得が認められているか |
| 10 | `PRICE_COMPARISON_ALLOWED` | 他市場との価格比較が認められているか |
| 11 | `DATA_STORAGE_ALLOWED` | 自社DBへの保存が認められているか |
| 12 | `PURCHASABLE_PRODUCTS` | そこで実際に買えるか（カタログだけではないか） |
| 13 | `PRICE_AVAILABLE` | 価格が取れるか |
| 14 | `STOCK_AVAILABLE` | 在庫が取れるか |
| 15 | `JAN_AVAILABLE` | JANが取れるか |
| 16 | `GTIN_AVAILABLE` | GTINが取れるか |
| 17 | `MODEL_NUMBER_AVAILABLE` | 型番が取れるか |
| 18 | `PRODUCT_URL_AVAILABLE` | 商品URLが取れるか |
| 19 | `IMAGE_AVAILABLE` | 画像が取れるか |
| 20 | `RATE_LIMIT` | 取得制限 |
| 21 | `API_COST` | 費用 |
| 22 | `APPLICATION_REQUIRED` | 申請・審査が必要か |
| 23 | `AI_ANALYSIS_ALLOWED` | AIによる分析が認められているか |
| 24 | `OTHER_DATA_COMBINATION_ALLOWED` | 他社データと混ぜてよいか |
| 25 | `LEGAL_CONFIDENCE` | 法務の確からしさ（HIGH / MEDIUM / LOW） |
| 26 | `TECHNICAL_DIFFICULTY` / `BUSINESS_VALUE` | 技術難度 / 事業価値 |

### 追加項目（今回の方針変更で追加）

| 項目 | 意味 |
|---|---|
| `SUPPLY_TYPE` | `ONE_OFF`（一点物） / `REPLENISHABLE`（再入荷あり） / `WHOLESALE`（卸） |
| `AMAZON_RESALE_ALLOWED` | 仕入れた商品をAmazonで転売してよいか |
| `MIN_ORDER` | 最低発注ロット・最低取引金額 |
| `SHIPS_TO_JAPAN` | 日本へ送れるか（海外候補のみ） |

---

## 4. UNKNOWN は絶対に加点しない

> [!danger] 「たぶん使える」は禁止
> `API_EXISTS = YES` でも `COMMERCIAL_USE_ALLOWED = UNKNOWN` なら、**Live Connector候補にしない**。
> 「禁止と書かれていない」は許可の根拠になりません（ルール58）。
> 原文引用＋出典URL＋確認日の3点セットが無い項目は、YESと数えません（ルール145）。

---

## 5. `SUPPLIER_CONNECTOR_SCORE`（100点満点）

| 配点 | 項目 | 何を見るか |
|---:|---|---|
| 25 | 正式利用可能性 | 規約上、堂々と使えるか。ここが低い候補は他が満点でも採用しない |
| 15 | 商品数 | 扱い商品の量 |
| 10 | 価格取得 | 価格が機械で取れるか |
| 10 | 在庫取得 | 在庫が機械で取れるか |
| 10 | JAN・GTIN・型番 | Amazon商品と**同一商品だと確定**できるか |
| 5 | 商品URL | 人間が「購入ページを開く」できるか |
| 10 | API自動化 | 自動で回せるか |
| 10 | 仕入価格競争力 | Amazon相場に対して安いか |
| 5 | APIコスト | 費用の重さ |

> [!danger] 法務Gateを通らない市場は、点数が高くても選択禁止
> スコアは「使ってよい候補の中での順位づけ」にしか使いません。
> 門が閉じている市場を、点数で開けることはできません。

---

## 6. `REPEATABILITY_SCORE`（継続して仕入れられるか）

一度きりの掘り出し物より、**同じ商品を繰り返し仕入れられる**方が自動化に向いています。

| 見るところ |
|---|
| 同じ商品を繰り返し購入できるか |
| 在庫が安定しているか |
| 一度に複数個買えるか |
| 商品IDが固定されているか（毎回変わらないか） |
| 価格の更新を取得できるか |

### なぜ重要か

- メルカリの中古一点物 → `ONE_OFF`。見つけても次が無い
- 卸の商品100個 → `WHOLESALE`。毎月同じ利益が積める

**この2つは、まったく別の事業です。**

---

## 7. 継続性を利益で見る

| 例 | 1個あたり利益 | 回数 | 合計 |
|---|---:|---:|---:|
| A：一点物の掘り出し物 | 5,000円 | 1回 | 5,000円 |
| B：卸の定番商品 | 1,500円 | 月100個 | **150,000円／月** |

→ 今後の仕入評価に **`EXPECTED_MONTHLY_PROFIT`（想定月間利益）** を持たせます。
1回の大当たりより、月10万円が続く方が価値があります。

---

## 8. データ源の費用は「悪」ではない

> [!note] 無料APIにこだわらない
> 月1万円のデータでも、月10万円以上の利益が増えるなら、使う価値があります。

そのため次の4つを設計します。

| 項目 | 意味 |
|---|---|
| `DATA_SOURCE_COST` | そのデータ源にかかる月額 |
| `EXPECTED_BUY_OPPORTUNITIES` | 月に何件の仕入候補が出るか |
| `EXPECTED_MONTHLY_PROFIT` | 想定される月間利益 |
| `DATA_SOURCE_ROI` | （想定月間利益 − 月額）÷ 月額 |

---

## 9. 使う順番（上から順に検討する）

```
1. 公式API
2. Partner API
3. 有料Feed
4. 卸Feed
5. 許可されたCSV
6. 手動入力  ← 最後の手段
```

人間の手入力は、**最後の手段**です。最初から手入力を前提にしません。

## 10. 検証のしかた（見つかったあとの手順）

### 10-1. 段階Gate（絶対に守る）

```
1件 → 5件 → 10件 → 47件
```

> [!danger] いきなり47件検索は禁止
> 現在 `SUPPLIER_SEARCH_PENDING = 47` 件が最初の検証セットです。
> 1件目でつまずいたら、そこで止めます。

### 10-2. 1件目で確認する連鎖（全部つながって初めて合格）

```
Amazon商品 → JAN/型番 → Supplier検索 → 同一商品候補
          → 仕入価格 → 送料 → 在庫 → 商品URL → Amazon利益計算
```

### 10-3. 保存済みKeepa100件で相性を見る

Amazonの需要がある100件に対して、その候補が

- 何件**検索できたか**
- 何件**実際に販売があったか**
- 何件**利益候補になったか**

例：検索可能70 / 販売あり30 / 利益候補8 → **かなり強い候補**。

## 11. 最終形（人が探すのをやめる）

正式なConnectorができたら、人間は探しません。

```
Keepa需要候補 → AI Commerce OS → Supplier Connector → 商品候補が自動で出る
```

### 「最安の市場を見つけるAI」にする

特定の仕入先を中心にしません。

| 仕入先 | 価格 |
|---|---:|
| A | 4,800円 |
| B | **4,300円** ← ルート候補 |
| C | 5,100円 |

Connectorは**複数**ある前提で作ります（A/B/C/D → 最適仕入）。

---

## 12. 変わらない安全装置

> [!danger] 自動購入はしない
> AIは仕入候補を見つけ、**[購入ページを開く]** まで。
> **購入は人間が行います。**

- スクレイピングはしない（実装の選択肢にすら入れない）
- 外部への問い合わせはAIがしない（人間が送る）
- 商品データ本体は、許可が出るまで1件も取得しない
