## 1. 前提：KOMEHYOは「最初の候補の1つ」でしかない

仕入先はどんどん追加する。**本体コードに店名を書かない。**

### 想定候補（あくまで候補。実施可否は各社の規約確認が必須）

| 分類 | 例 |
|---|---|
| ブランドリユース | KOMEHYO / BRAND OFF / 大黒屋 / RAGTAG |
| 総合リユース | BOOKOFF / HARD OFF / OFF HOUSE / セカンドストリート / ネットオフ |
| ホビー・トレカ | 駿河屋 |
| 業者向け | 古物市場 / 業者市場 / KOMEHYOオークション |
| 上流 | 卸会社 / メーカー |
| EC | 国内EC / 海外EC / Alibaba |

> [!danger] 追加する前に必ず確認する（例外なし）
> **データ取得・再販・自動購入が、その会社の規約・法人契約・API提供条件で認められているか。**
> 確認結果は `suppliers.terms_checked_at` と `terms_note` に必ず記録する。
> 確認が済んでいない仕入先は capability を `unavailable` のままにし、システムに載せない。
> 詳細な確認項目は [[02_Phase0_外部連携調査]] §5。

## 2. Multi Supplier Connector の構造

仕入先1社の追加が **「設定ファイル＋Adapter数枚」** で済む形にする。

```
SupplierConnector（1社 = 1つ）
  ├── capabilities         この店で何ができるか（api / csv / manual / unavailable）
  ├── AuthAdapter          ログイン・APIキー・法人契約の扱い
  ├── CategoryAdapter[]    ★カテゴリごとに1枚（本 / 家電 / ブランド / トレカ …）
  ├── PriceNormalizer      価格の意味を揃える
  ├── InventoryAdapter     在庫の意味を揃える
  └── RateLimitPolicy      アクセス頻度（先方に迷惑をかけない）
```

### 2.1 CategoryAdapter（同じ店でもカテゴリで別物）

BOOKOFF系は「本・ゲーム・トレカ・フィギュア・ホビー・家電・ブランド・時計・アパレル」で
**利益の出方も、同一商品の特定方法も、リスクもまったく違う。**

| カテゴリ | 同一商品の決め手 | 特有のリスク | 相場元 |
|---|---|---|---|
| 本・コミック | ISBN（**決定的に一意**） | 状態・書き込み・帯欠品 | Amazon / 中古相場 |
| ゲーム | JAN + 型番 | 動作不良・欠品（説明書・箱） | Amazon / 駿河屋 |
| トレカ | 型番 + レアリティ + **状態(PSA等)** | 真贋・状態評価のブレが大きい | スニダン / 遊々亭 |
| フィギュア・ホビー | JAN + 型番 | 箱潰れ・パーツ欠品 | 駿河屋 / ヤフオク |
| 家電 | 型番（**メーカー型番が命**） | 動作保証・PSE・付属品 | Amazon / 価格.com系 |
| ブランドバッグ・時計 | 型番 + シリアル + **画像** | **真贋** / 状態ランクの解釈差 | KOMEHYO / 各種 |
| アパレル | ブランド + 型番 + サイズ + 色 | サイズ表記の差・季節性が強い | 各種 |

**CategoryAdapter が持つもの**
- そのカテゴリの識別キー（ISBN / JAN / 型番 / シリアル…）と優先順位
- 必要な追加項目（トレカならレアリティと鑑定、家電なら付属品）
- MATCH_SCORE の閾値（**ISBNが取れる本は高く、一点物ブランドは慎重に**）
- リスク係数の初期値（真贋・状態・返品）
- 使うべき相場元（MarketDataConnector）

> [!important] 本は簡単・ブランドは難しい
> ISBNがある本は「同一商品判定」がほぼ100%決まる。LLM不要でコストも激安。
> ブランド一点物は画像判定が必須でコストも高い。
> **同じ閾値・同じコスト前提で設計してはいけない。** カテゴリごとに変える。

### 2.2 PriceNormalizer（価格の意味を揃える）

店によって「表示価格」の意味が違う。揃えないと利益計算が全部ズレる。

| 揃える項目 | 例 |
|---|---|
| 税込／税抜 | 税抜表示の店は税込へ換算 |
| 送料 | 送料込み価格／別途／条件付き無料（○円以上） |
| ポイント還元 | 実質コストから引くか引かないか（**既定：引かない＝保守的に見る**） |
| 会員価格・セール | 誰でも買える価格か、条件付きか |
| 手数料 | オークションの落札手数料・システム利用料 |
| 通貨 | 為替レートと取得時刻を保存 |
| 状態ランク | 店ごとの表記（S/A/B/C、未使用/美品/良品…）を**共通6段階へマッピング** |

**共通状態ランク（提案）**
```
N  新品・未使用
S  未使用に近い
A  目立った傷や汚れなし
B  やや傷や汚れあり
C  傷や汚れあり
D  全体的に状態が悪い / ジャンク
```
店ごとのマッピング表を `supplier_condition_map` に持つ。
**マッピングが定義されていない状態表記は `MANUAL_REVIEW` へ**（勝手に推測しない）。

### 2.3 InventoryAdapter
「在庫あり／残り1点／店舗在庫／取り寄せ」を共通表現へ。
**「取り寄せ」「予約」を在庫ありとして扱わない**（買えない商品を候補にしない）。

### 2.4 RateLimitPolicy
仕入先ごとに設定。既定：1リクエスト/2秒・同時1接続・差分取得優先。
**先方サーバーに負荷をかける取得はしない。**

## 3. 仕入先 × カテゴリの得意分野学習

### 3.1 学習すること
「どの店の、どのカテゴリが、実際にいちばん儲かったか」を **実販売結果から** 学ぶ。

```
KOMEHYO        → ブランドバッグ・時計に強い
BOOKOFF        → 本・ゲーム・トレカ・ホビー
HARD OFF       → 家電・楽器
セカンドストリート → アパレル・ブランド
```

> [!warning] これは「一般論」であって「事実」ではない
> 上の表は**仮説**。実際にどこが強いかは自社の販売結果でしか分からない。
> **一般論を初期値として持つのは可。だが3ヶ月後には自社データで上書きする。**
> 一般論をそのまま信じ続けるのが最悪。

### 3.2 学習の単位（`supplier_performance`）
```
仕入先 × カテゴリ × ブランド × 価格帯
```
それぞれについて次を集計：
- 仕入件数 / 販売件数 / 販売率
- 売上 / 純利益 / 平均ROI
- 平均在庫日数
- 返品率
- **予測精度**（予想利益 vs 実利益の誤差）
- **不良率**（状態不一致・偽物疑い・欠品）

### 3.3 学習結果の使い道
1. **探索の優先度**：儲かっている組み合わせを重点的に巡回する（頻度を上げる）
2. **BUY_SCORE の補正**：得意な組み合わせは加点、苦手は減点
3. **予測の補正**：「この店の状態Aは実際にはBに近い」といった補正係数
4. **撤退判断**：3ヶ月連続で赤字の組み合わせは巡回を止める

> [!important] 補正は必ずバックテストを通してから適用する
> サンプル30件未満の補正は適用しない（[[03_安全設計と事故防止]] §9）。

## 4. Supplier Performance Analytics（仕入先ランキング）

### 4.1 月次で自動集計する指標

| 指標 | 意味 |
|---|---|
| 仕入先別 売上 | |
| 仕入先別 純利益 | **ランキングの主軸** |
| 平均ROI | 効率 |
| 平均在庫日数 | 資金拘束 |
| 成功率 | 仕入れたうち黒字で売れた割合 |
| 返品率 | |
| 予測精度 | 予測と実績の誤差 |
| **資金拘束日数あたり利益** | ★真の評価軸 |
| 発見効率 | 発見1,000件あたりの利益商品数 |
| 判定コスト | 1件あたりのAI費用 |

### 4.2 表示例
```
── 仕入先ランキング（2026年8月・純利益順）──────────────
1位 KOMEHYO          純利益 820,000円  ROI 24.1%  在庫日数 18日  成功率 87%
2位 BOOKOFF          純利益 610,000円  ROI 31.5%  在庫日数  9日  成功率 92%
3位 HARD OFF         純利益 370,000円  ROI 19.8%  在庫日数 27日  成功率 78%
4位 セカンドストリート 純利益 140,000円  ROI 12.2%  在庫日数 44日  成功率 61%  ⚠️

AIコメント：
・BOOKOFFはROIと回転日数が最も良い。仕入額を増やす余地がある
・セカンドストリートはアパレルの在庫日数が長い。カテゴリを絞ることを推奨
・HARD OFFの家電は返品率が高い（8.2%）。動作確認済み商品に限定すべき
```

### 4.3 カテゴリ別の内訳も必ず出す
「BOOKOFFが2位」ではなく **「BOOKOFFのトレカが1位、本は赤字」** まで分解する。
店単位の平均は、良い分野と悪い分野を打ち消して見えなくする。

## 5. Winning Product Expansion（勝ち筋拡張）

### 5.1 目的
**売れた商品から、次に売れる商品をAIが自分で見つける。**

```
あるLouis Vuittonバッグが高回転で売れた
  ↓
① 同一商品を再仕入できないか探す
  ↓
② 同シリーズ（同じライン・同じ型番系列）を探す
  ↓
③ 似た型番・同価格帯を探す
  ↓
④ 同ブランドの他カテゴリを探す
  ↓
⑤ 類似商品（画像・属性が近いもの）を探す
  ↓
利益商品を追加 → 商品数が増える → さらに売れる → また拡張
```

### 5.2 拡張のトリガー
| トリガー | 条件（既定） |
|---|---|
| 高回転で売れた | 売却日数 <= 14日 かつ 純利益 > 0 |
| 高利益で売れた | ROI >= 25% |
| 複数回売れた | 同セグメントで3件以上の黒字 |
| 値上げに耐えた | ステップアップして売れた（→[[07_価格戦略設計]]） |

### 5.3 拡張の5段階（近い順に、優先度高→低）

| # | 拡張軸 | 探索キー | 信頼度 |
|---|---|---|---|
| 1 | **同一商品の再仕入** | 同じ型番・同じ状態 | 最高 |
| 2 | **同シリーズ** | 同ブランド × 同ライン名 × 型番の前方一致 | 高 |
| 3 | **同価格帯・同カテゴリ** | 同ブランド × 同カテゴリ × ±20%価格帯 | 中 |
| 4 | **同ブランドの他カテゴリ** | 同ブランド | 中〜低 |
| 5 | **類似商品** | 画像・属性の近さ（埋め込みベクトル） | 低（要検証） |

`expansion_seeds` テーブルに「どの実績から、どの軸で、何を探しているか」を記録する。

### 5.4 拡張が生む探索クエリ
拡張は「探し方の指示」を生成する。これを各 SupplierConnector へ配る。

```json
{
  "seed_inventory_id": "inv_123",
  "axis": "same_series",
  "brand": "Louis Vuitton",
  "series": "ネヴァーフル",
  "category": "ショルダーバッグ",
  "price_range_jpy": [80000, 160000],
  "condition_min": "B",
  "priority": 88,
  "expires_at": "2026-09-19"
}
```

- 優先度は「元になった実績の良さ × 拡張軸の信頼度」で決まる
- **有効期限を必ず持たせる**（古い勝ち筋を永久に追わない）
- 各仕入先の巡回スケジュールに、この探索クエリを差し込む

### 5.5 暴走防止（ここが一番危ない）

> [!danger] 勝ち筋拡張は「一極集中」を生む
> 「ルイヴィトンが儲かる」→ ルイヴィトンばかり探す → ルイヴィトンばかり買う
> → **資金がルイヴィトンに集中** → そのブランドの相場が崩れた瞬間に全滅。

| 防止策 | 内容 |
|---|---|
| ブランド集中上限 | 資金配分の `MAX_PER_BRAND_RATIO`（既定30%）が拡張にも効く |
| 探索の多様性枠 | 探索クエリの **30%は必ず「勝ち筋以外」に割り当てる**（`EXPLORE_DIVERSITY_RATIO`） |
| 拡張の深さ制限 | 拡張から生まれた商品がさらに拡張を生むのは **2段まで**（`MAX_EXPANSION_DEPTH`） |
| 実績の鮮度 | 90日より古い実績を種にしない |
| 相場下落の監視 | 種になったセグメントの相場が下落したら、拡張クエリを即停止 |
| サンプル数 | 1件の成功だけで大規模拡張しない（軸2以降は3件以上の実績を要求） |

### 5.6 拡張の効果測定
拡張から生まれた商品の成績を、通常発見と分けて測る。

```
通常発見    : 発見10,000件 → 販売120件 → 純利益 480,000円（1件あたり4,000円）
勝ち筋拡張  : 発見 1,200件 → 販売 68件 → 純利益 390,000円（1件あたり5,735円）★効率1.43倍
多様性枠    : 発見 3,000件 → 販売 22件 → 純利益  61,000円（1件あたり2,772円）
```
**多様性枠は効率が悪くて当然**（新しい鉱脈を探しているので）。
効率だけで多様性枠を削らない。削ると次の勝ち筋が見つからなくなる。

## 6. 仕入先を1社追加する手順（運用マニュアル）

```
1. 規約・法人契約・API提供条件を確認  ← ★ここが終わるまで何も作らない
2. 確認結果を suppliers.terms_note へ記録（確認日・URL・結論）
3. capability を決める（api / csv / webhook / manual / unavailable）
4. AuthAdapter を書く（必要なら）
5. 扱うカテゴリを決め、CategoryAdapter を用意
6. PriceNormalizer に税・送料・ポイント・状態ランクのマッピングを定義
7. RateLimitPolicy を設定
8. SANDBOX で取込テスト（外部送信なし）
9. 少量（例100件）で試験運転し、同一商品判定の精度を人間が検証
10. 精度が基準を満たしたら本運用へ
11. 1ヶ月後、supplier_performance で評価
```

**9を飛ばさない。** 新しい仕入先は必ず「少量 → 人間検証 → 本運用」の順。

## 7. Phase 対応

| 機能 | Phase |
|---|---|
| SupplierConnector / CategoryAdapter / PriceNormalizer の枠 | **Phase 1**（最初から複数仕入先を想定した形で作る） |
| 状態ランクの共通マッピング | **Phase 1** |
| 2社目・3社目の追加 | **Phase 2〜4**（規約確認が済んだ順） |
| supplier_performance の集計 | **Phase 4**（実績が出てから） |
| 得意分野の学習と補正 | **Phase 7** |
| Winning Product Expansion | **Phase 4 で記録開始 → Phase 6-7 で自動化** |

> [!important] 枠だけは最初から作る
> 「あとで複数仕入先に対応する」は必ず失敗する。**Phase 1 の時点で2社を想定した形**にしておく
> （実際に繋ぐのは1社でよい。構造だけ先に用意する）。
