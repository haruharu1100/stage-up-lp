## 2. 考え方の整理（ここが一番大事）

これまでは「AIにURLを作らせない」という一本のルールで守っていた。
しかし、よく見ると**危ないのはURLを組み立てる行為そのものではない**。

| | 危険か | 理由 |
|---|---|---|
| AIが「たぶんこのASIN」と文字列を作り、そこからURLを組む | **危険** | 実在する**別の商品**のページへ人を送る。人は「AIが出したリンクだから」と信じるので、いちばん気づきにくい |
| Keepaが「この商品が実在する」と返したASINから、Amazon公式の形（`/dp/{ASIN}`）で組む | 危険ではない | 材料が確かめられている。組み立て方は決まりきっていて、AIの判断が入る余地がない |

→ **問題は「組み立て」ではなく「材料」だった。**
そこで、材料（＝ASIN）に必ず出どころの札を付けて回す設計へ変えた。

## 3. 作ったもの

### 3-1. ASINの出どころ（`lib/keepa/asinsource.ts`）

このファイルは**何も読み込まない**（画面にも載せられる＝ルール37）。

**使ってよい出どころ 4つ**

| コード | 意味 |
|---|---|
| `KEEPA_API` | Keepaの正式なAPIが返したASIN |
| `OFFICIAL_AMAZON_SOURCE` | Amazon公式の画面・公式APIで確認したASIN |
| `AUTHORIZED_DATA_FEED` | 正式に提供を受けたデータの中にあったASIN |
| `HUMAN_INPUT` | 人が実際の商品ページを見て入力したASIN |

**禁止の出どころ 3つ**

| コード | 意味 |
|---|---|
| `AI_GUESS` | AIが推測で作った |
| `STRING_GENERATION` | 文字列として組み立てた |
| `UNVERIFIED_SEARCH_RESULT` | 検索結果に出てきただけで裏を取っていない |

**確からしさ 3段階**
`VERIFIED_EXISTS`（実在確認済み） / `REPORTED`（そう書かれていただけ） / `UNVERIFIED`（未確認）。
**「たぶん実在」という段階は作らない。**

### 3-2. 商品ページURLの組み立て（7つの検査）

`resolveAmazonProductUrl()` は、次の**7つを全部通ったときだけ**URLを作る。
1つでも欠けたら**作らず、理由を日本語で残す**。

1. 出どころが禁止リストに入っていない
2. 出どころが許可リストに入っている
3. 確からしさが `VERIFIED_EXISTS`
4. 確認した時刻が記録されている
5. ASINが10桁の形をしている
6. 対象がAmazon.co.jp（domain=5）
7. 親子の役割が `PARENT` / `UNKNOWN` ではない

作ったURLの出どころは **`AMAZON_OFFICIAL_ASIN_PATTERN`** と記録する。
**`AI_GENERATED` という選択肢は、そもそもコードに存在しない。**

組み立ててよいファイルは **`lib/keepa/asinsource.ts` の1つだけ**（受け入れテストが他の7ファイルを検査している）。

### 3-3. 親ASIN・子ASINの区別

サイズや色の違う商品は、Amazonでは「親（選ぶ前の画面）」と「子（実際に買える）」に分かれる。
**親ASINのページへ人を送ると、別の枝を買わせる事故になる。**

`STANDALONE` / `CHILD` / `PARENT` / `UNKNOWN` の4種で判定し、
**`PARENT` と `UNKNOWN` にはURLを作らない。分からないものを `STANDALONE` に寄せない。**

### 3-4. 「リンクが正しい」と「商品が同じ」を分ける

| 値 | 意味 |
|---|---|
| `URL_VALID` | このリンクは正しい形で、実在するASINを指している |
| `PRODUCT_MATCH_CONFIRMED` | このASINが、自分の仕入れたい商品と**同じもの**だと確認できた |
| `PURCHASE_URL_AVAILABLE` | 上の**両方**がそろった（＝ここで初めて「開く」導線を出せる） |

**`runOneAsin` は `PRODUCT_MATCH_CONFIRMED` に必ず 0 を入れる。**
機械が自分で「同じ商品だ」と決めることはしない。

### 3-5. 出どころは「名乗る」のではなく「記録から引く」

`npm run keepa:one` は、出どころを**コマンドの引数で受け取らない**。
`--source=KEEPA_API` と書けてしまうと、どんな文字列でも「Keepaが確認した」と名乗れてしまうため。

保存済みの `keepa_asin_candidates` から `lookupAsinProvenance()` で引くだけで、
引いたあとも**もう一度許可リストを通す**。
禁止の出どころが付いていた場合は、**通信する前に止まる**（枠を1つも使わない）。

### 3-6. 候補ASINを1件だけ選ぶ（`npm run keepa:discover`）

Keepaの商品検索（Product Finder）を**1回だけ**呼ぶ。`-- --dry` で通信ゼロの下見ができる。

- 枠は **11**（基本10 ＋ 結果100件ごとに1。`perPage` の最小が50なので1ページで11）
- `stats=1` は **+30** になるので**付けない**
- Best Sellers（50）は使わない
- 上限 `KEEPA_MAX_DISCOVERY_TOKENS = 15` を超える条件は投げない
- **1件も返らなくても条件を緩めない**（緩めれば必ず何か返るが、それは条件を満たした商品ではない）
- 返ってきた候補は**全部**保存し、選んだ1件に `chosen = 1` を立てる

**候補選定の枠は `purpose = 'DISCOVERY'`、商品取得は `'PRODUCT_FETCH'` と分けて記録する。**
混ぜると「1件1枠」に見えてしまい、1商品あたりの本当の費用が分からなくなる。

### 4-4. 今回わかった宿題（Buy Boxが取れない）

**候補を絞るときは Buy Box の価格（1,000円以上）で絞り込めたのに、
商品を取得すると Buy Box の価格が `-1`＝不明で返ってきた。**

これは当社のコードの不具合ではない（`SCHEMA_MISMATCH` は0件）。
Keepa は Buy Box の情報を、追加の指定（出品明細の取得）をしないと返さない仕様である。
**追加で頼むと枠が大きく増える**ため、今は頼んでいない。

- 今のまま：Buy Box と FBA/FBM は**常に「不明」**になる。
  ライバルの多さの採点で**2項目が点に入らない**（＝分からないものを都合よく0点＝安全と読まない）。
- 頼む場合：1商品あたりの枠が跳ね上がる。**どの商品に対して頼むかを決めてから**にすべき。

**→ いま決めることではない。** 判定に効いているのは事実なので、宿題として残す。
（勝手に「たぶんこのくらい」で埋めることは絶対にしない。）

## 7. 追加したルール（CLAUDE.md の98〜102）

- **98** ルール55を2つに割る。危ないのは「URLを組み立てること」ではなく「材料が確かめられていないこと」
- **99** ASINには必ず出どころを付けて回す。禁止の出どころは通信前に止める。**引数で名乗らせない**
- **100** `URL_VALID` と `PRODUCT_MATCH_CONFIRMED` を最後まで別の値として持つ
- **101** 購入導線には実際にOfferがあるChild ASINを使う。`PARENT` / `UNKNOWN` にはURLを作らない
- **102** 候補選定で大量の枠を使わない。使った枠は用途を分けて記録する

**ルール74（SP-APIはURLを返さないので組み立てない）は、98によって置き換わった。**
組み立て自体は禁止ではなく、**出どころが確かなときだけ**行う。
