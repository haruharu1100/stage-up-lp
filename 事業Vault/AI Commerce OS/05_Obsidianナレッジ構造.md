# Obsidian ナレッジ構造（AI会社の共有記憶）

> 上位文書: [[00_設計書v1_最上位]]

**目的**：Claude Code / Codex / OpenAI API が **同じルールと同じ失敗の記憶を参照する**ようにする。
コードのDBは「数字の記録」、Obsidianは「判断と理由の記録」。役割を分ける。

---

## 1. 使い分けの原則

| 置き場所 | 入れるもの | 例 |
|---|---|---|
| **DB（commerce.db）** | 数字・件数・時系列・個々の取引 | 商品ごとの利益、予測誤差、監査ログ |
| **Obsidian（事業Vault）** | 仕様・判断・理由・傾向・失敗の教訓 | 「このブランドは季節変動が大きいので在庫を持たない」 |
| **claims.jsonl（DIGEST）** | **全プロジェクト横断の絶対ルール** | 「景表法上こう書いてはいけない」 |

> [!warning] 二重管理しない
> 商品1件ごとの数字をObsidianへ書き出さない。**集計して分かった「傾向」だけ**を書く。
> 逆に、判断の理由をDBのカラムだけで表現しようとしない。

## 3. AIが書く／人間が書く

| 文書 | 書き手 | タイミング |
|---|---|---|
| 00〜05 の仕様書 | Claude Code | 仕様が変わったとき（**必ず統合。別ファイルを増やさない**） |
| 現行ルール / ルール変更履歴 | Claude Code | 閾値・重みを変更したとき |
| ブランド別／カテゴリ別／販路別傾向 | AIが自動生成 | 月次。サンプル30件以上のものだけ |
| 成功商品 / 失敗商品 | AIが自動生成＋人間が補足 | 損益確定時。**特に損切りは必ず記録** |
| SHADOW結果 / バックテスト | AIが自動生成 | 評価バッチ実行後 |
| インシデント | 人間が起票 → AIが原因分析を追記 | 事故発生時（**当日中に**） |
| 月次レポート | AIが自動生成 | 月初 |
| 改善案 | 両方 | 随時 |

## 4. テンプレート

### 4.1 失敗商品（最重要）
```markdown
---
type: 失敗商品
date: 2026-XX-XX
brand: XXX
category: XXX
marketplace: XXX
loss_jpy: -XX,XXX
---
# {商品名}

## 何が起きたか
（事実のみ）

## AIの予測
予想販売価格 / 予想日数 / 予想純利益 / BUY_SCORE / MATCH_SCORE

## 実際
実売価格 / 実日数 / 実純利益

## なぜ外れたか（原因）
- [ ] 同一商品の誤判定
- [ ] 相場データが古い／偏り
- [ ] 手数料の見落とし
- [ ] 需要の読み違い（季節・トレンド）
- [ ] 状態の見誤り
- [ ] 競合の急増
- [ ] その他：

## ルールへの反映
（→ 10_仕入ルール のどこをどう変えたか。変えないなら「変えない理由」を書く）
```

### 4.2 インシデント
```markdown
---
type: インシデント
date: 2026-XX-XX
severity: critical / warn
---
# {件名}

## 発生時刻・検知方法
## 影響範囲（金額・件数）
## 直接原因
## 根本原因
## 応急処置
## 再発防止（コード変更 / ルール変更 / 監視追加）
## 同じ仕組みで防げる他の事故はないか
```

### 4.3 ルール変更
```markdown
---
type: ルール変更
rule_version: v{n} → v{n+1}
date: 2026-XX-XX
---
## 変更内容（どの閾値・重みを、いくつから、いくつへ）
## 変更理由（どの実績データに基づくか）
## バックテスト結果（旧 vs 新・サンプル数・判定）
## SHADOW並走期間と結果
## 承認者
```

## 5. AIへの読ませ方

### 起動時に必ず読ませる
`ai-commerce-os/CLAUDE.md`（プロジェクト直下）に次を書く：

```
このシステムを触る前に、必ず以下を順に読むこと。
1. 事業Vault/AI Commerce OS/00_設計書v1_最上位.md
2. 同フォルダ内の全ファイル
3. 事業Vault/DIGEST.md（全プロジェクト共通の絶対ルール）
矛盾したら、常に最新のユーザー指示 > DIGEST > 本フォルダ の順で優先する。
```

### 判断のときに参照させる
- 仕入判断のとき → `10_仕入ルール/現行ルール` と `20_学習ログ/失敗商品`
- 新販路を追加するとき → `02_Phase0_外部連携調査`（規約確認の結論）
- 自動化を広げるとき → `03_安全設計と事故防止` と `40_運用記録/インシデント`

### 横断ルールへの昇格
このプロジェクトで得た教訓のうち、**他事業にも当てはまるもの**は
`事業Vault/20_KNOWLEDGE/claims.jsonl` へ昇格させる（`remember.sh` を使う）。
例：「応答不明の外部APIは再送しない」は全プロジェクト共通の原則になりうる。

## 6. 運用の注意

1. **書きっぱなしにしない。** 学習ログは月次で見直し、古い傾向は更新か削除。
2. **サンプル数を必ず書く。** 「3件でこう見えた」を法則として扱わない。
3. **不明は「不明」と書く。** 推測で埋めない（DIGEST の原則）。
4. **仕様変更は必ず 00 へ統合する。** メモを増やして仕様を分散させない。
5. **数字はDBが正。** Obsidianの数字が古いと感じたらDBを見に行く。
