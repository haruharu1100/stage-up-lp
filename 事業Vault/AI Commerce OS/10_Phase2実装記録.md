## 1. Phase 2 の範囲（ユーザー指示そのまま）

> 市場を「仕入先」と「販売先」に固定しないでください。
> 同じ市場が、安ければ仕入先／高く売れるなら販売先の両方になれる構造にしてください。

**やったこと**：取得 → 比較 → Route生成 → 利益計算 → SHADOW記録

**絶対にやらないもの（フラグOFFではなく、コードごと存在しない）**

- 実購入 / 実出品 / 実決済 / 実発送
- 外部サイトへの自動ログイン / 無許可スクレイピング
- 自動値上げ
- 所有していない商品の先行販売

受け入れテストで「購入・出品・決済・発送のテーブルが存在しないこと」を毎回検査している。

## 2. 最重要の設計判断

### 2.1 「できる」と「してよい」を別の欄に分けた

最初、スニダンを `can_sell = 0`（売れない）としてモデル化した。**これは間違いだった。**

`can_sell = 0` にすると、スニダンが販売先候補から消える。
すると **「本当は一番高く売れる販売先を取り逃している」という事実が画面から消える。**
自分が何を失っているかが見えないシステムは、判断材料として役に立たない。

修正後：

| 欄 | 何を表すか | スニダンの値 |
|---|---|---|
| `can_buy` / `can_sell` | 市場の構造として売買機能があるか | `1` / `1` |
| `terms_status` | 規約・契約上の状態 | `BLOCKED` |
| `automation_permission` | 自動化してよいか | `NOT_ALLOWED` |

→ **計算はする。実行だけを止める。** Routeは `status = 'BLOCKED'` として保存し、
`blocked_reason = 'SELL_TERMS_BLOCKED'` を持たせて「取り逃し一覧」に出す。

**この分け方は今後も崩さないこと。** 使えない市場を消すのは、目をつぶるのと同じ。

### 2.2 取り逃しを仮定値ででっちあげない

上の実装直後、KOMEHYO→スニダンで「平均31,987円の取り逃し」と表示された。
しかし対象はバッグと時計で、**スニダンが扱っていない商品だった。**

原因：相場が未登録の市場に対して、共通の参考相場（`REFERENCE_FALLBACK`）を当てはめていた。

修正：**使えない市場（BLOCKED / NOT_ALLOWED）は、実際の相場観測データがある時だけ取り逃しとして出す。**
無ければその組み合わせは作らない。

> 根拠のない機会損失額を自分に見せてはいけない。判断が歪む。
> 「わからない」は「データなし」と書く。数字を作らない。

### 2.3 異常価格チェックを除外条件の**一番先**に置いた

最初の実装では、除外条件の順が「赤字 → 利益不足 → ROI不足 → 売却確率不足」で、
異常価格チェックが入っていなかった。

結果、テストデータのロレックス（仕入 90,000円／相場 1,800,000円＝比率0.05）が
**ROI 1700%・利益 1,622,350円の「最優良Route」として最上位に出た。**

これは Phase 1 の `cheapFilter()` が `ANOMALY_LOW_RATIO = 0.15` で弾いていたケース。
Route側でも同じガードを、**除外条件の先頭**に置いた。

> [!danger] 順番が仕様
> 異常価格チェックを後ろに置くと、データ誤りが「利益が大きいRoute」として上位に出る。
> Fail Closed は「最後に確認する」のでは意味がない。**最初に止める。**

人間が現物・出典を確認済み（`human_verified`）の場合だけ、このチェックを通す。

### 2.4 BUY費用とSELL費用を1つの関数に混ぜない

Phase 1 の `calcProfit` は「仕入価格＋販売費用」を1つの固定費（`fixedCost`）に畳んでいた。
市場が仕入先にも販売先にもなる以上、**それでは「どこで買うか」を比較できない。**

`calcAcquisitionCost()`（BUY側）と `calcNetReceipt()`（SELL側）を完全に別関数にした。
片方に相手側の費用項目が混ざっていないかを、受け入れテストで毎回検査している。

**Phase 1 との整合の担保**：BUY側の費用をすべてゼロにすると、
Route の純利益は `calcProfit` と **1円単位で一致する**。これをテストで検算している。
式を単純化した瞬間に落ちるので、安全に触れる。

## 4. テストデータで確認できた挙動（2026-08-20）

```
取込 1,021件 → 分析 1,011件 → 相場観測 1,030件
組み合わせ 9,970通り計算 → Route 8,016件保存
  成立 562件 ／ 規約で使えない 30件 ／ 基準に届かず 7,424件
ベストが決まった商品 94件・予想純利益 合計 1,961,815円・平均ROI 42.6%
```

**双方向が実際に出ていることの確認**（同じ市場が両側に出ている）：

| 買う → 売る | 件数 | 平均ROI |
|---|---|---|
| ヤフオク! → Amazon | 75 | 40.5% |
| メルカリ → Amazon | 65 | 36.6% |
| ヤフオク! → eBay | 52 | 43.0% |
| ヤフオク! → メルカリ | 52 | 25.9% |
| メルカリ → ラクマ | 30 | 24.6% |
| ブックオフ → eBay | 11 | 61.5% |

メルカリとヤフオク!が **買う場所としても売る場所としても成立している**。これが狙い。

### 「利益が最大＝ベスト」にならないことの確認

ニコン Z fc（ブックオフ仕入）の12通り：

| 売る場所 | 純利益 | ROI | 30日確率 | 日数 | 点数 |
|---|---|---|---|---|---|
| eBay | **44,366円** | **81.9%** | 30.0% | 40日 | 71点 |
| Amazon | 41,348円 | 76.3% | 41.3% | 25日 | 75点 |
| ラクマ | 32,592円 | 60.2% | 45.8% | 18日 | 81点 |
| **メルカリ** | 30,980円 | 57.2% | **63.0%** | **12日** | **84点 ← ベスト** |

利益が一番大きい eBay は7位。**売れる確率と資金の回転で負けている。**
これが「単純に一番高い市場を選んではいけない」の実物。

## 5. 受け入れテスト

```
npm run test:phase2   → 49項目 全通過
npm run test:phase1   → 66項目 全通過（Phase 1 を壊していない）
```

**仕様を変えたら両方通すこと。** 片方だけ通して満足しない。

Phase 2 テストが見ているもの（要点）：

- 市場の能力欄（can_buy/can_sell/terms_status/automation_permission）が全市場で埋まっている
- 手数料が市場ごと×BUY/SELL別に分かれ、**一律の率になっていない**
- 同じ市場が仕入先にも販売先にもなっている／同一市場内の自己売買が成立していない
- BUY側の内訳にSELL専用費用が混ざっていない
- 純利益＝入金予想−仕入総額 が全件一致する（手数料表から計算し直しても一致）
- **BUY費用ゼロなら Phase 1 の純利益と完全一致**
- 異常価格（安すぎ／高すぎ）が成立Routeに残っていない
- 参考相場の仮定値だけでBUY判定にならない
- 使えない市場の取り逃しを仮定値ででっちあげていない
- 売却確率が 7日 ≦ 30日 ≦ 90日 になっている
- 利益が最大のRouteが必ずしもベストに選ばれていない
- 何も所有していない（`ownership_state` が全件 `NOT_OWNED`）
- 購入・出品・決済・発送のテーブルが存在しない

### テストを1つ書き直した（記録として残す）

最初「同じ2市場が向きを変えて**両方**成立している組があること」を条件にしたが、これは誤り。
A→Bが黒字で B→Aも黒字になるなら、**相場データの方が矛盾している**（安く買えて高く売れるが逆も成立、はあり得ない）。

正しい条件は「**同じ市場が、ある組み合わせでは買う側、別の組み合わせでは売る側になっていること**」。
そう書き直して通した。**テストが通らない時、実装ではなくテストの前提が間違っていることがある。**

## 6. 次にやること（Phase 3 の入口）

1. **SHADOW の答え合わせ**。30日後に「本当にその値段で売れたか」を突き合わせる仕組み。今は記録するだけ
2. **手数料の実額確認**。いま18件が概算のまま。公式の料金ページで確定させる（確定するまで自動購入は禁止）
3. **相場データの供給元**。いまはCSV取込のみ。公式API・正式なデータ提供の契約が取れた順に差し込む
4. Triangle Arbitrage（A買→B売→B買→C売）。データ構造は拡張可能にしてある
5. クロスリスティング（同じ在庫を複数市場へ同時出品）。**Routeとは別概念**として実装する
