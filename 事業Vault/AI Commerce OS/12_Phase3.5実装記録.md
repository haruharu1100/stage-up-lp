# 12_Phase3.5実装記録（実市場データ接続・SHADOW精度検証）

作成: 2026-08-20 ／ 対象コード: `hp-auto-system/ai-commerce-os/` ／ ポート 3910
上位ルール: [[00_設計書v1_最上位]] → [[09_Phase1実装記録]] → [[10_Phase2実装記録]] → [[11_Phase3実装記録]] → 本ノート の順で読む。

> このノートの目的は「次に入るAI・人間が、過去の判断を追体験できること」。
> **結論だけでなく、なぜそう決めたか・何を間違えたか** を残す。

## 0. 一番大事なこと（ここだけ読むなら）

**Phase 3.5 は「性能を上げる工程」ではなく「まだ進ませないための関門を作る工程」だった。**

Phase 3 完了時、画面には「平均ROI 42.6%」「予想純利益196万円」と出ていた。
だがこれは **全部テストデータ（seed）の数字** で、実市場の成績ではない。
この数字を成果として扱うと、次に入るAIは「もう十分では」と判断してしまう。

だから Phase 3.5 で、

1. テストデータの成績を**成績表から完全に外した**
2. 実市場データが0件なら「的中率100%」ではなく「**測定不能＝不合格**」と出すようにした
3. Phase 4 へ進む条件を **14項目の機械判定** にし、**条件を書き換える経路をコードに持たせなかった**

結果、画面の結論は **「まだ実購入に進めません。14項目中0項目クリア。」** になった。
**これが正しい状態である。** 数字が悪いのではなく、まだ測っていないだけ。

## 1. Phase 3.5 の範囲（ユーザー指示そのまま）

> 「この状態なら、次は実購入ではなく **Phase 3.5：実データ接続・精度検証** に進めるのが一番いいです。
> ①手数料を実額化、②仕入側・販売側の実相場を入れる、③SHADOWを100件以上ためる、④予測誤差を補正する。
> この4つを終えてから実売買へ進ませます。」

> 「**まだ実購入・実出品は絶対に解禁しないでください。**」

> 「次の大きな目標は「100件集めること」そのものではなく、
> **STRONG BUYだけに絞ったとき、どれくらいの確率で本当に利益が出るのかを測ること**です。
> 最終的に「STRONG BUYの実市場Precision 90%」のような数字が出てくれば、
> そこから初めて少額の実取引へ移す価値が出てきます。」

**やったこと**：手数料の確からしさ判定 → 実市場データ判定 → 時系列相場 → 利益機会の半減期 →
3本立て予測 → 誤りの種類分け（FP/FN） → 精度KPI → Phase 4 卒業条件の機械判定 →
少額実取引の安全設計（設計のみ） → 経営者向けレポート

**やっていないもの（フラグOFFではなく、コードごと存在しない）**

- 実購入 / 実出品 / 実決済 / 実発送
- 外部サイトへの自動ログイン・無断の自動巡回
- 自動値上げ
- AIが自分でしきい値や解錠フラグを変える経路

`EXECUTION_PATHS`（purchase / listing / payment / autoLogin）は全て `false` で、
`assertNoExecutionPath()` が受け入れテストで毎回それを確認する。

## 3. 実装で確定した仕様（なぜそうしたか）

### 3.1 手数料は「確認済み」でなければ STRONG BUY にしない

`fee_status` が `VERIFIED` 以外（概算・期限切れ・不明）の市場は、
データ信頼度が満点にならず、**利益がどれだけ大きくても90点に届かない**。

これは Phase 2 からある「概算のままで自動購入しない」の延長。
**利益率で押し切れないようにしてある**のがポイントで、
「ROI 60%だから多少の概算は許容」という判断ができない構造にした。

**料金改定があっても、過去のSHADOWを新料金で再計算しない。**
再計算すると、後から都合よく「あのときの判断は正しかった」に変えられてしまう。

### 3.2 実市場データは「両側」揃って初めて実データ

仕入側と販売側の**両方**が実観測のときだけ `REAL_MARKET_DATA = true`。
片方が参考値なら実データにしない。

片側だけで認めると、「販売相場だけ実データ、仕入は参考値」のような
**半分だけ本物の成績**が100件たまってしまい、精度を証明したことにならない。

### 3.3 相場は上書きせず、追記する

`market_snapshots` は追記型。現在価格でレコードを上書きしない。
上書きすると価格がいつ動いたかが消え、次の「利益機会の寿命」が測れなくなる。

### 3.4 半減期と「人の承認に間に合うか」

市場の組ごとに、利益機会の半分が消えるまでの時間（中央値）を測る。
消滅実績が5件未満なら `UNKNOWN` として判定しない（少ない実績で断定しない）。

| 判定 | 条件 | 意味 |
|---|---|---|
| `HUMAN_APPROVAL_OK` | 半減期 ≧ 承認時間×2 | 人の確認を挟んでも取れる |
| `TIGHT` | 半減期 ≧ 承認時間 | ぎりぎり |
| `AUTO_ONLY` | それ未満 | 承認前に消える |
| `UNKNOWN` | 実績5件未満 | 判定しない |

> [!danger] ここが一番誤読されやすい
> **`AUTO_ONLY` は「自動化してよい」という意味ではない。**
> 「人の承認前提では取れない機会である」という**事実の記録**である。
>
> × 間に合わないから自動購入を解禁する
> ○ 間に合わないから、その市場の組は**今の体制では取りに行かないと決める**
>
> 速さのために安全確認を飛ばさない。取り逃しは損失ではなく、**払っていないコスト**である。

### 3.5 予測は3本立て、実購入判断は保守値

| 名前 | 中身 | 使いどころ |
|---|---|---|
| `RAW` | 補正なしの理論値 | 素の計算を残すため |
| `CALIBRATED` | 実績のズレで補正 | 学習が効いているか見るため |
| `CONSERVATIVE` | さらに保守的に割り引く | **将来の実購入判断はこれ** |

補正は**実市場データからのみ**作る。
Phase 3 で出ていた −10.1pt の補正値はテストデータ由来なので、本番の補正には使わない。

あわせて 80%予測レンジ・`DOWNSIDE_PROFIT`（下振れ時の利益）・
`MAX_EXPECTED_LOSS`（最大想定損失）を持たせた。
**「うまくいけばいくら儲かるか」だけでなく「外したらいくら減るか」を必ず並べて出す。**

### 3.6 間違いの重さは同じではない（FPはFNの3倍）

| 種類 | 意味 | 痛み |
|---|---|---|
| FALSE POSITIVE | 買うと判断したが損した | **現金が減る** |
| FALSE NEGATIVE | 見送ったが儲かっていた | 儲け損ねただけ |

ユーザー指示「赤字商品を大量購入する方が危険」に従い、
重み付き誤りスコア ＝ **(FP×3 + FN) ÷ 全体** とした。

`WATCH` は「買う」と判断していないので FP 側には数えない。
ここを混ぜると、様子見が全部「間違い」に化けて数字が読めなくなる。

### 3.7 的中率には必ず95%下限を併記する

3件中3件当たったら的中率100%だが、それは**偶然と区別がつかない**。
Wilson下限（95%）を併記し、卒業条件でも下限側に閾値を置いた（75%以上）。

**実市場データが0件なら「測定不能」＝不合格。** 100%とは表示しない。

### 3.8 卒業条件は「測るだけ」で「書き換えない」

ユーザー指示「**勝手に条件を緩和しないでください**」。

- 判定コード（`lib/gate.ts`）は条件を測るだけ。条件を書き換える経路を持たない
- しきい値は設定（`GATE_*`）にあるが、**AIがそれを変更する手段は実装していない**
- 測れていない項目は **不合格** として扱う（データが無いほど通りやすくしない）
- 判定結果は `phase_gate_log` に残り、「いつ緩めたか」を人が後から追える

### 3.9 二重の鍵

```
鍵1：14項目すべて合格
鍵2：人間が PHASE4_UNLOCKED を true にする
```

鍵1が全部通っても、鍵2が無ければ何も起きない。
さらに現時点で**実購入のコードは1行も存在しない**。両方の鍵が開いても勝手には買わない。

### 3.10 少額実取引は「設計だけ」

| 上限 | 値 |
|---|---|
| 1件あたり | 10,000円 |
| 1日あたり | 30,000円 |
| 同一商品 | 1個まで |
| 対象判定 | `STRONG_BUY` のみ |
| 手数料 | 買う側・売る側とも `VERIFIED` のみ |

これに 人の解錠済み／卒業条件合格／実市場データ／半減期が `AUTO_ONLY` でない／冪等キーあり
を加えた9条件を全部満たしたときだけ「実行してよい」と**判定するだけ**。
判定の先に実行する処理は書いていない。

### 3.11 結論1行はAIが書き換えられない

日次レポート（`npm run report`）と画面 `/readiness` の一番上の1行は、
卒業条件の判定結果から**機械的に**生成される。
条件を1つでも満たしていなければ、必ず「**まだ実購入に進めません**」になる。

「次にやること」も**1つだけ**出す。
3つ並べると、一番簡単なものだけやって終わるため。

## 4. つまずいた点と対処

### 4.1 画面を開くだけで監査ログが増えていた

最初、卒業条件の判定関数がその場で `phase_gate_log` に INSERT していた。
これを画面から呼ぶと、**ページを開くたびに履歴が1行増える**。
「条件をいつ緩めたか」を後から追うための履歴が、閲覧ログに埋もれて読めなくなる。

→ `peekPhase4Gate()`（測るだけ）と `evaluatePhase4Gate()`（測って記録）に分離。
画面は peek、`npm run report` の実行時だけ record。

**教訓：監査ログは「実行の記録」であって「閲覧の記録」ではない。混ぜると監査にならない。**

### 4.2 テストの方が間違っていた（パーセンタイル計算）

受け入れテストで「パーセンタイルは線形補間されるはず」と書いて落ちた。
コードを読むと `Math.floor((件数-1)×p)` で、**実在する観測値のうち低い側を返す**実装で、
「件数が少ないときは一番低い値を返す（甘く見積もらない）」というコメントが付いていた。

→ **コードではなくテストを直した。**
中間の値を作ると「実際には一度も付いたことのない価格」を予測にしてしまう。
保守側に倒すこの実装が正しい。

**教訓：テストが落ちたとき、先に疑うのは実装ではなく自分の前提。**

### 4.3 型エラー2件

- 実データ判定を `=== 1` で比較していたが実体は真偽値 → 共通関数 `shadowIsRealMarket()` を通す形に統一
- `EXECUTION_PATHS` を `as const` にしたら全て `false` 型に狭まり、`=== true` の検査が意味を失った
  → `Record<string, boolean>` にして、**将来 true が混ざったら検知できる**ようにした

## 6. 実測（正直な数字・2026-08-20）

| 項目 | 今 | 必要 |
|---|---|---|
| 実市場データのSHADOW | **0件** | 100件 |
| STRONG BUY の判断件数 | **0件** | 30件 |
| STRONG BUY の的中率 | **測定不能** | 90%以上 |
| 同・95%下限 | **測定不能** | 75%以上 |
| 手数料の実額確認 | **0 / 18件** | 90%以上 |
| 正規の自動取得ができる市場 | **0件** | 1件以上 |
| Phase 4 卒業条件 | **0 / 14項目** | 14 / 14 |
| 人による解錠 | **まだ** | 人間のみ可 |

**結論：まだ実購入に進めません。**

> [!note] これは失敗ではない
> 実市場データ0件は「サボった結果」ではなく、**方針どおりの結果**である。
> 無断の自動巡回をしないと決めている以上、正規の取得手段が契約できるまで実データは増えない。
> ここで焦って**しきい値を下げる／スクレイピングで埋める**のが、
> このプロジェクトで最もやってはいけないこと。

## 7. 今いちばんの詰まりと、次の一手

**詰まり：正規の取得手段が1件も無い。**

打開策は **人が実際の公開画面を見て記録したもの**（`MANUAL_OBSERVATION`）を1市場ぶん入れること。
**契約を待たずに今日から始められる、当座の入り口**である。

> [!warning] 訂正（2026-08-20・ユーザー指摘）
> 「CSV連携だから規約上安全」という説明は**誤り**だったので取り消す。
> CSVは入れ物であって、根拠ではない。優先順位表の「④CSV連携」が指しているのは
> **事業者が正式に提供するデータフィード**（`OFFICIAL_CSV_FEED`）であって、
> 自分で画面を見て手で書き写したもの（`MANUAL_OBSERVATION`）ではない。
>
> この2つを同じ箱に入れると「手で写したものを正式提供データと同じ信頼度で扱う」という
> 一番危ない誤解が起きる。そこで `SourceClass` を新設して分離した。
> 詳細は `ai-commerce-os/lib/realdata.ts` の冒頭コメント。

順番はこう決めた。**同時に3つやらない。**

1. **1つの市場を選び、手動観測CSVを入れて実市場データを作り始める**（今ここ）
2. その市場の手数料を公式ページで実額確認する（`VERIFIED` にする）
3. 実市場SHADOWを100件ためる（件数が先。精度の議論はその後）
4. STRONG BUY の的中率と95%下限を測る ← **Phase 3.5 の本当のゴール**

## 8. 次に入るAIへの申し送り

1. **テストデータの数字を成果として報告しない。** ROIも利益額も、実市場データ0件なら0件と言う。
2. **卒業条件を緩めない。** 通らないのは条件が厳しいからではなく、まだ測っていないから。
3. **`AUTO_ONLY` を自動化の許可と読まない。** 「今の体制では取りに行かない」の意味。
4. **監査ログに閲覧を混ぜない。** 記録は実行時だけ。
5. **テストが落ちたら、まず自分の前提を疑う。**
6. **4つのテストを全部通す。** 66 / 50 / 113 / 110。
7. 実購入・実出品・実決済・自動ログインは**コードごと書かない**。人の明示指示があるまで着手しない。
