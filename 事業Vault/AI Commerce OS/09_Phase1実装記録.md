## 2. 今回の最重要の設計判断：価格方式を2つに分けた

ユーザー承認済み（2026-08-19）。**片方に統一してはいけない。**

| 対象 | 方式 | 中身 |
|---|---|---|
| 新品・型番商品（JAN/型番あり かつ 在庫>1） | **STEP_UP** | 売れたら次回の出品価格を **金額ベースで +5%**。`MAX_STEP_UPS=6` で頭打ち |
| 中古一点物（在庫1・個体差が大きい） | **PREMIUM_RATIO** | 「いくらで売れたか」ではなく **市場相場に対して何倍で売れたか** を学習。次の同種商品に倍率を当てる |

**なぜ分けたか**：中古一点物は同じ商品が二度と入らないので「前回の金額＋5%」に意味が無い。
一方「相場の1.08倍で売れる」は次の別個体にも使える知識になる。

**サンプルが足りないときの扱い**：`PREMIUM_RATIO_MIN_SAMPLES=5` 未満なら学習値を使わず
`DEFAULT_PREMIUM_RATIO=1.00`（＝相場どおり）を使い、画面に「実績が5件に満たないため暫定」と明記する。
推測値を実績のような顔で出さない。

学習の単位は段階的に広い方へ落ちる：`model`（ブランド＋型番）→ `brand_category` → `category`。

## 4. 計算の定義（曖昧にすると事故る所）

- **15%利益ルールは「仕入価格×1.15」ではない。** 全費用を引いたあとに純利益率15%が残る販売価格。
  `必要販売価格 = ceil( 固定費合計 × (1 + TARGET_NET_MARGIN) / (1 - 手数料率合計) )`
  実測例：仕入53,470円 → 単純な×1.15なら61,491円だが、正しい必要販売価格は**69,920円**。
- **損益分岐** `= ceil( 固定費合計 / (1 - 手数料率合計) )`
- 金額はすべて**整数の円**。丸めは常に自分に不利な側へ（費用は切上げ、利益は切捨て）。
- **LLMに金額計算をさせない。** Phase 1 はそもそもLLMを呼ばない。

### BUY SCORE（0〜100・ルールのみ）

利益30 ＋ ROI30 ＋ 相場余裕20 ＋ データ信頼度10 ＋ 在庫/状態リスク10
→ 90+ STRONG BUY / 80+ BUY / 70+ WATCH / 60+ LOW PRIORITY / それ未満 SKIP

### AIへ回す関門（Phase 1 では印を付けるだけ）

`除外されていない` かつ `BUY以上` かつ `スコア70以上` かつ `予想利益 ≥ AI単価15円 × 20倍 = 300円`
→ 実測 **37件 / 1,021件 = 3.6%**（要求は1〜5%）

## 5. つまずきと対策（同じ失敗を繰り返さないため）

| 症状 | 真因 | 対策 |
|---|---|---|
| 重複が0件と表示された | 再分析が `SKIPPED` 行を拾い直し、取込時に確定した `DUPLICATE` を上書きしていた | 再分析のWHEREから `skip_reason='DUPLICATE'` を除外。**取込時の判断は再分析で消さない** |
| AI候補が43%（要求は1〜5%） | ①WATCHまで通していた ②テストデータが儲かる商品に偏っていた | ①BUY以上に限定 ②**しきい値は下げず**、現実的な「儲からない商品」900件をテストデータへ追加（原則13） |
| 重複が235件に激増 | 重複キーが `型番 or 商品名` なので、大量生成データが同じ型番を共有して衝突 | 生成データの型番を1件ずつ別にした。**テストデータの作り方のバグを、判定側の緩和で隠さない** |
| 「チェ-ンショルダ-」と表示 | 全角→半角変換で長音符「ー」(U+30FC) をハイフンにしていた | 変換対象から除外。照合キー側は英数字以外を捨てるので影響なし |
| 本番ビルドが `node:crypto` で失敗 | 画面（クライアント）側が、暗号ハッシュを持つファイルから状態ランクを読んでいた | 状態ランクだけを `lib/conditions.ts` へ分離 |
| 除外理由が `NEGATIVE_PROFIT` と英語表示 | 取込結果画面だけ日本語辞書を通していなかった | 辞書を適用。**英語コードを人間に見せない** |
| 表の1行目（仕入価格など）が消えて見えた | 見出し行を `position: sticky` にしていたが、外側の `.scroll` が `overflow` を持つため見出しが表の中で固定され、下へスクロールすると1行目を覆っていた | 見出しの固定をやめた。**金額の行が隠れるのは致命的なので、見た目の便利さより正しさを取る** |

## 6. 受け入れテスト

`npm run test:phase1` … **66項目すべて合格 / 不合格0**

重要な点：テストは `calcProfit` を呼ばず、**利益・ROI・必要販売価格・損益分岐を独立に計算し直して照合する**。
本体にバグがあってもテストが一緒に間違えない作りにしてある。30件を抽出して全一致を確認。

確認している内容：テストデータ量 / 判定の全区分 / 除外理由10種の到達性 / 重複排除3層 /
利益計算の検算 / あといくら安く・高く / スコアと判定の整合 / AI費用の関門 / SHADOW /
価格方式の振り分け / 相場倍率の学習 / 人間確認 / 安全確認 / 判定ルール版。

### 架空データでの実測（2026-08-19）

```
取込 1,021件（KOMEHYO 343 / BOOKOFF 343 / HARDOFF 335）
分析 1,011件 完了1,003 → STRONG BUY 13 / BUY 24 / WATCH 16 / LOW PRIORITY 44 / SKIP 915
人間確認 11件（未登録の状態表記4種 + 価格異常2件）
AI候補 37件（3.6%）／ 処理時間 約1秒
仕入候補合計：必要資金 3,400,665円 / 予想純利益 1,657,885円 / 平均ROI 50.1%
```

### 画面の実動作確認（2026-08-19・ブラウザ）

- CSV貼り付け取込 → 取込と同時に分析され、除外理由が日本語で返る
- 知らない状態表記（例「ピカピカ」）は**推測せず人間確認へ**回る → 画面で登録すると即座に再判定される
- 価格異常（ロレックス 仕入9万/相場180万）は自動では買わず人間確認へ → 「データは正しい」を押すと再判定されSTRONG BUYへ
- 設定で目標利益率を15%→25%にすると、STRONG BUY 13→10 / SKIP 915→936 と全件が再計算される。判定ルール版も `v1-2be1ed80` → `v1-a02125df` へ変わる（後から「どのルールで判断したか」を追える）

## 7. 判定ルール版（rule_version）

しきい値10項目のハッシュ。現在 **`v1-2be1ed80`**。
全分析結果に記録するので、「この判断は当時どのルールだったか」を後から必ず追える。
しきい値を変えると版が変わる＝**過去の判断と混ざらない**。

## 8. 残っている課題（Phase 2 以降）

1. **手数料が全部「概算（ESTIMATED）」。** 各販路の公式料金ページで実額を確認して入れるまで、利益額は確定しない。
2. **相場価格の出どころが無い。** 今はCSVに書いてある値をそのまま信じている。相場データのConnectorが要る。
3. **売れた実績が0件。** よって相場倍率の学習はまだ全部が暫定値（1.00倍）。
4. **Next.js 14 に既知の脆弱性（高）が2件。** 内容はいずれも**インターネットに公開したサーバー**を攻撃するもので、
   手元のPCだけで動かしている今は実害が無い。ただし**外部公開する前に必ず Next.js 16 へ上げる**（作り直しが必要な大型更新のため、Phase 2 でまとめて行う）。
5. 仕入先は全部 `capability: csv`。**規約・法人契約を文書で確認できるまで `api` にしない。**
