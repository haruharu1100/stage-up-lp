## 1. 想定する事故（先に「何が怖いか」を並べる）

| # | 事故 | 被害 | 防ぐ仕組み |
|---|---|---|---|
| 1 | 別商品を同一商品と誤判定して仕入 | 売れない在庫が残る | MATCH_SCORE閾値・異常価格時の厳格化・画像照合 |
| 2 | 同じ処理が2回走り2重購入 | 資金が2倍出る | idempotency_key の UNIQUE 制約 |
| 3 | 在庫1個が複数販路で同時に売れる | キャンセル→評価悪化→アカウント停止 | 個体在庫＋条件付きUPDATE＋即時他販路停止 |
| 4 | 手数料を計算に入れ忘れて赤字仕入 | 買うほど損する | fee_rules の必須化・欠損時は SKIP |
| 5 | 古い相場データで判断 | 相場が崩れた商品を掴む | fetched_at の鮮度ガード |
| 6 | 相場データ取得が壊れ全商品が「激安」に見える | **暴走的な大量購入** | 異常検知＋自動停止＋1回あたり／日次の件数上限 |
| 7 | AIが閾値や予算を自分で緩める | 制御不能 | 設定変更はAI不可・人間のみ |
| 8 | 赤字ラインを割る値下げ | 売っても損 | listings.min_price_jpy を実行層で強制 |
| 9 | 偽物を仕入れて販売 | 法的責任・信用喪失 | AUTHENTICITY_RISK 閾値・FULL AUTO禁止 |
| 10 | アカウント規約違反で凍結 | **在庫が全部死ぬ最大リスク** | capability が api でなければ自動化しない |
| 11 | APIキー流出 | 金銭被害 | Secrets管理・コードに書かない・ログにマスク |
| 12 | LLMが壊れたJSONを返し不正な数値で判断 | 誤発注 | スキーマ検証必須・落ちたら SKIP |
| 13 | 予算超過 | 資金ショート | 4段階の予算上限＋最低現金残高 |
| 14 | 為替が動いて海外仕入が赤字化 | 損失 | fx_rate を保存し、変動幅が閾値超なら再評価 |

## 2. 権限設計（誰が何を変えられるか）

| 対象 | AI | 人間（運用） | 人間（管理者） |
|---|---|---|---|
| リサーチ・スコア算出 | ✅実行 | 閲覧 | 閲覧 |
| 購入の提案 | ✅ | 承認 | 承認 |
| 購入の実行（SAFE） | ❌ | ✅承認後 | ✅ |
| 購入の実行（FULL AUTO） | ✅条件内 | — | — |
| 出品内容の生成 | ✅ | 承認 | 承認 |
| 値下げ（赤字ライン上） | ✅モード依存 | ✅ | ✅ |
| 値下げ（赤字ライン下） | ❌**常に不可** | ❌ | ✅二段階確認 |
| 損切り実行 | ❌ | 提案のみ | ✅ |
| **閾値・重みの変更** | ❌ | ❌ | ✅ |
| **予算上限の変更** | ❌ | ❌ | ✅二段階確認 |
| **自動化モードの変更** | ❌ | ❌ | ✅二段階確認 |
| **Connector capability の変更** | ❌ | ❌ | ✅（規約確認記録の入力を必須にする） |
| EMERGENCY STOP | — | ✅ | ✅ |
| 解除 | ❌ | ❌ | ✅原因記録の入力を必須にする |

> [!danger] 最重要
> **AIは自分の制限を緩められない。** 提案はできる。変更は人間だけ。
> EMERGENCY STOP の解除に「原因の記録」を必須にするのは、同じ事故を2回起こさないため。

## 3. Action Gate（金銭を動かす唯一の入口）

購入・出品・値下げ・再仕入れ・発送は **必ずこの1本の関数を通る**。ここを通らない実装を禁止する。

```
executeAction(action) の処理順（1つでも落ちたら中止）

 1. 緊急停止フラグ確認          → 停止中なら即 reject
 2. 自動異常停止フラグ確認       → HALTED なら reject
 3. モード確認                  → SAFE で自動実行なら MANUAL_APPROVAL_REQUIRED
 4. Connector capability 確認   → 'api' 以外なら CONNECTOR_NOT_AVAILABLE
 5. データ鮮度確認              → 期限切れなら STALE_DATA
 6. スコア条件確認              → 未達なら SKIP
 7. 予算確認（4段階＋現金残高）   → 超過なら BUDGET_EXCEEDED
 8. 冪等性キー確認              → 既存なら「既に実行済み」を返す（再実行しない）
 9. トランザクション開始
10. 在庫引当 / 予算消費を先に確定
11. 外部API呼び出し（タイムアウト＋リトライ＋サーキットブレーカー）
12. 結果を保存
13. audit_logs へ追記
14. コミット（失敗時は10のロールバック＋補償処理）
15. 通知
```

### 外部API失敗時の扱い（最も難しい部分）
「送信したが応答が返ってこなかった」は **成功か失敗か不明** な状態。
このときは **勝手に再送しない**。`status = unknown` にして人間へアラートを上げ、
外部の注文一覧を照会して実際の結果を確認してから確定する。

> **不明なら止まる。不明なら再送しない。** これが二重購入を防ぐ最後の砦。

## 4. 二重購入・二重販売の防止（Idempotency）

### 冪等性キーの作り方
```
purchase : sha256(supplier_id + supplier_product_id + quantity + 判断日 + rule_version)
listing  : sha256(inventory_id + marketplace_id)
shipment : sha256(order_id)
order取込: (marketplace_id + external_order_id) を UNIQUE
```

DBの **UNIQUE制約で弾く**。アプリ側の「存在チェック→INSERT」だけでは同時実行で必ず抜ける。

### 二重販売の防止（在庫1個が複数販路で売れる事故）
```sql
-- 注文取込時。0件更新なら「既に他で売れている」
UPDATE inventory SET status='reserved', reserved_by_order_id=?
 WHERE id=? AND status='listed';
```
0件だったら：
1. その注文を `needs_human` キューへ
2. **全販路の当該出品を即時停止**
3. critical アラート

さらに **予防**として、
- マルチチャネル出品は「在庫2個以上」または「即時在庫同期が api で可能な販路」に限る
- 在庫1個しか無い高額商品は **単一販路のみ** に出す（既定）

## 5. 予算とガードレール

| 種類 | 既定値の考え方 |
|---|---|
| 1商品 最大購入額 | 総資金の 5% |
| 1日 最大仕入額 | 総資金の 10% |
| 1週間 最大仕入額 | 総資金の 25% |
| 1ブランド 最大保有額 | 総資金の 30% |
| 1カテゴリ 最大保有額 | 総資金の 40% |
| 1SKU 最大保有数 | 3個 |
| 最低現金残高 | 総資金の 20% |
| 1回のRunでの購入件数上限 | 5件 |
| 1日の自動購入件数上限 | 20件 |

**件数上限は金額上限と別に必ず設ける。** 「1件1万円 × 500件」は金額上限をすり抜けて暴走する。

## 6. 自動異常停止（Circuit Breaker）

次を検知したら **FULL AUTO を自動停止**し、SAFE へ落とす。

| 検知 | 条件例 |
|---|---|
| API異常 | 連続5回失敗 / エラー率20%超 |
| 認証エラー | 401/403 が1回でも |
| DB異常 | 書き込み失敗・整合性チェック失敗 |
| 商品一致精度低下 | 直近100件の human_verdict 誤り率 > 10% |
| 異常な大量購入 | 1時間で通常の3倍以上の購入判定 |
| 予算超過 | 上限の90%到達で警告、100%で停止 |
| 想定以上の赤字 | 直近30日の実績純利益 < 0 |
| 在庫不整合 | DB在庫と販路在庫の差異 > 0 |
| 相場データ異常 | 中央値が前日比±40%超 / 取得件数が前日比50%未満 |
| 外部仕様変更 | 期待するフィールドが欠損 |
| 重複注文 | idempotency 衝突が短時間に多発 |
| 利益計算異常 | ROI > 300% など明らかに異常な値 |

**復帰は人間のみ。原因の記録を必須にする。**

## 7. EMERGENCY STOP

- 管理画面トップ最上部に常設（赤・大きく）
- 押すと即時に停止するもの：自動購入 / 自動出品 / 自動値付け / 自動再仕入れ / その他金銭を伴う新規処理
- **停止しないもの**：既存注文の受信、発送準備、データ取得、レポート
  （止めると顧客に迷惑がかかる処理は止めない）
- 注文済み・発送待ちは削除せず `needs_human` キューへ退避
- 停止／解除は audit_logs に必ず記録

## 8. SHADOW MODE 設計

**目的：実弾を撃つ前にAIの実力を測る。**

### 動き
1. AIが `STRONG BUY` / `BUY` と判定した商品を、実際には買わず `shadow_trades` に記録
   （判定時の仕入価格・相場・スコア・rule_version をスナップショット保存）
2. 30日後（既定）に自動評価：
   - その期間に、その販路でその商品が **実際にいくらで何件売れたか**（`market_sales`）
   - 自分の想定価格で出していたら **何日で売れた可能性が高いか**（価格分位から推定）
   - 手数料を引いた **推定純利益**
3. 予測と推定実績の誤差を `prediction_accuracy_json` に保存

### 判定できない場合
成約データが1件も取れない期間があった等は **`undecidable`** にする。
**無理に「売れなかった」と決めつけない**（データが無いことと売れないことは違う）。

### 卒業条件（FULL AUTO へ進んでよい基準）
```
SHADOW取引 100件以上を評価済み
売却日数の予測誤差（中央値）      <= ±30%
純利益の予測誤差（中央値）        <= ±20%
STRONG BUY判定の推定黒字率        >= 85%
同一商品判定の人間検証 誤り率     <= 3%
undecidable 率                   <= 20%
```

**この基準を満たすまで実弾の自動購入は解禁しない。**

## 9. バックテスト設計

**新しい仕入ルールをいきなり本番適用しない。**

### 手順
1. ルール変更は `rule_version` を上げた新設定として登録（既存を書き換えない）
2. 過去データ（`supplier_products` / `price_history` / `market_sales` / `profit_records`）に対し、
   旧ルールAと新ルールBを **同じ期間・同じ入力**で再実行
3. 比較指標：
   - 期待純利益の合計 / 平均ROI / 平均売却日数
   - 実際に黒字だった率 / 損切りになった率
   - 資金拘束日数あたり利益（**最重要**）
   - 買い逃し（旧はSKIPだが実際は売れた商品）
4. `backtests.verdict` を `adopt_candidate` / `reject` / `inconclusive`
5. **`adopt_candidate` でも即本番にしない。** SHADOW で30日並走させてから採用

### 注意（バックテストの罠）
- **未来の情報を使わない。** 判断時点で存在しなかったデータを混ぜない（`fetched_at` で厳密に切る）
- **サンプル数が少ない改善を信じない。** 既定30件未満は `inconclusive`
- **手数料は当時の `fee_rules`（valid_from/to）で計算する**

## 10. SANDBOX 環境

`SANDBOX=true` のとき：
- 全Connectorが `mock` 実装に差し替わる（**外部への送信が物理的に不可能になる**）
- メール・LINE・Slack も送信されず、DBに記録されるだけ
- DBファイルは `commerce.sandbox.db` で本番と完全分離
- 起動時に画面上部へ黄色帯「SANDBOX」を常時表示（本番と間違えないため）

**mock は「偽の成功」を返さない。** 実装されていない機能は明示的にエラーを投げる
（Amazon AI Seller OS が画像mockで採った方針と同じ）。

## 11. セキュリティ

| 項目 | 方針 |
|---|---|
| Secrets | `.env` / Secret Manager のみ。コードに直書き禁止。`.gitignore` 必須 |
| ログ | APIキー・個人情報を必ずマスクして出力 |
| RBAC | viewer / operator / admin の3ロール |
| 2FA | admin は必須 |
| Rate Limit | 外部API・自社API とも設定 |
| Encryption | 保存時（DB）と通信時（TLS） |
| Backup | 日次スナップショット。**復元手順を実際に一度試すまで完了としない** |
| Transaction | 金銭処理は必ずトランザクション内 |
| Retry | 指数バックオフ。**ただし「不明」状態は再送しない** |
| Circuit Breaker | §6 |
| Idempotency | §4 |
| 監査ログ | 追記専用。UPDATE/DELETE禁止 |
