# 18. Phase 3.9 実装記録（「購入ページを開く」導線）

## 0. 30秒サマリー

- **作ったもの**：仕入候補の一覧（`/buy`）と、その右端の **「購入ページを開く」ボタン**。
- **AIがやること**：候補を並べる。押した記録を残す。結果を集計する。
- **AIがやらないこと**：**URLを作る／ボタンを押す／注文する／決済する／ログインする。** 1行も無い。
- **買うのは人**。ボタンは新しいタブで商品ページを開くだけ。
- **状態が確認できていない商品ページは開けない**（既定は「不明」）。
- 受け入れテストを **113項目追加**。既存7本と合わせて **合計811項目すべて合格**。`npm run build` も通した。
- **いま開ける候補は 0件。** 正規に自動取得できる市場が0件のため（[[17_市場別_正規データ取得調査]]）。
  道具はできたが、材料がまだ無い。ここを良く見せない。

## 1. なぜ「開くだけ」で止めたのか

ユーザー指示（項目1・4）:

> 購入ボタン自体をAIが勝手に押すのはまだ行わず、最終購入だけ人間が商品ページで確認して行う形が安全です。

理由を自分の言葉で書いておく。

- **AIが金を使う経路を1本も作らない。** 「押せるが押さない」ではなく「押す処理が存在しない」。
  フラグOFFは事故る。存在しなければ事故りようがない。
- **いちばん危ないのは「儲かって見える1件」。** 画面上でいちばん利益が大きく見える候補は、
  だいたい**別の商品を同じ商品と取り違えている**。人が商品ページを見れば気づく。AIは気づけない。
- **リンクを開くのは規約違反にならない。** 自動巡回・自動購入は規約と法令の問題になるが、
  人がブラウザで商品ページを開くのは普通の買い物と同じ。**ここだけは安全に前へ進められる。**

## 3. 歯止め（ここを崩すと事故る）

### 3.1 AIはURLを作らない

ユーザー指示（項目2）:

> リンク先をAIが生成してはいけません。取得元データに実際に存在するURLだけ使用してください。

- 画面のリンクは `href={url}` と**そのまま渡すだけ**。文字列を組み立てない。
- `buildUrl` `makeUrl` `generateUrl` のような関数が**増えていないことを毎回テストで検査**する。
- URLの出どころ（`URL_SOURCE`）は4種類のみ：
  `CONNECTOR_API` / `CONNECTOR_FEED` / `OFFICIAL_CSV` / `HUMAN_ENTRY`。
  **`AI_GENERATED` という選択肢を作らない。**

> **なぜここまでやるか**：AIが商品IDを推測してURLを組み立てると、
> 「実在するが別の商品」のページへ人を連れて行く。人は「AIが出したリンクだから合っている」と思う。
> 取り違えの中でいちばん気づきにくい形になる。

### 3.2 分からないものは開かせない（Fail Closed）

商品ページの状態（`URL_STATUS`）は4つだけ：
`ACTIVE`（出品中）/ `SOLD`（売り切れを確認済み）/ `REMOVED`（消えている）/ `UNKNOWN`（確認できない）。

- **既定は `UNKNOWN`。`ACTIVE` を既定にしない。**
- **開けるのは `ACTIVE` のときだけ。**
- `SOLD_PROBABLY` のような「たぶん」の状態を作らない（ルール30と同じ）。

さらに、以下は問答無用でボタンを無効にする：

| コード | 何を弾くか |
|---|---|
| `HOST_MISMATCH` | 市場と違うドメインのURL（メルカリの候補なのに別サイト） |
| `REDIRECTOR` | 転送・短縮URL（行き先が分からない） |
| `HAS_CREDENTIALS` | ログイン情報が埋め込まれたURL |
| `NOT_HTTP` | `http`/`https` 以外 |
| `EMPTY` | URLが無い |
| `VENUE_UNKNOWN` | どの市場か分からない |

### 3.3 押した瞬間の判断を凍結する

`page_open_events` は、押した瞬間の価格と判断を**丸ごと写して固定**する。
あとから相場が動いても書き換えない（ルール19と同じ考え方）。

> 書き換えると「押したときAIは何と言っていたか」が消える。
> するとAIの判断が当たっていたのか外れていたのかを**永久に測れなくなる**。

テストでも、記録後に相場を12,000円→30,000円に動かしても
記録の中の12,000円が動かないことを毎回確認している。

### 3.4 開いた結果は5択（「たぶん」を作らない）

`購入した` / `見送った` / `売り切れていた` / `価格が変わっていた` / **`違う商品だった`**

- **`違う商品だった` は重大扱い**で、**何が違ったかの記入を必須**にした（空欄では保存しない）。
- `違う商品だった` が付いた出品は、**以後ボタンを開けなくする**。
- `購入した` を選んだときだけ実購入価格・送料・購入日時を入れる。
  **送料が分からないときは空欄。0円と書かない**（ルール40と同じ）。

### 3.5 SHADOWと実取引を混ぜない

ユーザー指示（項目16）:

> SHADOWではなく REAL TRADE候補記録 として保存してください。

実際に買った記録は `real_trade_candidates` に入れ、**SHADOWの表には1列も足さない**。
`route_shadow_trades` に `actual_purchase_price` のような列が生えていないことをテストで検査する。

> 混ぜると「AIの予測が当たったか」の集計に、人が実際に買った結果が紛れ込む。
> AIの成績を人の行動で水増しすることになる。

### 3.6 自動購入は「構造だけ」

ユーザー指示（項目17・18）:

> 将来的に `AUTO_PURCHASE_CAPABLE = true` にできる構造だけ準備してください。
> APIがあるだけで自動購入可能にしないでください。

9条件を定義した：
`VENUE_OFFICIALLY_ALLOWS` / `FEE_VERIFIED` / `MATCH_CONFIDENCE_HIGH` / `DECISION_STRONG_BUY` /
`CONSERVATIVE_ROI_OK` / `REAL_PRECISION_OK` / `STOCK_CONFIRMED` / `WITHIN_BUDGET` / `ALL_GATES_PASSED`

**9つ全部そろっても、いまは `capable = false` を返す。** 実装しない方針だから。
環境変数で有効にする経路も作っていない（`process.env` が1つも無いことをテストで検査）。

### 3.7 市場の接続状況は、確認できたものだけ `CONNECTED`

`venue_connectors` の既定は `NOT_RESEARCHED`、取得手段の既定は `MANUAL_OBSERVATION`。
**2026-08-20 時点で `CONNECTED` は0件。**
認証情報そのものは持たず、**置き場所の名前（`credential_key`）だけ**を持つ。

## 4. 実装中に起きたこと（2件）

### 4.1 表の名前が受け入れテストに引っかかった

最初 `purchase_page_opens` と名付けたところ、`npm run test:phase3` の
**「購入・注文・決済・出品公開・発送のテーブルが存在しない」検査**に落ちた。

**検査をゆるめるのではなく、名前の方を実態に合わせた**（ルール46）。
→ **`page_open_events`**。この表に入るのは「ページを開いた」という事実だけで、購入は1件も入らない。

> 名前に purchase が入っていると、後から見た人が「ここに購入記録がある」と誤解する。
> 誤解した人が「じゃあ自動で買えるはずだ」と考える。名前は歯止めの一部。

### 4.2 受け入れテストが自分の安全装置を不合格にした（2件）

書いたテストが**誤って合格を妨げた**ケースが2件。どちらも**ソースではなくテストの方を直した**。

1. 「ログイン情報を扱わない」検査が `password` という語だけで判定していたため、
   `lib/producturl.ts` の `if (u.username || u.password) return ng('HAS_CREDENTIALS')`
   ＝ **ログイン情報入りURLを弾くための安全装置そのもの**が不合格になった。
   → 「読む」と「組み立てる・送る・保存する」を区別する検査に直した。
2. 「APIがあるから自動購入可、という近道を作っていない」検査が、
   `lib/autopurchase.ts` 冒頭に**引用してあるユーザー指示の原文**に反応していた。
   → コメントを外してからコード部分だけを調べるようにした。

> **教訓**：安全装置を消して検査を通すのは本末転倒。
> ただし「検査が厳しすぎるから直す」を安易にやると歯止めが崩れる。
> **直してよいのは「検査が事実を取り違えているとき」だけ**で、その理由をコードのコメントに残す。

## 5. 画面に出していないもの（正直に）

`/buy` に **利益額・ROI・Route Score・売却確率・Liquidity Score を出していない。**
ユーザー指示（項目12）では出す予定の項目だが、いまは出せない。

理由：いまの利益計算は「**仕入先の商品**」を起点にしていて、
「**この1件の出品を買ったらいくらになるか**」の形になっていない。
出品からRouteへ変換する層がまだ無い。

**無い数字を、それらしく埋めない**（ルール35）。
画面にもその理由をそのまま書いてある。作るのは自動収集が繋がってからでよい。
