# 商品大量生成とパイプライン設計（Mass Product Generation）

> 上位文書: [[00_設計書v1_最上位]]（v1.1で追加）
> 関連: [[07_価格戦略設計]] / [[08_仕入先ネットワークと勝ち筋拡張]] / [[01_DB設計案]]

---

## 1. 目的

「利益が出そうな商品を数個見つけて終わり」ではなく、
**条件を満たす商品をひたすら発見・登録・販売候補化し続ける**構造にする。

```
仕入先を監視 → 新商品発見 → 同一商品調査 → 利益判定 → 販売候補作成
     ↑                                                    │
     └──────────────── 次の商品 → 次の商品 → 次の商品 ──────┘
```

**目標**：AIが毎日 **数百〜数千件** の候補商品を自動生成する状態。
将来は毎日数万商品を分析する（[[00_設計書v1_最上位]] §15 の理想状態）。

> [!danger] 大量生成の最大の敵は「重複」と「誤マッチ」
> 重複＝同じ商品を何度も登録してDBとコストを食い潰す。
> 誤マッチ＝違う商品を同じだと思い込んで在庫の墓場を作る。
> **この2つを潰すことが、大量生成設計の本体**。件数を増やすことではない。

## 2. 商品パイプライン（状態遷移）

すべての候補商品は状態を持ち、状態機械として進む。

```
              ┌──────────────┐
              │  DISCOVERED  │ 仕入先で新商品を発見した
              └──────┬───────┘
                     ↓
              ┌──────────────┐
              │   MATCHING   │ 同一商品を特定中
              └──────┬───────┘
          ┌──────────┼──────────┐
          ↓          ↓          ↓
   ┌────────────┐ ┌──────────┐ ┌─────────┐
   │  ANALYZED  │ │  MANUAL  │ │ SKIPPED │
   │ 相場・利益 │ │  REVIEW  │ │ 不採用  │
   │ を算出済み │ │ 人間判断 │ └────┬────┘
   └─────┬──────┘ └────┬─────┘      │
         ↓             │             │ 条件が変わったら
   ┌────────────┐      │             │ 再評価で復活
   │ PROFITABLE │←─────┘             │
   │ 利益条件を │                    │
   │ 満たした   │                    │
   └─────┬──────┘                    │
         ↓                           │
   ┌────────────────┐                │
   │ READY_TO_LIST  │ 出品準備完了   │
   └─────┬──────────┘                │
         ↓                           │
   ┌────────────┐                    │
   │   LISTED   │ 出品中             │
   └─────┬──────┘                    │
         ↓                           │
   ┌────────────┐                    │
   │    SOLD    │ 販売完了           │
   └─────┬──────┘                    │
         ↓                           │
   ┌────────────────────┐            │
   │ REORDER_CANDIDATE  │ 再仕入候補 │
   └─────┬──────────────┘            │
         └──────────────→ DISCOVERED ←┘（再入場）
```

### 状態の定義

| 状態 | 意味 | 次へ進む条件 |
|---|---|---|
| `DISCOVERED` | 仕入先で新商品を検出。正規化前 | 重複チェックを通過 |
| `MATCHING` | 同一商品を特定中 | MATCH_SCORE が算出された |
| `ANALYZED` | 相場・売却確率・利益を算出済み | 計算が完了した |
| `PROFITABLE` | 利益条件を満たした（BUY以上） | BUY_SCORE >= 閾値 |
| `READY_TO_LIST` | 仕入完了・出品準備できた | 在庫が手元にある |
| `LISTED` | 出品中 | — |
| `SOLD` | 販売完了・損益確定 | — |
| `REORDER_CANDIDATE` | 再仕入の価値あり | 再仕入条件を満たす |
| `SKIPPED` | 不採用 | 再評価で復活しうる |
| `MANUAL_REVIEW` | **AIが自信を持てない**。人間判断待ち | 人間が判定 |

### 補助フラグ（状態とは別に持つ）
| フラグ | 用途 |
|---|---|
| `blocked_reason` | なぜ止まっているか（`STALE_DATA` / `NO_FEE_RULE` / `CONNECTOR_NOT_AVAILABLE` 等） |
| `skip_reason` | なぜ不採用か（下表） |
| `next_reevaluate_at` | いつ再評価するか |
| `reevaluate_count` | 何回再評価したか（無限ループ防止） |

## 3. SKIPPED の理由と再評価

**不採用にした理由を必ず記録する。** 理由によって「いつ見直すべきか」が違うから。

| skip_reason | 意味 | 再評価タイミング |
|---|---|---|
| `LOW_PROFIT` | 利益が足りない | 相場が動いたとき / 7日ごと |
| `LOW_SELL_PROBABILITY` | 売れそうにない | 30日ごと（季節で変わる） |
| `PRICE_TOO_HIGH` | 仕入価格が高い | **仕入価格が下がったら即時** |
| `NO_MARKET_DATA` | 相場データが無い | データが入ったら即時 |
| `NO_FEE_RULE` | 手数料が未登録 | 手数料を登録したら即時 |
| `LOW_MATCH_SCORE` | 同一商品と確信できない | 判定ロジック改善時／画像が増えたとき |
| `HIGH_RISK` | 真贋・状態リスクが高い | 原則 再評価しない |
| `BUDGET` | 予算上限で見送り | **翌日即時**（商品が悪いわけではない） |
| `OUT_OF_STOCK` | 仕入先で売切れ | 再入荷したら |
| `RULE_VERSION` | 旧ルールでの不採用 | **ルール更新時に全件再評価** |

> [!important] `RULE_VERSION` が重要
> 仕入ルールを改善したら、**過去に SKIPPED にした商品を全件再評価する**。
> 「昔の甘い／厳しい基準で捨てた宝」を拾い直せる。これは大量生成システムだけの利点。

再評価は `requeue` Run が担当。1回の Run で処理する件数に上限を設け、
`reevaluate_count` が上限（既定10回）を超えたら `SKIPPED_PERMANENT` にして掘り返しをやめる。

## 4. 重複登録の防止（最重要）

大量生成では重複が最大の敵。**多段の重複キー**で判定する。

### 4.1 3つのレベル

| レベル | 何の重複か | キー |
|---|---|---|
| **L1 出品の重複** | 仕入先の同じ出品を2回取り込んだ | `(supplier_id, external_id)` **UNIQUE** |
| **L2 個体の重複** | 同じ現物が別URLで2回出ている | `(supplier_id, content_hash)` |
| **L3 商品の重複** | 商品マスタに同じ商品が2件できた | `(brand_id, model_number, color, size)` / `gtin` |

### 4.2 content_hash の作り方（L2）
```
content_hash = sha256(
  正規化ブランド + 正規化型番 + カラー + サイズ +
  状態ランク + 価格帯(1000円丸め) + 画像の知覚ハッシュ(pHash)
)
```
中古の一点物は「同じ型番でも別個体」なので、**型番だけで重複と判定してはいけない**。
価格・状態・画像を含めることで「別個体」と「重複掲載」を区別する。

### 4.3 判定フロー
```
新規取込
  ↓
L1: (supplier_id, external_id) が既存？ → YES: 価格・在庫だけ更新して終了
  ↓ NO
L2: content_hash が既存かつ 直近30日以内？ → YES: MANUAL_REVIEW（重複の疑い）
  ↓ NO
L3: 商品マスタに一致する products がある？
     → YES: その product_id に紐づける
     → NO : 新しい products を作る（★ここでしか products は増えない）
  ↓
DISCOVERED として登録
```

> [!warning] products を安易に増やさない
> 商品マスタが汚れると、相場も実績も分散して**学習が全部壊れる**。
> `products` の新規作成は L3 を通った時のみ。迷ったら新規作成せず `MANUAL_REVIEW`。

### 4.4 商品マスタのマージ
後から「これとこれは同じ商品だった」と分かった場合、**マージ機能**を用意する。
- 片方を `merged_into` で指し、実績・相場・在庫を統合
- **削除はしない**（監査のため）
- マージは人間の操作のみ

## 5. 段階フィルタ（コストを制御する）

毎日数万件を全部LLMに投げたら破産する。**安い判定から順に、生き残ったものだけを高い判定へ回す。**

```
【L0】取込（コスト 0）
   数万件
     ↓ 仕入先側の在庫あり・価格あり・カテゴリ対象内
【L1】決定的フィルタ（コスト 0・SQLのみ）
   数千件
     ↓ JAN/型番の完全一致 → 即マッチ確定（LLM不要）
     ↓ 価格帯が明らかに対象外のものを除外
【L2】相場照合（コスト 小・自社DB参照）
   数百件
     ↓ ざっくり粗利がプラスになりうるものだけ残す
【L3】テキスト類似マッチ（コスト 小・ローカル計算）
   数百件
     ↓ 候補を3件以内に絞る
【L4】LLM／画像判定（コスト 大）★ここに来るのは全体の1%以下
   数十件
     ↓
【L5】精密利益計算・売却確率・BUY_SCORE
   数十件
```

### コストガード
- `L4` へ回す条件：**想定粗利が LLM費用の20倍以上** かつ 候補が絞れていること
- 日次のLLM費用上限を設定。超えたら `L4` を止め、`L3` までの結果で `MANUAL_REVIEW` へ回す
- 費用は `ai_usage` に記録し、**1商品あたりの判定コスト**をダッシュボードに出す

> [!tip] 「調べれば調べるほど儲かる」は嘘
> 1件あたりの判定コストが利益を超えたら、その商品を調べるのは損。
> **判定コストも利益計算に含める。**

## 6. MANUAL_REVIEW（人間に頼る場所）

### 送る条件
- MATCH_SCORE が 85〜94（グレーゾーン）
- 異常価格を検知した（相場より30%以上安い）
- 重複の疑い（L2ヒット）
- 高額商品（既定20万円以上）で MATCH_SCORE < 98
- 真贋リスクが中程度
- LLM判定が失敗／スキーマ検証に落ちた

### 人間の作業を軽くする工夫
- **1画面で10件を左右比較**（仕入先の写真 vs 相場側の写真を並べる）
- キーボードで「同じ／違う／保留」を連打できる
- **AIの判断理由と、どこが一致・不一致かを先に表示**
- 判定結果は `product_matches.human_verdict` へ保存し、**そのまま教師データになる**
- 溜まりすぎたら警告（既定：500件超で通知）

> [!important] MANUAL_REVIEW は「失敗」ではなく「学習の入口」
> ここでの人間判定が、同一商品判定の精度を上げる唯一の燃料。
> **件数を減らすことより、判定を溜めないことを優先する。**

## 7. 発見エンジンの運転

### スケジュール（例）
| Run | 頻度 | 内容 |
|---|---|---|
| `discover` | 15分ごと（仕入先ごとに時間差） | 新着の取込 |
| `match` | 30分ごと | MATCHING → ANALYZED |
| `research` | 1時間ごと | 相場の更新 |
| `evaluate` | 1時間ごと | 利益・スコア再計算 |
| `requeue` | 日次 | SKIPPED の再評価 |
| `expand` | 日次 | 勝ち筋拡張探索（→[[08_仕入先ネットワークと勝ち筋拡張]]） |
| `price_test` | 日次 | 価格ステップアップ判定（→[[07_価格戦略設計]]） |

### アクセス負荷への配慮（必須）
- 仕入先ごとにレート制限（既定：1リクエスト/2秒、同時1接続）
- 深夜帯に集中させない（先方サーバーの負荷を考える）
- 差分取得を優先（全件クロールを毎回しない）
- **規約・robots.txt で許可されていない取得はしない**（capability = manual なら CSV運用）

### 発見エンジンの異常検知
| 検知 | 条件 | 対応 |
|---|---|---|
| 発見数の急減 | 前日比 50%未満 | Connector故障を疑う → アラート |
| 発見数の急増 | 前日比 300%超 | 重複や誤取込を疑う → **自動的に評価を止める** |
| 利益候補率の急増 | 通常の3倍超 | **相場データ破損を疑う → FULL AUTO 停止** |
| MANUAL_REVIEW 滞留 | 500件超 | アラート |
| 判定コスト超過 | 日次上限到達 | L4停止 |

## 8. 発見KPI（経営指標にする）

日次で記録する（`discovery_kpi` テーブル）。

| 指標 | 意味 |
|---|---|
| `monitored_count` | 監視対象の商品数（累計） |
| `discovered_count` | 新規発見数 |
| `matched_count` | 同一商品を特定できた数 |
| `analyzed_count` | 利益計算まで進んだ数 |
| `profitable_count` | 利益条件を満たした数 |
| `strong_buy_count` | STRONG BUY 数 |
| `manual_review_count` | 人間判断待ちの数 |
| `listed_count` / `sold_count` | 出品数 / 販売数 |
| `skipped_count`（理由別） | 不採用数 |
| `cost_per_analysis` | 1件あたりの判定コスト |
| **転換率** | 発見→特定→利益→出品→販売 の各段階の通過率 |

> [!note] 見るべきは件数より「転換率」
> 発見1万件で販売10件（0.1%）なら、どこかで詰まっている。
> どの段階で落ちているかが分かれば、直すべき場所が分かる。

## 9. 品質を落とさないための鉄則

1. **商品数のために閾値を下げない。** MATCH_SCORE 閾値の変更は人間のみ。
2. **自信が無ければ作らず `MANUAL_REVIEW` へ。**
3. **`products` の新規作成は L3 通過時のみ。**
4. **重複キー L1 は DB の UNIQUE 制約で担保**（アプリ側チェックだけでは同時実行で抜ける）。
5. **判定コストを利益計算に含める。**
6. **発見数が急増したら疑う。** 良いニュースに見えるものほど故障を疑う。
7. **SKIPPED の理由を必ず記録する。** 理由が無い不採用は再評価できない。
