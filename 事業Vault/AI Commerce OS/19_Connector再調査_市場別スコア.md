## 0. この文書が作られた理由（訂正の記録）

前回わたし（Claude）は、Yahoo!ショッピングについて公式ヘルプに
「原則 非商用」と書かれているのを見つけ、**「使えない」と結論づけた**。

ユーザーからの指摘：

> 「Yahoo!については『原則非商用だから使えない』と確定させるのはまだ早いです。」
> 「Yahoo = PROHIBITED ではなく、Yahoo = APPLICATION / COMMERCIAL_USE_CONFIRMATION_REQUIRED
> くらいが適切です。」

**この指摘は正しい。** 理由は3つある。

1. Yahoo!ショッピングには**現在も公式のWeb APIが現役で存在する**（提供終了していない）。
2. 同じ公式ヘルプ記事の中に「**すべてを禁じるものではありません**」という文も併記されている。
3. 「商用利用については各APIの窓口へご相談ください」という**導線が公式に用意されている**。

つまりYahoo!の状態は「禁止」ではなく「**まだ確認していない**」である。
わたしは、確認していないものを禁止と書いてしまった。これは
CLAUDE.md ルール58（「禁止と書かれていない」を根拠にしない）の**逆方向の間違い**にあたる。

### そこで、この文書からルールを1つ増やす

**「使える／使えない」の2択で市場を判定しない。** 判定は必ず次の3つに分ける。

| 判定 | 意味 | やること |
|---|---|---|
| `CONFIRMED_ALLOWED` | 公式情報で「できる」と読めた | 実装してよい |
| `CONFIRMED_PROHIBITED` | 公式情報で「できない」と明記されていた | 打ち切る |
| `CONFIRMATION_REQUIRED` | **公式情報がある。ただし当社用途に使えるかは書かれていない** | **問い合わせる**（打ち切らない） |

Yahoo!ショッピングは3番目である。eBayは1番目と2番目が混在している。

## 1. ユーザー指示4への対応：「APIがある」と「使える」を分けて持つ

これまでは市場ごとに「自動取得できる／できない」という**1つの判定**しか持っていなかった。
これが今回の間違いの原因でもある（APIが現役なのに「使えない」の一言で潰した）。

そこで **8つの別々の項目**として管理する。1つでも欠けたら本番接続しない。

| # | 項目 | 質問の内容 |
|---|---|---|
| 1 | `API_EXISTS` | 公式APIが今も提供されているか（提供終了していないか） |
| 2 | `COMMERCIAL_USE_ALLOWED` | 事業者が商用目的で使ってよいか |
| 3 | `INTERNAL_BUSINESS_USE_ALLOWED` | 一般公開せず、自社の中だけで使う道具に使ってよいか |
| 4 | `PRICE_ANALYSIS_ALLOWED` | 価格比較・仕入判断に使ってよいか |
| 5 | `DATA_STORAGE_ALLOWED` | 取得したデータを自社DBに保存し続けてよいか |
| 6 | `AUTOMATED_COLLECTION_ALLOWED` | 定期的に自動取得してよいか |
| 7 | `AUTOMATED_PURCHASE_ALLOWED` | 自動購入してよいか |
| 8 | `AUTOMATED_LISTING_ALLOWED` | 自動出品してよいか |

各項目の値は `YES` / `NO` / `UNKNOWN` の3つだけ。**`UNKNOWN` を `YES` 寄りに扱わない。**

なお 7・8 については、たとえ `YES` でも当システムは実装しない
（ユーザー指示「今回も、購入 出品 決済 発送 自動ログイン 無許可スクレイピング は実装しません」）。
記録するのは「将来できるか」ではなく「**いま何が分かっているか**」のためである。

### 2-3. Rate Limit が UNKNOWN である理由（重要）

公式ドキュメント内で、次の3つの数字が別々の場所に書かれていた。

- 1クエリー／秒
- 1分あたり 30リクエスト
- 1日あたり 50,000リクエスト

**どれが商品検索v3に適用されるのか、3つが同時に適用されるのかが公式に書かれていない。**
矛盾したまま両方（3つとも）ここに残す。実効値は**問い合わせて確定させるまで UNKNOWN**。

暫定運用としては**一番厳しい値（1分30リクエスト）で設計する**のが安全側。

### 2-4. 新しく分かった、重い事実

Yahoo!の公式お問い合わせページに、次の趣旨の記載がある。

> 商用利用や利用回数制限の緩和についてのご相談 →（一覧の中で）**ショッピングAPIについては提供しておりません**

地図APIやテキスト解析APIには専用の相談フォームが用意されているのに対し、
**ショッピングAPIだけ「商用相談の窓口が用意されていない」**という状態になっている。

これは「禁止」とは違う。しかし「聞けば許可がもらえる」とも限らない、ということでもある。
問い合わせ先は開発者向けフォーム（`https://support.yahoo-net.jp/form/s/PccDeveloper`）だが、
**同社は個別回答をしない旨を明記している**ため、回答が来ない可能性がある。

### 2-5. もう1つの構造問題：クレジット表示

Yahoo! JAPANのクレジット表示は義務である。
しかし当システムは**社内でしか使わない道具**であり、一般に公開する画面が無い。
つまり「表示する場所が無い」。

- 表示しない → 義務を満たしていない可能性
- 社内画面に表示する → それで義務を満たすのかが公式に書かれていない（UNKNOWN）

**対応：社内画面にもクレジットを表示する実装にしておく**（表示して損は無い）。

## 3. ヤフオク!（完全に別調査）

**ユーザー指示3：「`YAHOO_SHOPPING` と `YAHOO_AUCTIONS` を同じVenueとして扱わないでください。」**
実際に調べた結果、**両者はまったく違う結論になった**。分けて正解だった。

### 3-1. 結論

| 項目 | 値 |
|---|---|
| 判定 | **`API_DISCONTINUED`（提供終了）** |
| いつ | オークションWeb API：**2018-02-22 提供終了**／評価API：**2020-01-29 提供終了** |
| 現況 | 旧ドキュメントURLは **404**。現行のAPI一覧に**オークション系が1つも載っていない** |

ショッピングは現役、オークションは終了。**同じ「Yahoo!」でもまったく別物だった。**

### 3-2. 落札相場（成約価格）について

ヤフオク!の落札相場は、当社にとって**最も価値が高いデータ**である
（「いくらで売れたか」が分かる数少ない国内市場だから）。しかし：

- 提供手段は**Web画面のみ**。API・CSV・フィードは存在しない。
- `robots.txt` が `/closedsearch/`（落札相場の階層）を **Disallow** している。
- ガイドライン細則 A.26：**自動出品ツールの利用を禁止**
- ガイドライン細則 A.33／E.1(6)：システムに**過度な負荷**をかける行為を禁止
- Yahoo! JAPAN共通利用規約 15(5)：**BOT等による自動化されたアクセス**を制限
- 同 8.3／15(8)：包括的な禁止条項

「スクレイピング」「クローリング」「自動入札」という**語そのものは細則に0件**だった。
しかし**無いことを許可と解釈しない**（ルール58）。上記の包括条項で十分にアウトである。

## 4. eBay（再調査）

### 4-1. APIの現況（ユーザー指示11）

| API | 現況 | 備考 |
|---|---|---|
| Browse API | **現役** | `itemWebUrl`（実URL）・`itemId`・`gtin`・`mpn` が取れる |
| Marketplace Insights API | **Limited Release のまま** | 承認されないと**ドキュメントすら閲覧できない**（OpenAPI仕様ファイルが0バイト） |
| Finding API | **2025-02-04 提供終了** | `findCompletedItems`（落札実績）は**消滅** |
| Shopping API | **2025-02-04 提供終了** | |
| Buy APIs | 現役だが段階的承認制 | 当社は実購入を実装しないので対象外 |
| Sell APIs | 現役 | 当社は実出品を実装しないので対象外 |

技術的な注意：**`gtin`（JANに相当）は検索結果には含まれず、1件ずつ `getItem` を呼ばないと取れない。**
つまり「100件検索して型番で突き合わせる」には**100回の追加呼び出し**が必要になる。
Rate Limit（既定 5,000回／日）を一気に消費する構造である。

### 4-2. 決定的な問題：規約が当社の用途を名指しで禁止している

eBayのAPIライセンス契約に、次の内容が含まれている。

1. **"seller arbitrage"（せどり・転売目的の利用）を明示的に禁止**
2. **"pricing tools"（価格設定ツール）としての利用には eBay の書面同意が必須**
3. **eBayのコンテンツと他社データを混ぜて表示することを禁止**
4. **AI／機械学習の学習データとしての利用を禁止**
5. **キャッシュはeBayの削除に追従すること（＝恒久保存不可）**

当システムは、まさに 1（安く買って高く売る判断）・2（価格判断）・3（他市場と並べて比較）を
やろうとしている。**規約の中心にぶつかっている。**

さらに **`EBAY_JP` というマーケットプレイスは存在しない**（前回調査と同じ結論）。
日本国内の仕入・販売の相場としては、そもそも使えない。

### 4-3. 8項目マトリクス

| 項目 | 値 |
|---|---|
| `API_EXISTS` | **YES**（Browse API） |
| `COMMERCIAL_USE_ALLOWED` | **NO**（seller arbitrage を明示禁止） |
| `INTERNAL_BUSINESS_USE_ALLOWED` | **UNKNOWN** |
| `PRICE_ANALYSIS_ALLOWED` | **NO**（書面同意が無い限り不可） |
| `DATA_STORAGE_ALLOWED` | **NO**（削除追従・恒久保存不可） |
| `AUTOMATED_COLLECTION_ALLOWED` | **YES（条件付き）** 既定5,000回／日 |
| `AUTOMATED_PURCHASE_ALLOWED` | **UNKNOWN**（Buy APIsは段階的承認制） |
| `AUTOMATED_LISTING_ALLOWED` | **YES（Sell APIs）** ただし当社は実装しない |

### 4-4. 判定

**`CONFIRMED_PROHIBITED`（当社用途において）。** 打ち切る。
「聞けば通るかもしれない」項目（pricing tools の書面同意）は理論上あるが、
**日本のマーケットプレイスが無い以上、通っても使い道が無い。** 問い合わせる価値も低い。

## 5. Amazon（再調査・3つを厳密に分ける）

**ユーザー指示10：「他社商品相場データと自社Sellerアカウントの商品・注文データを混同しない。
SP-APIで取得できるからといって、すべてのAmazon市場データを自由にリサーチできると判断しないこと。」**

この指示に従い、Amazonを**3つの別々のAPI**として調査した。結論はそれぞれ違う。

### 5-1. Amazon SP-API（Selling Partner API）

#### 前回の理解の訂正

前回わたしは「Amazonは自分の出品データしか見られない」と考えていた。**これは不正確だった。**

実際には、次のAPIは **ASINを指定すれば、自分の出品でない商品の他社価格も返す**。

| API | 何が取れるか |
|---|---|
| `getItemOffers` | 指定ASINの**他の出品者の価格**（1件ずつ） |
| `getItemOffersBatch` | 同上（まとめて） |
| `getCompetitiveSummary` | 指定ASINの**競合価格の要約** |
| `searchCatalogItems` | **カタログ全体**をキーワード＋JAN/EAN/UPC/GTIN/ISBNで検索 |
| `getCatalogItem` | `modelNumber`（型番）・`partNumber`・`salesRanks`（売れ筋順位）を返す |

つまり「自社データしか見えない」わけではない。**他社の相場が正規に取れる。**

ただし**ユーザー指示10の警告どおり、「全部自由に見られる」わけでもない。**
取れるのは上記の範囲であって、Amazon市場データを何にでも使ってよいという意味ではない。

#### データ保存について（ここが決定的に有利）

Amazonの Data Protection Policy（DPP）では、
**個人情報（PII）以外のデータは最長18ヶ月保存できる**。

これは当システムにとって非常に大きい。**相場の履歴を積み上げられる**からである。
（比較：eBayは恒久保存不可、Creators APIは24時間まで）

#### 自動巡回について

Amazon公式のFAQが、**リプライサー（価格自動改定ツール）を想定用途として明記している**。
つまり定期的な自動取得は**想定内の使い方**である。

#### 必要なもの（お金の話）

| 必要なもの | 費用 |
|---|---|
| **大口出品** | **月額 4,900円（税抜）** ※小口出品では SP-API を使えない |
| プライベート開発者登録 | 無料（ただし審査あり） |

#### 残っている規約リスク2点（UNKNOWN・ここは正直に書く）

1. **AUP 4.5**：「Amazonのビジネスに関するインサイトを自社のビジネス目的で使用してはいけない」
   → 「インサイト」の定義が書かれていない。他社価格を見て仕入判断することが
   これに当たるのかどうか、**公式に判断できない（UNKNOWN）**。
2. **Amazon以外の市場で売る商品**の仕入判断に使ってよいか
   → **記述が無い（UNKNOWN）**。SP-APIはAmazon出品者向けの道具なので、
   「Amazonで売るための判断」なら自然だが、「メルカリで売るための判断」は書かれていない。

#### さらに重い1点：Keepaとの併用問題

**AUP 4.3 が「Amazon以外のデータサービスの使用」を禁止している。**

当社は現在 Keepa（Amazon相場の外部データサービス）を別事業で使っている。
**SP-APIの開発者登録をすると、Keepaの併用が規約上できなくなるおそれがある。**

これは技術ではなく**経営判断**である。ユーザーに確認が必要。

#### 8項目マトリクス（SP-API）

| 項目 | 値 |
|---|---|
| `API_EXISTS` | **YES** |
| `COMMERCIAL_USE_ALLOWED` | **YES**（そもそも出品事業者向けのAPI） |
| `INTERNAL_BUSINESS_USE_ALLOWED` | **YES**（プライベート開発者＝自社専用アプリが正規の形） |
| `PRICE_ANALYSIS_ALLOWED` | **YES（Amazon内）／UNKNOWN（Amazon外で売る判断）** |
| `DATA_STORAGE_ALLOWED` | **YES**（PII以外・最長18ヶ月） |
| `AUTOMATED_COLLECTION_ALLOWED` | **YES**（Rate Limit公開・リプライサーが想定用途） |

## 11. 2026-08-22 追記：Amazon SP-API の規約本文を実際に読んだ結果

**きっかけ：** ユーザーから「すでに大口出品プランになっている」との情報。
これで「月4,900円（税抜）が新たにかかる」という論点は消えた。

### 11-0. 出典URLの訂正（先に書く）

`developer-docs.amazon.com/sp-api/docs/acceptable-use-policy` と
`.../data-protection-policy` は、**別ホストへ転送されたうえで「Page Not Found」になる**
（2026-08-22 に実際に開いて確認）。§5-1 に書いていたこの2本のURLは死んでいる。

規約の本文が実際に読めるのは、以下の Seller Central 側である。

| 文書 | URL |
|---|---|
| 利用規定（AUP・日本語） | `https://sellercentral.amazon.com/mws/static/policy?documentType=AUP&locale=ja_JP` |
| データ保護ポリシー（DPP・日本語） | `https://sellercentral.amazon.com/mws/static/policy?documentType=DPP&locale=ja_JP` |
| ソリューションプロバイダー契約 | `https://sellercentral.amazon.com/mws/static/agreement?locale=ja_JP` |

**ルール59「廃止されたものを前提にしない」は、APIだけでなく出典リンクにも当てはまる。**
調査記録に死んだURLを残しておくと、次に読む人が「確認済み」と思って開き、404を見て混乱する。

### 11-1. 【確定】Keepa は併用できないと読むのが素直（A4の答え）

**AUP 4.3（日本語原文・逐語）**

> 「Amazonのウェブサイトから入手した情報またはデータを提供する外部の（Amazon以外の）データサービスの使用、提供、宣伝をしてはいけません。」

Keepa は「Amazonのウェブサイトから入手したデータを提供する外部（Amazon以外の）データサービス」
そのものである。しかもこの条項は「提供」「宣伝」だけでなく **「使用」** まで禁じている。

**読み方を工夫して逃げ道を探さない（Fail Closed）。**

ただし正確に書くと、これは「規約違反かどうか」の話ではない。
**この条項は SP-API を使い始めなければ、そもそも掛からない。**
つまり実態は次のどちらを取るかの経営判断である。

| 選ぶもの | 得るもの | 失うもの |
|---|---|---|
| SP-API を使う | Amazonの他社出品価格・売れ筋順位を正規に自動取得できる | **Keepa が使えなくなる** |
| Keepa を使い続ける | 既存事業の作業が今のまま回る | AI Commerce OS の第1自動市場が無くなる |

**参考：** 同じセクションの他の条項も逐語で控えておく。

| 条 | 原文 |
|---|---|
| 4.1 | 「購入者の個人識別情報を、出品者出荷または税務上および規制上の要件などの法的要件を満たすため以外の目的で使用してはいけません。」 |
| 4.2 | 「AmazonサービスAPIまたは外部（Amazon以外）のデータサービスから取得したデータを使用して、Amazonの購入者を商品マーケティングやレビューの捏造または変造の対象にしてはいけません。」 |
| 4.3 | 「Amazonのウェブサイトから入手した情報またはデータを提供する外部の（Amazon以外の）データサービスの使用、提供、宣伝をしてはいけません。」 |
| 4.4 | 「競合する認定ユーザーを含む当事者への提供または販売を目的として、AmazonサービスAPIを通じて取得した認定ユーザーのビジネスまたは購入者間のデータを集計してはいけません。」 |
| 4.5 | 「Amazonのビジネスに関するインサイトを宣伝、公開、共有してはいけません。Amazonのビジネスに関するインサイトを、ご自身のビジネス目的で使用してはいけません。」 |

### 11-2. 【確定】カタログAPIは商品ページURLを返さない（A1の答え）

Catalog Items API v2022-04-01 の応答項目を1つずつ確認した。

| 階層 | 返ってくるもの | 商品ページURL |
|---|---|---|
| `Item` | asin / attributes / classifications / dimensions / identifiers / images / productTypes / relationships / salesRanks / summaries / vendorDetails | **無い** |
| `ItemSummaryByMarketplace` | brand / itemName / manufacturer / modelNumber / partNumber / color / size / style / releaseDate / packageQuantity ほか | **無い** |
| 識別子 | ASIN / JAN / EAN / UPC / ISBN / GTIN / MINSAN / SKU | — |

URLらしきものは **画像URL** と **売れ筋カテゴリのURL** だけ。**商品ページのURLは返らない。**

**これが何を意味するか：**

ASIN が返るので、そこから商品ページのURLを組み立てることは技術的にはできる。
だが **それはルール55「AIはURLを作らない」に真正面から反する**のでやらない。

> 推測で組み立てると「実在するが別の商品」のページへ人を連れて行く。
> 人は「AIが出したリンクだから合っている」と思うので、**いちばん気づきにくい取り違え**になる。

したがって **SP-API だけでは `/buy`（購入ページを開く）の導線は作れない。**
採点表の「商品ページURLが公式に取れるか＝0点」は、推測ではなく**確定**になった。

### 11-3. 【確認】保存期間 18か月は正しかった

**DPP（日本語原文・逐語）**

> 「ソリューションプロバイダーは、法令や規制により、より長期の保存が必要とされる場合を除き、個人識別情報以外のデータ（PII以外のデータ）を18か月以内に削除する必要があります。」

前回「PII以外は最長18ヶ月保存可」と書いたのは正しかった。裏が取れた。
ただし表現は「保存してよい」ではなく **「18か月以内に削除する必要がある」**。
**相場データを消す仕組みを作らないと規約違反になる**ということなので、
実装するなら削除処理が必須項目になる。

### 11-5. 点数は変わらない（77点・Gate通過のまま）

商品ページURLの項目はもともと0点で採点していたため、**確定しても合計点は動かない。**
Gate（商用／社内利用／価格判断／保存）にも触れていないので、**Gate通過も変わらない。**

**ただし「1位のままだから進めてよい」ではない。**
点数は「どれが有望か」を示すもので、「着手してよいか」を示すものではない。
着手の可否は §11-1 と §11-2 の2点を人が判断してから決まる。
