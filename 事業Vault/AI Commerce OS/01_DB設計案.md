# AI Commerce OS DB設計案

> 上位文書: [[00_設計書v1_最上位]]

- DB: libsql（開発=ローカルファイル `commerce.db` / 本番=Turso）
- Postgres へ移す時に触るのは `lib/db/schema.ts` と `lib/db/client.ts` だけで済むよう、型は TEXT / INTEGER / REAL ＋ JSON文字列 に寄せる（Amazon AI Seller OS と同方針）
- 金額は **円の整数（INTEGER）** で持つ。小数の丸め誤差で利益計算を壊さない
- 日時は **ISO8601 文字列（UTC）** で統一

---

> [!danger] 二重販売防止の核
> **在庫は「個体単位」で持つ。** 「SKU × 数量」で持つと複数販路で同時に売れた時に必ず事故る。
> 注文取込時に `inventory.status` を `reserved` へ更新する処理は **トランザクション＋条件付きUPDATE**
> （`WHERE status='listed'`）で行い、0件更新なら「既に売れている」として即座に他販路を停止する。

## 9. v1.1 追加テーブル

### 9.1 重複防止に使うキー（[[06_商品大量生成とパイプライン]] §4）

```
L1 出品重複 : UNIQUE(supplier_id, external_id)
L2 個体重複 : content_hash = sha256(
                正規化ブランド + 正規化型番 + カラー + サイズ +
                condition_rank + 価格帯(1000円丸め) + 画像pHash )
L3 商品重複 : gtin  または  UNIQUE(brand_id, model_number, color, size)
```

`products` に **`merged_into`（TEXT・マージ先ID）** を追加。
後から同一と判明した商品マスタを統合する。**削除はしない**（監査のため）。マージは人間のみ。

| result_json | この種から生まれた発見数・販売数・純利益（効果測定） |

---

## 10. 設計上の重要ポイント（実装時に必ず守る）

1. **金額は円の整数。** REAL で持たない。為替は `fx_rate` を別に保存して換算履歴を残す。
2. **`fetched_at` を持たないデータで判断しない。** 鮮度チェックが通らなければ SKIP。
3. **`idempotency_key` に UNIQUE 制約。** 購入・出品・発送・注文取込の4つは必須。
4. **在庫は個体単位。** SKU数量方式にしない。
5. **`raw_json` を捨てない。** 解析ロジックを直したとき過去分を再計算できる。
6. **`rule_version` をスコアと予測に必ず入れる。** これが無いとバックテストが成立しない。
7. **`fee_rules` に `valid_from/valid_to`。** 手数料改定後も過去の利益計算を再現できる。
8. **audit_logs は追記専用。**
9. **削除しない。** 論理削除（`status`）で表現する。
