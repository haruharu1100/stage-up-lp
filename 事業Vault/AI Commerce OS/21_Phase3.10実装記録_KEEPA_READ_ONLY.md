## 3. 「気をつける」ではなく「できないようにする」

### 3-1. 1件より多く取れない

`KEEPA_MAX_ASINS_PER_RUN = 1` は **コードの定数**で、環境変数では増やせない。
`policy.ts` に `process.env` を1つも書いていないことを、受け入れテストが検査している。
増やすには数字を書き換えてコミットするしかない。
→ **「設定ミスで100件取っていた」が起こらない。**

段階は `KEEPA_STAGES`（1→5→20→100件）で、いまは **S1（1件）**。次へ進む判断は人がする。

### 3-2. 繰り返し実行しても大量取得にならない

「1件ずつ何回も回す」で上限を回避できてしまうので、3重にしてある。

| 歯止め | 値 |
|---|---|
| 1回の件数 | 1件 |
| 同じASINの取り直し | **24時間あけないと不可**（`KEEPA_MIN_REFETCH_HOURS`） |
| 1日に使える枠 | **2,000**（`KEEPA_DAILY_TOKEN_BUDGET`） |
| 手元に残す枠 | **100**（下回る取得はしない。0まで使い切らない） |

### 3-3. APIキーの値が出る経路が無い

「漏らさないよう気をつける」ではなく、**出口を作らない**。

- キー入りURLは `fetchKeepaProducts` の中だけで組み立て、**関数の外へ一切返さない**
- 外に出るのは `{endpoint, method, params}` だけで、`params` に `key` を入れない
- 保存する表に `request_url` 列を**作らない**
- 保存直前に `redactKeepaKey()` を通す（最後の保険。一次の対策はURLを保存しないこと）
- 画面・ログに出すのは「設定済みかどうか」だけ。**先頭4文字だけ表示、もしない**

### 3-4. 画面に取得ボタンを置いていない

`/keepa` は**見るだけ**の画面。理由は「ボタンにすると連打できてしまう」から。
取得は `npm run keepa:one` を人が打つときだけ起きる。

## 4. 枠（トークン）の管理 — 主軸は「1分あたり」

ご本人の指摘どおり、**月の総量では管理しない**。

- 補充：**1分あたり20**（API応答の `refillRate` で必ず上書きする）
- 貯められる上限：**補充速度 × 60 = 1,200**。使わなかったぶんは**60分で消える**
- 1件・統計のみの取得＝**1**（＝3秒ぶんの補充）

> 月の総量（20×60×24×31 = 892,800）だけを見ると、
> **「1時間で1,200を使い切ったらそこで止まる」という壁が見えない。**
> 画面の見出しは必ず「1分あたり」から始める（受け入れテストで固定）。

**取得の実額**（公式ドキュメントの記載。2026-08-25 に数字を訂正した）

| 付けるもの | 枠 |
|---|---|
| 商品1件（基本） | 1 |
| `stats`（順位の下落回数・平均価格） | **0（無料）** |
| `buybox` | +2 |
| `offers`（出品者一覧・1ページ最大10件） | **+6** |

> [!warning] 直したこと
> 実装当初 `OFFERS: 19` と書いていた。**根拠のない多めの見積もりだった。**
> 公式の実額は6。根拠のない数字をコードに置くと、そのうち事実として扱われる。
> なお当システムは `1 + 6 = 7` と見積もる（Keepa側は offers 使用時に基本の1を足さない）。
> **少なく見積もって足りなくなるより、多く見積もって余らせる方を選ぶ。**

## 5. 取ったデータの扱い

| 決め | 理由 |
|---|---|
| **円は100で割らない** | Keepa は「その通貨の最小単位の整数」で返す。円に小数は無いので 1234 = 1,234円 |
| **`-1` は「不明」** | 0円ではない。0にすると「タダで買える」と読める |
| **`domainId` が 5 でなければ保存しない** | 日本以外の相場で日本の仕入を判断させない |
| **商品ページURLは作らない** | Keepa は返さない。ASINから組み立てられるが**ルール55違反**なのでやらない |
| **7日間の下落回数は「不明」のまま** | Keepa にあるのは 30/90/180/365 の4つだけ。自作は Keepa の数字ではない |
| **`monthlySold` は判定に使わない** | U4（Amazon側の制約）が未確認。**保存と表示だけ** |
| **実市場データ100件に数えない** | Keepa は Amazon ではない（`counts_as_real_market = 0` で固定） |
| **異常値は直さず人に見せる** | 直すと、なぜ汚れたのか分からなくなる |

## 6. 同一商品判定（ASIN_MATCH_SCORE）

手元の商品と ASIN が同じものかを100点満点で採点する。

| 材料 | 配点 |
|---|---|
| バーコード（JAN/EAN/UPC）一致 | 50 |
| 型番一致 | 20 |
| ブランド一致 | 10 |
| 商品名の似ぐあい | 10 |
| 色 | 4 |
| 入数 | 6 |

- **75点以上**＝同一とみなす／**40点未満**＝候補にもしない／その間＝**人が確認**
- 候補が複数あるときは、**1位と2位の差が15点以上**なければ確定させない
- **拒否権は3つだけ**（バーコードが食い違う／入数が違う／ブランドが違う）。
  1つでも当たれば点数に関係なく `MISMATCH`。**増やさない**（増やすほど正しい一致を弾く）

## 7. 規約の扱い（2026-08-25 に自分の記録を訂正した）

実装の途中で、**自分が前に書いた記録が間違っていたことに気づいて直した。**

| 直した箇所 | 前 | いま |
|---|---|---|
| `lib/venuepermissions.ts` の KEEPA_API | 8項目のうち `api_exists` だけ YES、残り UNKNOWN | 条文を根拠に **6項目 YES／自動購入・自動出品は NO** |
| Keepa 由来データの注意書き | 「規約本文を確認できていません」 | **2(4) の内容を明記**（完全性は保証しない・正確性も保証できない・妥当性の確認は利用者の義務） |
| CLAUDE.md ルール82 | 「keepa.com は403で規約本文を読めていない」 | **403 は取得ツールによる現象。`/api-docs/` は200で読め、規約本文はブラウザで読んである** |

> [!danger] ここが今回いちばん大事な学び
> 「読めなかった」を記録に書くと、**次のセッションがそれを事実として引き継ぐ。**
> 未到達は「未到達」であって「存在しない」ではない。
> [[20_Keepa公式API調査]] を読み直さなければ、間違った前提のまま実装を確定させていた。

### 条文で確認できたこと（[[20_Keepa公式API調査]] より）

- **できる**：自社の事業目的での取得・表示（11(1)）／保存（11(2)）／商用利用（2(2)・3(4)）
- **できない**：生データの転売（6.1(1)）／書面同意の無い第三者目的での提供（2(2)）／契約終了後の利用（11(1)）
- **保証されない**：完全性・正確性。**妥当性チェックは利用者の義務**（2(4)）
  → 当社の Fail Closed 設計は、この義務そのもの

### それでも本番運用しない理由

許可が取れたことと、本番で動かしてよいことは**別**。
まだ答えの出ていない問いが6件ある。

| # | 未確認 |
|---|---|
| U1 | 取得データを自社システム用に**正規化・整形して保存**してよいか |
| U2 | **契約終了後**に保存済みデータを保持・利用してよいか |
| U3 | 将来SaaSとして他社へ提供する場合の書面同意の範囲 |
| U4 | `monthlySold` の元データに関する Amazon 側の制約 |
| U5 | 国内法（特定商取引法・古物営業法）の観点での制約 |
| U6 | AUP と同趣旨の条項が Amazon の別契約にもあるか |

そこで `mayStartAutoCollection()` を直し、**`unknowns` が1件でも残っていれば自動取得を始めない**ようにした。
（それまでは8つの許可項目しか見ておらず、8項目に収まらない問いを無視していた。）

> **Gate通過は「候補にしてよい」までの意味しかない。** 実際の使用範囲は
> `KEEPA_USE_SCOPE = INTERNAL_VERIFICATION_ONLY` が別に縛っている。

## 10. ついでに直した本物の不具合

11個のテストを通す途中で、`npm run test:phase2` が落ちた。
調べると、**商品6件が「無効になったRoute」を指したまま**になっていた。

原因は `lib/pipeline/routes.ts` の更新条件に `WHERE best_buy_venue IS NOT NULL` が付いていたこと。
ベスト市場が無くなった商品の古い番号が消えず、SKIP になったRouteを指し続けていた。
条件を外し、`npm run routes` で全行を書き直して解消。

> **11個とも通す運用でなければ、この不具合は見つかっていない。**
> 1つだけ通して満足しない、という決まりが実際に効いた。

## 11. いま強い点／これから良くする点

### いま強い点

1. **上限が「設定」ではなく「コード」で縛られている** — 設定ミスで大量取得が起きない
2. **APIキーの値が出る経路そのものが無い** — うっかりログに出す事故が構造的に起きない
3. **枠の管理が「1分あたり」主軸** — 月の総量では見えない詰まりを先に見つけられる
4. **URLをAIが作らない** — Keepa はURLを返さないので、`/buy` の導線は作らないままにした
5. **判定に使う数字と、表示だけの数字を分けてある** — `monthlySold` は表示のみ

### これから良くする点

1. **B3（U1・U2 の問い合わせ）を先に進める** — ここが閉じないと用途を広げられない
2. **1件取ったあとの監査項目を先に決めておく** — 取ってから考えると甘くなる
3. **`fbaFees` と `referralFeePercentage` を手数料台帳へ流し込む** — 手数料の実額確認が1/18件で止まっている
4. **7日窓の扱いを決める** — 自社計算にするなら、出どころを Keepa と分けて持つ
5. **`/keepa` に「いつ取ったか」の一覧を出す** — 24時間ルールに引っかかる理由が画面で分かるように
